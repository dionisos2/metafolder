* Folding a field's pending index writes chunk by chunk
Agreed with the user, 22 November 2026. Today a fold step takes *all* the pending
index writes of one field, every chunk, in one transaction (=fold_events=,
=kvstore/events.rs= 487; chosen in the step picker, =events.rs= ~640,
=List::Events(field)=). An add or a remove reads the posting of its value. A set or
an unset calls =postings_of(field)= — every value of the field with its holders,
every chunk, whole — and calls it again for each set or unset pending. On a field
of many values, that is all its postings in memory and a long transaction every
request waits behind.

The step becomes one (field, chunk):

1. read and decode the postings of that field in that chunk — every value's
   bitmap, restricted to the chunk (keys =posting_prefix(field, key)= then the
   chunk; =nothing= has a key of its own and is one value among the others);
2. read the pending index writes of that (field, chunk) (table
   =index_pending_writes=, keyed field · chunk · write number, oldest first;
   =read_events= reads a whole field today);
3. replay them *all, in order*, in memory: union, difference on bitmaps of at most
   65 536 ids. Not "from the last set or unset only": a set or an unset names a
   bitmap of ids, not the chunk, so it decides only its own ids (discussed and
   dropped, 22 November 2026: replaying is simple and cheap anyway);
4. update the histograms with the same differences (=hist_bump=), in the same
   step — check against doc "Mass writes in the store" which side the write
   already counted at once ("the histograms for a value added or removed") and
   which the fold counts (a set's or an unset's removed values, today =events.rs=
   511), so that nothing is counted twice or missed;
5. encode and write the postings changed, delete that chunk's pending index
   writes, commit; then the next (field, chunk) that still has some.

- Memory and the length of a step are bounded by one chunk, as the fold of a
  part's records is (=fold_part=, one part of 65 536 ids per step).
- The pending count per field (=self.events=, =eventful=, =events.rs=) and the
  step picker (biggest first, measured per field in bytes) go per (field, chunk).
- Listing the values a field has in one chunk walks the keys of the field's
  postings and keeps those of the chunk: a walk of keys, not of bitmaps — say so
  in the note if it shows in the bench.
- Reads need no change: they replay the pending writes chunk by chunk already
  (doc "Mass writes in the store": chunks name disjoint ids), so a field half
  folded reads right. A test should still say so: a field with two chunks pending,
  one folded, reads the same before and after.
- Tests first: the fold of a (field, chunk) touches only that chunk's postings
  (count the keys read: a second chunk of the field is not read); a set then adds
  then a remove on overlapping ids replays to what the reads answered before the
  fold; the histograms agree with a count from the postings after the fold.
- Write it down in doc "Folding in idle time" (§ How: the unit becomes a field's
  chunk, not a field) and doc "Mass writes in the store".

** Operation and entry: two words, two things
A *log entry* is a key of the log (=log_entries=): an individual operation, or a
mass operation. A *log operation* is an individual operation, the thing that has
an operation id; an entry holds one or several (doc "Log storage"). Every "op" /
"operation" of the log (about 870 =ops= in the code, 11 notes) is to be read
again and named one or the other.

** The byte of a former kind at the head of the index keys
When =sets= and =grams= were split into a table per kind, each key kept the byte
that told the kinds apart (=UNIVERSE=, =ABSENT=, =PARENTS=, =REFERRERS=,
=POSTINGS=, =SETS=, =GRAMS=, =GRAM_VALUES=…), and =index_histogram_keys= its =FF=
(commit =6d3c00d1=, doc "Store tables"): the code reached a kind's table by that
byte, so the split did not rewrite it. Nothing needs the byte any more, a byte per
key: it is to be removed (user decision, 21 November 2026), and doc "Store
tables" no longer to present it as a design. The vocabulary that goes with it (the
"part" =VALUE= / =NAME= of =source.rs=, "absent", "referrers", "postings"…) is to
be gone through case by case. Dropping the byte changes the keys: a derived
format, =DERIVED_VERSION= to bump (a reindex, no conversion).

* Storage: what is left after the dense id work
The invariant "a record keeps its dense id between two reindexes" is built (doc
"Deleting a metarecord in the store"). What is left:

- Open questions, none decided (doc "Storage open questions"): replace and rename
  not being mass writes, the marks a deleted record loses, compressing what the log
  keeps of a deletion.
- The =undo_redo_properties= suite takes about 3 minutes on four cores; the cost
  left is the writes of its cases, not their set-up.
- The sync store (=sync.rs=, one LMDB per pair of repositories: =meta=, =links=,
  =by_a=, =by_b=, =snaps=) was left out of the review of the store's tables
  (user decision, 20 November 2026): independent, with a migration of its own. To
  go over later on the same principles: compact encoding, snapshot fields in the
  record value format rather than JSON, the tables' names.
- A trace of the values a retype loses (user decision, 20 November 2026, to do
  later): with the store's table review, a value a retype cannot convert is
  removed rather than turned into =nothing=, and the field goes when none
  converts. The retype's summary says so and the log can undo it, but nothing
  finds those metarecords afterwards. Proposed: a multi-valued user field, say
  =retype_lost=, one text per lost value (=<field> = <original value>=), without a
  prefix so that it is cleared without =--force=, as =orphan= is (doc "Orphans");
  =mfr_retype_lost= was the alternative.
- Strings of any bytes (user wish, to decide later): a string should be able to
  hold whatever a =tree_ref= name holds, bytes that need not be UTF-8. The store
  will be ready (the table review encodes a string as =varint len · bytes=), but
  the model is not: =Value::String= is a Rust =String= (=core/metarecord.rs=), and
  so are the wire, the queries and the trigrams; doc "Changing a field's type"
  turns a name that is not UTF-8 into its displayed form (=%XX=). The wire would
  carry such a string as paths are carried, ={text, bytes}= (doc "Tree
  names").
- Seen 21 November 2026, not looked into: =kv_cost= takes 915 s in a row (40 to
  170 s a test) where doc "Performance testing" says seconds — the set-up of its
  16 000 to 64 000 files, or more. And =query.subtree_range_text= measured 4 to
  9 ms at =main= against 0.7 to 1 ms at =2c8bb168= (9 November): the bench at
  size S is too noisy to bisect it (two commits with the same daemon measured 1.03
  and 2.67 ms) — compare the keys its =kv_cost= test reads
  (=a_subtree_a_range_and_a_text_combine=) at both commits instead. The history's
  baseline of 9 November gives false alarms (=tree.resolve_page=: 2.75 to 5 ms at
  =2c8bb168= today, against 1.55 recorded); measure in the repository itself, not
  in a worktree under =/tmp= (doc "Storage pitfalls": writes on the wrong
  filesystem).
- The mass-write threshold (=mass-write-threshold=, 20 to start) is one number for
  every operation: a way to derive better values from the repository is to come
  (doc "Mass writes in the store").
