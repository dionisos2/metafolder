* TODO the event log as a set of operations
Proposed 12 October 2026 (doc "The operation log", =status: proposed=): the
history tree, HEAD navigation, rollback and revisions replaced by an ordered
set of operations, reverted onto the current state, grouped by nested labels
opened as contexts; undo and redo by label; retention per origin. What
motivates it is in doc "Why the log stops being a tree" — three undo/redo bugs
left unfixed meanwhile: a redo lost when the watcher writes after an
undo-by-rollback, a redo stopping at an undo it already redid, the tagging
scripts' going back rolling over watcher writes. A wire break and a
persisted-format change (conversion shipped). Deferred past the first build:
the GUI's work context (its scope is undecided).

** TODO the query planner: the next choices
Built September 2026 from the cases profiling found, not from the old design
(the old adaptive planner stays a record: doc "Indexing architecture"): a deferred text leaf's
candidates narrowed by trigrams (=495ea1b=), and the first choice made on a
cost — an =osm= path's anchors cut by a rare earlier term (=1140e07=). What
is left, each to measure before building:
- an unsorted page under a large subtree: =FollowsTransitive= reads the
  root's whole descendant bitmap where a page wants 100 ids. Measured 7
  October 2026 (=query.folder= against =query.page=, a folder holding the
  whole repository): +0.08 ms on M (21 000 nodes), +0.4 ms on L (105 000),
  about 4 ms extrapolated to a million. The way out — a per-candidate
  ancestry check stopping at the page — costs ≈ 100 × depth × 2 µs ≈ 1 ms,
  so it loses below roughly 300 000 nodes, and its walk cannot be budgeted
  without the subtree's size, which the store does not keep. Not built;
- a two-term =osm= path whose earlier term is common: the bench's finder,
  still ≈ 5 ms on L, nearly all of it each anchor's ancestry (≈ 2 µs a random
  read). No bitmap formulation found cheaper on that shape;
- whatever the next reading shows: the slow log of a repository in daily use
  is replaced by doc "The session scenario" (=scripts/session.sh=, 11 October
  2026), a scripted day of GUI use on 50 000 files with every operation
  logged. Its runs show no query over budget: every list, finder and
  folder step stays under 1 s on a neutral machine, the most keys a list step
  read being 19 000 for five pages. What it did find is below.

** TODO what the session runs found (11–12 October 2026, 50 000 files)
Recorded on a neutral machine (=benchmarks/session/=). The background tasks
are in the slow log since =e7d7ffff=, which showed the biggest cost at once: a
path's resolution compared each name with all its siblings (=e7882221=). A
reconcile with nothing to do went from 43.8 s and 242 million keys to 9.7 s and
3.8 million; the first one from 60 s to 25 s; the watcher's flushes from 2.1
million keys (a folder of 292 files renamed) to 20 000, and from 1.56 million
(1 000 files created) to 53 000. Every step is within its budget. Left:
- the duplicate scan: 29.5 s, then 15 s once its writes were committed every
  two seconds instead of 503 times (=9212c562=). It still holds the store for
  the whole scan, so the GUI's change feed waits as long: releasing it between
  windows would let another write change the records under the scan's maps —
  the "operations stay sequential" decision (doc "Storage open questions").
- a second reconcile read 3.8 million keys, ≈ 75 a file: each path resolved
  four times, and every file's path read back by the orphan scan. Resolved
  once since =a46549ef=: 2.2 million keys, 7.3 s. Not all of it is "nothing to
  do": in the session it is the first one computing MIME types, so it writes
  =mfr_mime= on every file. A truly idle one, measured 12 October 2026 (every
  phase now named in the slow log): ≈ 22 keys a path, the same on 8× the files
  — 3 resolving it, 13 comparing its stat fields (one prefix each), 3 and 2
  checking its MIME type and metadata, 1 listing it for the orphan scan. One
  read of the record's rows would answer the last three passes at once (≈ 1
  key a row), a gain only on records with few user fields: not built.
- reading the log right after an undo read the whole log (=42287c53=): the
  redo's two reads went from 702 000 keys to 171 000, which is what was undone
  (a revision of 50 000 operations). The run that read only 20 000 keys was a
  lost redo: the watcher wrote between an undo-by-rollback and its redo (see
  the event log below).

** TODO keep hunting with the simulated kernel
=watchd/src/sim.rs= (a kernel kept in step with the real filesystem, held to
the real one by a fidelity test) found a bug a commit on its first day
(=8dea90c=, =3a9c64a=, =287a225=, and the inotify one it led to, =5e013ff=).
Driven 9 October 2026: bursts mixing renames and removals of the same names
read late (=early_journey.rs=, every regime), and nested roots of two
subscribers (=sim.rs=). They found two bugs, both in the inotify half the
journey runs beside the simulator (=77776ca1=, =5614e701=); the overlapping
roots behave; a root moved away freezes its repository until it is loaded
again (doc "When the root moves"). A kernel overflow end to end
(=tests/watch_overflow.rs=): its diagnostic named only =mf reconcile=, which
recovers neither a lost deletion nor a lost rename of an unhashed file; it names
the orphan scan now.

The mount table, driven 10 October 2026 (=tests/watch_mounts.rs=, both
sources, each test in a user namespace; the simulator keeps a mount table held
to the kernel by the fidelity test): a drive plugged in and out with work going
on, mounted over a tracked directory, mounted at two points of one repository.
Found: the broker's path memo outlived a mount change (=701881a0=); the inotify
source never watched a drive plugged in (=75c6022f=); and two points of one
drive could only ever be reported through one — a second mount is now an
entry, never walked (doc "Second mounts").

One drive in two repositories, the case it left: the broker resolved through
one mount point, so the other repository heard nothing; each event is now told
again at every mount of the filesystem showing its path (doc "Second mounts").
Nothing named is left to drive.

** TODO the mock =mf= log loses argument boundaries
=scripts/lib/mf-mock.sh= (and =daemon-fixture.sh=) log each call as ="$*"=,
arguments joined by spaces, so an assertion glob can match text *inside* an
argument — a DSL query holds spaces. No false positive seen, and the log's
form is the interface of =mock_count= / =mock_calls_matching=: changing it
rewrites the hundred assertions of six suites. Deferred, cost above gain. If it
ever bites: keep =$*= as the readable log and write a second one, arguments
separated by =\x1f=, with a =mock_count_argv= for the assertions that need it.

** TODO =mf path= once per question in the tagging scripts
=gui-tag-folder.sh= and =gui-tag-pair.sh= call =mf path "$uuid"= for the preview
at each question, right after reading the same record's *relative* path
(=--resolve-tree mfr_path=). Only the repository's absolute root is missing to
build it without the round-trip. One HTTP call per keystroke of a human: not
felt. Clean fix: a CLI printing a repository's root (=mf repo root=, or a
=--root= on =mf repo list=, whose JSON would need =jq=), read once per run —
a CLI addition to weigh first.
