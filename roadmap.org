** DONE one engine on the serving path (September 2026)
The daemon no longer has a second query engine. Every operand is now served from
a resident structure — the bitmaps, or the forest through the tree cache — and
=POST /query= does not fall back: an =Unsupported= shape is a daemon bug (a
=500=), not a slow answer (spec-indexing "No operand runs in SQL").

What it took, in order: the bitmap index serves =:parent= (a uuid, so a regex and
an ordering on it are refused, and =!== is served); the forest answers =:path=
leaves and order-sensitive =osm= paths by rewriting each into the =uuid_in= set it
matches (=daemon/src/forest_query.rs=) instead of handing SQLite a =VALUES= list;
type validation moved ahead of any engine (=query_validate.rs=); the SQL engine
left the daemon for =crates/query-oracle=, a dev-dependency of the daemon and of
nothing else, where it stays as the *test oracle* the index is validated against
(the semantics batteries run on both engines). The FTS5 trigram index was dropped
in the same pass, with a migration.

Three items below shrank or changed shape as a consequence, and two sections of
=docs/review-followups.md= (§7, §8) now describe a component that is no longer on
the serving path — see "documentation drift" below.

** TODO performance — one request per metarecord
The recurring defect of this project, in its HTTP form.

*** TODO =mf order= writes one revision per child
Measured with a counting stub: N children cost N+1 =PUT=s, so N transactions,
N fsyncs, and — the part that matters — *N revisions of the log*, where every
other bulk operation in the project is one revision (see the =write_matches=
scaffold in =routes.rs=). Undoing a numbering therefore takes N rollbacks.

The read side is already bulk (one paginated =follows= pass over the children,
one =resolve-tree=); only the write loop is left (=core/src/order.rs=, the
=client.put= per planned position).

Blocked on a decision: the set layer applies the *same* value to a whole set,
while each child here gets its own position. It needs an endpoint taking
=(uuid, value)= pairs — purely additive, so no =API_VERSION= bump.

*** TODO =mf sync plan=: the target-side position lookup is still per-record
The bulk pass took the linking phase from 6 reads per scope record to 1. The one
left is =record_at_path= (=core/src/sync/plan.rs=), which asks for the occupant of
a position on the *other* side, once per identity position.

*Unblocked since it was written.* It was waiting on a set endpoint able to answer
"who is at this path", and the =:path= aspect now is one: =field:path = "/a/b"= is
an exact-node predicate the forest resolves in memory, so N positions are one
=Or= of =:path= equalities — rewritten into a single =uuid_in= set before the
index sees it — and =query/fields/resolve-tree= maps the answers back to their
paths. What is left is the rewrite of the caller, not a missing mechanism.

*** TODO =FollowsTransitive=: linear in the subtree, but no longer in SQL
=docs/review-followups.md= §7 described the hybrid compilation: a BFS over the DB
(one =tree_children= query per node) whose result was inlined as =VALUES=
literals — ~19 Mo of SQL text for 500k descendants. *Both costs are gone*: the
index expands the subtree by iterative bitmap expansion over the reverse
(direct-children) index (=index::expand_subtrees=), in memory, with no SQL and no
per-node round-trip.

What §7 called the real problem stands: the whole subtree is still materialised
where only the page is wanted. It is now a bitmap union per level rather than a
DB walk, so the constant is small — and the inherent limit named there has not
moved: sorting by a field needs the full candidate set anyway, so only unsorted
queries could ever stop early. Rewrite §7 to match when it is next touched.

** TODO query API limits
*** TODO execution timeout
The node cap bounds a query's *compilation*, never its *time*. A small, slow query
(a =matches= regex over millions of rows, a =->*= across the whole repo) is still
unbounded. Cancellation exists — a query task polls =cancel()= between phases, so
a client can stop one — but nothing enforces a deadline on its own. §8's SQLite
lead (=progress_handler=, =interrupt()=) is obsolete with SQL off the path; the
place to poll is the index evaluation loop.

*** DONE a DSL spelling for an explicit list of UUIDs (September 2026)
There was never a cost argument here: an =Or= of bare UUID atoms is *not* N
predicate nodes — the parser folds it, concatenating the lists whenever every
operand of an =Or= is a =UuidIn= (=core/src/dsl.rs=, =or_expr_inner=) — only a
spelling one, N =OR= keywords for N uuids in the query box.

Shipped as =uuid_in(<uuid>, <uuid>, …)=, compiling to that same single node. The
form is the =osm=/=osmd=/=same= one, a word recognised only when immediately
followed by =(=, and *not* the bracketed =uuid_in [...]= this entry used to
propose: brackets would spend two of the free punctuation characters the DSL
deliberately keeps in reserve, and the named-operator precedent spends none. A
trailing comma is accepted (a loop emits one) and =uuid_in()= is the empty set,
so a client with an empty selection needs no special case. The simplified
language gets nothing: =+= already joins pasted uuids there.

*** TODO the CLI cannot read a scope by batches: no =--cursor=
The daemon already pages: =POST /query= takes =limit= + an opaque keyset
=cursor=, answers =next_cursor=, and returns the full =total= on =count: true=
(O(1) through the bitmap index). *Half of it now reaches the shell.* =mf
metarecord get --limit N= caps the *total* and loops over the pages internally
(=commands.rs=, the =next_cursor= loop), so there is still no way to say "the
next 100 after those" — a shell client either takes everything or takes a
prefix.

=--count= is *done* (September 2026): =mf metarecord [-q …] get --count= prints
the match count, one round-trip, exact, query selectors only. It was the one
prerequisite left for [[file:docs/gui-tag-folder-rework.md][gui-tag-folder-rework]], and it removes the reason those
scripts count by counting lines.

What is left is the =--cursor= half, and it is still exposure rather than new
machinery: print =next_cursor= (stderr, or a =--tsv= column) and accept
=--cursor <token>=. Performance is unaffected: keyset pagination is index-backed
and stable under concurrent writes (unlike an offset), which is precisely why
the cursor is what should be exposed rather than a =--offset=.

Two caveats to spell out in the spec when it is done: a cursor is bound to a
hash of (query, sort) and is rejected by any other request shape, and a record
edited between two pages moves with its sort key like any keyset paging.

** TODO the read side is no longer link-aware
Found during the documentation pass above, and the one thing in it that is not
about words. Reads used to exclude *link metarecords* — a metarecord owned by
more than one repository — because the SQL engine's =_repo= universe CTE
demanded *exclusive* ownership (=COUNT(*) = 1= over =metarecord_db=). That CTE
left with the engine: the bitmap index's universe is
=SELECT uuid FROM metarecord= (=RepoIndex::build= via =db::list_entries=), every
metarecord of the database.

*No consequence today* — links are =:v2:=, nothing creates one, and a
metarecord has exactly one owner, so the two expressions select the same set.
It matters because of *when* it would break: the day links arrive, the serving
path and the oracle would disagree silently, and the equivalence battery would
not catch it (there is no link in any fixture to reveal it). The =metarecord_db=
join belongs back in the universe — or a fixture with a link belongs in the
battery — before that work starts, not after.

Recorded at =index/mod.rs= (the =universe= field) and in
=docs/review-followups.md= §9, which claimed the opposite.

*** DONE =gui-tag-folder.sh=: the query is the walk state (September 2026)
Coded to [[file:docs/gui-tag-folder-rework.md][docs/gui-tag-folder-rework.md]], which now records the four places the
implementation departed from it. An answer is already a write, so "what is left
to ask" is a query rather than bash bookkeeping: one question per step with
=--limit 1= over =<scope> AND <undecided> AND <not skipped>=, a =--count= for
the counter, and a walk holding one string — the current folder, since *the path
is the stack*. Gone with it: the in-memory scope, =DECIDED=/=PRUNED=/=SUBTREE=/
=RANK=/=KIND=/=PATH_OF=/=ENTRIES=/=WALK=/=STEPS=, the external =sort=, and
=MF_GUI_MAX_ENTRIES= for this script — while the =mf order= walk order and the
exact counter both stay.

Two things the design did not have. A *skip* is now recorded (a
=gui_tag_skipped= field holding a ref to the tag entry, one marker per tag), so
it survives the run, is undone by =back= like any other answer, and is offered
for cleanup at the end and again at the next run's start. And =--redo=, which
drops the clauses that would narrow the query, keeps its own =uuid_in= list of
what it has asked — bounded by keypresses, like the skipped-folder list.

Prerequisites, both met on the way: =:parent= served by the index, then
=mf … --count=. =docs/review-followups.md= §12 is rewritten, and its conclusion
("paging costs either the walk order or the exact total") is recorded there as
wrong. The other two tagging scripts still read their scope up front — they
classify one metarecord or a pair, not a subtree, so the bound suffices.
