#+TITLE: Metafolder — General Specification
#+OPTIONS: toc:2 num:t

* Project Overview

Metafolder is a local metadata management system. It tracks files and
directories in /repositories/ — watched directory trees — and associates
arbitrary structured metadata with each metarecord. The system is split into
four crates:

- =core=: shared data model (metarecords, fields, values, queries)
- =daemon=: background HTTP server managing repositories and exposing a REST API
- =cli=: command-line tool that communicates with the daemon
- =gui=: graphical interface (Tauri v2 + Svelte 5, see spec-gui.org)

* Daemon

** General description

The daemon is a long-running background HTTP server that manages one or more
/repositories/. A repository is a directory tree on the filesystem whose
metarecords are tracked in a local SQLite database. The daemon exposes a REST API
consumed by the CLI and GUI.

The daemon is local-only (binds to =127.0.0.1= by default). It performs no
*user* access control (single-user model), but it does gate every request with
a per-session token that only a process able to read a user-only token file can
supply (see [[file:spec-auth.org][spec-auth.org]]). This keeps web content
running in the user's browser — which can reach =127.0.0.1= — out.

** Non-goals

- No built-in remote protocol: the daemon is local-only and makes no network
  calls. Cross-machine synchronisation is handled at the CLI/script level (e.g.
  loading a remote repo over an SSH-mounted filesystem into the local daemon).
- No multi-user access control. A single local user is assumed; the only
  authentication is the loopback session token of [[file:spec-auth.org][spec-auth.org]]
  (which keeps non-token-bearing local processes, notably browser content, out
  — it is not a user-to-user mechanism).
- No conflict resolution between concurrent daemon instances on the same repo.

** Version scope

Features tagged =:v2:= on headings or marked =[v2]= inline are deferred to
version 2. Version 1 covers: CRUD, =TreeRef= / tree cache, file watcher (basic
events), reconcile (fingerprint phase only), query language, reserved fields
(=mfr_*= / =mf_*=), the watch/ignore system, the user schema
([[file:spec-schema.org][spec-schema.org]]), cursor pagination, and the
daemon-side event log ([[file:spec-event-log.org][spec-event-log.org]]):
logged write flow, =pending_operation= buffer, atomic metadata-only rollback,
log reading and pruning. The coordinated navigation protocol and the
log/rollback/prune CLI (originally v2) are now implemented as well. Background
tasks and progress reporting ([[file:spec-tasks.org][spec-tasks.org]]) — async
reconcile, observable queries, the task registry — are part of version 1.

** Key invariants

- Every filesystem metarecord in a watched repository has exactly one corresponding
  metadata metarecord in the database.
- When a file or directory is deleted, its metadata metarecord is preserved; the
  =mfr_path= field is set to =Nothing= rather than deleting the row.
- =set_field= replaces *all* rows for =(uuid, field_name)=, collapsing multi-map
  fields to a single value.
- Cross-repo sync state (links and snapshots) lives outside the data model,
  in per-pair sync databases under =.metafolder/internal/=; it is never
  recorded in the event log and can only be modified when both repositories
  of the pair are simultaneously loaded in the same daemon instance
  (see [[file:spec-sync.org][spec-sync.org]]). [v2]
- The =version= counter on a metadata metarecord is managed exclusively by the
  daemon and cannot be set directly by users. Versions are assigned from a
  per-metarecord monotonic allocator (=next_version=) that rollback never
  restores: a version number is never reused for a different state, so equal
  versions imply identical field states — even across rollback/redo cycles.
- A repository database must be held under an exclusive SQLite lock for the
  entire lifetime of the daemon connection (=PRAGMA locking_mode = EXCLUSIVE=).
  This prevents a second daemon instance from loading the same repo
  simultaneously, which would cause version drift and watcher conflicts (e.g.
  one daemon's watcher updating =mfr_path= and bumping =version= while the other
  is committing a sync). A load that finds the lock already held is refused
  *immediately* — the lock belongs to a live daemon and waiting for it is
  pointless — with a =409 Conflict= naming the cause: another metafolder daemon
  is already using this repository. In particular the connection's busy handler
  must not be left to retry the lock, or every repository already held costs
  seconds of silence at startup.
- Opening a repository database performs *no* schema work once it is
  up to date. Each migration is idempotent, which is not enough on its own: it
  must also detect that its result is already in place and do nothing, rather
  than re-apply it. A migration that re-does its work costs nothing on a small
  database and minutes of full CPU at *every* startup on a large one — an index
  re-keyed by dropping and recreating it is the shape to watch for. The witness
  is =PRAGMA schema_version=, which counts DDL: it must not move across two
  consecutive opens of the same database.
- A query that joins =field= to itself on =metarecord_uuid= must say
  =INDEXED BY idx_field_metarecord= on every correlated side. The EAV schema
  offers two indexes with two equality columns each —
  =idx_field_name_type(field_name, value_type)= and
  =idx_field_metarecord(metarecord_uuid, field_name)= — and the database carries
  no statistics (=ANALYZE= is never run), so SQLite is free to pick the first.
  It does not carry the uuid, so the correlated side then *scans every row of
  that field name in the repository* to keep one: the read becomes quadratic in
  the repository. Measured on the bundled SQLite with 20 000 orphaned
  metarecords, the orphan read took 39.9 s unguarded against 17 ms guarded. A
  =CROSS JOIN= pins the join *order* and says nothing about the index, so it is
  not a substitute.
- =TreeRef= references must form a forest (no cycles per =field_name=) with a
  maximum depth of 1000. The daemon rejects any write that would create a cycle
  or exceed this depth. The check walks the parent chain iteratively using the
  tree cache (fetching missing nodes from the DB step by step as needed).

The daemon listens on =127.0.0.1:7523= by default (configurable via =--port=).
All request and response bodies are JSON. Errors return a JSON object
={"error": "<message>"}= with an appropriate HTTP status code.

** Daemon configuration

The daemon reads an optional configuration file at startup:
=$XDG_CONFIG_HOME/metafolder/daemon/config.toml= (i.e.
=~/.config/metafolder/daemon/config.toml= on Linux). The =--config= flag
overrides this path. This file is distinct from the per-repository
=.metafolder/config.json= (machine-managed repo data, kept as JSON).

#+BEGIN_SRC toml
[[load]]
root = "/data/music"

[[load]]
metafolder = "/ssd/meta/music/.metafolder"
#+END_SRC

- =load= (optional): repositories to load at startup. Each entry has the
  same shape as a =POST /repos/load= body: exactly one of =root= or
  =metafolder=.
- =[settings]= (optional): UX/performance knobs, each independently optional —
  =watch-quiet-period-ms= (default 500, the executor's flush quiet period),
  =watch-budget-share= (default 50, the percentage of
  =fs.inotify.max_user_watches= one daemon will spend — see
  [[file:spec-file-tracking.org][spec-file-tracking.org]] "The watch budget")
  and =orphan-cascade-limit= (default 10 000, =0= to disable: the largest cascade of
  =mfr_path = Nothing= a single watcher batch may apply — see
  [[file:spec-file-tracking.org][spec-file-tracking.org]] "Mass-orphan circuit
  breaker"). A key the daemon no longer knows is *ignored*, not fatal: a
  setting can be retired without breaking every configuration that carries it
  (=tree-cache-max-nodes= was, see [[file:spec-file-tracking.org][spec-file-tracking.org]]
  "No node budget").
- A missing configuration file is equivalent to an empty one.
- A malformed configuration file (invalid TOML, unknown keys, a metarecord with
  both or neither of =root=/=metafolder=) aborts daemon startup with an
  error message.
- A repository that fails to load (missing path, locked database, ...) is
  reported as a warning on stderr; the daemon starts anyway and the other
  metarecords are still loaded.
- The startup report is written as the loading goes, one repository at a time:
  each repository is named before its load starts, and its outcome — the
  =Loaded= line or the warning — is written before the next one is attempted.
  Nothing about a repository is deferred to the end of the run, so a startup
  that is taking a long time always says which repository it is waiting for.
  On a terminal the announcement is the warmup progress line itself.
- Within a repository, every *phase* of the load announces itself on stderr
  before it runs — the schema migrations one by one, the case probe, the
  schema and metadata map, the replay of buffered filesystem events, the query
  index build, the tree cache, the watch placement:

  #+BEGIN_SRC
  [load music] field_text trigram index…
  [load music] field_text trigram index: 4m12s
  #+END_SRC

  A phase's duration is reported when it ends, but only past a small threshold
  (10 ms) — a load walks a dozen migrations that are no-ops, and echoing each
  one twice would bury the one that costs. The reading rule: *the last line of
  the report names the phase that is running*. Load work is proportional to the
  repository, not to the code: a single phase can run for minutes at full CPU on
  a large repository, and without this the operator can see the daemon is busy
  but has no way to tell which phase to look at.
- The replay of buffered filesystem events reports *inside* itself, because it
  is the phase whose cost is least predictable: it says how many events it read,
  how many compaction left, and then names each event as it applies it. A
  per-event counter is not enough on its own — one event can hide an
  arbitrarily large subtree, since a directory pasted or moved in whole arrives
  as a single =Create= and everything already inside it is ingested by that one
  event's scan — so the scan reports the entries it has ingested as it goes:

  #+BEGIN_SRC
  [load photos]   1 event(s) buffered
  [load photos]   1 event(s) after compaction
  [load photos]   event 1/1: arrived /photos
  [load photos]     scanning /photos: 2326 entries ingested
  #+END_SRC

  These lines are rate-limited to one per second: the reporting side cannot
  know which report matters, so it reports everything and the printing side
  decides. The first and last event always get a line — a batch that finishes
  inside the interval must not go by in silence, which is the case that is
  indistinguishable from a hang.
- Applying one event is itself several steps of very different cost (the
  ancestor walk for eligibility, the path resolution, the fingerprint search
  among orphans, the orphan cascade, the write), so each announces itself. But
  an announcement cannot report the step that *stalls*: the code that would
  report it is the code stuck inside it, and the rate limit above will have
  swallowed its announcement a millisecond earlier. So a **watchdog** reports
  from outside — while the same step stays current it names it once per second,
  and it says nothing at all while the steps flow:

  #+BEGIN_SRC
  [load home]   still on: event 2/426: modified /target/…/acl-manifests.json — refresh the stat fields (4.12s)
  [load home]   event 2/426 took 5.14s
  #+END_SRC

  An event that took longer than a second is named with its cost once it
  finishes, so the report still says where the time went after the load ends.

** Health

#+BEGIN_SRC
GET /health
#+END_SRC

Response: =200 OK=, body ={"status": "ok", "version": "<crate version>",
"repos": <number of loaded repos>}= — enough for a client to confirm the daemon,
its build, and that it has repositories loaded in one call.

** Diagnostics feed

#+BEGIN_SRC
GET /diagnostics?since=<id>&limit=<n>
#+END_SRC

The warnings the daemon prints to stderr, also kept in a bounded in-memory ring
so a client can read them. The daemon runs as *its own process*: a GUI has no
handle on its stderr, so a warning from the watcher — a directory it could not
watch, filesystem events it had to drop, a file it had to skip — reached only
whichever terminal started the daemon and was invisible to the person actually
using the software.

Response: ={"entries": [...], "next_since": <id>, "dropped": <n>}=. Each entry
is ={id, at_ms, level, scope, message, repo}=, where =level= is =warning= or
=error= and =scope= names the part that spoke (=watcher=, =reconcile=,
=executor=, =prune=, =warmup=…). Entries come oldest first.

- =since= is the last id the client saw; *0 means "everything the ring still
  holds"*. Ids start at 1 and are monotonic **per daemon run** — they are not
  stable across restarts, so a client that reconnects starts from 0 again and
  sees whatever the current run has recorded.
- =next_since= is where to resume. A client passes it back unchanged; it never
  has to compute a cursor.
- =dropped= counts entries that fell out of the ring before this poll could read
  them, so a client that fell behind can *say so* instead of quietly showing an
  incomplete history.

The ring holds 500 entries and a page is capped at 500. This is an operator aid,
not a control channel: recording never fails and never blocks a write, and the
oldest entries are dropped rather than any write being delayed.

Not everything on stderr is here. Timing traces (tree-cache scans, warmup
phases) stay stderr-only — they are for whoever is profiling the daemon, not for
the person using it.

** Repository management

#+BEGIN_SRC
GET    /repos
POST   /repos/init
POST   /repos/load
GET    /repos/:repo_uuid                read one repo's info
PATCH  /repos/:repo_uuid                rename a repo
POST   /repos/:repo_uuid/unload
#+END_SRC

*** =GET /repos=

Returns the list of currently loaded repositories. *System* repositories
(=system= flag in their =config.json= — e.g. a cross-repo sync *plan repo*,
see [[file:spec-sync.org][spec-sync.org]]) are omitted unless =?all=true= is passed; they are
loaded and usable like any repo, just hidden from the default listing.

Response body:
#+BEGIN_SRC json
  [
  {
  "repo_uuid": "...",
  "name": "...",
  "root": "/path/to/dir",
  "internal_dir": "/path/to/dir/.metafolder/internal",
  "system": false,
  [...]
  }
  ]
#+END_SRC

*** =GET /repos/:repo_uuid=

Returns one loaded repository's info — the same object shape as an entry of
=GET /repos=. =404= if the repository is not loaded.

*** =PATCH /repos/:repo_uuid=

Renames a loaded repository. Body ={"name": "<new name>"}=. The name must stay
unique among loaded repos (=409= on collision), since =-n <name>= resolves it to
a UUID. The new name is persisted to =config.json=. Response: the updated repo
info object.

*** =POST /repos/init=

Initialises a new repository. Creates =config.json= and =internal/db.sqlite=
inside the =.metafolder/= directory. Fails if a repository already exists
there.

Request body:
#+BEGIN_SRC json
{"root": "/absolute/path"}
#+END_SRC

Optional: =metafolder= overrides where =.metafolder/= is created (external
database). Defaults to =<root>/.metafolder/=.
#+BEGIN_SRC json
{"root": "/data/music", "metafolder": "/ssd/meta/music/.metafolder"}
#+END_SRC

Optional: =name= sets the repository name. When absent (or empty), the name is
derived from the root directory's file name.
#+BEGIN_SRC json
{"root": "/data/music", "name": "My Music"}
#+END_SRC

Response body: ={"repo_uuid": "..."}=

*** =POST /repos/load=

Loads an existing repository into the daemon's in-memory state, starts the
file watcher.

The load is *rejected with =409=* if another loaded repository already has the
same =name= (from its =config.json=). Names are therefore unique among loaded
repositories, so the CLI's =-n <name>= selector resolves to exactly one UUID.

The response returns the repository uuid *immediately*; the in-memory
accelerators (tree cache + query index) are then warmed in the *background* as
an observable =load= task (see [[file:spec-tasks.org][spec-tasks.org]]), so a
client can show a load progress bar. The response also carries the warmup's
=task_id= (=null= when the repository is already warm, e.g. a redundant load;
the id of the *running* warmup when one is already in flight), so a client can
wait on the task without discovering it through the task list.

While warming, the repository *reports its state and refuses its data*. It
appears in =GET /repos=, describes itself through =GET /repos/:repo=, and its
=load= task names the phase it is on — everything a client needs to know when to
come back. Every endpoint that reads or writes repository data answers
=503 Service Unavailable= instead. This is not a policy choice: the query engine
and the watcher's executor both run against the accelerators, so a repository
whose index is not built cannot answer slowly, it can only not answer. A warmup
that *fails* leaves the repository registered and never ready — its =load= task
carries the error, and its data endpoints go on answering =503= until it is
unloaded. An =unload= is refused with =409= until the warmup finishes.

The repository's *configuration* — the user schema and the embedded-metadata map
— is read before it is registered at all, not by the warmup. Those are small
files that need no accelerator, and an invalid one makes the repository bad
rather than slow: it fails the load itself, with the =400= naming the offending
constraint, and nothing is registered.

The load builds the accelerators *before* starting the watcher and its executor,
so the executor works against them from its very first flush, exactly as it does
at runtime — rather than replaying a backlog through cold database walks while
the index it is about to need is built behind it. (=POST /repos/init= and startup
auto-load warm synchronously — no client is watching. For each repository of
its config's =load= list, the daemon renders the warmup itself on *its own
stderr*: the same progress-bar format as the CLI, drawn only when stderr is a
terminal, followed by a plain =[daemon] Loaded <name>= line.)

Standard form (=.metafolder/= is inside =root=):
#+BEGIN_SRC json
{"root": "/absolute/path"}
#+END_SRC

External database form (specify the =.metafolder/= path directly; =root= is
read from =config.json= inside it):
#+BEGIN_SRC json
{"metafolder": "/ssd/meta/music/.metafolder"}
#+END_SRC

Response body: ={"repo_uuid": "...", "task_id": "...|null"}=

*** =POST /repos/:repo_uuid/unload=

Unloads a loaded repository: removes it from the daemon's in-memory state,
stops its file watcher and executor, and releases the exclusive SQLite lock — so
the repository can be re-loaded later or opened by another daemon. The on-disk
data is untouched (this is *not* a delete). No request body.

Response body: ={"repo_uuid": "..."}=

- =404= if the repository is not loaded.
- =409= if a coordinated-rollback navigation is in progress (complete or abort
  it first; see [[file:spec-event-log.org][spec-event-log.org]] "Rollback
  lock"). Its lock must not be silently dropped.
- =409= if a cancellable task (reconcile/query) is in flight: the repository is
  never pulled out from under running work. Stop the task first
  (see [[file:spec-tasks.org][spec-tasks.org]] "Cancellation"), then unload. A
  transient =flush= task does not block the unload.

| Repository already initialised         | 409         |                                |
| Reconcile requested while one in flight | 409        | see [[file:spec-tasks.org][spec-tasks.org]]            |

| TreeRef write would create a cycle     | 400         |                                |

* CLI

** General description

The CLI is a thin client over the daemon's HTTP API: it performs no direct
database or filesystem-watching work itself. The binary is named =mf=. Each
spec file documents the CLI commands for its own feature area in its =* CLI=
section; this section defines the conventions shared by all commands.

| Spec file                                          | Commands                                          |
|----------------------------------------------------+---------------------------------------------------|

| [[file:spec-data-model.org][spec-data-model.org]]   | =mf metarecord [-q/-i] {get,set,add,delete,field …}=, =mf field {get,set,delete} <id>=, =mf retype= |
| [[file:spec-query.org][spec-query.org]]             | query DSL grammar (consumed by =mf metarecord get=) |
| [[file:spec-file-tracking.org][spec-file-tracking.org]] | =mf reconcile=, =mf track=, watch-scope workflow |
| [[file:spec-schema.org][spec-schema.org]]           | =mf schema {check,reload,show}=                    |

| [[file:spec-tasks.org][spec-tasks.org]]             | =mf task {list,show}=                              |
| [[file:spec-sync.org][spec-sync.org]]               | =mf sync= (v2)                                    |
| [[file:spec-duplicates.org][spec-duplicates.org]]   | =mf duplicate {list,scan,clear}=                  |

** Global options

The repository and daemon are selected once, by flags preceding the command:

| Option        | Env variable             | Description                                              |
|---------------+--------------------------+---------------------------------------------------------|
| =-n <name>=   | =METAFOLDER_REPO_NAME=   | Target repository by (unique) name                      |
| =-u <uuid>=   | =METAFOLDER_REPO=        | Target repository by UUID                               |
| =-p <port>=   | =METAFOLDER_DAEMON_PORT= | Daemon port on =127.0.0.1=; default =7523=              |

=-n= and =-u= are mutually exclusive (a usage error if both are given). The
daemon listens only on loopback, so a port fully addresses it — there is no
base-URL option. =-n= resolves to a UUID through the daemon's repository list,
relying on name uniqueness among loaded repos (this file, =mf repo load=).

A repo-scoped command invoked with no repository selector (neither flag nor env)
fails immediately with a usage error (exit code 2), without contacting the
daemon. Daemon-wide commands (=mf repo=, =mf task=) ignore =-n=/=-u=.

** Output conventions

- Normal results go to stdout; errors and warnings to stderr.
- Machine-friendly by default: UUID lists are printed one per line; structured
  results are JSON. Commands with a human-oriented default format provide a
  =--json= flag that prints the raw response body instead.
- Daemon error responses (={"error": "..."}=) are printed to stderr as
  =error: <message>=.

** Exit codes

| Code | Meaning                                                          |
|------+------------------------------------------------------------------|
| 0    | Success                                                          |
| 1    | Operation failed (daemon error, violations found, no match, ...) |
| 2    | Usage error (bad arguments, unparsable DSL/field spec, missing repo selector) |

** Repository commands

Grouped under =mf repo=; =list= is the default (=mf repo= ≡ =mf repo list=).
These are daemon-wide and ignore =-n=/=-u= (except =unload=, which uses them to
pick its target).

*** =mf repo list=

Calls =GET /repos= and prints the loaded repositories as pretty-printed JSON.
The default subcommand of =mf repo=.

*** =mf repo init <root> [--metafolder <path>]=

Calls =POST /repos/init= and prints the new repository UUID. =--metafolder=
selects an external database location (see [[*=POST /repos/init=]]).

*** =mf repo load <root | --metafolder <path>> [--no-wait]=

Calls =POST /repos/load= (standard form with a root path, or external
database form with =--metafolder=), *waits for the warmup* and prints the
repository UUID. The daemon *rejects the load if the repository's name collides
with an already-loaded one* (=409=), keeping names unique among loaded repos so
=-n= resolves unambiguously.

The command is synchronous by default: it polls the =task_id= returned by the
load response until the =load= task is terminal, rendering a progress bar to
stderr like the GUI's (a bar when =done= / =total= are known, a spinner
otherwise) — only when stderr is a terminal, so pipes and scripts see nothing.
The UUID is printed once the repository is warm. A =null= =task_id= (already
warm) finishes immediately.

- =--no-wait= restores the asynchronous behaviour: print the UUID immediately
  and let the warmup proceed in the background (pollable with =mf task=).

*** =mf repo unload=

Picks its target with =-n=/=-u= (or env). Calls
=POST /repos/:repo/unload= and prints the repository UUID. The repository is
removed from the daemon (its watcher stopped, its DB lock released); its on-disk
data is untouched. A repository not loaded (404) or in a rollback navigation
(409) is reported as an error (exit 1).
