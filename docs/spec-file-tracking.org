* Overview

File tracking covers how the daemon discovers, monitors, and reconciles
filesystem metarecords with their database representations. It encompasses the
file watcher (real-time events), reconcile (on-demand synchronisation), the
tree cache (efficient path resolution), and the watch/ignore system (scope
control).

** =mf order <folder> [--meta <field>] [--max-gap <n>] [--dry-run]=

Numbers a folder's *direct children* so a "sort by position" orders them
sensibly (an album's tracks, a series' seasons). Files and directories are
numbered independently into two integer fields, =order_file= and =order_dir= (so
each kind can be sorted on its own), and a child that already has a position is
*never overwritten* — user corrections survive a re-run. Operates on
already-tracked children (reconcile the folder first if some are missing).

The three fields share the =order_= prefix deliberately — =order_file=,
=order_dir=, =order_numbered= form one family, so typing =order= in the field
catalogue or a completion shows all of it. They live in the *user's* namespace
(no =mfr_= / =mf_= prefix), so they are ordinary fields a user may edit.

Each kind's children are ordered by three heuristics in turn, over a running
maximum position (=next= = max+1); gaps are intentional (they mirror the number
differences) and positions are not compacted:

1. *Metadata* — children carrying an integer ordering field (=--meta=, default
   =mfr_meta_track=), sorted by it: an anchor at =next=, then
   =pos = anchor_pos + (value − anchor_value)= (ties share a position).
2. *Name pattern* — children whose basename is =<prefix><number><suffix>=,
   clustered by identical =(prefix, suffix)= (the *last* digit run is the
   number). A cluster needs ≥2 members and a minimal consecutive gap ≤
   =--max-gap= (default 1000; a larger gap means the number is an id/hash, not
   an order). A member already positioned (e.g. by metadata) pins the cluster;
   otherwise its lowest-numbered member is placed at =next=. Others:
   =pos = anchor_pos + (number − anchor_number)=.
3. *Creation date* — everything left, by =mfr_btime= ascending (missing btime
   last, then by name), each at =next=.

Once the children are numbered the *folder* is marked with =order_numbered =
true= (a plain boolean field, written once — a re-run on an already marked
folder produces no revision for it). It tells a processed folder from an
untreated one: =order_numbered = true= finds the folders already numbered,
=order_numbered is absent= the ones still to do.

=--dry-run= prints the planned =uuid<TAB>field=pos<TAB>name= lines without
writing — the marker included, nothing at all is written; otherwise the number
of fields written is printed (the marker is not counted).

*** Migrating from =order_position_*=

The two position fields were first called =order_position_file= and
=order_position_dir=. A repository written under those names is migrated when
the daemon opens it, in the data *and* in the log — an inverse applied by a
rollback re-inserts the field name recorded in =op_snapshot=, so a log left in
the old vocabulary would resurrect the old name later. This mirrors what the
legacy-table migration already does to =operation.op_type=.

Two limits, both deliberate:

- The pass is guarded by an indexed probe on =field=, because =operation= and
  =op_snapshot= carry no index on =field_name= and scanning them at every open
  is the repeated work a load must not do (see [[file:spec-main.org][spec-main.org]]). A repository
  whose position fields were *all deleted* before the upgrade therefore keeps
  the old name in its log alone; rolling back to such a revision restores a
  field called =order_position_file= — inert user data, not corruption.
- A name is renamed only when it is *free*. A repository that already has a
  field of its own called =order_file= keeps both and the daemon warns: merging
  two unrelated fields into one multi-map is worse than one stale name.

The heuristic and the whole orchestration (read the children, write the
positions, mark the folder) live in =metafolder_core::order=, shared with the
GUI's =mf:order= command (see [[file:spec-gui.org][spec-gui.org]] "Order a
folder's children").
