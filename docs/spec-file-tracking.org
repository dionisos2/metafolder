#+TITLE: Metafolder — File Tracking Specification
#+OPTIONS: toc:2 num:t

* Overview

File tracking covers how the daemon discovers, monitors, and reconciles
filesystem metarecords with their database representations. It encompasses the
file watcher (real-time events), reconcile (on-demand synchronisation), the
tree cache (efficient path resolution), and the watch/ignore system (scope
control).

* Concepts

** File fingerprint

Used by reconcile and the watcher to detect identity across renames/moves.
*mtime is never used as a criterion* because it can change without the content
changing (e.g. =touch=, copies without =--preserve=).

Fingerprint is computed lazily in cascading steps — each step is only reached
when the previous one is insufficient:

1. *File size* (from =stat=, free during directory walk) — eliminates most
   non-matches without opening any file.
2. *Partial hash* — xxHash3 of the first 4 KB + last 4 KB of the file.
   Computed on first open; stored in the database alongside the metarecord.
3. *Full hash* — xxHash3 of the entire file content.
   Computed only when size and partial hash both match and a definitive
   identity check is required — re-homing an orphan, or confirming a duplicate
   group ([[file:spec-duplicates.org][spec-duplicates.org]]).

A stored hash describes the file *as it was when the hash was computed*, so it
is only reusable while the file has not changed since. The watcher's =Modify=
invalidation covers the watched case; where watching is off the subtree is
deliberately frozen and no event fires, so the hashes carry their own stamp —
=mfr_hash_mtime= and =mfr_hash_size=, written and cleared with them. A stored
hash is trusted only while both still match the live =stat=. Using mtime this
way does not contradict the rule above: that rule forbids mtime as a criterion
of *identity*, whereas here it invalidates a *cache*, and it fails safe — a
mismatch costs a recomputation, never a wrong match. See
[[file:spec-duplicates.org][spec-duplicates.org]] "The hash cache and its
validity stamp".

Hash functions are provided by the =xxhash-rust= crate. For content-based
similarity between files that do not share an exact hash (e.g. slightly
modified files), the =fast-tlsh= crate provides a TLSH locality-sensitive hash
that can be used as an additional signal in the similarity phase (see
[[*File Similarity]]).

Files and directories are both tracked as first-class metarecords. Directories can
carry arbitrary metadata fields (e.g. =mf_sync=, spec-sync) that files can inherit via
the =value_uuid= chain of their =mfr_path= TreeRef field.

The root directory metarecord has =mfr_path= with =value_uuid = x'00...00'= and
=value_name = ""=. All other metarecords reference their direct parent directory via
=value_uuid=. The root is looked up by
=WHERE field_name = 'mfr_path' AND value_uuid = x'00...00' AND value_name = ''=.

** File Similarity

Used by reconcile as a fallback when fingerprint matching fails — either because
no =mfr_partial_hash= is stored for the orphaned metarecord, or because the file was both
moved and modified (so hashes no longer match).

*Orphaned metarecord*: a metarecord whose =mfr_path= TreeRef points to a filesystem location
that no longer exists on disk (stale path), and that was not matched by
fingerprint during the current reconcile run.

*Unmatched new file*: a file present on disk that has no corresponding database
metarecord and was not claimed by fingerprint matching.

Similarity between an orphaned metarecord and an unmatched new file is computed from
four signals:

| Signal           | Formula                                                                  | Weight |
|------------------+--------------------------------------------------------------------------+--------|
| =name_sim=       | Trigram Jaccard similarity of basename without extension                 |    0.5 |
| =ext_match=      | 1 if extensions are identical, 0 otherwise                               |    0.2 |
| =size_proximity= | =max(0, 1 − |sz_a − sz_b| / max(sz_a, sz_b))=; 0 if either size unknown |    0.2 |
| =path_sim=       | Longest common directory prefix length / max directory depth             |    0.1 |

Final score = weighted sum of the four signals (range [0, 1]).

*Candidate selection with MinHash banding* (crate: =probabilistic-collections=):

Repositories can contain millions of files; O(n²) pair evaluation is
impractical. Instead, a MinHash banding scheme is used to find candidate pairs
in O(n) expected time:

1. Each filename (basename without extension) is decomposed into character
   trigrams. A MinHash signature of =k= hash values is computed over the trigram
   set (=k= ≈ 128 in practice).
2. The signature is split into =b= bands of =r= rows each (=k = b × r=). For
   each band, the =r= hash values are combined into a single bucket key. Two
   files are candidate pairs if and only if they share at least one bucket —
   i.e. their MinHash signatures are identical on at least one band.
3. The probability that two files with Jaccard similarity =s= become candidates
   is =1 − (1 − sʳ)ᵇ=. Choosing =b= and =r= controls the recall/precision
   trade-off independently of =n=.

After candidate selection via banding, the full four-signal score is computed
only for surviving pairs. The size range pre-filter (range scan on a
size-sorted list, O(n log n)) is applied first to further reduce the candidate
set before banding.

Only pairs with =score ≥ threshold= are included in the reconcile response.

*Implementation note*: the current implementation evaluates the four-signal
score directly over the residual sets — the orphaned metarecords and new paths
left *unmatched after the fingerprint phase*, which are typically small — rather
than MinHash banding. Only same-kind pairs (file↔file, dir↔dir) are compared.
MinHash banding (above) remains the planned optimisation for repositories whose
*unmatched* sets are themselves very large.

** Watch and Ignore

The daemon uses two =mf_*= fields on directory metarecords to determine which
files and directories to track. Both are inherited from the nearest ancestor
that defines them. The root metarecord always defines =mf_watch= (=false= at
init); =mf_ignore= is *not* written by the daemon at all (see "Ignore presets"
below) — it is applied by the client tooling from named presets.

*** Fields

- =mf_watch= (Bool): whether this metarecord is eligible for tracking. Set on
  directory metarecords to control whole subtrees; can also be set on individual
  files for per-file override. Default on root: =false= (opt-in by default —
  nothing is tracked until explicitly whitelisted).
- =mf_ignore= (String, multi-map): each row is a regex pattern tested against
  the path of a candidate, *relative to the tracking-scope root* — the nearest
  ancestor on which =mf_watch= is set directly (the repository root in the
  common case, giving a repo-root-relative path such as =/music/.git/config=;
  see the eligibility algorithm below for the re-anchoring rule). All stored
  paths are repo-root-relative so that the repository can be moved without
  invalidating stored patterns. The nearest ancestor that has at least one
  =mf_ignore= row provides the effective pattern set; patterns from different
  ancestors are *not* merged.

At =repo init= the daemon writes =mf_watch = false= on the root and *no*
=mf_ignore= rows: the daemon carries no built-in ignore policy (it stays
consistent with the config system's "no embedded defaults / no runtime
fallback" rule — spec-config). A bare =POST /repos/init= therefore yields a
root with an empty ignore set; this is harmless because =mf_watch= is =false=,
so nothing is tracked until the user opts in, at which point they also choose an
ignore set. The familiar default patterns are applied by the client tooling as
the =default= preset (below), so the normal =mf repo init= / GUI "create repo"
flow ends up with exactly the same patterns as before — they are merely sourced
from configuration instead of being baked into the daemon.

*** Ignore presets

Ignore *presets* are named, reusable groups of =mf_ignore= patterns living in
the user configuration (=~/.config/metafolder/core/ignore-presets.toml=, shipped
from =crates/core/default-config/= and installed by =metafolder-sync-config=,
like the simplified-query grammar). They exist purely for naming, documentation
and grouping: expansion (preset name → patterns) is a *pure, client-side*
transformation performed by =core::ignore_presets= and shared by the CLI and the
GUI; the daemon never sees a preset name — it only ever receives the final
=mf_ignore= strings.

A preset is either a *leaf* (a =patterns= list) or a *group* (a =pattern-set=
list of other preset names), or both (their expansions are unioned). Groups are
expanded recursively; a reference cycle is a hard error. The file is *required*:
a missing or malformed =ignore-presets.toml= is a startup/usage error pointing
at =metafolder-sync-config= (never a silent fallback — spec-config).

#+BEGIN_SRC toml
[rust-build]
description = "Cargo build intermediates (keeps the final binaries)"
patterns = ['(^|/)target/([^/]+/)?[^/]+/(deps|build|incremental|examples|\.fingerprint)(/.*)?$']

[node]
description = "npm dependencies"
patterns = ['node_modules(/.*)?$']

[python]
description = "Python caches"
patterns = ['__pycache__(/.*)?$']

[git]
description = "Git metadata"
patterns = ['\.git(/.*)?$']

[metafolder]
description = "The .metafolder configuration directory"
patterns = ['\.metafolder(/.*)?$']

[hidden]
description = "Every hidden (dot-prefixed) entry"
patterns = ['(^|/)\.[^/]+']

# … plus the shipped leaves node-build, julia, cpp, java, cache, os, editor
# (abbreviated here; see crates/core/default-config/ignore-presets.toml).

# A group preset: expands to the union of the referenced presets' patterns.
[default]
description = "The default set of mf_ignore patterns for a fresh root"
pattern-set = ["rust-build", "node", "node-build", "python", "julia", "cpp",
               "java", "cache", "os", "editor", "git", "metafolder", "hidden"]
#+END_SRC

The shipped file defines a preset per common toolchain / junk source:
=rust-build=, =node= / =node-build= (npm deps; JS-TS build caches and compiled
native addons), =python= (bytecode + tool caches), =julia= (coverage/build/doc
output), =cpp= (object files, precompiled headers, CMake files), =java=
(=.class= + the Gradle cache), =cache= (generic caches/temp), =os= (=.DS_Store=,
=Thumbs.db=, …), =editor= (swap/backup/autosave), and =git= / =metafolder= /
=hidden=. It stays *conservative*: only clearly regenerable intermediates and
junk are matched — never ambiguous names like =dist/= / =build/=, static
libraries, or extension-less executables, which are often tracked deliverables.

=git= and =metafolder= are kept as leaf presets distinct from =hidden= (which
already subsumes them) so that dropping "ignore all hidden entries" from a
target does not silently un-ignore =.git= / =.metafolder=.

The =rust-build= patterns ignore the intermediate build output cargo regenerates
on every =cargo build= — =deps/=, =build/=, =incremental/=, =.fingerprint/= and
=examples/= under =target/<profile>/= (and the cross-compile
=target/<triple>/<profile>/…= form) — while leaving the *final* artifacts that
sit directly in =target/<profile>/= (the built binaries and libraries) tracked.
Splitting the shipped =default= into named leaf presets lets a user apply a
subset (e.g. just =rust-build,node=) or drop one group without touching the
others.

**** Applying presets

Applying a preset expands it to patterns client-side and writes them into the
target metarecord's =mf_ignore= set via the daemon API: =add= appends,
=remove= deletes the matching rows, and =set= *replaces* the whole set (drops
every current =mf_ignore= row on the target, then writes the expanded patterns).
Because the effective set is the nearest
ancestor's (patterns are never merged across ancestors — see below), a preset is
normally applied at the tracking-scope root it should govern.

The full "create a repo with its default ignores" flow — =POST /repos/init=
followed by applying the =default= preset to the new root — lives in =core= (a
=core::repo_init= orchestration over a thin =DaemonClient= trait, in the same
spirit as =core::sync= / =core::trash=) and is reused verbatim by both the CLI
(=mf repo init=) and the GUI "create repo" flow, so the two behave identically.
The preset-application half is exposed separately (=core::ignore::apply=) for the
=mf ignore= command.

*** Eligibility algorithm

For a given repo-root-relative path =p= with direct metarecord =e=:

1. Walk the ancestor chain (including =e= itself) to find =watch_ancestor= —
   the nearest metarecord that has an =mf_watch= field.
2. If =mf_watch= on =watch_ancestor= is =false= → *skip*.
3. If =watch_ancestor= is =e= itself (=mf_watch= is set directly on =e=, not
   inherited) → *track unconditionally*; skip steps 4–5.
4. Walk the ancestor chain (*excluding* =e= itself) to find =ignore_ancestor= —
   the nearest ancestor that has at least one =mf_ignore= row.
5. Let =p_scoped= be =p= re-anchored at =watch_ancestor= — i.e. with the
   directory prefix of =watch_ancestor= removed, so it is a leading-slash path
   *relative to the tracking-scope root*. (When =watch_ancestor= is the
   repository root this is =p= unchanged.) If any pattern in
   =ignore_ancestor='s =mf_ignore= rows matches =p_scoped= → *skip*.
6. Otherwise → *track*.

Step 3 is the per-metarecord override: setting =mf_watch = true= directly on a
metarecord forces *that metarecord* to be tracked regardless of any ancestor's
ignore patterns. Its descendants still go through the ignore check (they inherit
=mf_watch = true= but it is not "direct" on them) — but, by step 5, that check is
performed *relative to the directly-watched directory*, which becomes a new
tracking-scope root. So directly watching a directory tracks its contents, with
the ignore patterns applying from that directory downwards:

- The watched directory's own name is stripped before matching, so watching a
  directory whose name would otherwise be ignored (e.g. a hidden =.config=, or
  =.git= itself) no longer prunes its subtree.
- Patterns still apply *inside* the scope: with the default rows, =.git=,
  =node_modules= and hidden entries found *below* the watched directory remain
  ignored.

To instead give a directly-watched directory a different pattern set, set
=mf_ignore= on it to replace the ancestor's patterns (they are not merged;
including removing unwanted ones).

*Replacing ignore patterns*: because patterns are not merged, a directory that
needs a different pattern set must re-declare all desired patterns in its own
=mf_ignore= rows. The recommended workflow is: query the effective =mf_ignore=
rows for the target directory (via inherited property lookup), copy them, write
them to the directory metarecord, then remove the unwanted pattern.

*** Cascading skip

When a directory is skipped (=mf_watch = false= or matched by an ignore
pattern), all of its descendants are also skipped without further evaluation.
The tree cache is used to collect descendants efficiently.

*** Interaction with reconcile and watcher

Both reconcile and the watcher evaluate eligibility before creating, updating,
or clearing any metarecord. Ineligible paths are silently ignored. The watcher
additionally uses eligibility to decide *where to place its inotify watches* —
only eligible directories are watched (see [[*File Watcher]]).

*** Behaviour when =mf_watch= or =mf_ignore= changes

Changing =mf_watch= or =mf_ignore= on a metarecord does *not* automatically
modify any existing database metarecords. The changes take effect only on the next
event (watcher or reconcile) for each affected path. The watcher does, however,
*immediately re-place its inotify watches* to match the new eligible-directory
set (see [[*File Watcher]]), so filesystem events arriving in a newly-eligible
subtree start being captured at once — but the metarecords for files *already*
present there still require a reconcile:

- *=mf_watch= set to =true=* on a previously-unwatched directory: existing
  files under that directory have no metarecords yet. A subsequent reconcile is
  required to create them.
- *=mf_watch= set to =false=* (or a new =mf_ignore= pattern now matches
  existing metarecords): those metarecords are preserved as-is. They will no longer be
  updated by the watcher or reconcile, but their metadata (including
  =mfr_path=) remains unchanged until the user explicitly removes them.

This is intentional: existing metadata is never silently discarded. To clean
up after a watch scope change, the client should use targeted delete
operations:

| Goal                                                    | Mechanism                                              |
|---------------------------------------------------------+--------------------------------------------------------|
| Remove all metarecords under a directory recursively        | Query =mfr_path follows_transitive "/dir"=, batch delete |
| Remove metarecords whose =mfr_path= is =Nothing= (deleted)  | Query =mfr_path is_absent=, batch delete               |
| Remove metarecords no longer in the watch scope             | Query the untracked subtree, batch delete              |

These operations are available through the existing query + delete API
primitives. No data is ever lost implicitly; the user remains in control.

** Mount points

A directory inside a watched tree can be the mount point of a removable or
network volume (a USB key, an external drive, an SSHFS export). When the volume
is not mounted, the directory is still there — it is simply empty. Nothing in
its content distinguishes that state from "the user deleted everything inside
it", which is why it needs an explicit concept: metafolder must never conclude,
from an empty mount point, that a thousand tracked files are gone.

A tracked path therefore has three states, not two:

- *present* — the file is there.
- *absent* — the file is gone: =mfr_path = Nothing= (only the watcher,
  =mf orphan clear= and =force= writes ever record this).
- *unavailable* — the volume holding it is not mounted. Nothing is recorded:
  the metarecord keeps its =mfr_path=, its metadata is frozen, and the subtree
  is skipped by every component until the volume comes back.

The third state is never stored on the affected metarecords: it is derived, at
the moment the question is asked, from the mount point above them.

*** =mfr_mount=

=mfr_mount= (String) is written by the daemon on a *directory* metarecord that
is a mount point at the time it is seen — by reconcile (walk and refresh phases)
and by the watcher when such a directory appears. It is an =mfr_*= field:
daemon-owned, user-writable only with =force=.

- *Detection* asks the kernel's mount table (=/proc/self/mountinfo= on Linux,
  cached), falling back to the device-id comparison where that is unavailable —
  a directory being a mount point iff its device id differs from its parent's.
  Either way it needs no privileges and, unlike "the directory is empty", it
  tells "unmounted" apart from "emptied". The two sources disagree on a
  same-filesystem bind mount and on btrfs subvolumes; see
  [[file:spec-platform.org][spec-platform.org]] "Mount point detection".
- The *value* is a best-effort identity of the volume that was mounted, used to
  tell the user what to plug back in and to notice that a *different* volume is
  mounted now. The per-platform sources and the string forms (=uuid:…=,
  =label:…=, =device:…=, and the bare =mounted= fallback) are specified in
  [[file:spec-platform.org][spec-platform.org]] "Mount point detection".
  Consumers treat it as opaque: the *presence* of the field carries the
  semantics, the value is informational.
- It is *never cleared by the daemon*. A directory that has =mfr_mount= and is
  not currently a mount point is precisely the "unavailable" state — the one
  thing that must not be forgotten. A directory that has stopped being a mount
  point for good is un-declared explicitly by the user (=mf mount forget=, a
  =force= unset).
- On a mount point that *is* mounted, =mfr_mount= is refreshed like any other
  daemon-written field, so a volume swapped for another one updates the recorded
  identity at the next reconcile.

*** Offline subtrees

A declared mount point is *offline* when its metarecord has an =mfr_mount= field
and the path is not, right now, a mount point on disk — including when the
directory itself no longer exists. Everything at or below an offline mount point
is *frozen*:

| Component     | Behaviour on an offline subtree                                         |
|---------------+-------------------------------------------------------------------------|
| watcher       | places no watch there, and drops any event landing in it                 |
| reconcile     | prunes it from the walk: no create, no refresh, no candidate, no MIME. A *scoped* reconcile aimed at (or into) an offline mount point is rejected with =400= rather than silently reporting "no change" |
| orphan scan   | reports "unknown", never an orphan (see [[*Orphan scan]])                   |
| =mf_watch= / =mf_ignore= | unchanged: eligibility is evaluated as usual, the freeze is an additional filter |
| queries       | unaffected — the metadata of a disconnected drive stays fully queryable, which is the whole point of recording it |

The freeze is decided by the *presence of a mount*, not by identity: if a
*different* volume is mounted at the point, the subtree is live and is tracked
normally (those files really are there); the identity mismatch is reported by
[[*Mount status]] but changes no behaviour.

Remounting resumes tracking — the watches are re-placed by the next watch-set
refresh — but does *not* trigger a reconcile: its cost is unbounded on a large
disk, and the volume may have been mounted for hours elsewhere. Changes made
while a volume was away are therefore picked up only by an explicit
=mf reconcile --metarecord <mount>=, which the client is expected to offer
rather than run behind the user's back.

*** Cost of the orphan search

The fingerprint search an arrival runs (=Rename(To)=, and the children of a
directory that arrives whole) is served from an index of the repository's
matchable orphans, built once per event group. It must be *maintained*, never
dropped: a group that orphans a metarecord and then takes an arrival — which is
what a rename over a tracked destination does, and what a compiler writing into
a build tree does hundreds of times in a row — would otherwise rebuild it from a
full scan of every orphan in the repository, once per event. A record the group
has just orphaned is added to the index instead, which is the one read it costs.

The scan that *builds* the index joins =field= to itself on =metarecord_uuid=,
and must seek those rows rather than scan them — see the =INDEXED BY= invariant
in [[file:spec-main.org][spec-main.org]]. Unguarded it is quadratic in the
repository, which on a build tree (where most metarecords are orphans of deleted
artifacts) is the difference between milliseconds and never finishing.

*** Mass-orphan circuit breaker

Independently of mount points: a single filesystem event batch that would orphan
a very large number of metarecords is a symptom, not a legitimate deletion — a
filesystem going away, an unmount metafolder did not recognise, a mount point
moved under the daemon's feet. The executor refuses a cascade of more than
=orphan-cascade-limit= metarecords (daemon setting, default 10 000; =0= disables
the check): the cascade is skipped, a warning is logged, and the metadata is
left untouched.

The refusal is deliberately recoverable rather than fatal: nothing is lost, the
paths simply stay stale, and a genuinely huge deletion is confirmed with the
tool that exists for it — =mf orphan clear=, which is user-driven and
re-verifies every path against the disk before writing =Nothing=.

* Daemon

** Tree Cache

The daemon maintains one in-memory tree per loaded repository for resolving path
strings to metarecord UUIDs without issuing recursive SQL queries. The cache is shared
across all =TreeRef= field names within a repository; the field name forms the
first level of the tree.

*** Path string format

A path string is the ordered list of =value_name= components from the root down
to a metarecord, joined by =/=. There is no trailing =/=.

The root's own =value_name= determines whether paths in the tree have a leading
=/=:

| Tree type                    | Metarecord                     | Path string        |
|------------------------------+---------------------------+--------------------|
| filesystem (root: name=""=, parent=NULL)   | root           | =""=               |
| filesystem                   | child ="projects"= of root | ="/projects"=      |
| filesystem                   | child ="rust"= of above   | ="/projects/rust"= |
| tags (root: name="tag1", parent=NULL)     | root ="tag1"= | ="tag1"=           |
| tags                         | child ="tag2"= of ="tag1"=| ="tag1/tag2"=      |

For the filesystem tree the root has =value_name = ""=, so all paths naturally
start with =/=. For other trees (e.g. tags) the roots have non-empty names and
there is no leading =/=. Multiple roots are allowed within the same field name.
The uniqueness of the filesystem root =(field_name='mfr_path', value_uuid=x'00...00',
value_name='')= is enforced by the =idx_field_tree= UNIQUE index.

*** Structure

#+BEGIN_SRC
root (virtual)
├── "mfr_path"
│   └── [root metarecord, parent=NULL]
│       └── "music"  → uuid_music
│           └── "jazz"  → uuid_jazz
│               └── "file.mp3"  → uuid_file
└── "parent"
    └── "animaux"  → uuid_animaux
        └── "félins"  → uuid_felins
#+END_SRC

Each node stores:
- =children=: map of name → child node
- =uuid=: the metarecord UUID at this position (=None= for the virtual root and field-name nodes)
- =last_used=: logical clock updated on every traversal of this node
- =heap_handle=: reference into the LRU heap (leaf nodes only)

*** Eviction

A *min-heap of leaf nodes* (nodes with no children), keyed by =last_used=,
drives eviction when the cache exceeds its configured size limit (default: 100 MB).

On eviction of a leaf:
1. Remove the leaf node from the tree and the heap.
2. If its parent has no remaining children, the parent becomes a new leaf —
   insert it into the heap with its own =last_used=.

Only leaves are evicted; internal nodes are kept as long as they have children.
Because every traversal updates =last_used= on all nodes along the path, a newly
promoted leaf always carries the correct recency timestamp.

*** Operations

| Operation              | Complexity       | Notes                                                        |
|------------------------+------------------+--------------------------------------------------------------|
| Path → UUID (hit)      | O(depth)         | Traverse tree; update =last_used= on each node              |
| Path → UUID (miss)     | O(depth × log n) | Iterative indexed DB queries; populate tree on the way      |
| Rename (same parent)   | O(1)             | Update label of one node                                     |
| Move (different parent)| O(1)             | Detach node, reattach under new parent; descendants follow   |
| Evict leaf             | O(log k)         | Heap pop; k = number of leaves in cache                     |

*** Startup

The whole TreeRef forest is loaded into the cache at repository load, in a
single scan of the =tree_ref= rows, so that read-side navigation (path
resolution, descendant collection, path reconstruction) is served entirely from
memory rather than walking the database node by node — the dominant cost of a
first =FollowsTransitive= query on a large repository. The lazy, DB-backed path
(populate-on-miss, descendant walk) is kept as a fallback for the case where the
forest exceeds the in-memory node budget (it then no longer fits, and the cache
reports itself incomplete). Manual API writes that change a TreeRef field rebuild
the cache; the watcher and reconcile keep it in sync incrementally.

** File Watcher

The daemon watches each loaded repository root for filesystem events (inotify
on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows, via the =notify=
crate; per-backend differences are detailed in
[[file:spec-platform.org][spec-platform.org]]). *The watcher and manual writes
with =force= are the only components that set =mfr_path= to =Nothing=*;
reconcile leaves =mfr_path= stale rather than setting it to =Nothing=.

The =notify= crate correlates raw rename-out / rename-in event pairs (e.g.
matched by inotify cookie on Linux) into a single =Rename(Both)= event when
both paths are inside the same watched tree. =Rename(From)= alone means the
file definitively left the repository (destination is outside the watched
tree or in a different repo root). =Rename(To)= alone means the file arrived
from outside. On backends where rename correlation is unavailable, a rename
surfaces as =Remove= + =Create= and identity is recovered via the fingerprint
search of the =Rename(To)= path (see
[[file:spec-platform.org][spec-platform.org]]).

=notify='s own From/To correlation can still fail under load and deliver a
single in-tree rename as separate =Rename(From)= and =Rename(To)= events. To
avoid degrading such a rename into a delete + arrival (two revisions; identity
preserved only when the content is unchanged), the watcher records each rename
event's inotify cookie in =pending_operation.tracker=, and compaction re-fuses
a =Rename(From)= / =Rename(To)= pair sharing the same non-null cookie back into
a single =Rename(Both)=. Events without a cookie, and genuine one-sided renames
(no matching cookie), are left as-is.

The watcher places one *non-recursive* watch per *eligible directory* only
(see [[*Watch and Ignore]]), rather than a single recursive watch on the whole
root. The eligible set is computed by the same walk reconcile uses: descend only
through eligible directories, prune ineligible subtrees, never follow symlinked
directories (so a watch can never escape the repository root — e.g. a Wine
=dosdevices/z: -> /= symlink is not traversed), and skip a directory that cannot
be read rather than aborting the whole watch. A repository with =mf_watch =
false= everywhere (the opt-in default of a fresh repo) is therefore watched
nowhere at all. The set is maintained incrementally as directories appear or
disappear, and recomputed after a manual write changes =mf_watch=/=mf_ignore=
(see [[*Behaviour when =mf_watch= or =mf_ignore= changes]]). An *offline* mount
point is pruned like an ineligible directory — no watch on it, none below it
(see [[*Offline subtrees]]); the watch set is recomputed on the next refresh, so a
remounted volume starts being watched again without restarting the daemon.

Before processing any event, the daemon evaluates eligibility for the affected
path (see [[*Watch and Ignore]]). Ineligible paths are silently ignored. Events
inside the repository's own =.metafolder/internal/= directory are always
ignored — matched by absolute path, since =.metafolder/= may live anywhere
(external database), including inside the watched root at an arbitrary depth.
This directory holds the live database and its WAL/journal sidecars: tracking
it would feed the daemon's own writes back into the event stream. The same
exclusion applies to the reconcile walk. The rest of =.metafolder/=
(=config.json=, =schema.json=) is ordinary trackable content, subject to the
normal eligibility rules.

The watch backend's event callback does *no* work of its own: it translates the
event and hands it to the watcher's ingest thread, which writes the buffer and
places any new directory's watch. The backend delivers events and serves watch
placements from a single thread, so a callback that waited on the repository
connection would freeze every watch placement — and deadlock outright against a
write that recomputes the watch set while holding that connection (see
[[*Behaviour when =mf_watch= or =mf_ignore= changes]]). Nothing that can block
may run on the callback.

*** Event batching

The watcher does not process events one by one. Instead, it buffers incoming
events *in memory* and the executor applies the buffer once a quiet period of
*500 ms* has elapsed with no new events. This default is configurable per
repository.

The buffer does **not** survive the daemon. It used to: the watcher wrote each
event into the =pending_operation= table and the buffer was replayed at load.
That bought nothing. A daemon that is down misses every event that happens while
it is down, so the repository is already out of step with the disk on restart
and only a =reconcile= can close that gap — and a reconcile closes the buffer's
gap along with it. What the persistence did cost was a transaction on the
watcher's hot path (the database is in WAL mode with the default durability, so
every transaction is an =fsync=: 3 ms per commit against 0.011 ms in memory, on
the same machine and filesystem), and a failure mode of its own — a batch the
executor *could not* apply was retried for ever, restart included, silently
switching tracking off for the repository. That needed a bounded retry budget to
be survivable at all. In memory, a batch that cannot be applied is retried until
the daemon stops, and stopping the daemon is what clears it.

Buffering is still done *in batches*: the watcher's ingest thread takes
everything the backend has already delivered (up to a few thousand events) and
hands it over in one go, so a mass arrival costs a handful of lock acquisitions
rather than one per event. Whatever an ingest batch cannot include is simply the
next batch.

A batch the executor does not apply — a failure, or a stop the user asked for —
goes back to the head of the buffer and is retried on the next flush.

The =restore_*= rows of =pending_operation= are a *different population* and stay
persistent: they belong to the event log (restoration ops left by skipped
rollback steps, see [[spec-event-log.org]]), not to the watcher. A repository
opened with filesystem events left in that table by an older daemon drops them.

Rationale: a user pasting N files into a directory generates N =Create= events
in rapid succession. Batching them into one revision makes the operation
rollbackable as a unit.

Processing the buffer happens in two steps:

*Step 0 — Rename correlation.* A rename the backend reported as a separate
=RenameFrom= / =RenameTo= pair is fused back into one =Rename= by matching the
inotify cookie both halves carry. The lookup is by cookie, not by scanning the
batch backwards: files moved in from *outside* the repository arrive as
=RenameTo= events whose =RenameFrom= half is not in the batch (and never will
be), so a backwards scan reads the whole batch per event — quadratic on the most
ordinary gesture there is, dropping a folder in.

*Step 1 — Compaction.* Redundant sequences are simplified before any database
write:

| Sequence within the window         | Compacted result              |
|------------------------------------+-------------------------------|
| =Create A=, =Remove A=             | nothing (metarecord never written) |
| =Create A=, =Rename A→B=           | =Create B=                    |
| =Create A=, =Modify(Data) A=       | =Create A= (final state)      |
| =Rename A→B=, =Rename B→C=         | =Rename A→C= (but see below)  |
| =Modify(Data) A= × N               | one =Modify(Data) A=          |

A rename chain is *not* collapsed when its destination is the source of a rename
still to be applied. Collapsing hoists the arrival at that destination in front
of the departure from it, turning the sequence into a cycle — the swap
=A→TMP=, =B→A=, =TMP→B= would become =A→B=, =B→A=, which no order can apply,
since a tree position belongs to one metarecord at a time. The hop through the
intermediate path is what breaks the cycle, exactly as it did on disk; keeping it
costs one extra =file_moved=.

*Step 2 — Split by op_type.* After compaction, operations are grouped by their
resulting =op_type= (see [[spec-event-log.org]]). Each group becomes its own
revision, committed in order of the first event timestamp in that group.

This guarantees that reversible and irreversible operations are never mixed in
the same revision, and that semantically distinct event kinds remain separate
and independently rollbackable.

Example: if the buffer contains 5 =Create= events and 2 =Modify(Data)= events,
two revisions are produced — one with 5 =create_metarecord= operations, one with 2
=file_modified= operations.

Note: for very large copies (slow media, network filesystems), events may
arrive over a span longer than the batching window and be split across multiple
revisions. This is acceptable — each revision is still rollbackable
individually.

*** Pausing ingestion

A flush is not always short. A directory of a hundred thousand files dropped
into a watched repository arrives as one batch, and applying it takes as long as
it takes — during which the repository's connection is held and nothing else
about that repository answers. The user must be able to say *stop*.

Stopping a flush is therefore a real operation, and it means **pause ingestion
for this repository**:

- The flush polls a cancellation flag as it applies events, and stops at the
  next event boundary. The group in progress is *abandoned, not committed* (its
  transaction is dropped), so no half-group is ever visible; groups already
  committed stay committed.
- The batch goes *back into the buffer*, at its head. Nothing is lost, and
  nothing is half-recorded: on resume the whole batch is applied again from the
  start (the event semantics are idempotent for that reason).
- The *tree cache is rebuilt* from the database. It is maintained incrementally
  as events are applied, in memory and outside the transaction, so the rollback
  that undoes the writes does not undo it: without the rebuild the cache would
  go on resolving paths to metarecords that were never committed.
- The repository then stays **paused**: the watcher keeps buffering events, and
  the executor does not flush them. This is the
  difference between stopping a flush and merely deferring it — without the
  pause, the next event would start the very flush the user just stopped.
- A cancelled flush is *not* a failed one: it does not count against the failure
  budget above, and never leads to the batch being dropped.

Ingestion is resumed explicitly (see [[*Watch status, pause and resume]]).
Resuming flushes what accumulated meanwhile, as a normal flush. A paused
repository is otherwise fully functional: queries, writes, reconcile and
rollback all work — a reconcile even picks up what the buffered events carried,
since it reads the filesystem directly.

The pause is *in memory*, like the task registry: unloading the repository or
restarting the daemon clears it, and the buffered events are then replayed at
load. It is a deliberate "let me look at this before it lands", not a durable
setting — the durable way to stop tracking a subtree is =mf_watch=.

*** Event semantics

| Filesystem event   | Action                                                                                                     |
|--------------------+------------------------------------------------------------------------------------------------------------|
| =Create=           | Resolve the path first: if a metarecord already holds this =mfr_path=, refresh it as for =Modify(Data)= (idempotent — crash replay, or a file that appeared where the database already expected one, e.g. a cross-repo sync placement). Otherwise look up the parent UUID via the tree cache and create a metarecord with =mfr_path= TreeRef and fields =mfr_type=, =mfr_size=, =mfr_mtime=, =mfr_permissions=, =mfr_uid=, =mfr_gid= |
| =Remove=           | Snapshot the current path into =mfr_path_old= (see "Orphan origin" below), then set =mfr_path= to =Nothing= (metarecord preserved) and delete =mfr_duplicate_group= (the hashes are deliberately *kept* — re-homing a re-appearing file needs them); if a directory, cascade both to all descendants in the same transaction. *Skipped when the path exists again on disk at flush time* — the deletion was undone within the batching window (a recreate, or a =mf trash -f= → =mf trash restore= round-trip), so the still-linked metarecord is left alone and the paired arrival in the same batch refreshes it (see the note below) |
| =Rename(Both)=     | Update =mfr_path= TreeRef: =value_name= (rename in place) or =value_uuid= (move to different parent) — O(1); children of a renamed directory are unaffected (they reference the parent by UUID). If the destination path is *itself tracked*, the rename destroyed the file that was there: that metarecord is orphaned first (as for =Remove=), then the moved one takes the position — one metarecord may hold a given tree position |
| =Rename(From)=     | File left the watched scope: snapshot =mfr_path_old= then set =mfr_path= to =Nothing= (as for =Remove=); if a directory, cascade both to all descendants in the same transaction. *Not applied when the same batch finds the file again* inside a directory created in it (see "Moves into a new directory" below) — the two halves are re-paired into a move |
| =Rename(To)=       | File arrived from outside: compute =mfr_size= + =mfr_partial_hash= from disk; search orphaned metarecords (=mfr_path = Nothing=) for a fingerprint match — if =mfr_full_hash= confirms identity → update =mfr_path= TreeRef and refresh =mfr_*= fields; otherwise → create new metarecord |
| =Modify(Data)=     | Content changed: refresh =mfr_size=, =mfr_mtime= from =stat=; delete =mfr_partial_hash=, =mfr_full_hash=, their stamp (=mfr_hash_mtime=, =mfr_hash_size=) and =mfr_duplicate_group= — the content that made it a duplicate is gone (see [[file:spec-duplicates.org][spec-duplicates.org]]) |
| =Modify(Metadata)= | Attributes changed: refresh =mfr_permissions=, =mfr_uid=, =mfr_gid=, =mfr_mtime= from =stat=; hashes remain valid |

On platforms where the =Data= / =Metadata= distinction is unavailable (e.g.
some macOS or Windows backends), the daemon falls back to =Modify(Data)=
semantics (full refresh + hash invalidation).

*=mfr_inode= is part of the stat field set*, written by every path that refreshes
stat fields (=Create=, both =Modify= forms, reconcile's create and refresh
phases) and by none other. Unlike the rest it is *conditional*: the value
="<st_dev>:<st_ino>"= is written when =st_nlink > 1= and removed when the link
count is back to one, so the field's presence alone means "this file has more
than one name" (see [[file:spec-duplicates.org][spec-duplicates.org]] "Hard
links"). =st_dev=, =st_ino= and =st_nlink= all come from the =stat= these paths
already perform, so the field costs no extra syscall. Note that creating or
removing a link produces an event for *that* path only: the paths already
pointing at the inode see their link count change with no event of their own, so
their =mfr_inode= is stale until a reconcile re-stats them (see
[[file:spec-duplicates.org][spec-duplicates.org]] "Known staleness").

*Undone deletions.* A =Remove= / =Rename(From)= is applied only if its path is
*still gone at flush time*: the check is deferred to application, not enqueue, so
a delete followed by a recreate of the same path within one window collapses to a
plain refresh rather than orphan-then-arrival. This matters most for the trash:
=mf trash restore= (and the GUI equivalent) re-link the metarecord *before*
moving the file back, but if the restore beats the buffered =file_deleted= from
the trashing, that =file_deleted= would otherwise fire against the restored file
and — since a freshly-tracked file has no stored =mfr_full_hash= for the arrival
to re-home it — strand the original metarecord and create a duplicate. Skipping
the stale removal closes that race (see [[file:spec-trash.org][spec-trash.org]] "Restore").

The refresh is *idempotent*: when the stored =mfr_size= / =mfr_mtime= (and,
for =Modify(Metadata)=, the attribute fields) already equal what =stat=
reports, no field is written — hence no operation and no =version= bump.
This keeps redundant events (crash replay, or the watcher's echo of a change
the daemon itself just recorded, e.g. a cross-repo sync file operation) from
churning versions; a genuine change differs in =stat= and is applied
normally.

The check is on the *stat alone*, deliberately: what a redundant event must not
do is *destroy* derived data. A =Modify(Data)= that is applied clears the
content-derived fields — the hashes, their stamp, and =mfr_duplicate_group=
([[file:spec-duplicates.org][spec-duplicates.org]] "Invariant") — so making the
skip conditional on those being absent would invert it, and every echo would
throw away a valid hash cache and a scan's whole result with it. Size and mtime
are the same evidence of "unchanged" the hash stamp relies on, and they fail the
same safe way: a same-second, same-size rewrite is missed and reconcile is what
catches it.

*Moves into a new directory.* A move is delivered as a =Rename(From)= /
=Rename(To)= pair that compaction fuses back into one =Rename(Both)=. When the
*destination directory is itself new* — "create a folder, drop a file into it" —
only the =From= half is ever delivered: watching is per-directory, and the new
directory's watch cannot be in place before the kernel has reported its
creation, so the =To= fires into an unwatched directory. Taken literally that
pair of facts says "the file left the repository" and "an unrelated file
appeared", which loses the metarecord: everything the user attached to it stays
behind on an orphan while the file is tracked afresh.

The destination is found instead by the new directory's scan (see the =Create=
row), and the executor re-pairs the halves there: a path arriving with no
metarecord of its own, and no fingerprint match among the orphans, is matched
against the paths *renamed away in the same batch* that are now gone from disk
and still tracked. Identity is settled on what a rename preserves exactly —
=mfr_type=, =mfr_size= and =mfr_mtime= — because the fingerprint search cannot
help: a metarecord the watcher created carries no hashes, and its file has
already left the old path, so there is nothing left to hash. On a match the
event is applied as an ordinary move (one =file_moved=, no orphan, no
duplicate); a moved *directory* carries its whole subtree with it, since
children reference their parent by uuid.

The batch's departures are indexed by that key once, not walked per arrival:
a flush holds the repository connection for its whole duration, so a pairing
that cost a =stat= and a database read per (arrival, departure) *pair* turned a
batch that both loses and gains a few hundred files into a minute of held
connection — with every query queuing behind it.

*Orphan origin.* When a metarecord is orphaned (=Remove= / =Rename(From)=, and
their cascades), its last filesystem path is first captured into an
=mfr_path_old= field — a frozen =String= (not a =TreeRef=: it does not
participate in the =mfr_path= forest and is never rewritten by later moves), so
the origin of every orphan is legible directly on the record without walking the
event log. It is written only on the transition to =Nothing= (a plain move does
not touch it), and overwritten on any subsequent orphaning. It is not cleared
when an orphan is later re-homed, so it records where the record last lived
before it was last orphaned. Because only the watcher and =force= writes orphan,
reconcile never populates it; a file deleted while its subtree is unwatched
keeps its stale =mfr_path= and gets no =mfr_path_old=. Like every daemon write
it is snapshotted in the event log and restored exactly by rollback.

Parent directory lookup on =Create= or =Rename(To)= uses the tree cache
(see [[*Tree Cache]]); on cache miss, falls back to iterative indexed queries
on =(field_name, value_uuid, value_name)=.

** Single-metarecord track

#+BEGIN_SRC
POST /repos/:repo_uuid/track
#+END_SRC

Creates a metadata metarecord for a single filesystem path without activating
tracking. Intended for use from =file-manager= (and scripts) when the user
wants to add a file or directory to the DB before deciding on its watch scope.

Request body:
#+BEGIN_SRC json
{"path": "/absolute/path/to/file-or-dir"}
#+END_SRC

The path must be inside the repository root; otherwise =400= is returned.

If the path is already tracked (a metarecord with a matching =mfr_path= TreeRef
exists), the call is *idempotent*: the existing metarecord UUID is returned
(=200=), and nothing is changed. Callers can therefore =track= a path to obtain
its UUID without first checking whether it exists.

Otherwise the daemon:
1. Creates any missing parent directory metarecords along the path (with
   =mf_watch = false=), using the tree cache for lookup.
2. Creates the target metarecord with =mfr_path=, =mfr_type=, =mfr_size=,
   =mfr_mtime=, =mfr_permissions=, =mfr_uid=, =mfr_gid= taken from =stat=,
   and =mf_watch = false=.

The new metarecord is *not* subject to eligibility checks (=mf_watch= / =mf_ignore=
evaluation); the caller is responsible for configuring the watch scope
afterwards (see [[*Watch and Ignore]]).

Response body: ={"uuid": "<entry_uuid>"}= (newly created, or the existing one).

** Scoped (single-metarecord) reconcile

There is a *single* reconcile endpoint (see [[*Reconcile]]); a scoped reconcile
is the same =POST /repos/:repo_uuid/reconcile= with a =metarecord= field in the
body (32-char hex). It runs reconcile semantics scoped to the subtree rooted at
that metarecord. Intended to be called after =mf_watch= is set to =true= on a
metarecord added via [[*Single-metarecord track]] or created manually.

Behaviour:
- Walks the directory on disk (or refreshes a single file).
- For each filesystem path found inside the subtree, evaluates eligibility
  (=mf_watch= / =mf_ignore=) and creates missing metarecords with all =mfr_*=
  fields; refreshes the =mfr_*= stat fields of metarecords that already exist
  (the same refresh phase as full reconcile, disabled with ={"refresh": false}=).
- Does not perform fingerprint or similarity matching (no orphan detection).
  For orphan detection, omit =metarecord= (whole-repository reconcile).
- Creates missing parent directory metarecords along the path if needed.

Like every reconcile it is asynchronous (202 + task id, see
[[file:spec-tasks.org][spec-tasks.org]]). Scope errors surface as the task
becoming =failed=: an unknown metarecord, or one with no valid =mfr_path= (path
is =Nothing= or unknown). The result has =moved= always =0= and =candidates=
always empty.

** Reconcile

#+BEGIN_SRC
POST /repos/:repo_uuid/reconcile
#+END_SRC

Walks the repository root on the filesystem and synchronises the database.

This endpoint is *asynchronous*: it returns =202= with a =task_id= immediately
and runs the work (the steps below, unchanged) as a background /task/, rejecting
a concurrent reconcile with =409=. Progress and the final =ReconcileResult= are
observed via the task; see [[file:spec-tasks.org][spec-tasks.org]] "Reconcile as
a task". An optional ={"metarecord": "<hex>"}= scopes it to a subtree (see
[[*Scoped (single-metarecord) reconcile]]); absent, it covers the whole
repository. The steps, the single transaction, the candidate semantics and the
response body below describe the work the task performs.

An optional ={"threshold": <0..1>}= body enables the similarity phase and
sets the minimum similarity score (absent disables it; v1 behaviour). The
optional ={"mime": false}= disables MIME computation (on by default; see
[[file:spec-platform.org][spec-platform.org]] "MIME detection"). The optional
={"refresh": false}= disables the refresh phase (on by default), which
re-reads the stat-derived =mfr_*= fields of files and directories still at
their recorded path — catching in-place edits made while the watcher was not
running. This makes the full and single-metarecord reconcile behave the same
way for unmoved files.

*Steps:*

1. Load all metarecords with a non-Nothing =mfr_path= TreeRef from the DB; separate
   them into /active/ (path exists on disk) and /orphaned/ (path no longer
   exists on disk, i.e. stale path).
2. Walk the filesystem; collect all file and directory paths.
3. *Fingerprint phase* — for each orphaned metarecord, search unmatched filesystem
   paths using stored fingerprint data:
   - Pre-filter by =mfr_size= (if stored): discard paths with different size.
   - Among size matches, if =mfr_partial_hash= is stored: compute partial hash
     of the disk file and compare:
     - Partial hash matches AND =mfr_full_hash= is stored: compute full hash of
       disk file → if matches → *definitive identity* → auto-update =mfr_path=
       TreeRef and refresh =mfr_*= fields (counted as =moved=).
     - Partial hash matches but no =mfr_full_hash= stored: *strong candidate* →
       added to =candidates=.
     - Partial hash does not match: discard.
   - Size matches but no =mfr_partial_hash= stored: *weak candidate* → added
     to =candidates=.
   - No =mfr_size= stored: metarecord skipped (no fingerprint available).
   New files that appear as a fingerprint candidate are *not* auto-created;
   they wait for explicit confirmation.
4. *Similarity phase* — for each still-unmatched orphaned metarecord and each
   still-unmatched new path, compute the similarity score (see [[*File Similarity]]).
   Pairs with =score ≥ threshold= are appended to =candidates=. New files that
   appear as a candidate for at least one orphaned metarecord are *not* auto-created
   as new metarecords; they wait for explicit confirmation.
5. *Create* — new files not claimed by fingerprint (or similarity) → create
   metarecord with =mfr_path= TreeRef and all =mfr_*= fields (=mfr_size=, =mfr_mtime=,
   =mfr_permissions=, =mfr_uid=, =mfr_gid=, =mfr_type=); create missing parent
   directory metarecords if needed.
6. Orphaned metarecords not matched by fingerprint and not present in any candidate
   pair keep their stale =mfr_path= TreeRef unchanged. *Reconcile never sets =mfr_path=
   to =Nothing=.*
7. *Refresh phase* — unless disabled (={"refresh": false}=), every metarecord
   still at its recorded path (file or directory) has its stat-derived =mfr_*=
   fields (=mfr_size=, =mfr_mtime=, =mfr_type=, =mfr_btime=, =mfr_permissions=,
   =mfr_uid=, =mfr_gid=) re-read from disk and rewritten where they changed,
   catching in-place edits. Only changed fields are written (idempotent runs do
   not grow the log); content hashes are left untouched, like elsewhere in
   reconcile.
8. *MIME phase* — unless disabled (={"mime": false}=), every eligible file on
   disk that has no =mfr_mime= gets one from content analysis
   (see [[file:spec-platform.org][spec-platform.org]] "MIME detection"). Idempotent: existing values are
   not recomputed.

*Offline mount points*: the walk prunes any directory that is a declared but
currently unmounted mount point, exactly as it prunes an ineligible one, so no
metarecord below it is orphaned, refreshed or offered as a fingerprint candidate
while the volume is away (see [[*Offline subtrees]]). Step 1's active/orphaned split
skips those paths as well: their existence on disk is unknown, not false.

*Directory identification*: directories have no fingerprint and are matched only
by their path string. A directory metarecord whose path no longer exists on disk
is left with its stale path (like any other orphan); it may appear in candidates
if a new directory with a similar name exists.

*Cascading Nothing*: whenever any metarecord's =mfr_path= is set to =Nothing= (by the
watcher or manually), all metarecords whose =value_uuid=
(directly or transitively, for =field_name = 'mfr_path'=) points to this metarecord are
also set to =Nothing= in the same transaction. Descendants are collected
iteratively using the tree cache (fetching missing nodes from the DB step by
step), then cleared in a single batched UPDATE. No metarecord can have a valid path
if one of its ancestors is gone.

All creates and updates execute inside a single transaction.

*Confirming a candidate*: the client sends a =PATCH= request to update the
orphaned metarecord's =mfr_path= field to the chosen new location. The new file is then
considered matched; if the client calls =reconcile= again without the candidate
having been confirmed, the same candidate will be returned again.

Response body:
#+BEGIN_SRC json
{
  "created": 2,
  "moved": 1,
  "candidates": [
    {
      "metarecord_uuid": "abc...",
      "stale_path": "/music/jazz/old.mp3",
      "matches": [
        {"path": "/music2/jazz_copy.mp3", "fingerprint": "partial_hash"},
        {"path": "/backup/unknown.mp3",   "fingerprint": "size"}
      ]
    }
  ]
}
#+END_SRC

Similarity-based candidates carry =fingerprint = "similarity"= and a =score=
field:
#+BEGIN_SRC json
{"path": "/archive/old_renamed.mp3", "fingerprint": "partial_hash", "score": 0.82}
#+END_SRC

** Orphan scan

Reconcile re-homes moved files and leaves the rest stale; it never writes
=Nothing=. But a metarecord whose file was deleted *while its subtree was
unwatched* keeps a live-looking =mfr_path= and no =mfr_path_old= — invisible to a
query, which sees only the database, never the disk. The *orphan scan* is the
diagnostic for exactly this state, and *clear* is its cleanup.

*Scan* (=POST /repos/:repo/orphans/scan=, read-only). Driven by the *tracked
set*, not the eligible tree: every metarecord that still resolves an =mfr_path=
is checked against the disk, so a subtree deleted while unwatched is still found.
A record is reported *only when a readable ancestor directory proves the file is
truly absent*: the scan climbs from the path to its nearest existing ancestor and
reports an orphan only if that ancestor could be read (=read_dir= succeeded) and
the path is absent below it. An unreadable (=EACCES=) or stale-handle
(=ENOTCONN=) ancestor — or a broken symlink still present at the path — yields
"unknown", never an orphan.

That guard is *not* sufficient on its own for a removable volume: an unmounted
mount point is an ordinary directory that reads back empty, so its whole subtree
would look "definitely gone". Paths at or below an *offline* mount point
([[*Offline subtrees]]) therefore yield "unknown" too, before the ancestor walk is
even attempted. The two guards together are what make it safe to null the paths
afterwards: neither a permission drop nor an unplugged drive can mass-orphan a
subtree.
Response: ={"count": N, "orphans": [{"uuid": "<32hex>", "stale_path": "/…"}]}=.

*Clear* (=POST /repos/:repo/orphans/clear=, body ={"uuids": ["<32hex>", …]}=).
For each given metarecord *still* definitely gone (re-verified, so a
since-recreated file is skipped), it performs the same transition the watcher
makes on a live delete: snapshot =mfr_path_old=, set =mfr_path= to =Nothing=, and
cascade both to every descendant — all in one revision. Response:
={"cleared": N}=. This is a new, explicit component that writes =Nothing=,
alongside the watcher and =force= writes; *reconcile still never does*.

** Mount status

#+BEGIN_SRC
GET /repos/:repo_uuid/mounts
#+END_SRC

Lists the repository's declared mount points — every metarecord carrying an
=mfr_mount= field (see [[*Mount points]]) — with the state computed at request
time. Read-only, and cheap: one =lstat= pair per declared mount point, no walk.

#+BEGIN_SRC json
{"mounts": [
  {"uuid": "<32hex>", "path": "/media/backup",
   "expected": "uuid:1234-ABCD", "current": "uuid:1234-ABCD", "state": "online"},
  {"uuid": "<32hex>", "path": "/media/photos",
   "expected": "label:PHOTOS", "current": null, "state": "offline"}
]}
#+END_SRC

- =path= — the mount point's repo-root-relative path, or =null= when its
  =mfr_path= no longer resolves (the metarecord is itself orphaned).
- =expected= — the stored =mfr_mount= value.
- =current= — the identity read from disk right now; =null= when nothing is
  mounted there.
- =state= — one of:
  - =online= — a volume is mounted and its identity matches =expected=;
  - =mismatch= — a volume is mounted but reports a different identity (or none
    could be determined). The subtree is *not* frozen: those files exist;
  - =offline= — nothing is mounted there: the subtree is frozen
    ([[*Offline subtrees]]).

This is the endpoint a client uses to explain a subtree that looks empty or
stale, instead of presenting it as deleted — see
[[file:spec-gui.org][spec-gui.org]] "Unmounted volumes".

** Watch status, pause and resume

#+BEGIN_SRC
GET  /repos/:repo_uuid/watch
POST /repos/:repo_uuid/watch/pause
POST /repos/:repo_uuid/watch/resume
#+END_SRC

Reads and sets whether the executor is ingesting filesystem events for this
repository (see [[*Pausing ingestion]]). All three answer the same body:

#+BEGIN_SRC json
{"paused": true, "pending_events": 12043}
#+END_SRC

- =paused= — whether ingestion is paused. In memory: a reload or a daemon
  restart starts unpaused.
- =pending_events= — how many filesystem events are waiting in the in-memory
  buffer (what a resume would apply). Always exact: reading it does not touch
  the repository's connection, so it answers even while the flush the caller is
  trying to stop is holding it.

=pause= also *cancels the flush in progress*, if any — it is the same operation
as cancelling that flush's task (see [[file:spec-tasks.org][spec-tasks.org]]
"Cancellation"), reachable without knowing a task id. =resume= clears the pause
and pings the executor, so what accumulated is flushed after the usual quiet
period. Both are idempotent: pausing a paused repository (or resuming a running
one) is =200= and changes nothing.

** Eligibility explain

#+BEGIN_SRC
POST /repos/:repo_uuid/eligibility
#+END_SRC

Read-only *dry run* of the [[*Eligibility algorithm]] for a list of paths, with
the reason attached. The algorithm's inputs (=mf_watch= / =mf_ignore= on the
ancestor chain, the re-anchoring at the tracking-scope root, the
nearest-ancestor-wins rule) are entirely daemon-side, so a client that wants to
show *why* a path is or is not tracked — the GUI file manager greying out the
entries an ignore pattern excludes, or answering "why is this file not tracked?"
— must ask the daemon rather than re-implement the walk and re-run the regexes
in another engine's dialect.

Request body: repo-root-relative paths (leading slash, =""= is the root), at
most 1000 per call:
#+BEGIN_SRC json
{"paths": ["/music/track.flac", "/target/debug/deps"]}
#+END_SRC

Response: one result per requested path, in the order given.
#+BEGIN_SRC json
{"results": [
  {"path": "/music/track.flac", "eligible": true,  "reason": "tracked",
   "watch_scope": "", "ignore_source": "", "pattern": null},
  {"path": "/target/debug/deps", "eligible": false, "reason": "ignored",
   "watch_scope": "", "ignore_source": "", "pattern": "(^|/)target/…"}
]}
#+END_SRC

- =reason= — the algorithm step that decided: =no_watch= (no =mf_watch= anywhere
  on the chain: the opt-in default), =watch_false= (the nearest =mf_watch= is
  =false=), =direct_watch= (=mf_watch= set directly on the path: tracked
  unconditionally, step 3), =ignored= (a pattern matched, step 5), =tracked=
  (step 6).
- =watch_scope= — the path of the tracking-scope root (the metarecord whose
  =mf_watch= decided), against which patterns are matched; =null= when no
  =mf_watch= was found.
- =ignore_source= — the path of the nearest ancestor providing the effective
  pattern set, =null= when none has one.
- =pattern= — the pattern that matched, only for =reason = "ignored"=.

Evaluating a path costs an ancestor-chain walk served by the tree cache; the
call compiles each pattern once for the whole batch (the reconcile walk's
=EligibilityCache=), so a directory listing is one request.

** Effective ignore set

#+BEGIN_SRC
GET /repos/:repo_uuid/ignore/effective?path=<repo-root-relative>
#+END_SRC

The =mf_ignore= pattern set that *governs* the given directory, and where it
comes from. Since sets are never merged across ancestors (the nearest ancestor
with at least one row wins), writing a single pattern onto a directory that has
none silently drops the whole inherited set for that subtree — a trap this
endpoint exists to let a client show and avoid (spec-gui "Ignore patterns"
describes the copy-on-write flow built on it).

#+BEGIN_SRC json
{"source": "/music", "source_uuid": "<32hex>", "direct": false,
 "patterns": ["\\.git(/.*)?$", "…"]}
#+END_SRC

- =source= — the path of the metarecord providing the set, =null= when no
  ancestor (nor the directory itself) has any =mf_ignore= row.
- =direct= — whether =source= *is* the requested path (its own set, so editing
  it changes nothing else) rather than an inherited one.
- =patterns= — the source's rows, in order.

Unlike the eligibility walk, the search *includes* the requested path itself:
the question is "which set governs writes here", not "which set filtered this
entry" (the algorithm's step 4 excludes the entry itself, which matters only for
a file being tested).

* CLI

** =mf reconcile=

Calls =POST /reconcile= (full reconcile) and prints a summary followed by the
candidate list:

#+BEGIN_SRC
created: 2  moved: 1

Candidates (confirm with: mf set <uuid> 'mfr_path:tree_ref=<parent_uuid>/<name>' --force):
  abc...  /music/jazz/old.mp3
      → /music2/jazz_copy.mp3   (partial_hash)
      → /backup/unknown.mp3     (size)
#+END_SRC

Candidates are informational: the CLI never auto-confirms a match. To confirm
one, the user updates the orphaned metarecord's =mfr_path= as shown (a =force=
write, since =mfr_path= is an =mfr_*= field).

| Flag                  | Description                                                          |
|-----------------------+----------------------------------------------------------------------|
| =--metarecord <uuid>= | Scope the reconcile to that metarecord's subtree (sends =metarecord= in the body); otherwise the whole repository |
| =--threshold <0..1>=  | Enable the similarity phase with this minimum score (full reconcile only) |
| =--no-mime=           | Do not compute =mfr_mime= for files that lack it (sends =mime: false=) |
| =--no-refresh=        | Do not refresh =mfr_*= stat fields of in-place (unmoved) files (sends =refresh: false=) |
| =--json=              | Print the raw JSON response body                                     |

** =mf track <path>=

Calls =POST /track= for the given path (OS-native absolute path, or relative
to the current directory — the CLI absolutises it). Prints the metarecord UUID.
Idempotent: an already-tracked path prints its existing UUID rather than
failing. Fails with exit code 1 when the path is outside the repository root.

** =mf path <uuid>=

Prints the absolute filesystem path of a metarecord by walking the =mfr_path=
parent chain up to the root metarecord (repository root from =GET /repos=).
With =--relative=, prints the repo-root-relative path instead, starting
with =/= (the root metarecord itself is =/=). Fails with exit code 1 when the
metarecord has no =mfr_path= TreeRef (untracked or deleted file).

** =mf orphan {list, clear}=

Diagnoses and cleans up metarecords whose file is gone (see [[*Orphan scan]]).
=list= (the default) calls =POST /orphans/scan= and prints =uuid <TAB>
stale_path=, one per line, or a "no orphans" line. =clear [-y]= scans, prints the
records to stderr, prompts for confirmation (skipped with =-y=), then calls
=POST /orphans/clear= with the scanned uuids and prints =cleared N=. It is kept
separate from =mf reconcile= on purpose: detection needs a disk scan, but the
intent (diagnose / clean up missing files) is not reconcile's sync semantics.

** =mf mount {list, forget}=

Inspects the repository's declared mount points (see [[*Mount points]]).

=list= (the default) calls =GET /mounts= and prints one line per mount point,
=state <TAB> path <TAB> expected <TAB> current=, or a "no mount points" line.
=--json= prints the raw response body. Typical output:

#+BEGIN_SRC
online     /media/backup   uuid:1234-ABCD  uuid:1234-ABCD
offline    /media/photos   label:PHOTOS    -
#+END_SRC

=forget <uuid> [-y]= un-declares a mount point: a =force= unset of =mfr_mount=
on that metarecord. The directory becomes an ordinary tracked directory again —
so if the volume is *not* mounted, its former contents stop being frozen and the
next =mf orphan= run will legitimately report them as gone. It is the escape
hatch for "this is not a mount point any more", and prompts for confirmation
unless =-y= is given.

There is no =mf mount add=: mount points are detected, not declared. Mounting a
volume and running =mf reconcile= is what records one.

** =mf watch {status, pause, resume}=

Controls the ingestion of filesystem events for the repository (see
[[*Pausing ingestion]]).

=status= (the default) calls =GET /watch= and prints one line — =running= or
=paused=, with the number of buffered events:

#+BEGIN_SRC
paused     12043 events waiting
#+END_SRC

=pause= calls =POST /watch/pause=: it stops the flush in progress (its
uncommitted group is abandoned, its events stay buffered) and keeps the executor
from starting another. =resume= calls =POST /watch/resume= and prints how many
events are about to be applied. =--json= prints the raw body for all three.

** =mf order <folder> [--meta <field>] [--max-gap <n>] [--dry-run]=

Numbers a folder's *direct children* so a "sort by position" orders them
sensibly (an album's tracks, a series' seasons). Files and directories are
numbered independently into two integer fields, =order_position_file= and
=order_position_dir= (so each kind can be sorted on its own), and a child that
already has a position is *never overwritten* — user corrections survive a
re-run. Operates on already-tracked children (reconcile the folder first if
some are missing).

Each kind's children are ordered by three heuristics in turn, over a running
maximum position (=next= = max+1); gaps are intentional (they mirror the number
differences) and positions are not compacted:

1. *Metadata* — children carrying an integer ordering field (=--meta=, default
   =mfr_meta_track=), sorted by it: an anchor at =next=, then
   =pos = anchor_pos + (value − anchor_value)= (ties share a position).
2. *Name pattern* — children whose basename is =<prefix><number><suffix>=,
   clustered by identical =(prefix, suffix)= (the *last* digit run is the
   number). A cluster needs ≥2 members and a minimal consecutive gap ≤
   =--max-gap= (default 1000; a larger gap means the number is an id/hash, not
   an order). A member already positioned (e.g. by metadata) pins the cluster;
   otherwise its lowest-numbered member is placed at =next=. Others:
   =pos = anchor_pos + (number − anchor_number)=.
3. *Creation date* — everything left, by =mfr_btime= ascending (missing btime
   last, then by name), each at =next=.

Once the children are numbered the *folder* is marked with =order_numbered =
true= (a plain boolean field, written once — a re-run on an already marked
folder produces no revision for it). It tells a processed folder from an
untreated one: =order_numbered = true= finds the folders already numbered,
=order_numbered is absent= the ones still to do.

=--dry-run= prints the planned =uuid<TAB>field=pos<TAB>name= lines without
writing — the marker included, nothing at all is written; otherwise the number
of fields written is printed (the marker is not counted).

The heuristic and the whole orchestration (read the children, write the
positions, mark the folder) live in =metafolder_core::order=, shared with the
GUI's =mf:order= command (see [[file:spec-gui.org][spec-gui.org]] "Order a
folder's children").

** Configuring the watch scope

The watch/ignore system is driven by the =mf_watch= and =mf_ignore= fields
(see [[*Watch and Ignore]]); no dedicated commands are needed:

#+BEGIN_SRC
# Activate tracking for a directory metarecord
mf set <dir_uuid> mf_watch:bool=true

# Then create metarecords for the files already inside it
mf reconcile --metarecord <dir_uuid>

# Replace the ignore patterns of a directory (multi-map: one add per pattern)
mf set <dir_uuid> 'mf_ignore:string=\.git(/.*)?$'
mf add <dir_uuid> 'mf_ignore:string=target(/.*)?$'
#+END_SRC

* Open questions

** Watcher reliability on the repository root
A removable volume *inside* a repository is specified — see [[*Mount points]].
The remaining hole is the repository *root* itself going away while the daemon
runs (the whole repo on the unplugged drive, or the root renamed): the root has
no ancestor to compare device ids with, its =.metafolder/internal/db.sqlite= may
vanish under an open, exclusively-locked connection, and the absolute =root= in
=config.json= is not a stable identity across remounts. The daemon should detect
this, mark the repository unavailable and drop its connection — and, on the way
back, be able to find the repository by volume identity rather than by absolute
path. Undefined for now.
