#+TITLE: Metafolder — Cross-platform Compatibility Specification
#+OPTIONS: toc:2 num:t

* Overview

Metafolder targets Linux, macOS, and Windows. This file centralises every
platform-dependent behaviour; the other spec files describe behaviour in
platform-neutral terms and link here for the per-platform details. The data
model itself is platform-independent: a repository created on one OS must be
loadable on another (e.g. a repo on a removable drive).

* Concepts

** Path representation

- Internally (database, HTTP API, query DSL, tree cache), paths are always
  repo-root-relative and use =/= as separator, regardless of platform.
  =TreeRef= =value_name= components are single path components and never
  contain a separator.
- Conversion to and from the OS-native form (e.g. =\= separators, drive
  prefixes on Windows) happens only at the filesystem boundary (watcher,
  reconcile, track, file transfers). Rust's =std::path= handles this
  conversion.
- Absolute paths appear only in =config.json= (=root=, =metafolder=) and in
  API parameters that designate filesystem locations (=/repos/init=,
  =/repos/load=, =/track=). These are OS-native and therefore not portable
  across platforms; when a repository is moved to another machine or OS, the
  =root= in =config.json= must be updated (loading by =metafolder= path
  already re-reads =root= from =config.json=).
- File names are stored in =value_name= verbatim, as returned by the OS
  (UTF-8; on Windows, the UTF-16 names are converted to UTF-8). Names that
  are not valid Unicode are not supported in v1 and are skipped with a
  warning.

** Case sensitivity

Default filesystems are case-sensitive on Linux and case-insensitive (but
case-preserving) on macOS and Windows. The stored =value_name= always keeps
the on-disk casing. When the daemon loads a repository it probes the
filesystem's case sensitivity (by creating a temporary file inside
=.metafolder/internal/= and testing access through a different casing) and records the
result in the in-memory repo state. On case-insensitive filesystems, path
comparisons performed by the watcher, reconcile, and the tree cache use
case-insensitive matching, so that an event reported with different casing
still resolves to the existing metarecord.

** File metadata fields

Availability of the =mfr_*= stat-derived fields per platform:

| Field              | Linux           | macOS             | Windows                       |
|--------------------+-----------------+-------------------+-------------------------------|
| =mfr_type=         | yes             | yes               | yes                           |
| =mfr_size=         | yes             | yes               | yes                           |
| =mfr_mtime=        | yes             | yes               | yes                           |
| =mfr_btime=        | if FS supports (=statx=) | yes (=st_birthtime=) | yes (=ftCreationTime=) |
| =mfr_permissions=  | yes             | yes               | *never written* (absent)      |
| =mfr_uid=          | yes             | yes               | *never written* (absent)      |
| =mfr_gid=          | yes             | yes               | *never written* (absent)      |
| =mfr_mount=        | yes             | yes (no identity) | *never written* (absent)      |

- =mfr_permissions=, =mfr_uid=, =mfr_gid= are Unix-specific. On Windows they
  are never written; on a metarecord they remain in the "unknown" state
  (=IsUnknown=). A repository written on Unix and later watched on Windows
  keeps the Unix values untouched (Windows daemon operations simply do not
  refresh them).
- =mfr_btime= is read through =std::fs::Metadata::created()=, which abstracts
  the per-OS source. It is absent when the filesystem does not provide it.
- Hashing (=mfr_partial_hash=, =mfr_full_hash=) is pure content-based
  (=xxhash-rust=) and fully portable.
- =mfr_mount= marks a mount point; its detection and the identity string it
  stores are platform-dependent — see [[*Mount point detection]] below.

** MIME detection

=mfr_mime= is computed by content analysis. The backend is the pure-Rust
=infer= crate (magic-byte signatures) on every platform — no system
=libmagic= dependency. The stored value is always a standard MIME string.
=infer= recognises common binary formats (images, audio, video, archives,
documents); types it cannot classify from magic bytes (e.g. plain text) leave
=mfr_mime= absent.

Detection is triggered by =reconcile= (full and single-metarecord), which fills
=mfr_mime= for files that do not already have one. It is enabled by default and
opted out per call with =mime: false= in the request body (CLI: =--no-mime=).
Computation is idempotent — an existing =mfr_mime= is never recomputed, so a
content change is not reflected until the field is cleared.

** Embedded metadata extraction

Many media formats carry *embedded* metadata describing the content itself —
an audio file's artist/album/title, an image's capture date/camera/GPS, a
video's title. Unlike the =mfr_*= stat fields (which describe the filesystem
entry) these describe the *payload*. The daemon extracts a curated, normalised
subset into reserved =mfr_meta_*= fields, so they are queryable through the
ordinary EAV model like any other field.

*** Backend

Extraction is done with **pure-Rust, memory-safe parsers** — no external
subprocess and no system dependency, mirroring the =infer= choice for MIME:

- audio (=lofty=): ID3v2/ID3v1, Vorbis comments (FLAC/Ogg/Opus), MP4/M4A
  atoms — tags *and* stream properties (duration, bitrate, sample rate,
  channels);
- images (=nom-exif= / an EXIF reader): EXIF/TIFF tags of JPEG, TIFF and
  common RAW — capture date, camera make/model, orientation, GPS, dimensions;
- video containers (Matroska/MP4, best-effort): container title and, where
  cheap, dimensions and duration.

Memory-safety is the reason a subprocess sandbox is *not* required for this in
the daemon: a crafted file can at worst make a parser panic or return wrong
values (which the extraction pass catches and treats as "no metadata"), never
the passive code-execution vector that the C media decoders behind =ffmpeg= /
the WebView are (those stay confined by the GUI's =bwrap= sandbox — see
spec-gui "Untrusted media"). A richer =exiftool=/=ffprobe= backend is a
possible **future extension**, but only once that sandbox machinery is
available daemon-side; it is explicitly out of scope here.

*** Fields and the source→field mapping

The same *meaning* is spelled differently across formats (a track's performer
is ID3 =TPE1=, Vorbis =ARTIST=, MP4 =©ART=), and which keys are worth
extracting is a matter of taste. So the daemon does *not* hard-code the field
set: extraction is driven by a **user-editable mapping** (see *Configuration*
below). Each entry names a target field, its =Value= type, and the list of
native source keys that feed it:

: from = [source key, source key, …]  →  mfr_meta_<name> : <type>

Only a *normalised* set of well-known keys is stored, never the hundreds of raw
format-specific tags (which would flood the field catalogue and index). The
extractor collects every =(source key, value)= pair a file provides, then, for
each mapping entry, writes =mfr_meta_<name>= from the *first* present source
key in its =from= list. A source whose text cannot be parsed into the entry's
=type= is skipped (the next source is tried), so a malformed tag never poisons
a field.

Source-key vocabulary (what may appear in =from=):
- *audio tags* — the =lofty= normalised item keys (=TrackTitle=,
  =TrackArtist=, =AlbumTitle=, =AlbumArtist=, =Genre=, =RecordingDate=,
  =Year=, =TrackNumber=, =DiscNumber=, =Comment=, …), which already unify
  ID3 / Vorbis / MP4 spellings; an unmapped native tag is also offered under
  its raw name;
- *image tags* — EXIF/TIFF tag names (=DateTimeOriginal=, =Make=, =Model=,
  =Orientation=, =GPSLatitude=, =GPSLongitude=, =Artist=, =Copyright=, …);
- *stream properties* — computed, not tags, so they are offered under
  reserved =@=-prefixed synthetic keys: =@duration_ms=, =@bitrate=,
  =@sample_rate=, =@channels=, =@width=, =@height=.

=DateTime= fields store Unix-ms (via =core::date=); a bare year (e.g. Vorbis
=DATE 1998=) is normalised to that year's January 1st, 00:00 UTC, and EXIF
=DateTimeOriginal= to its exact instant. Only keys the file actually provides
are written; the rest stay in the "unknown" state. Values are the daemon's, so
all =mfr_meta_*= names are reserved (=mfr_*=): a user write requires =force=,
like any stat field.

*** Configuration

The mapping is **per repository**, living at =.metafolder/metadata-map.toml=,
alongside =config.json= and the optional =schema.json= — ordinary trackable
content (not under =internal/=), following the user-schema model rather than the
git-backed =~/.config/= configs. Per-repo is deliberate: repositories in
different languages or cataloguing conventions want different mappings, and the
map belongs with the repository it describes.

- =mf init= **seeds** the file from a default baked into the daemon
  (=include_str!= of =crates/daemon/src/default-metadata-map.toml=), the same
  way init writes =config.json= and the root metarecord's defaults. The shipped
  default therefore only affects *new* repositories; editing it never rewrites
  an existing repo's map.
- At repo *load* the daemon reads the file. If it is **absent** (a repo created
  before this feature, or a deleted file) the daemon self-heals: it writes the
  baked-in default, then reads it (this is repository-owned data, not user
  config, so writing a default does not conflict with spec-config's "No runtime
  fallback"). If it is **malformed**, only *that* repository fails to load
  (a targeted error/warning), never the whole daemon — exactly like an invalid
  =schema.json=.

(=string=/=int=/=float=/=datetime=), and =from= (ordered source keys). Editing a
repo's file changes what that repo extracts; a newly-mapped field is picked up
by the next extraction of a file (re-extraction requires clearing
=mfr_meta_extracted=, below). The baked-in default that seeds new repos:

*** Trigger and idempotency

Extraction is a =reconcile= phase (full and single-metarecord), enabled by
default and opted out per call with =metadata: false= in the request body
(CLI: =--no-metadata=), the same shape as =mfr_mime=.

Because a file may legitimately carry *no* embedded metadata (a plain =.txt=,
a data blob), "is any =mfr_meta_*= field absent?" cannot gate re-extraction —
it would re-parse such files on every reconcile. Instead a boolean marker
=mfr_meta_extracted = true= records that a file has been analysed. The phase
skips any file that already has the marker and sets it (alongside whatever
keys were found) after analysing one. Extraction is thus idempotent: re-running
reconcile never re-parses nor grows the log. A content change is not reflected
until =mfr_meta_extracted= (and, to re-read, the stale =mfr_meta_*= values) are
cleared — the same "clear to recompute" contract as =mfr_mime=.

** Mount point detection

The =mfr_mount= field marks a directory that is the mount point of another
volume, and its absence-while-declared freezes the subtree
([[file:spec-file-tracking.org][spec-file-tracking.org]] "Mount points"). Both
halves are platform-dependent.

*** Is this directory a mount point?

*Linux — ask the kernel.* A path is a mount point iff it appears as one in
=/proc/self/mountinfo=. That list is authoritative for the daemon's mount
namespace, and it is the only source that gets both of these right:

- a =mount --bind= of a directory from the *same* filesystem shares its
  superblock, so its device id equals its parent's — invisible to a =st_dev=
  comparison, yet =umount= still empties it. (Every real filesystem has its own
  superblock — ext4, btrfs, tmpfs, NFS, and every FUSE mount such as gocryptfs,
  encfs or sshfs — so this superblock *sharing* is the only blind spot a device
  comparison has;)
- btrfs gives each *subvolume* an anonymous device id, so a device comparison
  calls a plain subvolume boundary a mount point although nothing is mounted
  there and nothing can be unplugged.

The table is re-read at most once per second and kept as a process-wide
snapshot: every directory a reconcile touches asks the question, and the kernel
regenerates that file on each read. A second of staleness is harmless — mounting
a volume triggers no reconcile of its own, so the answer is consumed by a later
operation anyway.

Paths are matched verbatim against the table's canonical form. Every path the
daemon builds starts at the canonicalized repository =root= and never traverses
a symlinked directory (neither the reconcile walk nor the watcher follows one),
so no per-probe =canonicalize= is needed.

*Other Unix (macOS), and Linux with an unreadable =/proc=* — fall back to
comparing the device id of the directory with that of its parent (=st_dev=, via
=std::os::unix::fs::MetadataExt::dev=), with the two divergences above. An
empty mount-table snapshot is precisely the signal to fall back.

The repository root is a special case in both cases — its parent lies outside
the repository — and is never marked.

*Windows*: =std::fs::Metadata= exposes no device id, and a removable volume is
normally a drive letter (its own repository root) rather than a directory inside
a tree. Mount points are therefore *not detected on Windows*: =mfr_mount= is
never written, exactly like =mfr_permissions=. A repository whose =mfr_mount=
fields were written on Unix keeps them, and a Windows daemon still honours the
freeze — which needs only the field's presence and a "is something mounted
here" answer.

*** Volume identity (the field's value)

Best effort, in this order; the first form that can be determined wins:

| Form            | Source                                                                 |
|-----------------+------------------------------------------------------------------------|
| =uuid:<UUID>=   | Linux: the entry of =/dev/disk/by-uuid/= whose =rdev= equals the mount's =major:minor= (from =/proc/self/mountinfo=) |
| =label:<LABEL>= | Linux: same, through =/dev/disk/by-label/=                              |
| =device:<SRC>=  | Linux: the mount source field of =/proc/self/mountinfo= (=/dev/sdb1=, =user@host:/export=, =tmpfs=…) |
| =mounted=       | anything else (no mount table available, or nothing identifiable found) |

Matching by =rdev= rather than by symlink target makes the lookup immune to
=/dev/mapper= indirections and multi-hop symlinks. =/proc/self/mountinfo= is
Linux-only; macOS falls back to =mounted= (=getmntinfo= would require a =libc=
dependency the daemon does not have — a possible refinement, not a requirement:
the value is informational, and the semantics ride on the field's presence).

The value is *opaque to every consumer*. Only =GET /mounts= interprets it, and
only to compare the stored string with the one read from disk (=mismatch=).

** File watcher backends

The =notify= crate abstracts the per-OS event APIs: inotify (Linux), FSEvents
(macOS), ReadDirectoryChangesW (Windows). Behavioural differences the daemon
must absorb:

- *Rename correlation*: on Linux, =MOVED_FROM= / =MOVED_TO= pairs are matched
  by inotify cookie into =Rename(Both)=. On backends where correlation is
  unavailable or unreliable, a rename may surface as =Remove= followed by
  =Create=; identity is then recovered through the orphan fingerprint search
  of the =Rename(To)= / reconcile path (see
  [[file:spec-file-tracking.org][spec-file-tracking.org]]). The data model is
  unaffected.
- *Data/Metadata distinction*: where the backend cannot distinguish
  =Modify(Data)= from =Modify(Metadata)=, the daemon falls back to
  =Modify(Data)= semantics (full refresh + hash invalidation).
- *Recursion*: inotify requires one watch per directory (the =notify= crate
  manages this); FSEvents and ReadDirectoryChangesW are natively recursive.
  This is an implementation detail with no spec-visible effect, except that
  on Linux very large repositories may hit
  =fs.inotify.max_user_watches=; the daemon logs a clear error when watch
  registration fails.

** Network and special filesystems

SQLite WAL mode requires shared-memory files (=.wal-shm=), which network
filesystems (SSHFS, NFS, SMB/UNC shares) generally do not support. When a
repository's =.metafolder/= directory resides on such a filesystem, the
daemon switches that connection to =PRAGMA journal_mode=DELETE=. The switch
is per-connection and does not alter the database permanently; the next local
connection resumes WAL. Detection: the daemon attempts to open in WAL mode
and falls back to DELETE if SQLite reports an error.

** GUI WebView

The GUI (Tauri) renders in the system WebView: WebKit2GTK on Linux, WKWebView
on macOS, WebView2 on Windows. Media codec support in the =file= panel type
therefore varies by platform; on Linux, H.264 may require GStreamer plugin
packages (e.g. =gst-plugins-bad=, =gst-libav=).

** Session-token runtime directory

The loopback session tokens ([[file:spec-auth.org][spec-auth.org]]) live in a
per-user runtime directory. On Unix this is =$XDG_RUNTIME_DIR/metafolder/=
(typically =/run/user/<uid>/=, already =0700=) or, when =XDG_RUNTIME_DIR= is
unset, a hardened =/tmp/metafolder-<uid>/= (created =0700=, refused if squatted
or a symlink). On Windows, which has neither =XDG_RUNTIME_DIR=, uid, nor the
=0600/0700= mode model, the tokens fall back to
=%LOCALAPPDATA%\metafolder\= with a best-effort restriction; full Windows
hardening is an open question (deferred with v1).

* Daemon

- Path conversion and case-sensitivity probing as described in
  [[*Concepts]]. The probe runs once per =load= and its result is kept in
  =RepoState=.
- The daemon never creates files outside =.metafolder/=, so Windows reserved
  device names (=CON=, =NUL=, ...) only matter when *reading* the tree: such
  names are tracked like any other if the filesystem reports them.
- The exclusive-lock invariant (=PRAGMA locking_mode = EXCLUSIVE=) works on
  all three platforms via SQLite's portable locking.

* CLI

- Path arguments (=mf init=, =mf load=, =mf track=) accept OS-native paths
  and are sent to the daemon as such (the daemon and CLI run on the same
  machine).
- Paths printed in output (query results, reconcile candidates) are the
  internal repo-root-relative =/=-separated form, on every platform.
- Rollback =move_file= operations execute the file move with OS-native paths
  derived from the internal form.

* Open questions

** Unicode normalisation

macOS filesystems normalise names (HFS+: NFD; APFS: normalisation-
insensitive). A repo created on Linux with NFC names and opened on macOS may
see the "same" name with a different byte sequence. Whether =value_name=
should be normalised (e.g. to NFC) at the filesystem boundary, or compared
normalisation-insensitively like case, is unresolved.

** Windows long paths

Paths longer than 260 characters require the =\\?\= prefix or a registry
opt-in on Windows. Whether the daemon should apply the prefix automatically
is unresolved.

** Symbolic links

Symlinks are **never dereferenced**: the daemon stats them with =lstat=
(=symlink_metadata=), never =stat=. A symlink is a first-class tracked entity
described by *its own* metadata — =mfr_type = "symlink"=, the link's own
=mfr_size= / =mfr_mtime= / =mfr_permissions=, and =mfr_symlink_target= holding
the target **path** (from =readlink=). The target's content is never read and
never fingerprinted, so the daemon never stats or reads a location outside the
repository through a link, and the watcher and reconcile agree. The reconcile
walk does not descend into a symlinked directory (it is a leaf symlink).

Platform note: on Windows, *creating* a symlink requires privileges, but
reading one (=lstat= / =readlink=) does not, so tracking is unaffected.
