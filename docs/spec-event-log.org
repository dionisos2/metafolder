#+TITLE: Metafolder — Event Log and Rollback Specification
#+OPTIONS: toc:2 num:t

* Overview

Every write operation on metadata metarecords is recorded in an append-only event
log stored in the same =db.sqlite= file. The log maintains a tree of /operations/
that enables:

- *Auditing*: full history of changes to any metarecord.
- *Rollback*: navigating the history tree to any past or future state.
- *Revert*: undoing one past revision or operation in place, by writing the
  state it replaced as a new revision rather than by moving HEAD.
- *Undo* / *Redo*: taking back the newest change /the user/ made — and taking
  that back in turn — choosing between the two mechanisms above according to
  what has been written since (see [[*Undo]], [[*Redo]]).
- *Non-destructive branching*: after rolling back, any new write creates a new
  branch — previously "future" operations are never lost.

The current database state reflects exactly the operation pointed to by /HEAD/.
Formally: replaying, in order, all operations on the path from the root to HEAD
reproduces the current state of all data tables.

* Concepts

** Revision and operation

An /operation/ is one atomic change (e.g. setting one field on one metarecord). It
is the node of the history tree and the unit of crash-safe rollback.

A /revision/ groups all operations produced by a single API call. It is a
grouping annotation on operations, not a tree node. It is not possible to roll
back a single operation within a multi-operation revision via the high-level
rollback API — the revision remains the minimum unit of user-facing rollback.
Direct operation-level navigation is available via =op_id=. Undoing one
operation of a revision /in place/ is a different matter, and is what
[[*Revert]] is for.

In practice, most revisions contain a single operation (a user editing one
field). Revisions with many operations arise from batch commands: a =batch_set=
on K metarecords produces K operations; a =reconcile= creating M files produces M
operations; a watcher =Remove= on a directory with N descendants produces N+1
=file_deleted= operations. For large batches, operations are inserted in bulk.

** Revision origin

A revision records /who asked for it/: =revision.origin= is =watcher= for the
revisions the daemon writes on the filesystem's behalf — the watcher's flush and
the restoration replay that follows a skipped navigation step — and =NULL= for
every write a client requested.

It is the revision that carries this, not the operation types, because the types
cannot express it. A file *arriving* is recorded as a =create_metarecord= plus
its field writes, indistinguishable by type from a metarecord the user created;
only =file_deleted=, =file_moved= and =file_modified= name the watcher, and they
cover the changes to an /existing/ record, not the new ones. A reader that judged
by type alone would read every arrival as the user's work.

The distinction exists for [[*Undo]], which must not rewind past what the
filesystem really did. It is also displayed: the GUI's log panel dims the
watcher's revisions (spec-gui "Event log").

A database written before the column existed has =NULL= everywhere; a reader
falls back to the operation types there, which is sound (the watcher does write
those types) without being exact (an arrival still reads as the user's).

** History tree

Operations form a tree: each operation has a =parent_id= pointing to the
operation it was created from (=NULL= for the root). The /HEAD/ pointer metarecords
the current operation — the one whose state is reflected in the data tables.

Operations within the same revision form a chain: the first operation's
=parent_id= is the HEAD before the revision; each subsequent operation's
=parent_id= is the previous operation in the revision. HEAD advances to the
last operation of the revision on commit.

Example (two revisions, =rev_1= with one op and =rev_2= with two ops):

#+BEGIN_SRC
op_1 [rev_1] ← op_2 [rev_2] ← op_3 [rev_2] ← HEAD
#+END_SRC

After rolling back to =op_1= and writing =op_4=:

#+BEGIN_SRC
op_1 ← op_2 ← op_3   ← branch (still reachable)
     └─ op_4           ← HEAD
#+END_SRC

History is lost in exactly two ways, both configured: an explicit prune (see
[[*Log pruning]]) and the retention limit (see [[*Automatic retention]]), which
keeps the last 200 revisions out of the box. Nothing else drops an operation —
a rollback abandons a branch, it does not delete it.

** HEAD pointer

A singleton table =log_head= records the current operation. All data tables
(=metadata=, =field=) reflect exactly the state of the
operation at HEAD.

Invariant: HEAD and the data tables are always mutually consistent. Every HEAD
update and every data change execute in a single SQLite transaction, so a crash
leaves both in a consistent state.

** Label

A revision may carry an optional human-readable =label=. A label serves as a
named rollback target: ={"label": "before-cleanup"}= navigates HEAD to the last
operation of the most recent revision carrying that label.

A label is set either at write time (passed in the API call that creates the
revision) or post-hoc via =PATCH /log/revisions/:rev_id=. Labels are not
unique; rollback to a label targets the most recent matching revision.

** Operation types

| =op_type=        | Description                                              | Filesystem coordination   |
|------------------+----------------------------------------------------------+---------------------------|
| =create_metarecord=   | New metadata metarecord created                               | None                      |
| =delete_metarecord=   | Metarecord deleted (all fields cascade)                       | None                      |
| =set_field=      | All rows for =(uuid, field_name)= replaced               | None                      |
| =append_field=   | One field row appended (multi-map)                       | None                      |
| =delete_field=   | One field row removed (by =field_id=)                    | None                      |
| =file_deleted=   | Watcher: file removed; =mfr_path= → =Nothing=            | File is gone              |
| =file_moved=     | Watcher: file renamed/moved; =mfr_path= TreeRef updated  | =mv= required (see below) |
| =file_modified=  | Watcher: file content changed; hashes invalidated        | Content is gone           |
| =unknown=        | Unlogged write; marks a weak root (see [[*Normal write flow]]) | None               |

Reversibility is assessed dynamically at rollback time, not stored statically:

- =create_metarecord= … =delete_field=: always fully reversible (pure metadata).
- =file_deleted=, =file_modified=: reversible at the filesystem level *only if
  the content is in the trash-bin* — the change passed through it, e.g. an
  =mf trash -f= or an earlier rollback. The CLI then puts the file back and lets
  the daemon apply the real inverse, so content and metadata come back together.
  A trashed *directory* covers its whole subtree: restoring that one blob makes
  every descendant's step reversible too, whatever order the cascade is
  navigated in.

  Otherwise the content is gone and the CLI passes =skip: true=, which skips the
  *filesystem* action and nothing else. The daemon still applies the metadata
  inverse — HEAD has to cross the operation, and the HEAD↔data invariant forbids
  passing one without applying it — and then enqueues a /restoration operation/
  that re-records the truth on the new branch once the navigation ends (see
  [[*Filesystem coordination]]). So a =file_deleted= has its =mfr_path=
  restored and set back to =Nothing= one revision later, and a =file_modified=
  has its hashes cleared with =mfr_size= and =mfr_mtime= left stale until a
  reconcile. The state one ends up in is truthful; it takes two revisions to
  get there.
- =file_moved=: reversible if and only if the file still exists at its current
  location at rollback time. If the file has since been deleted or moved again,
  the =mv= cannot be executed and only the metadata can be restored (stale
  path).

That assessment is about the filesystem, it is genuinely dynamic, and it applies
to a rollback and to a revert alike. Whether an operation can be undone /on its
own/ is a different question, structural and answered from the log alone — see
[[*Operation dependencies]]. It concerns the revert only.

** Revert

Rollback moves HEAD: it undoes everything back to a point in time, and the
operations it passes over are undone because they are /in the way/, not because
anyone objected to them. That is the right tool for "take me back to how things
were at lunchtime". It is the wrong tool for "that one rename was a mistake" —
especially in a watched repository, where the watcher writes a revision per
batch of filesystem events and dozens of unrelated ones may have landed since.

A /revert/ answers the second question. It undoes one revision — or one
operation — *without moving HEAD*: the daemon computes the state that operation
replaced and writes it back as an ordinary new revision at HEAD. The log grows
by one entry saying so. Nothing is removed from the history: the mistake and its
correction are both on the record, which is what an audit log is for.

A revert is an ordinary write in every other respect. It goes through
[[*Normal write flow]] like any other; it can itself be reverted (restoring the
original change); it can be rolled back across, pruned, and trimmed by
retention. The only thing that marks it is a =reverts_op_id= column naming what
each of its operations undid, kept for display and provenance.

Not every operation can be reverted on its own: a later one may have overwritten
what it wrote, in which case there is no meaningful "before" left to restore.
That is what [[*Operation dependencies]] decides.

** Operation dependencies

Every operation writes one /cell/:

- an operation carrying a =field_name= writes the cell =(entity_uuid,
  field_name)=. That includes the watcher's =file_deleted=, =file_moved= and
  =file_modified=: they are set-field-shaped and each names the field it wrote.
- =create_metarecord=, =delete_metarecord= and =set_metarecord= carry no field
  name and write the *whole entity*. Their cell is =(entity_uuid, *)=, which
  intersects every cell of that entity.

Two operations are /independent/ when their cells do not intersect. Independent
operations commute: applying them in either order, or removing one and keeping
the other, yields the same state. Operations sharing a cell do not commute —
=set_field= replaces every row of its cell, so the later one erases what the
earlier one wrote and the earlier one's "after" state survives nowhere.

Hence the rule:

#+BEGIN_QUOTE
A set =S= of operations is *revertable* when no operation outside =S=, between
the oldest member of =S= and HEAD along HEAD's ancestry, writes a cell that =S=
writes.
#+END_QUOTE

When one does, =S= is *blocked by* it and the daemon names it, so the answer to
"why can I not undo this?" is an operation the user can go and look at — and
usually revert first.

This check is *structural, not dynamic*. It reads the =operation= table and
nothing else: not the filesystem, not the current field values, not even the
snapshot contents. Two callers asking at the same HEAD get the same answer, and
it remains the answer until HEAD moves. It is also cheap: =idx_operation_entity
(entity_uuid, id)= is exactly the index it wants.

*Rollback has no equivalent check and needs none.* It undoes operations in
reverse order down to its target, so any operation that overwrote another has
already been undone by the time that other one's turn comes. Ordering
guarantees structurally what the dependency check must establish explicitly for
a revert, which is why the check belongs to the revert alone.

It is a separate axis from the filesystem reversibility of
[[*Operation types]], and the two are evaluated independently: dependency asks
whether the metadata change is still meaningful, filesystem reversibility
whether the file action that accompanies it is possible.

*** Reverting the dependents too

Being told what blocks a revert is often the answer: revert that first, or pick
a narrower set. Sometimes it is not — the blocker is unwanted too, or it is a
watcher event that only brushed the cell in passing. So a revert may be asked to
*take the blockers with it*.

What it then reverts is the /dependency closure/ of =S=: add every blocker to
=S=, recompute, repeat until nothing new appears. One pass does not suffice,
because an entity-scoped blocker widens the cells the set writes — a
=delete_metarecord= dragged in makes every operation on that entity a blocker in
turn. The iteration terminates: a blocker is always younger than the oldest
member of =S=, so it never escapes the window between that operation and HEAD.

The closure is revertable by construction, and reverting it is the same
operation as before over more members. It need not be contiguous in the log:
operations writing none of its cells sit between its members and are left
alone — which is the whole point, they are independent, so undoing the closure
does not disturb them.

What it *is* worth doing is looking at how far it grew before confirming. At
the limit, where the closure swallows everything between =S= and HEAD, a
dependent-including revert *is* a rollback to the parent of =S='s oldest member,
written forward as a new revision instead of by moving HEAD. Between "undo this
one field" and "undo everything since" the mechanism is continuous, and the size
of the closure is what tells the user where on that scale the request landed.

*** Reverting a set

The unit a user reverts is a revision, the same unit rollback offers; the
definition above is given on an arbitrary set because operation-level revert is
available for the finer case. Order matters inside it, because a revision
routinely writes the same cell more than once — =retype_field= alone emits a
=delete_field= and an =append_field= per converted row, all on one cell.

A revert applies the inverse of each member of =S=, from the newest to the
oldest. Nothing more. The inverse of an operation is the one rollback already
computes ([[*Inverse operations]]), and undoing a set in the reverse of the
order it was written is what makes the composition land where a rollback would
have landed — with no reasoning about cells at all. A revision of four
operations is reverted by a revision of four operations, its mirror image.

Two things separate this from a rollback, and only two. The inverses are
*written*, through =log::Writer=, as new operations rather than applied to the
data tables directly, so they are logged and HEAD moves forward. And the
dependency check stands in for the ordering that a rollback gets for free: it
guarantees nothing outside =S= wrote those cells in the meantime, which is the
condition under which undoing =S= alone is meaningful.

The target must lie on HEAD's ancestry. An operation on a branch abandoned by a
past rollback is not part of the current history, so there is nothing there to
undo; the daemon rejects it with =400=.

** Undo

Rollback and revert are two mechanisms; /undo/ is the question a user actually
asks — "take back what I just did" — and it is answered by choosing between
them. The choice is not the user's to make: which one applies depends on what
has been written since, which is exactly what they are not watching.

*** Why stepping HEAD back is the wrong answer

The obvious undo — roll HEAD back one revision — is wrong as soon as the watcher
is running. Between the change a user wants back and the present sit the
watcher's own revisions: a file touched, a directory renamed, a file gone.
Rewinding HEAD over those *unrecords facts that are still true on disk*, and the
metadata comes out of step with the filesystem the daemon exists to track. The
watcher's revisions are not the user's to undo.

*** The selection

Undo looks down HEAD's ancestry for the newest revision *the user wrote*, and
undoes that one:

- if it is the revision HEAD sits in, and all of it still stands: a *rollback*,
  because HEAD can simply move back over it and the log keeps no trace of a
  mistake that was never seen;
- otherwise: a *revert*, which leaves everything written since exactly where it
  is.

A revision is *not* a candidate when:

- it is the daemon's (=origin = 'watcher'= — see [[*Revision origin]]; on a
  pre-migration database, when all its operations are watcher types);
- it is *itself* a revert (any of its operations carries =reverts_op_id=).
  Undoing an undo is a redo, and the next undo would put it back: this is the
  rule that makes undo repeatable instead of a two-state oscillation;
- every one of its operations has already been reverted;
- it holds only =unknown= operations, which carry no snapshots to invert;
- it is the root of the history — the first revision of a repository is the root
  metarecord the daemon writes at init, and after a [[*Log pruning]] the oldest
  revision left is a weak root whose predecessors are gone. Either way there is
  no state to go back to. (=mf log revert <id>= still reaches it.)

When a revision is only *partly* undone — some of its operations were reverted
individually — undo targets the operations that are left, not the revision.

The search walks HEAD's parent chain, so a redo future left by an earlier
rollback, and any divergent branch, are ignored: they are not applied, and
undoing them would mean nothing.

*** Where it lives

The selection is a *pure function of the log* and belongs to no front end: the
CLI and the GUI read =GET /log= and share =core::undo=. The daemon has no undo
endpoint — it offers the two mechanisms, and the client says which one it wants.
The log is read in two bounded passes (500 operations, then 20 000) rather than
one unbounded one: after a large reconcile an unbounded ancestry is millions of
rows, and a repository whose last manual change is older than the second window
is told so rather than scanned in full.

** Redo

Redo is the mirror of [[*Undo]]: where undo looks for the newest change the user
made and takes it back, redo looks for the newest *undo* and takes *that* back.
It has to survive the same thing undo does — the watcher writing in between —
which is why "move HEAD forward one revision" is no more sufficient than its
inverse was.

*** The selection

Three cases, in order:

1. *HEAD is not at a tip.* An earlier undo rolled it back and the operations it
   unapplied are still in the log, ahead of it. Moving HEAD forward onto them is
   the exact inverse of that rollback, and it is what redo has always meant.
2. *HEAD sits in a revert, and nothing has been written since.* Rolling back
   over it removes the undo as cleanly as it was made — no trace either way.
3. *The newest revision the user wrote is a revert, with the daemon's own
   revisions on top of it.* HEAD cannot be rewound over those, so the undo is
   undone in place: a revert of the revert. This is the case redo exists for.

Anything else is nothing to redo. In particular, when the newest revision the
user wrote is an ordinary change rather than an undo, redo does nothing: it
takes an undo back, it does not re-apply arbitrary history — that is what
=mf rollback= is for.

*** The two rules that keep it from oscillating

Undo and redo move in opposite directions over the same revisions, so each needs
a rule saying which ones are *not* theirs:

- *A revert of a revert is a redo, not an undo.* Redo steps over those (case 3
  looks for a revert of an /ordinary change/), or pressing it twice would undo
  again. A target outside the read window counts as an ordinary change: the
  conservative reading, which at worst offers a redo with nothing to take back.
- *Case 1 never moves forward onto an undo.* What lies ahead of HEAD after a
  redo-by-rollback (case 2) is precisely the revert that redo just stepped back
  over; re-applying it would undo, and redo and undo would trade the same
  revision back and forth forever.

There is a third, shared with undo: an operation counts as undone only while the
revert that undid it is *itself* still standing. A revert that has been reverted
undid nothing any more, and the change it had taken back stands again. Liveness
is therefore resolved along the whole revert chain, not read off a single
=reverts_op_id=. Without it the pair does not compose: after undo → redo, undo
would find its target "already undone" and refuse to take it back a second time.

* Daemon

** SQLite Schema

#+BEGIN_SRC sql
-- Grouping annotation for operations produced by a single API call.
CREATE TABLE revision (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp  INTEGER NOT NULL,   -- Unix ms
    label      TEXT               -- optional; see Label
);

-- Tree node: one row per atomic change.
CREATE TABLE operation (
    id                    INTEGER PRIMARY KEY AUTOINCREMENT,
    parent_id             INTEGER REFERENCES operation(id),  -- NULL for the root operation
    rev_id                INTEGER NOT NULL REFERENCES revision(id) ON DELETE CASCADE,
    seq                   INTEGER NOT NULL,    -- ordering within the revision (1-based, for display)
    op_type               TEXT    NOT NULL,    -- see Operation types
    entity_uuid           BLOB    NOT NULL,    -- UUID of the affected metadata metarecord
    entity_version_before INTEGER,             -- metadata.version before this op; restored on inverse
    entity_version_after  INTEGER,             -- metadata.version after this op; restored on redo
    field_name            TEXT,                -- for field operations; NULL otherwise
    reverts_op_id         INTEGER REFERENCES operation(id)  -- see Revert
);

-- Before/after snapshots for each operation, stored as normalized rows
-- mirroring the field table. is_new=0: state before the op; is_new=1: after.
-- field_id is the original field.id, restored exactly on inverse.
CREATE TABLE op_snapshot (
    op_id          INTEGER NOT NULL REFERENCES operation(id) ON DELETE CASCADE,
    is_new         INTEGER NOT NULL CHECK (is_new IN (0, 1)),
    field_id       INTEGER NOT NULL,   -- original field.id
    field_name     TEXT    NOT NULL,
    value_type     TEXT    NOT NULL,
    value_text     TEXT,
    value_int      INTEGER,
    value_real     REAL,
    value_uuid     BLOB,
    value_ref_repo BLOB,
    value_name     TEXT,
    PRIMARY KEY (op_id, is_new, field_id)
);

-- Singleton: current position in the history tree.
-- Inserted with op_id = NULL at repo init time.
CREATE TABLE log_head (
    singleton  INTEGER PRIMARY KEY CHECK (singleton = 1),
    op_id      INTEGER REFERENCES operation(id)
);

CREATE INDEX idx_operation_parent ON operation(parent_id);
CREATE INDEX idx_operation_rev    ON operation(rev_id, seq);
CREATE INDEX idx_operation_entity ON operation(entity_uuid, id);

-- Restoration ops awaiting commit (rollback `skip`). Execution is suspended
-- during rollback lock; they survive a daemon crash and are replayed on
-- restart. Watcher events are NOT held here: they are buffered in memory
-- (spec-file-tracking "Event batching"). The path/tracker columns below are
-- what a daemon that did persist them used, kept so an older database opens.
CREATE TABLE pending_operation (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    op_type        TEXT NOT NULL,  -- watcher event type or restoration op type
    entity_uuid    BLOB,           -- NULL for unresolved path-based watcher events
    path           TEXT,           -- for watcher events: affected path
    from_path      TEXT,           -- for file_moved watcher events
    to_path        TEXT,           -- for file_moved watcher events
    field_name     TEXT,           -- for restoration ops
    value_type     TEXT,           -- for restoration ops: new value to set
    value_text     TEXT,
    value_int      INTEGER,
    value_real     REAL,
    value_uuid     BLOB,
    value_ref_repo BLOB,
    value_name     TEXT
);
#+END_SRC

=reverts_op_id= is set on each operation a [[*Revert]] writes, naming the
operation it undid. Two readers use it: displays, and [[*Undo]] — which is why a
revert has to record it and not merely look like one. Nothing in the /write/
path branches on it, and it is allowed to dangle: [[*Log pruning]] and a retention trim (see
[[*Automatic retention]]) may remove the operation it points at, and neither
goes back to clear the column. A database written before the column existed is
migrated by adding it (=ALTER TABLE operation ADD COLUMN=), which leaves every
existing operation with =NULL=: no revert has happened yet.

*** Snapshot rows (=op_snapshot=)

Each operation stores its before/after state as rows in =op_snapshot=,
mirroring the =field= table columns. =is_new=0= = state before the op;
=is_new=1= = state after. =field_id= is the original =field.id= and is
restored exactly on inverse (see [[*Field ID and version stability]]).

Per operation type:

| =op_type=       | =is_new=0= rows (before)                             | =is_new=1= rows (after)                          |
|-----------------+------------------------------------------------------+--------------------------------------------------|
| =create_metarecord=  | none                                                 | all field rows of the created metarecord              |
| =delete_metarecord=  | all field rows of the deleted metarecord                  | none                                             |
| =set_field=     | all previous rows for =(uuid, field_name)=           | the new single row                               |
| =append_field=  | none                                                 | the appended row                                 |
| =delete_field=  | the deleted row                                      | none                                             |
| =file_deleted=  | the =mfr_path= row(s) before deletion                | one row: =value_type=nothing=                    |
| =file_moved=    | the previous =mfr_path= row(s)                       | the new =mfr_path= row(s)                        |
| =file_modified= | =mfr_size=, =mfr_mtime=, hash rows before            | new =mfr_size=, =mfr_mtime= rows                 |

For =file_deleted= on a directory: each descendant metarecord receives its own
=file_deleted= operation within the same revision. Operations and their
snapshot rows are inserted in bulk for large cascades.

*** Field ID and version stability

=field.id= is =AUTOINCREMENT=. Snapshot rows in =op_snapshot= preserve the
original =field_id=. On inverse, the daemon restores rows with their original
primary key: =INSERT INTO field (id, …) VALUES (?, …)=. This ensures that
operations on other branches that reference the same =field_id= remain valid
after navigating across that operation's boundary.

The =metadata.version= counter is likewise saved and restored via the
=entity_version_before= / =entity_version_after= columns on =operation=: the
inverse sets =metadata.version= back to =entity_version_before=, the forward
action to =entity_version_after= — both exactly. (The after value must be
recorded because versions are assigned from the =next_version= allocator,
not computed as before + 1 — see [[file:spec-data-model.org][spec-data-model.org]].) This ensures that
=version= remains a reliable cache key across rollback/redo cycles.

=next_version= itself is deliberately *not* restored by navigation — its
monotonicity across branches is what guarantees that version numbers are
never reused for different states. When navigation recreates a metarecord
whose row (and thus =next_version=) had been deleted, =next_version= is
recomputed as 1 + the maximum version recorded for that entity across the
whole =operation= table.

** Normal write flow

Every API call that modifies metadata:

1. Opens a SQLite transaction.
2. Inserts one =revision= row with the optional =label= from the request.
3. For each change (first to last):
   a. Records the before state: reads the affected =field= rows and the current
      =metadata.version=, to be written as =op_snapshot= rows (=is_new=0=).
   b. Applies the change to the data tables (=metadata.version= is assigned
      from =next_version=, which is incremented).
   c. Records the after state: reads the resulting =field= rows, written as
      =op_snapshot= rows (=is_new=1=).
   d. Inserts one =operation= row with:
      - =parent_id= = current =log_head.op_id= (the running HEAD within this transaction)
      - =rev_id= = the revision created in step 2
      - =seq= = incrementing from 1
      - =entity_version_before= = the version recorded in step 3a
      - =entity_version_after= = the version assigned in step 3b
   e. Inserts the =op_snapshot= rows for this operation.
   f. Updates the running HEAD to this new operation's =id=.
4. Writes the final =log_head.op_id= to the singleton row.
5. Commits the transaction.

For batch operations, all =operation= rows are inserted together in a single
=INSERT= after computing all =parent_id= values.

All write operations — including =reconcile= — follow this flow and produce
log metarecords. If performance ever becomes a concern for large bulk operations,
an optional =no_log= flag may be added to the relevant API endpoints. When
used, a single =unknown= operation is inserted at HEAD instead of individual
change metarecords. It has no =op_snapshot= rows, acts as a weak root (navigation before
it is impossible, like after Prune-before), and the =unknown= flag is noted
in the response.

** Navigation

Navigation moves HEAD from its current position to any target operation in the
tree. The target may be an ancestor (rollback), a descendant (redo), or any
node on a different branch.

*** Algorithm

Given =current= (=log_head.op_id=) and =target=:

1. Find the Lowest Common Ancestor (LCA) of =current= and =target=.
2. Collect the /unapply path/: operations from =current= to LCA (LCA
   excluded), ordered most-recent-first.
3. Collect the /apply path/: operations from LCA to =target= (LCA excluded),
   ordered oldest-first.
4. Execute in a single SQLite transaction:
   a. For each operation on the unapply path: execute its inverse (see below).
   b. For each operation on the apply path: execute its forward action.
   c. Update =log_head.op_id= to =target=.

The entire navigation is atomic. A crash leaves HEAD and data tables in their
pre-navigation state.

If =target= is =NULL= (empty state), all =metadata= and =field= rows are
deleted and =log_head.op_id= is set to =NULL=.

*** Inverse operations

| =op_type=        | Inverse action                                                                                    |
|------------------+---------------------------------------------------------------------------------------------------|
| =create_metarecord=   | Delete the metarecord and all its =field= rows                                                      |
| =delete_metarecord=   | Recreate =metadata= (with =entity_version_before=) and =field= rows from snapshots                 |
| =set_field=      | Delete current rows for =(uuid, field_name)=; insert =is_new=0= snapshot rows with original ids  |
| =append_field=   | Delete the field row whose =id= matches the =is_new=1= snapshot =field_id=                        |
| =delete_field=   | Insert the =is_new=0= snapshot row with its original =field_id=                                   |
| =file_deleted=   | Delete the current =mfr_path= Nothing row; insert =is_new=0= snapshot rows with original ids     |
| =file_moved=     | Delete current =mfr_path= row(s); insert =is_new=0= snapshot rows with original ids              |
| =file_modified=  | Delete current =mfr_size=, =mfr_mtime=, hash rows; insert =is_new=0= snapshot rows               |
| =unknown=        | Not possible — navigation before an =unknown= op is rejected with =400=                          |

*** Filesystem coordination

The daemon applies metadata changes as instructed and does not assess whether
an operation is reversible in the current context. That responsibility belongs
to the CLI, which has access to the filesystem state, user permissions, and
interactive input.

Three op types require attention at rollback time:

- =file_moved=: the CLI checks whether the file still exists at its current
  location before executing the =mv=. If the file is gone or inaccessible,
  the CLI calls =step= with =skip: true=. If the destination path is
  occupied, the =mv= would overwrite it — the CLI first moves that file to
  the trash-bin (file content is never destroyed by rollback, as by sync; see
  [[file:spec-trash.org][spec-trash.org]] for the layout, the manifest, and
  =mf trash restore=/=prune=).
- =file_deleted=, =file_modified=: the content is gone *unless the change
  passed through the trash-bin*. On an inverse (rollback) step, the CLI looks
  for a trash entry matching this metarecord and the version the record held
  *before the revision being undone* (=entity_version_before_revision=, exposed
  on the op — see below); if found, it moves the file back and calls =step {}=
  (the real inverse restores =mfr_path= and the version), *auto-restoring* the
  exact deleted content. Otherwise the content is truly gone: the CLI calls
  =step {"skip": true}= (metadata rewinds) and, if some other content for the
  record is trashed, prints a =mf trash restore= hint. See
  [[file:spec-trash.org][spec-trash.org]] "rollback auto-restore".
  For this correlation the daemon exposes, on each *inverse* step's op JSON
  (omitted on forward/redo steps, so auto-restore never fires while re-applying
  a deletion), both =entity_version_before= — the version *this* step restores
  to — and =entity_version_before_revision= — the lowest of them across the
  revision's operations on that record, i.e. the version anything outside the
  revision (a trash entry) observed. One event may write several fields of one
  record, so only the latter is a stable correlation key: every operation of the
  revision carries the same value and therefore reaches the same decision.

When =skip: true= is used, the daemon *still applies the step's metadata change*
(the inverse on a rollback step, the forward action on a redo step — maintaining
the HEAD↔data invariant). It additionally enqueues a /restoration operation/ in
the watcher buffer — a synthetic write that is replayed as a new branch after
navigation completes, correcting the metadata to match the actual filesystem
state:

- =file_moved= skip: restoration *rewinds* =mfr_path= to the location the file
  is recorded at *before this step* — the snapshot the step did not just apply.
  On a rollback (inverse) step that is the =is_new=1= snapshot (post-move); on a
  redo (forward) step it is the =is_new=0= snapshot (pre-move). No filesystem
  check is needed. Skip is meant for a file that is still present but could not
  be moved, so the rewind keeps the metadata truthful; when the file is *gone*,
  the CLI uses =step {}= instead (see [[*Policies for =move_file=]]).
- =file_deleted= skip: restoration sets =mfr_path= to =Nothing= (re-metarecords
  the deletion since the file is still absent).
- =file_modified= skip: restoration clears =mfr_partial_hash= and
  =mfr_full_hash= (→ =Nothing=); size and mtime are left stale until the
  next reconcile.

For the v1 atomic rollback (=POST /rollback=), the daemon always applies all
metadata changes. The CLI should inspect the plan first (=GET /rollback/plan=)
and use the coordinated navigation protocol if selective per-operation
handling is needed.

** Writing a revert

A revert takes a set of operations (a revision's, or an explicit list), checks it
is revertable, computes the state its members replaced, and writes that state as
one new revision at HEAD. It is a normal write: same =log::Writer=, same
transaction, same retention trim, same tree-cache and watch-set follow-up.

*** Revert content

The inverse of each operation is the one [[*Inverse operations]] already defines
for a rollback. The difference is that a revert *writes* it instead of applying
it: each inverse goes through the =log::Writer= method that expresses it, so it
is logged, and the rows it inserts take fresh ids and versions
([[*Field ids and versions]]).

| Reverted =op_type=           | Written as                                                               |
|------------------------------+--------------------------------------------------------------------------|
| =create_metarecord=          | =delete_metarecord=                                                      |
| =delete_metarecord=          | =create_metarecord=, same UUID                                           |
| =set_metarecord=             | =set_metarecord=                                                         |
| =set_field=                  | =set_field= with the before rows, or a cleared cell when there were none |
| =file_deleted=, =file_moved= | =file_moved=                                                             |
| =file_modified=              | =file_modified=                                                          |
| =append_field=               | =delete_field=                                                           |
| =delete_field=               | =append_field=                                                           |
| =unknown=                    | not revertable — no snapshots to invert                                  |

*The fresh ids have one consequence to handle.* A rollback's inverse restores
=field.id= exactly, and that is what lets it compose inverses blindly: when a
set holds an =append_field= and a later =delete_field= of the same row, undoing
the delete puts the row back under its original id, so undoing the append then
finds it there. A revert's inserts get new ids, so it has to carry a map from
the reverted operations' =field_id= to the id its own write produced, and
resolve each row-scoped inverse through it. Only =append_field= and
=delete_field= are concerned: every other type names a cell or an entity, never
a row.

Two consequences worth stating outright:

- *A revert writes the type of the change it actually makes, filesystem
  included.* =op_type= is not a note on who asked for the write: it is what
  tells a later navigation that crossing this operation requires a file action
  (=file_moved= is what the daemon turns into a =move_file= step, and
  =file_deleted= / =file_modified= are what make the CLI look in the trash-bin).
  A revert that performed the =mv= must therefore record =file_moved=, or a
  rollback across it would rewrite =mfr_path= while leaving the file where the
  revert put it. There is no third case: an operation whose file action could
  not be carried out is not part of the revert at all.

  =file_moved= carries this in both directions — it is already the type
  =reconcile= writes when it relinks an orphan, whose =mfr_path= was =Nothing=
  before the content reappeared — so reverting a =file_deleted= that the
  trash-bin could satisfy is a =file_moved= like any other homecoming.
- *Restoring an empty cell is not the same as writing =Nothing=.* When the
  reverted operation's before-snapshot has no rows, the field did not exist
  before it and the revert removes the cell entirely — a =set_field= operation
  with no rows after — rather than setting the explicit-absence sentinel. The
  distinction is the data model's (spec-data-model "Nothing"), and a revert must
  not blur it.

A revert of a whole revision writes one operation per reverted operation, in
the reverse of their original order, so the two revisions read as mirror images
in =mf log --ops=. Reverse order is required — it is what makes the composition
correct — but it costs nothing elsewhere: forest integrity is checked once at
commit rather than per operation, so a revert restoring a whole subtree's
=mfr_path= passes as long as the state it leaves is consistent.

An operation removed from the log — by [[*Log pruning]] or by a retention trim
(see [[*Automatic retention]]) — cannot be reverted: it took its snapshots with
it, and the state it replaced is no longer recorded anywhere. The daemon answers
=404=, naming retention as the likely reason so the message does not read as a
bug.

*** The dependency query

Given the set's operation ids and HEAD, the blockers are the operations on
HEAD's ancestry, younger than the oldest member of the set, that write one of
the set's cells and are not themselves in the set. Entity-scoped operations
(=field_name IS NULL=) intersect every cell of their entity, on both sides of
the comparison.

The ancestry is walked as it is everywhere else in this module (=ancestry=), and
the cell test is an indexed lookup per entity on =idx_operation_entity
(entity_uuid, id)=, so the cost is proportional to the number of operations
recorded for the entities the set touches, not to the size of the log.

The same query computes the closure when the dependents are wanted: re-run it
with the blockers added to the set, until a run adds nothing. Each round is
another indexed lookup over the same entities, and the set only grows, so the
number of rounds is bounded by the operations in the window.

The check runs in =GET /revert/plan=, so a client can show what is possible
before asking for it, and again inside the transaction that writes the revert,
so what is written was checked against the state it is written into. The second
run is what makes the rule a daemon guarantee rather than a client convention;
in the coordinated form it cannot fail once =start= has succeeded, because the
lock holds HEAD still (see below).

*** What a revert inherits from an ordinary write

Being an ordinary write settles three questions that a new route would otherwise
decide by accident.

- *The cache and the watch set follow, and the =Writer= notices on its own.*
  Reverting an =mf_watch= write is an =mf_watch= write: =observe_effects=
  accumulates it into =WriteEffects= like any other, with no revert-specific
  logic. What is not automatic is applying those effects — =settle= lives on
  =RepoState= because it needs the tree cache and the watcher handles, which the
  =Writer= does not have, and it has to run after the transaction commits. So
  the revert routes end the way the twelve other write routes do: read
  =effects()= off the writer *before* =commit= consumes it, then call
  =repo_state.settle(&conn, &effects)=. Nothing warns when that is left out; the
  cache simply drifts.

- *Reserved names stay writable.* =mfr_*= fields need =force= from a client, but
  that check lives in the routes, not in the =Writer=. A revert restores values
  the daemon itself recorded, =mfr_path= among them, so the revert routes do not
  apply it. Adding it "for consistency" would refuse every revert of a =file_*=
  operation.

- *Type validation moves to the revert's commit.* =Writer::validate_value_type=
  runs on every ordinary write, but the reverse walk reaches the pre-revision
  state through intermediate ones that need not be type-consistent even when the
  one it lands on is. Undoing a =retype_field= is the case: once the last
  converted row's =append_field= is undone, the cell still holds the others in
  the *new* type, and restoring the old one reads as a conflict. So a revert
  calls =Writer::defer_type_checks=, and the rule is enforced once at commit
  over the state the revision actually produces — every field name it wrote must
  carry a single value type repository-wide.

  Deferring is not skipping. A =retype= the revert is *not* undoing can have
  established another type for the name without ever writing the reverted cell:
  no dependency blocks that, and restoring the old value would leave two types
  under one name. That is refused with a =400= at commit, and remains the third
  reason a revert can be refused, next to a blocking dependency and an
  impossible filesystem action.

  A rollback needs none of this. Navigation does not go through a =Writer= at
  all — =apply_inverse= writes rows directly — so it never validates, on the
  grounds that it restores a state the log already recorded as valid. A revert
  cannot borrow that reasoning, because it produces a state the repository has
  never held; so it checks the result instead of trusting the source.

*** Filesystem actions

Three reverted operation types describe something that happened to a file, and
undoing them has to happen to the file too:

| Reverted operation | Filesystem action                                                           |
|--------------------+-----------------------------------------------------------------------------|
| =file_moved=       | =mv= the file back, from where it is recorded now to the restored location   |
| =file_deleted=     | restore the content from the trash-bin, if the deletion passed through it    |
| =file_modified=    | restore the content from the trash-bin, if the change passed through it      |

As for rollback, the daemon neither touches the filesystem nor judges whether
the action is possible: the client does, and then tells the daemon what it
managed to do. The protocol is =POST /revert/start= → filesystem actions →
=POST /revert/commit=, holding the [[*Rollback lock]] in between.

The lock is not a formality here. While it is held the watcher keeps observing
but its events are not executed, so the =mv= the client has just performed
cannot be ingested as a genuine rename before the metadata explaining it is
written. Without it, the watcher would resolve the moved file's old path to
nothing, treat the arrival as a new file, and leave a duplicate metarecord at
the destination — the same race a trash restore once lost a file to (see
[[file:spec-trash.org][spec-trash.org]]). It also freezes HEAD, which is what
lets the dependency check taken at =start= still hold at =commit=.

One shape deserves naming, because a revert makes it more common than it is
today. Reverting a =file_deleted= that the trash-bin could satisfy writes a
=file_moved= whose =is_new=0= snapshot is =Nothing=: the file came back from
nowhere. Navigating *back* across that operation would have to make the file go
away again, which a =move_file= action cannot express — it has no destination.
The daemon already answers this by omitting =from= and =to= whenever a
=file_moved= snapshot is not a =TreeRef=; the CLI reads the missing =from= as
"the file is unavailable" and resolves it by policy, leaving the metadata
rewound and the file in place until a reconcile. This is a pre-existing shape —
=reconcile= writes exactly this operation when it relinks an orphan — and the
revert neither improves nor worsens it.

A revert whose plan contains no filesystem action needs none of this: the
single-shot =POST /revert= writes it in one transaction, no lock, no
round-trip. That is the common case — most of a log's revertable mistakes are
metadata.

*** Skipping is free

When the client cannot carry out an operation's filesystem action, it leaves
that operation out of the commit and the daemon does not revert it. Nothing
else is needed.

This is where the revert model is simpler than navigation, and it is worth
being explicit about why. Rollback must apply a skipped operation's metadata
change anyway — HEAD has to reach the target, and the HEAD↔data invariant
forbids passing an operation without applying it — which leaves the metadata
describing a filesystem that does not match, to be corrected afterwards by a
synthetic /restoration operation/ replayed on a new branch. A revert moves HEAD
forward by exactly what it wrote, so "do not undo this one" is directly
expressible, and what lands in the database is true at the moment it is written.
There is no restoration operation in a revert, and no correcting branch.

*** Field ids and versions

A revert is a new write and behaves like one: the rows it inserts take fresh
=field.id= values from the =AUTOINCREMENT= sequence, and the entities it touches
take fresh versions from =next_version=. It does *not* restore the ids and
versions the reverted operation held.

That is deliberate, and the contrast with [[*Field ID and version stability]] is
the point. Navigation recreates a state the log already described, so it can and
must restore its identifiers exactly. A revert produces a state the repository
has never been in — the reverted change is gone, everything after it is still
there — so a new version is the truthful answer, and every cache keyed on
=version= correctly sees a change.

** Log pruning

Two pruning operations are available. Both require the target to be an
ancestor of HEAD (or HEAD itself). Targets are specified as ={"id": N}=,
={"label": L}=, or ={"timestamp": T}=, with the same resolution rules as
rollback targets.

After deleting the operations, both prune commands compact the database file
(=VACUUM= followed by a WAL checkpoint), returning the reclaimed space to the
filesystem — snapshot rows are the dominant share of the database size, so
pruning is the retention mechanism for disk usage.

*** Prune-before(X)

Makes operation X the new root (=X.parent_id= set to =NULL=). Deletes all
operations strictly older than X, plus any branch whose entire ancestry lies
before X.

*Limitation*: after pruning, X is a /weak root/ — its predecessors are gone,
so the database state at X cannot be reconstructed from the log alone. This
does not affect navigation within the remaining tree (operations X→HEAD are
intact), but a fresh replay from scratch is no longer possible. For disaster
recovery, use a filesystem-level backup of =db.sqlite= rather than relying on
log replay.

*** Linearize(X)

X must be an ancestor of HEAD. Deletes all branch operations that diverge from
the HEAD path between the root and X. After this, the segment root→X is a
straight line.

** Automatic retention

Pruning above is a command the user runs. Retention is the same idea as a
standing policy: a repository under an active watcher writes a revision per
batch of filesystem events and accumulates them for ever, and most of that
history is of no interest — one would rarely walk back a thousand revisions,
but one might well want to walk back a few large ones.

Two settings, resolved per repository (its own =config.json= where set, the
daemon's =[settings]= otherwise):

- =log-retention-revisions= — how many revisions to keep behind HEAD. Default
  200; =0= keeps everything. The unit matters: a revision is an *event* — a
  batch of filesystem changes, one command — not an operation, and one event
  routinely carries thousands of operations. 200 events is therefore far more
  history than anyone walks back through, while bounding what a default
  installation accumulates.
- =log-retention-keep-labels= — when true, a labelled revision is a floor:
  nothing older than the oldest label is dropped, and the log grows past the
  limit rather than losing a named checkpoint. Default true, because the limit
  is on by default: the history a user deliberately named is the one kind the
  limit must not be allowed to take, and =mf log mark-checkpoint= is how one
  says "keep everything from here".

A limit that is on by default means an existing repository is trimmed on its
first write after the upgrade, permanently and without asking. That is the
intent — an unbounded log is what the default is protecting against — but it is
a one-way door: a repository whose whole history matters wants
=log-retention-revisions = 0=, or a label at the point worth keeping, *before*
the daemon writes again.

*** What a trim does

A trim is a [[*Prune-before(X)]] with =X= chosen by the limit — the first
operation of the oldest revision to keep — so the same rules and the same
/weak root/ limitation apply, permanently: with retention on, the database at
the surviving root cannot be reconstructed from the log alone. Disaster
recovery is a filesystem-level backup, not a replay.

It runs *inside the transaction of the write that triggered it*, after HEAD is
updated. That is what makes it affordable: the deletion is a range delete over
the oldest operations (their snapshots follow by foreign-key cascade), which
costs less than the append that triggered it, and it rides a commit that was
going to be paid for anyway rather than adding an =fsync= of its own.

Two things it deliberately does not do:

- *No =VACUUM=.* In a steady state the pages a trim frees are the pages the next
  appends write into, so the database settles on a plateau. Returning them to
  the filesystem at every trim would rewrite the whole file — the =field= table
  included — to reach the same steady state. =mf log prune=
  keeps its compaction for when the space is actually wanted back.
- *No trim per write.* The log is allowed to drift one tenth of the limit past
  it (at least one revision) before a trim runs. Hysteresis, not sloppiness:
  trimming one revision per write dirties the oldest, coldest pages of the log
  at every single commit, where one trim per slack revisions does the same work
  spread over the transactions that were going to write anyway.

*** When a trim declines

The cutoff must be an ancestor of HEAD, exactly as for an explicit prune. After
a rollback it may not be: the newest revisions by id sit on the branch the
rollback abandoned, and cutting there would delete the history HEAD stands on.
The trim then does nothing and the log grows past the limit — deliberately, and
temporarily: as the current line of history becomes the newest again, the cutoff
lands on it and the trim resumes, collecting the abandoned branch with
everything else below the cut (a branch rooted before the cutoff loses its
ancestry, so it goes with it rather than becoming unreachable).

A trim only happens on a write, and every write of a loaded repository carries
the repository's retention — the exception is the root metarecord written when a
repository is created, which has no history to trim. A repository that is not
being written to keeps whatever it has.

** Coordinated navigation
Coordinated navigation handles =file_moved= operations by coupling each
metadata change with a CLI-executed =mv= command. It proceeds one operation at
a time, so a crash leaves at most one file and one metadata metarecord in an
inconsistent state.

The target may be any operation in the tree: an ancestor (rollback), a
descendant (redo), or a node on a different branch. The daemon computes the
correct =from=/=to= paths for each =move_file= step based on the navigation
direction (unapply vs. apply).

*** Rollback lock

=POST /rollback/start= — and =POST /revert/start=, which needs the same
protection for the same reason ([[*Filesystem actions]]) — enters /rollback
lock/ mode:

- The file watcher *continues to run normally*, buffering events as usual.
- *Execution of pending operations is suspended* — buffered events accumulate in
  memory and restoration ops from =skip= accumulate in =pending_operation=, but
  neither is committed to the data tables.
- All metadata write endpoints return =423 Locked= until the lock is released.
- Read-only endpoints continue to work normally.

The lock is released by the final =POST /rollback/step= (when HEAD reaches the
target), by =POST /revert/commit=, or by either =abort=. On release, pending operations are
processed and committed as a new revision on the current HEAD branch (applying
the same compaction and batching rules as the normal watcher flush; see
[[spec-file-tracking.org]]).

The lock is *not* stored in the database. If the daemon crashes, it restarts
unlocked. Pending operations accumulated in =pending_operation= are preserved
and replayed automatically on restart before the daemon accepts new requests.

*** Crash recovery

If the daemon crashes during a coordinated navigation:

- HEAD reflects the last committed =step= (SQLite ACID).
- The rollback lock is not restored on restart.
- Restoration ops from =skip= are held in =pending_operation= and replayed
  automatically on restart as a new revision. Buffered *watcher events* are not:
  they live in memory and a stopped daemon loses them, along with everything
  else that happened while it was down — =reconcile= is what recovers that
  (spec-file-tracking "Event batching").
- Any file moves executed before the crash but after the last committed step
  leave =mfr_path= stale until the replayed restoration ops correct them.
  Running =reconcile= is still recommended to catch any remaining filesystem
  drift.
- To resume the navigation: call =POST /rollback/start= again with the same
  target — it recomputes the plan from the current HEAD. File moves already
  completed are idempotent (the =mv= may fail harmlessly or be skipped by the
  CLI after checking).

*** =GET /repos/:repo_uuid/log=

Returns the history as a flat list of operations and revisions, with HEAD
marked. The client reconstructs the tree from =parent_id=.

Query parameters:

| Parameter            | Default    | Description                                                                          |
|----------------------+------------+--------------------------------------------------------------------------------------|
| =mode=               | =linear=   | =linear=: HEAD ancestry only (root → HEAD); =active=: the line through HEAD (ancestry + forward to the most-recent leaf); =tree=: all branches |
| =metarecord_uuid=         | —          | Only operations whose =entity_uuid= matches this metarecord UUID                          |
| =limit=              | —          | Maximum number of operations to return (applied after filtering; most recent first)  |
| =since=              | —          | Include only operations in revisions with timestamp ≥ T (Unix ms)                    |
| =until=              | —          | Include only operations in revisions with timestamp ≤ T (Unix ms)                    |
| =include_snapshots=  | =false=    | If =true=, each operation includes =snapshots_before= and =snapshots_after= arrays   |

In =linear= mode, operations are ordered from root to HEAD (oldest first). In
=active= mode, operations are ordered root → HEAD → leaf (oldest first): the
HEAD ancestry plus the forward continuation that, at each fork below HEAD,
follows the child whose subtree holds the most recently created operation. This
keeps a rolled-back "future" visible for redo while hiding operations on
divergent branches. In =tree= mode, operations are returned in insertion order
(by =id=). The client reconstructs tree structure from =parent_id= in all cases.

For =linear= and =active= modes, =limit= is not merely a post-filter: it bounds
the walk itself, so listing the most recent =N= operations stays O(N) on a
repository with millions of operations (a large initial reconcile) instead of
loading the whole history. =linear= walks HEAD's ancestry capped at =limit=;
=active= does the same whenever HEAD has no forward continuation (the common
case, checked with an indexed lookup) and otherwise falls back to the full
computation so a rolled-back redo future is still surfaced. The observable
result is unchanged — the most recent =limit= operations of the selected line.
GUI clients use this to page the log list ("Show more" grows the window).

     "reverts_op_id": null}

    {"id": 1, "timestamp": 1700000000000, "label": null, "origin": null},

  "total_revisions": 2

repository, not the returned window: they are unaffected by =mode=, =limit=,
=metarecord_uuid= and the time filters. A client showing a bounded window (the
GUI log panel fetches only the most recent =limit= operations) reports how much
log there is from them.

*** =POST /repos/:repo_uuid/rollback=

Metadata-only rollback: navigates HEAD to the target in a single atomic SQLite
transaction. For =file_moved= operations in the path, only the metadata change
is applied — the file is not moved. Use the coordinated navigation protocol
if filesystem coordination is needed.

Request body:
#+BEGIN_SRC json
{"target": {"id": 2} | {"timestamp": T} | {"label": "before-cleanup"} | {"prev_revision": true}}
#+END_SRC

- ={"id": N}=: navigate to operation N.
- ={"timestamp": T}=: navigate to the most recent operation on the HEAD
  ancestry path whose revision timestamp is ≤ T.
- ={"label": L}=: navigate to the last operation of the most recent revision
  carrying label L on the HEAD ancestry path.
- ={"prev_revision": true}=: navigate to the parent of the first operation in
  HEAD's current revision (i.e. undo the entire last revision). If HEAD's
  revision has only one operation, this is equivalent to ={"id":
  parent_id_of_HEAD}=. If HEAD has no parent (tree root), navigates to the
  empty state.

Response body:
#+BEGIN_SRC json
{
  "previous_head": 4,
  "new_head": 2,
  "operations_unapplied": 2,
  "operations_applied": 0
}
#+END_SRC

*** =POST /repos/:repo_uuid/log/prune=

Request body:
#+BEGIN_SRC json
{"mode": "before" | "linearize",
 "target": {"id": N} | {"timestamp": T} | {"label": "…"}}
#+END_SRC

Response body: ={"pruned_operations": 47, "pruned_revisions": 12}=

*** =GET /repos/:repo_uuid/rollback/plan=
Returns the full ordered list of operations that would be processed to reach
the target, without entering lock mode. Operations are listed in execution
order (unapply path first, then apply path).

Query parameters: =target_id=, =target_label=, =target_timestamp=,
=target_prev_revision= (same semantics as =POST /rollback/start=).

Example response:
#+BEGIN_SRC json
{
  "operations": [
    {"id": 101, "op_type": "move_file", "entity_uuid": "...",
     "from": "/repo/B.mp3", "to": "/repo/A.mp3"},
    {"id": 102, "op_type": "set_field", "entity_uuid": "..."},
    {"id": 103, "op_type": "create_metarecord", "entity_uuid": "..."}
  ],
  "total": 3
}
#+END_SRC

*** =GET /repos/:repo_uuid/rollback/plan/summary=
Returns statistics for the navigation without entering lock mode.

Query parameters: same as =GET /rollback/plan=.

Example response:
#+BEGIN_SRC json
{
  "total_operations": 157,
  "by_type": {
    "file_moved": 45,
    "file_deleted": 3,
    "create_metarecord": 89,
    "set_field": 20
  },
  "revisions_affected": 12
}
#+END_SRC

*** =POST /repos/:repo_uuid/rollback/start=
Enters rollback lock, suspends pending operation execution, stores the target
internally, and returns the first operation to process.

If target == current HEAD there is nothing to do: the lock is not entered and
the response is ={"op": null, "remaining": 0}= immediately.

Request body:
#+BEGIN_SRC json
{"target": {"id": 42} | {"label": "before-cleanup"} | {"timestamp": T} | {"prev_revision": true}}
#+END_SRC

Response body:
#+BEGIN_SRC json
{
  "op": {
    "id": 101,
    "op_type": "move_file",
    "entity_uuid": "...",
    "from": "/repo/music/B.mp3",
    "to": "/repo/music/A.mp3"
  },
  "remaining": 156
}
#+END_SRC

The daemon computes the inverse of each operation and returns what the CLI
must execute. For =move_file=, =from= and =to= are the paths to pass to =mv=
(already computed — the CLI executes them as-is). For all other operation
types, =from= and =to= are absent — no filesystem action is required.

Note: =op_type= in the coordinated navigation response reflects the *action to
execute*, not the stored event. A =file_moved= metarecord in the DB produces a
=move_file= response op; all other DB op types appear unchanged.

The daemon does not check the filesystem state. The CLI inspects it and
decides whether to proceed with the =mv= or call =step= with =skip: true=.

*** =POST /repos/:repo_uuid/rollback/step=
Applies the inverse of the current operation atomically (SQLite transaction),
advances HEAD, and returns the next operation to process. The daemon always
knows the current position (=log_head.op_id=) and the target (stored at lock
time) — no =op_id= is needed from the client.

Request body (normal — apply inverse):
#+BEGIN_SRC json
{}
#+END_SRC

Request body (skip — apply metadata inverse + enqueue restoration op):
#+BEGIN_SRC json
{"skip": true}
#+END_SRC

Response body (more operations remain):
#+BEGIN_SRC json
{
  "op": {
    "id": 102,
    "op_type": "set_field",
    "entity_uuid": "..."
  },
  "remaining": 154
}
#+END_SRC

Response body (navigation complete — =op= is =null=):
#+BEGIN_SRC json
{"op": null, "remaining": 0}
#+END_SRC

When =op= is =null=, HEAD has reached the target. The lock is automatically
released and the watcher buffer is replayed.

*** =POST /repos/:repo_uuid/rollback/abort=
Releases the lock and replays the watcher buffer. HEAD remains at its current
position — operations already applied by previous =step= calls are not undone.

The caller is responsible for reversing any =mv= commands already executed
(or running =reconcile= to re-sync the filesystem state).

Response body: ={"head": <current_op_id>}=

*** Revert target

Every revert endpoint takes the same =target= object, naming the set of
operations to undo:

| Form                     | Set                                                     |
|--------------------------+---------------------------------------------------------|
| ={"rev_id": N}=          | every operation of revision =N=                         |
| ={"rev_id": "head"}=     | every operation of the revision containing HEAD         |
| ={"op_ids": [22, 23]}=   | exactly these operations                                |

All members must lie on HEAD's ancestry, or the daemon answers =400=.

Every endpoint also takes =with_dependents= (default =false=). When true, the
set actually reverted is the dependency closure of the target — the operations
asked for plus everything that blocks them (see [[*Reverting the dependents
too]]) — and a blocked target stops being an error.

*** =GET /repos/:repo_uuid/revert/plan=

Describes what a revert would do, without writing anything and without taking
the lock. Query parameters =target_rev_id= or =target_op_ids= (comma-separated)
and =with_dependents=, with the semantics above.

#+BEGIN_SRC json
{
  "revertable": false,
  "requires_lock": true,
  "operations": [
    {"id": 22, "op_type": "set_field", "entity_uuid": "…", "field_name": "rating",
     "writes": "set_field",
     "restores": [{"field_name": "rating", "value_type": "int", "value_int": 3}],
     "filesystem": null,
     "blocked_by": null},
    {"id": 23, "op_type": "file_moved", "entity_uuid": "…", "field_name": "mfr_path",
     "writes": "file_moved",
     "restores": [{"field_name": "mfr_path", "value_type": "tree_ref",
                   "value_uuid": "<parent_uuid>", "value_name": "old.mp3"}],
     "filesystem": {"action": "move",
                    "from": "/repo/music/new.mp3", "to": "/repo/music/old.mp3"},
     "blocked_by": {"op_id": 91, "rev_id": 40, "timestamp": 1700000900000,
                    "op_type": "file_moved", "field_name": "mfr_path",
                    "entity_uuid": "…"}}
  ],
  "blocked": [{"op_id": 91, "rev_id": 40, "…": "…"}],
  "dependents": [{"op_id": 91, "rev_id": 40, "…": "…"}]
}
#+END_SRC

- =writes= is the operation type the revert would record (see
  [[*Revert content]]), which is a =file_*= type exactly when =filesystem= is
  not =null=.
- =restores= is the state the revert would write, in the =op_snapshot= row
  shape used by =GET /log/revisions/:rev_id=. An empty array means the cell
  would be removed.
- =filesystem= is =null= when no file action is needed, and otherwise one of
  ={"action": "move", "from": …, "to": …}= — the paths to pass to =mv=, already
  computed, as in =POST /rollback/start= — or ={"action": "restore_content"}=,
  meaning the content has to come back from the trash-bin. The daemon does not
  look: whether it is there is the client's question to answer.
  =requires_lock= is true when any operation has an action, and is the client's
  signal to use the coordinated form.
- =blocked_by= names the operation standing in the way, or =null=. =blocked= is
  the deduplicated union of them, which is what a client shows the user.
  =revertable= is true exactly when =blocked= is empty.
- =dependents= is the dependency closure minus the operations asked for: what
  =with_dependents= would add. It is reported whether or not =with_dependents=
  was passed, so a client can offer "revert these N as well" without a second
  round-trip, and it is empty exactly when =blocked= is. With
  =with_dependents=true=, =operations= is the whole closure — each entry
  carrying =origin: "requested"= or =origin: "dependent"= — =blocked= is empty
  and =revertable= is true.

*** =POST /repos/:repo_uuid/revert=

The single-shot form: checks, writes and commits one revision in one
transaction.

Request body:
#+BEGIN_SRC json
{"target": {"rev_id": 12},
 "label": "undo the bulk rename",
 "with_dependents": false,
 "skip_filesystem": false}
#+END_SRC

=label= is the label of the revision the revert creates, as on any other write.
=skip_filesystem= (default =false=) decides what happens to operations that
would need a file action: refuse the whole revert, or leave those operations
out of it. It never means "write the metadata anyway" — a revert never records a
change it knows to be untrue of the filesystem.

Response body:
#+BEGIN_SRC json
{
  "revision": 57,
  "head": 140,
  "reverted_operations": [22],
  "skipped_operations": [{"op_id": 23, "reason": "requires_filesystem"}]
}
#+END_SRC

Errors:

| Status | Condition                                                                  |
|--------+----------------------------------------------------------------------------|
|  =400= | target not on HEAD's ancestry; an =unknown= operation has no snapshots     |
|  =404= | no such revision or operation — pruned or trimmed away, or never existed   |
|  =409= | blocked, and =with_dependents= not set — the body adds =blocked=          |
|  =409= | a file action is needed and =skip_filesystem= is false                     |
|  =423= | a rollback or revert lock is held                                          |

A revert with nothing left to apply writes nothing: the response carries
=revision: null= and lists everything under =skipped_operations=. An empty
revision would be a log entry claiming a change that did not happen.

*** =POST /repos/:repo_uuid/revert/start=

The coordinated form. Enters the [[*Rollback lock]], stores the target (the
closure, when =with_dependents= is set), and returns the same body as
=GET /revert/plan=. A blocked target is rejected with =409= and the lock is
*not* entered.

Request body: ={"target": {"rev_id": 12}, "with_dependents": false}=

*** =POST /repos/:repo_uuid/revert/commit=

Writes the revert as one revision, releases the lock and replays the watcher
buffer. The client lists the operations whose filesystem action it carried out
successfully; the others are simply not reverted.

Request body:
#+BEGIN_SRC json
{"apply": [22, 23], "label": "undo the bulk rename"}
#+END_SRC

Response body: as =POST /revert=, with the operations left out of =apply=
reported in =skipped_operations= with =reason: "client_skipped"=. An id in
=apply= that is not part of the stored target is a =400=: the set to revert was
fixed at =start= and =commit= may only narrow it.

The dependency check is re-run inside the transaction. Under the lock it cannot
have changed — write endpoints answer =423= and the watcher's execution is
suspended, so HEAD stands still — which is why =commit= has no conflict status:
the check is re-run for the daemon's own guarantee, not to catch a race.

*** =POST /repos/:repo_uuid/revert/abort=

Releases the lock and replays the watcher buffer, writing nothing. The client is
responsible for reversing any filesystem action it already performed (or for
running =reconcile=), exactly as for =POST /rollback/abort=.

Response body: ={"head": <current_op_id>}=

*** Wire compatibility

Everything the revert adds is additive — five new endpoints and one new nullable
=reverts_op_id= field on the operations returned by =GET /log= and
=GET /log/revisions/:rev_id= — so it does not bump =core::API_VERSION=. An older
client keeps working; it simply cannot revert, and does not show what a revert
undid.

* CLI

The log and rollback CLI (=mf log=, =mf log show=, =mf rollback=, =mf revert=,
=mf prune=) is implemented over the daemon endpoints described above. They are
all subcommands of =mf log= — =mf log rollback=, =mf log revert=, =mf log
prune= — and named here by their verb alone for brevity.

** =mf log=
Displays the history of revisions or operations.

*** Synopsis

#+BEGIN_SRC
mf log [options]
#+END_SRC

*** Behaviour

Calls =GET /log= and formats the result. By default, displays the active line
through HEAD (=mode=active=: the ancestry plus the most-recent forward
continuation, so a rolled-back future stays listed for redo while divergent
branches are hidden) grouped by revision, most recent first. HEAD is marked
with an asterisk.

Default output (one line per revision):

#+BEGIN_SRC
> rev 12  2024-01-15 14:32  "before-cleanup"   ← HEAD
  rev 11  2024-01-15 14:30  (5 ops: create_metarecord ×3, file_moved ×2)
  rev 10  2024-01-14 09:12
#+END_SRC

With =--ops=, each revision is expanded to show its individual operations:

#+BEGIN_SRC
> rev 12  2024-01-15 14:32  "before-cleanup"   ← HEAD
    op 23  set_field(rating)  on <uuid>
    op 22  set_field(genre)   on <uuid>
  rev 11  ...
#+END_SRC

A revision written by =mf revert= is tagged =(revert of rev N)=; with =--ops=,
each of its operations names the operation it undid.

With =--tree=, every branch (including those left behind by past rollbacks) is
shown as a flat list, with off-active-line revisions tagged =(branch)=. With
=--graph=, every branch is instead drawn as an ASCII graph: the active line
keeps the leftmost column and a divergent branch opens a column to its right,
converging back into its parent with a =/= connector:

#+BEGIN_SRC
*      rev 12  2024-01-15 14:32   ← HEAD
| *    rev 11  2024-01-15 14:30
|/
*      rev 10  2024-01-14 09:12
#+END_SRC

*** Options

| Flag                   | Description                                                                    |
|------------------------+--------------------------------------------------------------------------------|
| =--tree=               | Show all branches as a flat list, not just the active line (passes =mode=tree=) |
| =--graph=              | Draw all branches as an ASCII graph (passes =mode=tree=)                       |
| =--ops=                | Expand each revision to show its individual operations                         |
| =--metarecord <uuid>=       | Show only revisions/ops that affected this metarecord (passes =metarecord_uuid=)         |
| =--limit N= / =-n N=   | Show at most N revisions (or operations with =--ops=); default: 20             |
| =--since T=            | Include only revisions with timestamp ≥ T (ISO-8601, or @<unix-ms>)               |
| =--until T=            | Include only revisions with timestamp ≤ T (ISO-8601, or @<unix-ms>)               |
| =--all=                | Remove the default limit of 20 (equivalent to =--limit 0=)                    |

=--tree= / =--graph= and =--limit= / =--since= / =--until= can be combined.
=--tree= with =--metarecord= returns all branches that contain at least one
operation touching the given metarecord.

** =mf log undo [plan]=

Undoes the newest change *you* made, whichever mechanism that takes — the
[[*Undo]] selection, on the command line. It takes no target: finding one is the
whole job.

*** Synopsis

#+BEGIN_SRC
mf log undo [options]
mf log undo plan
#+END_SRC

*** Behaviour

1. Reads =GET /log?mode=linear= twice at most (500 operations, then 20 000) and
   applies the [[*Undo]] selection.
2. With =plan=, prints what it would do — the mechanism, the revision, and why
   that mechanism — and writes nothing.
3. =Rollback=: runs =mf rollback= with the implicit previous-revision target,
   coordinated file moves and all.
4. =Revert=: runs =mf revert= on the chosen revision (or on the operations of it
   that are left, when part of it was reverted already).
5. With nothing to undo, prints =Nothing to undo.= and exits =0=.

A blocked revert, or one needing a filesystem action, behaves exactly as
=mf revert= does — same report, same prompts, same policies. Undo picks the
target; it does not change what the mechanism then does.

*** Options

| Flag                      | Description                                                |
|---------------------------+------------------------------------------------------------|
| =--with-dependents=       | Passed to the revert: also undo whatever blocks the target  |
| =--metadata-only=         | Passed to the revert: leave out operations needing a file action |
| =--on-move-available P=   | Policy for a =move= whose file is present; default =apply=  |
| =--on-move-unavailable P= | Policy for a =move= whose file is gone; default =ask=       |
| =--force=                 | Skip the confirmation prompt                                |
| =--silent=                | Suppress informational output                               |

The GUI's =log:undo= (=ctrl+z=) is the same selection, made against the same
=core::undo= (spec-gui "Event log").

** =mf log redo [plan]=

Takes the newest undo back — the [[*Redo]] selection, on the command line. Like
=mf log undo= it takes no target.

*** Synopsis

#+BEGIN_SRC
mf log redo [options]
mf log redo plan
#+END_SRC

*** Behaviour

1. Reads =GET /log?mode=active= (the *active* line, not the ancestry: it carries
   HEAD's forward continuation, which case 1 re-applies) twice at most, 500
   operations then 20 000, and applies the [[*Redo]] selection.
2. With =plan=, prints the mechanism and the revision, and writes nothing.
3. =Forward=: runs =mf rollback --id <op>= on the last operation of the revision
   ahead of HEAD.
4. =Rollback=: runs =mf rollback= with the implicit previous-revision target.
5. =Revert=: runs =mf revert= on the revert that undid the change.
6. With nothing to take back, prints =Nothing to redo.= and exits =0=.

*** Options

The same as [[*=mf log undo [plan]=]], and passed on the same way: the flags
belong to the mechanism redo picks, not to the picking.

** =mf rollback [<target>]=

Navigates the history tree to a target operation using the coordinated
navigation protocol.

*** Synopsis

#+BEGIN_SRC
mf rollback [<target>] [options]
mf rollback plan [<target>]
#+END_SRC

Target forms:
- omitted: undo the last revision (passes ={"prev_revision": true}= to the
  daemon — navigates to the parent of the first op in HEAD's current revision)
- =<label>=: most recent revision with this label on the HEAD ancestry path
- =--id N=: operation by id
- =--timestamp T=: most recent operation on the HEAD ancestry path whose
  revision timestamp ≤ T (ISO-8601, or @<unix-ms>)

*** Behaviour

1. Calls =GET /rollback/plan/summary= and displays a summary.
2. Calls =POST /rollback/start= to enter lock mode.
3. For each operation:
   - =move_file=: checks whether the file exists at =from=, applies the
     relevant policy (see below), then calls =step {}= or =step {"skip":true}=.
   - =file_deleted=, =file_modified=: if the trash-bin holds the content this
     step deleted (matched by metarecord + =entity_version_before_revision=), moves the
     file back and calls =step {}= (auto-restore); otherwise calls
     =step {"skip": true}= — no filesystem action is possible and the
     restoration op corrects the metadata on the new branch.
   - All other types: calls =step {}=.
4. On completion (=op= is =null=): displays a summary and exits.
5. On error or user interrupt: calls =POST /rollback/abort= before exiting.

*** Policies for =move_file=

All four policies are available in both situations (some combinations are
unusual but never forbidden):

| Situation           | Default  | Available                     |
|---------------------+----------+-------------------------------|
| File available      | =apply=  | =apply=, =skip=, =abort=, =ask= |
| File unavailable    | =ask=    | =apply=, =skip=, =abort=, =ask= |

- =apply=: the metadata follows the navigation (call =step {}=). When the file
  is present, =mv from to= is executed first; when it is *gone*, no =mv= is
  attempted — the metadata still follows the rollback, keeping the recorded
  path rather than =Nothing= (a later reconcile corrects it). If =to= is
  occupied by a file, the =mv= would overwrite it — the CLI first moves that
  file to the trash-bin (=reason=rollback=), so no byte is ever lost (see
  [[file:spec-trash.org][spec-trash.org]]; recover it with =mf trash restore=). If =to= is occupied by a
  *directory*, the CLI skips just this step (=step {"skip": true}=) with a
  warning rather than aborting: trashing a whole directory (and displacing all
  its tracked children) to make room for one file is too destructive to do
  silently during an automated navigation — the user can trash it explicitly
  with =mf trash -f= first, then rerun. The trash-then-=mv= is not atomic: a
  rename that fails after trashing leaves =to= empty with its content
  recoverable from the trash, and the navigation aborts mid-way.
- =skip=: call =step {"skip": true}= without touching the filesystem — the
  metadata is rewound to the file's current recorded location (restoration op,
  see above). Intended for a file that is present but could not be moved; it is
  still selectable for a gone file (the rewind then points at a missing
  location, the caller's choice).
- =abort=: call =POST /rollback/abort= and exit with a non-zero status
- =ask=: prompt the user to choose between =apply=, =skip=, and =abort=

Flags:
- =--on-move-available [apply|skip|abort|ask]=
- =--on-move-unavailable [apply|skip|abort|ask]=
- =--silent=: suppress informational output and warnings; does not suppress
  =ask= prompts

*** =mf rollback plan [<target>]=

Calls =GET /rollback/plan= and displays the full ordered list of operations
that would be processed, without executing anything. Target is optional; omitted
defaults to the previous revision (same as =mf rollback= with no target).

** =mf revert [<target>]=

Undoes one revision, or one operation, by writing the state it replaced as a new
revision at HEAD. HEAD does not move backwards and nothing leaves the history:
=mf log= afterwards shows both the mistake and its correction.

*** Synopsis

#+BEGIN_SRC
mf revert [<target>] [options]
mf revert plan [<target>]
#+END_SRC

Target forms:
- omitted: the revision containing HEAD (undo what was just done)
- =<N>=: revision id — the number shown by =mf log=
- =--op N=: a single operation, for when only part of a revision is wrong
  (repeatable: =--op 22 --op 23=)

*** Behaviour

1. Calls =GET /revert/plan=.
2. If the plan is blocked and =--with-dependents= was not passed, prints the
   blocking operations, says how many more the closure would take, and exits
   =1= without writing anything.
3. If no operation needs a filesystem action, calls =POST /revert= and prints
   what it wrote.
4. Otherwise prints the plan, asks for confirmation unless =--force=, then calls
   =POST /revert/start= and, for each operation:
   - a =move= action: checks whether the file is at =from=, applies the relevant
     policy (the same four as =mf rollback=, see [[*Policies for =move_file=]]),
     and adds the operation to the =apply= list when the =mv= succeeded. An
     occupied destination goes to the trash-bin first, as in a rollback, so no
     byte is lost.
   - a =restore_content= action: if the trash-bin holds the content this
     operation destroyed (matched by metarecord and
     =entity_version_before_revision=, as in a rollback), moves it back and adds
     the operation to =apply=; otherwise leaves it out, with a
     =mf trash restore= hint if some other content of that record is trashed.
   - every other operation is added to =apply= unconditionally.
5. Calls =POST /revert/commit= with the =apply= list, or =POST /revert/abort= on
   error or interrupt.

With =--metadata-only=, step 4 never runs: the CLI calls =POST /revert= with
=skip_filesystem: true=, which reverts everything that needs no file action and
reports the rest as left out.

Operations left out are named in the summary: a revert reports what it did not
undo as plainly as what it did.

Example of a blocked target:

#+BEGIN_SRC
Cannot revert revision 12: 1 of its 2 operations is blocked.

  op 23  set_field(mfr_path)  on 5f2a1c88…
    blocked by op 91  (rev 40, 2024-01-16 08:04, file_moved mfr_path)

Revert rev 40 first, or pass --op 22 to revert only what is free,
or --with-dependents to revert those 1 operation(s) along with it.
#+END_SRC

Example of a successful revert:

#+BEGIN_SRC
Reverted revision 12 as revision 57 (2 operations, 1 file moved).

  op 22  set_field(rating)    5 → 3
  op 23  file_moved(mfr_path) music/new.mp3 → music/old.mp3   (mv)
#+END_SRC

*** Options

| Flag                      | Description                                                    |
|---------------------------+----------------------------------------------------------------|
| =--op N=                  | Revert this operation only (repeatable)                        |
| =--with-dependents=       | Also revert whatever blocks the target (the closure)           |
| =--label L=               | Label the revision the revert creates                          |
| =--metadata-only=         | Leave out the operations needing a file action                 |
| =--on-move-available P=   | Policy for a =move= whose file is present; default =apply=     |
| =--on-move-unavailable P= | Policy for a =move= whose file is gone; default =ask=          |
| =--force=                 | Skip the confirmation prompt                                   |
| =--silent=                | Suppress informational output; does not suppress =ask= prompts |

A metadata-only revert asks for nothing: it is itself revertable, which is the
whole point of preferring it to a rollback. The confirmation exists only for the
filesystem actions — and for =--with-dependents=, which always prints the
closure's size and asks, because how much history it pulls in is exactly what
the user cannot predict from the target alone. =--force= skips that prompt as it
skips the other; it does not imply =--with-dependents=, and the two are
deliberately separate flags.

*** =mf revert plan [<target>]=

Calls =GET /revert/plan= and prints it — the operations, the state each would
restore, the file actions each would need, the blockers if any, and how many
operations =--with-dependents= would add — without writing anything and without
taking the lock. Accepts =--with-dependents= to plan the closure itself.

** =mf prune=
Permanently removes operations from the history. Both sub-commands are
*irreversible* — deleted operations cannot be recovered via rollback. Use
=mf log --tree= beforehand to visualise what will be removed.

Both sub-commands require the target to be an ancestor of HEAD (or HEAD
itself); the daemon returns =400= otherwise.

Target forms (same as =mf rollback=):
- =<label>=: most recent revision with this label on the HEAD ancestry path
- =--id N=: operation by id
- =--timestamp T=: most recent operation on the HEAD ancestry path whose
  revision timestamp ≤ T (ISO-8601, or @<unix-ms>)

Both sub-commands ask for confirmation before calling the daemon unless
=--force= is passed.

*** =mf prune before <target>=

Makes the target operation the new root of the history tree. Deletes all
operations strictly older than the target, plus any branch whose entire
ancestry lies before the target.

The target itself is preserved and becomes a /weak root/: navigation within
the remaining tree works normally, but a full replay from scratch is no longer
possible (see [[*Prune-before(X)]]).

Calls =POST /log/prune= with ={"mode": "before", "target": ...}=.

Output on success:

#+BEGIN_SRC
Pruned 47 operations across 3 revisions.
New root: op 55 (rev 8, 2024-01-10 09:00)
#+END_SRC

*** =mf prune linearize <target>=

Deletes all branch operations that diverge from the HEAD ancestry path between
the root and the target. After this, the segment root→target is a straight
line with no side branches.

Calls =POST /log/prune= with ={"mode": "linearize", "target": ...}=.

Output on success:

#+BEGIN_SRC
Pruned 12 operations across 4 revisions. History linearized up to op 55.
#+END_SRC

*** Common options

| Flag        | Description                                                         |
|-------------+---------------------------------------------------------------------|
| =--force=   | Skip confirmation prompt                                            |
| =--silent=  | Suppress informational output (confirmation prompt still shown)     |

* Open questions

** Collapsing a revert to one operation per cell

A revert currently writes one operation per reverted operation. It could
instead write one per *cell*: for each cell the set touches, compute the state
it held before the set's earliest operation on that cell, and write that once.
Reverting a =retype_field= revision of four operations would become a revision
of one.

Deferred deliberately. The gain is log volume, on revisions that are rarely
large; the cost is a second way of computing what a revert writes, with its own
case analysis for the entity-scoped and =file_*= types, and correctness that no
longer follows from the rollback inverses already covered by tests. Worth
revisiting only if batch reverts turn out to bloat the log in practice.
