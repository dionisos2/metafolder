#+TITLE: Metafolder — Disk-Resident Storage & Query Backend
#+OPTIONS: toc:2 num:t

* Status

*Design document; the prototype of increment 1 is built and measured*
(September 2026): =prototypes/kvstore= (the store, an oracle, cost tests, the
=kvproto= measuring tool) and =prototypes/resident-compare= (the resident engine
timed on the same records). Nothing in the daemon changes yet. The measured
numbers are in [[*Prototype results]]; they replace the estimates this document
started from. Like
[[file:spec-indexing.org][spec-indexing.org]], this describes a direction, not
the code. It is the answer to the limit that document leaves open: the query
engine is fast because *everything* it needs is resident — the bitmap/BSI index,
the id registry, the whole TreeRef forest — so a repository only works while its
index fits in RAM.

The goal is a *second* storage-and-query backend that keeps the full generality
of the query language without loading the repository in memory, *next to* the
current one, which stays as it is.

* Requirements

- *Arbitrary repository size* on an ordinary PC (8–16 GB of RAM). Nothing whose
  size is proportional to the repository may be resident, except the transient
  result bitmap of a query (≤ n/8 bytes: 12 MB at 100 M metarecords).
- *Everyday use must stay close to the resident backend*: opening a folder
  (sorted, paginated), filtering by tag or any categorical field, searching a
  name, sorting by date. Target: at most ×2 on a warm cache (see
  [[*Acceptance criteria]]). A ×10 regression on those gestures would make the
  backend unusable, whatever it buys at scale.
- Queries that are intrinsically global (a regex with no literal over every
  file, a negation on a rare field sorted by another) may be slower — they are
  already O(n) today; only their constant changes.
- *Both backends remain possible*, chosen per repository. Everything above the
  storage layer — the event log, undo/redo and navigation, the watcher, the
  reconcile, sync, trash — must work unchanged on either.
- *Safety is not traded*: atomic writes, no corruption on crash or power loss,
  and a bug in derived data must never lose user data ([[*Safety]]).

* Why not SQL

The resident backend already removed SQL from query evaluation
([[file:spec-indexing.org::*No operand runs in SQL][spec-indexing "No operand runs
in SQL"]]); what SQLite does today is store rows and the log. A disk-resident
engine performs many small reads — a bitmap container, a dictionary key, the
children of a directory — and for that access pattern SQL is the wrong layer:

- *Per-access cost.* A SQLite statement step (bind, execute, decode) is in the
  microsecond range. A lookup in a memory-mapped B+tree on a warm cache is a
  few hundred nanoseconds with no copy. Over the hundreds of thousands of
  accesses of a heavy query, that difference alone is a large part of the ×10
  the requirements forbid.
- *Locking.* The repository connection runs =locking_mode = EXCLUSIVE=, and a
  long write holds the connection readers queue on (the "read blocked by the
  write lock" class of slow reads). An MVCC store with a single writer and
  non-blocking readers removes that class structurally.
- *Memory management.* A memory-mapped store needs no cache of its own and no
  memory budget: the operating system's page cache holds the pages in use and
  evicts the others ([[*The page cache is the cache]]).

SQLite stays for what it is good at: the SQLite backend itself, the per-pair
sync database (spec-sync, out of scope here), and the test oracle
([[*Testing]]).

** Candidate stores

Transactional, ordered key-value stores (to be confirmed by the prototype —
maturity and current state of each crate must be checked):

| Store   | Kind                             | Notes                                                      |
|---------+----------------------------------+------------------------------------------------------------|
| LMDB (=heed=) | mmap'd copy-on-write B+tree | fastest reads, MVCC, one writer; C library, very mature   |
| =redb=  | same model, pure Rust            | somewhat slower reads; page checksums (to verify)          |
| =fjall= | LSM tree, pure Rust              | better write throughput, worse point reads, compaction     |

The workload is read-dominated, with writes arriving in bursts (watcher
flushes, reconcile) that batch well: *LMDB is the default choice*, =redb= the
fallback if a pure-Rust dependency or page checksums turn out to matter more.
The rest of this document assumes an mmap'd copy-on-write B+tree.

** The page cache is the cache

The store file is mapped into the daemon's address space (=mmap=): to the
program it is one large byte array, but nothing is read at open. The first
access to a page faults, the kernel reads that page from disk and resumes the
program; later accesses are plain memory reads. When memory runs short the
kernel drops the least recently used pages — they are clean copies of the file,
so dropping costs nothing but a later re-read.

Consequences:

- no memory budget to configure: a small repository ends up fully cached on its
  own, a large one keeps its working set;
- the database can never exhaust memory — the worst case is being slower;
- the design effort moves to *layout*: data used together must be stored
  together. Ten neighbouring pages are fast, ten thousand scattered ones are
  not. Every key layout below is chosen for that.

* Architecture

** The storage boundary

A =Store= trait sits under everything that today speaks =rusqlite= (22 source
files at the time of writing). Two implementations:

- =SqliteStore= — the current schema and code paths, behaviour unchanged;
- =KvStore= — the layout below.

The trait is kept *narrow*, because every method is a place where two backends
can diverge:

- read the field rows of a set of metarecords; write/replace/delete field rows;
  create/delete a metarecord;
- append an operation (with its before/after snapshots) to the log; read a
  range of the log; read and move HEAD;
- resolve a path / list the children of a node / walk ancestors (the forest);
- open a read snapshot and a write transaction (one write transaction = one
  =log::Writer= revision).

The first increment is to *extract* this boundary with SQLite as its only
implementation: =log.rs= and =db.rs= currently mix the logic (what to undo, in
what order, what a revert writes) with the SQL (how rows are read and written).
Separating them is worth doing even if the second backend never ships.

*** Increment 2, concretely (done, September 2026)

*State.* Built as described below, with two amendments the code forced.
=crates/daemon/src/store.rs= holds the traits — =Rows=, =Log=, =Questions=
(=Store= is the three), =WriteTxn=, =Begin=, =Database= — and SQLite's
implementation of them; a loaded repository holds a =store::Handle=
(=Box<dyn Database + Send>=). Outside the SQLite layer itself (=db.rs=, the
statements still defined in =log.rs=, =repo.rs= as the opener) and the per-pair
sync database, no daemon module names =rusqlite=: the query index, the tree
cache, the writer, navigation, pruning, the log listing, reverts, the watchers,
the reconcile, the schema, duplicates, orphans and mounts all take the traits.
=tests/store_contract.rs= asks every method through the traits only, and is
the file a second backend runs.

- *Questions stayed with the store, not the index.* The schema check's
  candidates count a field's rows *per metarecord*, which the index does not
  keep; serving them from it meant either growing the index or validating every
  holder of a field (minutes on millions of files). Instead each question has a
  default derived from =Rows= alone — correct on any backend, so a new one
  writes nothing — which SQLite overrides with its indexed query; the contract
  test holds every override to its default.
- *Interruption is a capability.* A task's Stop used SQLite's interrupt handle;
  it is now =Begin::interrupter()=, none by default. =as_sqlite()= remains, for
  the tests that run raw SQL against a loaded repository.

Found on the way: the executor used to dequeue the restorations a skipped
navigation step leaves *after* committing the revision that re-records them —
a crash between the two replayed them. They are now dequeued in that revision.

The proposal as written:

Measured on the code: the SQL is concentrated — =db.rs= (55 public functions,
≈ 96 statements) and =log.rs= (≈ 82 statements: the =Writer=, snapshots, the
ancestry walks, navigation, pruning and retention) — and about fifteen other
modules only *carry* a =&Connection= to call them. =sync.rs= holds the per-pair
sync database, which stays SQLite and is out of scope.

Two traits, both behind one transaction type (=Store::read()= /
=Store::write()=; one write transaction is still one =Writer= revision):

- =Rows= — the data model's primary state: a metarecord's existence and
  version; its field rows (all, or by name); a row by id; insert a row (the
  store allocates the id) or re-insert one *with* its id (navigation restores
  rows exactly); delete a row; create and delete a metarecord; and the three
  scans a load needs (every row in id order, every metarecord, the forest).
- =Log= — revisions, operations and their snapshots; one operation by id; the
  bounded ancestry walks (=ancestry_ops_until=, =ancestry_ops_limited=); HEAD;
  labels; the range deletions pruning and retention perform.

Everything else in =db.rs= is a *question* — "the metarecords missing a field",
"tracked files by size", "string fields", "children of a node" — asked by the
schema validation, the duplicates and orphan scans, the reconcile. Those are
answered by the query index (or the forest), not by the store: one engine per
question, and no per-backend SQL to keep in step. Where the index cannot answer
one yet, it gets the operand rather than the store getting the method.

*Row ids are part of the data model.* =Field.id= is in every API response and
=…/fields/:id= addresses a row by it; navigation restores the original ids. So
every backend allocates monotonic row ids and can re-insert a row under its old
one — the KV layout gains a =row id → (metarecord, position)= key space.

Order of work, each step behaviour-preserving with the whole test suite as its
oracle: the traits and a =SqliteStore= wrapping today's statements; the
=Writer= and the navigation on them; the load scans and the readers; the
questions moved onto the index; finally no module but =SqliteStore= names
=rusqlite=.

The query side has the same boundary one level up: the evaluator of
=crates/daemon/src/index/= reads bitmaps, BSI slices and value dictionaries
through a source trait, implemented by the resident index (today's structures)
and by the store (the key spaces below). The algebra — =And=/=Or=/=Not=,
three-valued predicates, =Follows=, keyset pagination, exact counts — is shared.

** Primary and derived data

The store holds two kinds of data, in separate key spaces:

- *Primary* — metarecords, their fields, the event log, HEAD. The source of
  truth; the only thing a backup must carry.
- *Derived* — postings, BSI slices, ordered indexes, descendant bitmaps,
  trigrams. Everything here is a function of the primary data and can be
  rebuilt from it by a =reindex= (an observable task).

A bug in derived data yields wrong query results, never lost data, and a
consistency check (the same comparison the oracle performs) detects it. This
split is the main safety property of the design.

** Key layout

Every key space is an ordered table; keys are byte strings compared
lexicographically, integers big-endian so that byte order is numeric order.

| Key space   | Key                          | Value                          | Serves                                          |
|-------------+------------------------------+--------------------------------+-------------------------------------------------|
| records     | =id=                         | the metarecord's field rows    | reading a result page (k lookups)               |
| uuid→id     | =uuid=                       | =id=                           | replaces the resident =IdRegistry=              |
| id→uuid     | =id=                         | =uuid=                         | turning a result bitmap into uuids (k lookups)  |
| postings    | =(field, value, chunk)=      | roaring container              | =Eq= on a value held by ≥ 64 records            |
| presence    | =(field, present/absent, chunk)= | roaring container          | =IS PRESENT= / =IS ABSENT= / =IS UNKNOWN=       |
| ordered     | =(field, sort key, id)=      | —                              | sort and range on any type                      |
| bsi         | =(field, min/max, slice, chunk)= | roaring container          | numeric ranges, numeric top-k                   |
| forest      | =(field, parent, name)=      | =id=                           | path resolution, children *already sorted*      |
| descendants | =(field, node, chunk)=       | roaring container              | subtree membership ([[*The forest: descendant bitmaps]]) |
| children    | =(field, node, chunk)=       | roaring container              | a folder's direct entries as one bitmap         |
| trigrams    | =(field, trigram, chunk)=    | roaring container              | =Matches= / =Osm= on text and names             |
| log         | =op_id=                      | operation + snapshots          | history, undo/redo, navigation, incremental reads |
| meta        | name                         | HEAD, format version, …        |                                                 |

=chunk= is the high 16 bits of an id: one roaring container covers 65 536 ids,
so a bitmap is read container by container and a write rewrites at most a few
KB. A value gets a posting only once 64 records hold it; a rarer one is
answered from =ordered=, where its ids are adjacent under one prefix. A bitmap
per unique value is exactly what makes the resident index expensive on
=mfr_mtime=, =mfr_size= and the hashes: in the prototype, postings for every
value weighed 200 bytes per record, promoted ones 5. A posting is never
demoted, so "a value has a posting" always means "all its ids are in it".

Containers are read *in place* from the mapped page, without deserialising. If
the roaring crate in use cannot expose a zero-copy view of its serialised form,
a small read-only view over that format is written for it — a small piece, but
on the critical path of every query.

** Ids and locality

A metarecord's =id= is a dense =u64= (=u32= per chunked bitmap) allocated
*in discovery order* and never renumbered. The reconcile walks the filesystem
directory by directory and the watcher reports a new directory's content
together, so the files of one subtree mostly receive *consecutive* ids. That
locality is what keeps descendant bitmaps small (they compress to roaring runs)
and makes a folder's records neighbours in the =records= table.

Deleted ids are not reused (a tombstone costs one absent key). A full
=reindex --compact= may renumber; it is an explicit maintenance operation, never
an effect of a write.

** The forest: descendant bitmaps

This answers the question spec-indexing leaves open ("tree as a range": stable
tree-order ids vs nested intervals), without renumbering anything.

Each node with children keeps the bitmap of *all* its descendants, per
=tree_ref= field.

Maintenance:
- *a node is created* under a parent: its id is added to the bitmap of each
  ancestor — ≈ depth container writes;
- *a subtree moves*: its descendant bitmap (plus the node itself) is removed
  from each old ancestor and added to each new one — ≈ depth OR/ANDNOT
  operations on a compact bitmap, *independent of the subtree's size*;
- *a rename* changes nothing here (the =forest= key of the node moves, one
  delete and one insert).

What it buys:
- =field ->* "/dir"= (=FollowsTransitive= on a path) is one bitmap read — no
  level-by-level expansion;
- *sort by path*, including a global one: a depth-first walk of =forest= in
  name order, pruning every subtree whose =descendants ∩ match= is empty,
  stopping at the k-th result — ≈ k × depth reads whatever the repository size;
- order-sensitive =Osm= path matching without walking the forest: along a
  matching path, the shortest matching prefix ends at a node whose own name
  holds the end of the last term (what follows its last =/=), so the trigrams
  give the candidate "anchors", each is verified on its assembled path (its
  ancestors read once, shared between candidates), and the match set is the
  union of the verified anchors' subtrees — the descendant bitmaps again. An
  anchor matching only through a position other than its first matches alone,
  its descendants hanging from the first. A last term *ending* with =/= has no
  anchor and falls back to the walk (=forest_query.rs=). The =:path= aspect
  still walks the whole forest :deferred: (/pruned =:path= walk/: an arbitrary
  predicate on the path gives no anchor);
- the forest invariants (no cycle, depth ≤ 1000) only need the ancestor chain:
  ≈ depth reads per checked write.

Write amplification: about depth times more containers per tree write. Opening
a folder — the central gesture of the GUI — costs a handful of reads in return.

** Text: trigrams

A =Matches= or =Osm= leaf on a high-cardinality field (file names) cannot scan
the distinct values on disk at every keystroke. Each string and =tree_ref=
name is indexed by its trigrams: the literal parts of the pattern (or the
terms) give trigram postings, their intersection gives the candidates, and only
the candidates' values are read and matched against the real predicate. A
pattern with no usable literal (or a term shorter than three characters) falls
back to scanning the value dictionary, restricted as today to the candidate
set of the enclosing =And=.

*A page without a count checks text lazily.* A text leaf, or the text
conjuncts of an =And=, are split off the filter: what is evaluated is the
candidate bitmap (the trigram intersection, or every holder of the field when
there is no trigram), and the predicate itself is checked only on the ids the
sort visits, stopping at the page's end. A search as you type then costs its
page (0.5–3 ms on 5 M files) instead of its whole match set (170–530 ms); only
a request that asks for the total pays for the whole set.

This reintroduces what spec-indexing removed (the FTS5 trigram pre-filter):
that removal was justified by the dictionary being resident, which is exactly
what no longer holds here. The resident backend keeps its scan.

** Sort

The filter produces a bitmap first, so |match| is known *exactly and for free*
before sorting. The sort chooses among:

- *fetch*: read the sort key of each matched id (=records=, or the path from
  =position=), sort;
- *walk*: walk the =ordered= index — or the forest, for a path sort — and test
  membership in the match bitmap until k are found.

The choice compares the two estimated costs: fetching costs |match| random
reads (weighted ×8 against an index step), walking costs k × rows / |match|
steps if the matches are spread evenly along the index (the whole index when k
covers the match). No statistics: |match| is exact, and rows is the field's
presence count (or the size of the walk's subtree). A count of matches alone
is not enough: a 2 500-file folder is "large", yet walking the date index of a
5 M-file repository for 100 of its files reads ≈ 200 000 keys.

A path walk starts at the lowest node whose descendants hold every match
(found from the first match upwards), not at the forest root — otherwise
browsing a folder pays for the siblings of its ancestors. It streams each
folder's children from =forest= and stops at the page's end, and a folder
filter is the =children= bitmap: a folder of 250 000 entries opens in 0.4 ms.

Keyset pagination is unchanged: the cursor carries the last sort key and uuid,
and each strategy resumes strictly after it. (The prototype serves first pages
only; the cursor is not built.)

* Writes and atomicity

One =log::Writer= revision is one write transaction of the store: the field
rows, the log operations and their snapshots, HEAD, *and* every derived key
space. It commits entirely or not at all; readers keep seeing the previous
snapshot until it does. There is no snapshot-plus-replay scheme and no
"refresh to HEAD" step on the read path: the derived data is consistent with
HEAD by construction.

Bulk writers (reconcile, a large watcher flush) accumulate the derived updates
of their transaction in memory per container and write each container once.

One writer at a time, as today (the executor and the API already serialise
writes). Readers never block.

* Safety

- *Crash and power loss.* A copy-on-write B+tree never modifies a live page: a
  commit writes the new pages elsewhere, syncs them, then flips a small header
  pointing to the new root (two alternating headers). A crash before the flip
  leaves the previous header intact: the store opens at the last committed
  transaction, with no recovery log to replay.
- *Our own memory bugs.* The map is opened *read-only* (=MDB_WRITEMAP= stays
  off): writes go through the library's system calls, so a stray write in the
  process cannot reach the file.
- *Storage lying about =fsync=, bad sectors.* As with SQLite, a damaged page
  can make part — or, for a page near the root, all — of the store unreadable.
  LMDB has no page checksums (SQLite has none by default either; =redb= may —
  to verify). The defence is backups: the store supports a consistent hot copy
  (=mdb_copy=), which a =mf repo backup= would expose.
- *Network filesystems* (NFS, SMB) are not supported by LMDB. A repository whose
  =.metafolder/internal/= lives on one keeps the SQLite backend; creating a
  KV repository there is refused.
- *Map size.* The map grows with the store ([[*Choosing the backend]]); a
  single revision too large for the room left fails whole (=MDB_MAP_FULL=),
  without corruption.
- *Long read transactions* pin old pages and make the file grow. Read snapshots
  are held for one request at most — a code rule, enforced like the other
  invariants (=.semgrep/invariants.yml=).
- *Derived data* can always be rebuilt ([[*Primary and derived data]]);
  =reindex= and a =check= comparing a sample of queries against a rebuild are
  part of the backend, not an afterthought.

* Choosing the backend

The backend is a property of the repository, recorded in
=.metafolder/config.json= (=storage: "sqlite" | "kv"=, absent = =sqlite=), chosen
at =init= and changed only by a conversion (=mf repo convert=, both directions,
an observable task that writes the new store beside the old one and switches on
success). Per the migration policy, the conversion *is* the migration script
for this format.

On disk, a SQLite repository keeps =internal/db.sqlite=; a KV one keeps
=internal/kv/= (the LMDB environment, plus =daemon.lock=: LMDB has no
exclusive mode, so the "one daemon per repository" lock SQLite gets from
=locking_mode = EXCLUSIVE= is an =flock= held for the store's lifetime).
LMDB reserves its whole map in the address space up front, and a daemon holds
one map per loaded repository: a fixed 1 TiB map ran the 128 TiB of x86-64
out at about 120 repositories. And LMDB grows a map only between
transactions, so the room a write transaction starts with is the most it can
write. That room is the *free space of the disk*, capped at 128 GiB per store
(=kvstore::map_to_grant=): granted at the start of a write transaction — the
one moment LMDB allows a resize, no transaction being open — and renewed when
it falls below the free space (below half the cap on a disk with more). A
revision of any size — a first reconcile of a large tree, a conversion —
therefore commits unless the disk is full (or, past the cap, beyond 64 GiB
written in one revision); at 128 GiB some 900 repositories fit in the address
space. The first version doubled the map once half full, so a revision larger
than what the store already held failed whole with =MDB_MAP_FULL= (a 1 GiB
repository could not be converted). Such a failure cannot corrupt the store. The
legacy-layout migration at load is SQLite's alone — no KV repository predates
=internal/=.

A new repository is created on the KV store; until =init= takes a flag
(increment 5), =METAFOLDER_DEFAULT_STORAGE=sqlite= creates it on SQLite
instead. That variable is also how the integration suite is run on each
backend; tests about SQLite's own layout (the file, its tables, its legacy
migrations) pin SQLite with =init_repository_with=. An existing repository
keeps its backend: a =config.json= without =storage= is SQLite, since every
repository written before the choice existed is one.

The resident query index remains available on top of either store: on a
repository that fits in memory it may still be the faster engine. Whether it is
still worth keeping on the KV store, where a small repository is fully in the
page cache anyway, is decided by measurement, not in advance.

* Testing

- *Every integration test runs on both backends*, the way
  =tests/common/engines.rs= already runs both query engines. A behaviour tested
  on one backend only is where the two drift.
- *The oracle stays SQL.* =crates/query-oracle= compiles to the SQLite schema;
  on the KV backend the tests export the repository into a throwaway SQLite
  database and compare. Three engines, one answer.
- *Scale is tested by counting, not timing* — the =perf_cost.rs= idea applied
  to page and key reads: opening a folder reads the same number of keys on a
  5 k and an 80 k repository; a tag filter reads a number of containers
  proportional to the ids it spans; no bounded query reads a whole key space.
  This needs no large data set and cannot flake under load.
- *Synthetic scale.* Millions of metarecords are generated directly into a
  store (no files on disk: a metarecord needs rows, not a file), from the
  =regression/synth.rs= generator. At that size only the KV backend is
  measured — the resident one would need the memory the machine does not have.
- *Cold cache.* The page cache is dropped between runs
  (=sync; echo 3 > /proc/sys/vm/drop_caches=, root) to measure first access
  separately from everyday use.

** Acceptance criteria

Measured on =benchmarks/bench_data= and =bench_data_big= against the resident
backend, warm cache, with the scenario list of =scripts/bench.sh=:

- the everyday gestures of [[*Evaluation cost, per gesture]] at most ×2;
- writes (single-field, watcher flush, reconcile) at most ×2 end to end;
- on the synthetic multi-million store: the everyday gestures independent of
  the repository size (cost assertions), and usable on 8 GB of RAM.

If a gesture misses its target, the prototype says which one and why; the
decision to migrate waits for that answer.

* Prototype results

Machine: i7-7500U, 4 cores, 7.6 GB of RAM (swapping during the runs), SSD.
Synthetic repository of =metafolder_kv_proto::synth=: an 8-way directory tree,
20 files per directory, the root holding the remainder (its largest folder);
each file carries =mfr_path=, =mfr_type=, =mfr_ext=, =mfr_size=, =mfr_mtime=, a
unique =mfr_hash=, 0–2 tags and a rating one time in three. Times are medians
of seven warm runs; a page is 100 results *and their records read*. "Cold" is
the first run after the store's pages were evicted from the page cache.

Twenty-five times the data leaves every page under 3 ms warm; the heap stays
at a few MB (at 476 MB per 210 000 records, the resident engine would need ≈ 12 GB here). Writes stay under
10 ms whatever the subtree moved: a move costs the depth, not the size.

Where it is not yet good enough:
- *Cold cache*: 70–240 ms for an everyday gesture, seconds for a text search
  over a large candidate set. The first gesture after a start or after memory
  pressure pays for scattered page reads.
- *Counts of text searches*: the total needs the whole match set (0.2–0.5 s on
  5 M). The GUI's list asks for a count with its first page; it would have to
  ask for it separately, after the page.
- *Size*: ≈ 1.2 KB per record, of which the log, the ordered index and the
  records are ≈ 270 bytes each (the SQLite database of the same 210 000
  records is 410 MB against 324 MB; on the M regression repository, 31 MB
  against 22 MB). A bulk load leaves freed pages in the file (438 → 274 MB
  used on one run): a compacting copy after an import would reclaim them.
- *Bulk load*: 16 000 records/s at 200 k, 6 300/s at 5 M (a reconcile of a
  large tree would be minutes).

Two measurements about the environment rather than the design: a synced
commit costs ≈ 2 ms on the home filesystem but ≈ 20 ms on the container's
=fuse-overlayfs= root, so writes must be measured where repositories live;
and =MDB_NOMETASYNC= saved almost nothing — one =fsync= dominates either way.

* Conflicts with existing decisions

- *Adaptive planner* — off the roadmap because each operand had one way to be
  answered (spec-indexing "Status"). The sort choice and the trigram/scan choice
  bring alternatives back. They are fixed, statistics-free rules driven by exact
  counts, not a planner — but the premise that there is "no plan to pick" stops
  holding on this backend.
- *The trigram pre-filter* removed by spec-indexing returns on this backend
  (see [[*Text: trigrams]]).
- *The oracle depends on =tree_cache=* for path shapes. On the KV backend it is
  fed the exported SQLite database, where the full forest is available.
- *Network filesystems*: the SQLite backend falls back to =journal_mode =
  DELETE= there; the KV backend refuses them. A user moving a repository onto a
  network share must convert it first.
- *One persisted format more* to migrate for the lifetime of the project.

* Open questions

- LMDB vs =redb= — read speed on the prototype, and whether page checksums are
  worth the difference.
- Whether =id= allocation in discovery order gives enough locality after years
  of moves and renames, or whether =reindex --compact= must be scheduled.
- The exact shape of the =Store= trait around the log's navigation (LCA,
  inverse/forward application restoring =field.id=s): today it relies on SQL
  row ids, which the KV backend must reproduce or replace.
- Whether the resident index is kept on top of the KV store at all. On the
  measurements, no: the disk backend's page costs are below the resident
  engine's at 210 000 records, the page cache holding the store.
- Cold-cache latency: whether to warm the hot key spaces (=forest=, =kids=,
  =presence=, postings) at load with =madvise(WILLNEED)=, and how much that costs
  on a store larger than memory.
- *(done, September 2026)* The resident engine adopted the page-bounded sort
  and the lazy text checks (spec-indexing "A page costs the page"). On the same
  210 000 records, in-process: first page 5.7 → 0.08 ms, by size 50 → 0.3 ms,
  all files by path 152 → 1.5 ms, a tag by date 7.9 → 0.2 ms, name searches
  without a count 66–118 → 1–11 ms. What remains is the filter itself: a
  11 699-file subtree still costs ≈ 5 ms to evaluate (iterative expansion,
  where the disk backend reads one descendant bitmap), and a counted text
  search still scans every distinct name (≈ 70 ms).

2. *(done)* *Extract the =Store= boundary* with SQLite as its only

3. *(done)* *=KvStore=* for primary data and the log; every integration test
   on both backends; the KV store is the default for a new repository.
4. *Derived key spaces* and the disk query source; the oracle comparison

5. *=mf repo convert=*, =reindex=, =check=, backup; the backend choice at =init=.
   *(convert and the choice at init done)* =mf repo convert --to kv|sqlite=
   (=POST /repos/:repo/convert=) unloads the repository, waits for its store
   to be released, and converts it on disk: the new store is written beside
   the old one (=internal/converting-…=) by a faithful copy — metarecords and
   versions, every row under its own id, the history under its own ids
   (operations and snapshots, revisions, HEAD, queued restorations), and the
   id counters, so no id is ever handed out twice — through three import
   primitives both backends implement (=import_revision=, =import_op=,
   =raise_counters=), in one write transaction whatever the size (see
   "Choosing the backend" for the room a KV one starts with); a KV target is reindexed for the locality of its dense ids; both stores are then read and compared (a digest of all of it); the
   new store takes its name; =config.json= — now always written atomically,
   a new file renamed over the old — switches; the old store is set aside as
   =internal/pre-convert-<time>-<name>=, for the user to delete. An
   interruption before the config write leaves the repository as it was (the
   leftovers are removed by the next attempt); after it, only the old store
   is left to set aside. The repository is loaded back either way.
   Measured: 50 000 files (200 000 rows) in 9 s to KV, 13 s back.
   =mf repo init --storage= chooses the backend; =GET /repos= reports it.
   *(check and reindex done)* =mf repo check= (=POST /repos/:repo/check=)
   lists what no longer holds together — on the KV store, the derived key
   spaces against a rebuild from the primary data (=check_derived=: ids,
   sets, partitions, forest, trigrams); on SQLite, =PRAGMA integrity_check= —
   and exits 1 on a problem. =mf repo reindex= (=POST /repos/:repo/reindex=)
   derives again: the KV store's derived key spaces (=KvStore::reindex=), or
   SQLite's =REINDEX= and then the resident index and forest, rebuilt as a
   load builds them. Both are methods of the store's =Begin= trait, required
   of every backend, and hold the repository while they run.
   *(backup done)* =mf repo backup [--to DIR]= (=POST /repos/:repo/backup=)
   takes a consistent copy of the store while the daemon runs — LMDB's
   compacting hot copy, SQLite's =VACUUM INTO=, both =Begin::backup_to= —
   with the repository's =config.json= and =schema.json= and a =backup.json=
   (time, backend, metarecords). It is written under a temporary name, then
   opened and checked (=Begin::check=) before it takes its place: a store
   damaged since the last backup fails its new one, which never replaces a
   good one. By default it goes under =internal/backups/= (never tracked);
   =--to= names a new directory. The daemon takes each loaded repository's
   /automatic/ backup every =auto-backup-days= days (daemon settings, default
   1, 0 turns it off) into the single slot =internal/backups/auto/=, looking
   at startup and then every hour; a failure is a warning in the repository's
   diagnostics. Restoring is manual: with the daemon stopped, the backup's
   =db.sqlite= or =kv/= goes back into =.metafolder/internal/= (and its
   =config.json= into =.metafolder/=, if the config itself was lost).

** Increment 4, concretely

The resident index is not rewritten for the disk: its evaluator — the part
that holds the query semantics (three-valued logic, aspects, =osm=, follows,
the page strategies), validated against the oracle — is made generic over
*where its bitmaps come from*, and the KV store becomes a second source. One
evaluator, two sources, one oracle: a second evaluator would be a second copy
of every subtle rule, and the place the two drift.

a. *(done)* *Dense ids and derived key spaces* in =KvStore=, written in the revision's
   own transaction, maintained at the row level (every row insert and delete,
   navigation included, goes through the same two primitives): =uuid→id=,
   =id→uuid=, the universe, =presence= (present / absent per field), the
   =ordered= index (=(field, sort key, id)=, which also answers equality and
   the distinct-value scans), =referrers= for =ref= / =tree_ref= values, and
   the forest's =children= (ids with at least one child). A =rebuild= derives
   them all from the primary data; the tests hold the maintained spaces equal
   to a rebuild after every write sequence, navigation included.
b. *(done)* *The evaluator's source trait*: the questions the evaluator asks of its
   data (the universe, presence, a field's type, id ↔ uuid, a comparison on a
   field, a text scan over its distinct values, referrers, forest roots and
   parents, sort representatives) become a trait the resident index
   implements. No behaviour change.
c. *(done)* *The KV source* implements it over the derived key spaces, inside one read
   transaction per query; the oracle and page-strategy suites run it as a
   third engine.
d. *(done)* *Serving from the disk*: a KV repository answers its queries through the KV
   source and no longer builds the resident index at load. A query still
   takes the repository's connection lock, as every read did before: the read
   snapshot borrows the store behind it. So a read waits for a long write —
   the field catalogue included, which the resident engine served past a
   writer from its stale-but-committed index. Letting reads open their
   snapshot without that lock ("Readers never block", [[*Writes and
   atomicity]]) needs the map's growth to exclude open readers, since LMDB
   resizes only with no transaction open in the process. /Deferred by
   decision (September 2026)/: operations stay sequential for now.
e. *The forest on disk*: the tree cache is no longer built for a KV
   repository. *(done)* It is created /without a forest/: a load leaves it
   empty, the upkeep after a write has nothing to do, and a lookup starts from
   scratch (the nodes one lookup brings in are dropped by the next, so nothing
   grows and nothing goes stale). Every forest question goes to the store:
   paths resolve component by component, the full-path sort keys and the
   =:path= / =osm= path leaves are computed from the store's positions by the
   resident rules (a child hangs under its parent's first position; a node
   whose parent holds no position is in no path), and the key-order walk of a
   path sort declines, so a path-sorted page is fetched. Measured (quick bench,
   size S): opening a folder 0.53 → 1.44 ms, resolving a page of paths 0.41 →
   1.21 ms — costs of the result, not of the repository. Then *(done)*:
   - /The folder walk/: a page sorted by path below a bound (a folder, a
     subtree) walks the store's forest in key order — each folder's children
     read a page at a time from the forest table (=Rows::children_page=),
     which orders them by name bytes — and stops at the page's end, resuming
     a cursor by descending its key's components. It declines, and the page
     is fetched, on a name that is not plain UTF-8 above the separator or is
     keyed by hash (over 300 bytes), on a node at several positions, and
     without a bound (a whole-forest walk would have to find the detached
     nodes).
   - /Children bitmaps/: the ids pointing at a uuid in a field (a folder's
     children, a =ref='s referrers) are one chunked bitmap per (field,
     target), so a folder filter reads a key per 65 536 children.
   - /Descendant bitmaps/, for =mfr_path= only: there a node holds one
     position, so a move is set arithmetic — the moved node's descendants
     plus itself leave each old ancestor's bitmap and join each new one's,
     ≈ depth chunk writes, independent of the subtree's size. A forest whose
     nodes may hang at several places keeps the level-by-level expansion
     (maintaining the closure there would need its paths counted).
   =tests/kv_cost.rs= pins all three: a page of a 16 000-entry folder by path
   (either way), a subtree by path, and a count over a subtree of 800
   folders read what they read on the eighth of it.
f. *Trigrams* and the lazy text checks; postings for frequent values; the
   cost assertions (key reads counted, not timed). *(trigrams and cost
   assertions done)* Each field's texts (strings, =tree_ref= names) are
   indexed by the trigrams of their lower-cased form, one chunked bitmap per
   trigram (so a frequent trigram costs a few reads, not one per row); a text
   over 512 bytes is not split — its id joins the field's long-text set,
   which every search checks. A search's required literals (the literal runs
   every match contains, extracted from the pattern's syntax tree, a
   case-insensitive letter counting as the letter; an =osm= term) give the
   trigrams, their intersection the candidates, and each candidate is checked
   on its values. A pattern with no literal of three characters scans as
   before. =tests/kv_cost.rs= counts the keys a KV query reads on a
   repository and on one eight times larger: a rare value, a page sorted on a
   value and a literal search read the same number (a search read the whole
   field before: 2 004 keys against 16 004). The lazy text checks already hold
   on this backend (a deferred name check reads the record's positions);
   postings for frequent values are not built — the value partition serves
   equality with one key per holder.

Each step leaves every suite green on both backends.

*Keys have a size limit* (found building step a). LMDB refuses a key over
511 bytes, and both a partition key (which holds the value) and a forest key
(which holds the node's name) can hold arbitrary text. So:
- a text over 256 escaped bytes is keyed by that prefix, the marker =00 01=
  (which sorts after the =00 00= ending the text equal to the prefix, and
  before anything longer) and a 64-bit hash of the whole. Order is kept
  except among the long texts sharing the prefix; a reader resolves that
  case, and a hashed equality, from the values themselves — rare, local, and
  exact;
- a node name over 300 bytes is keyed by its first 300 bytes and a hash (a
  key no whole name has the length of), and read back from its row.
A field name is still part of every key: one over ≈ 200 bytes cannot be
written on this backend.
