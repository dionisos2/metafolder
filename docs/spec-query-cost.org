#+TITLE: Metafolder — Query Cost Estimation (=query/explain=)
#+OPTIONS: toc:2 num:t

* Overview

A client cannot tell, before sending a query, whether it will come back in a
millisecond or in a minute. That matters wherever a query sits inside a loop
with a human in it: the tagging scripts ask one question per entry and want a
live counter next to it ([[file:gui-tag-folder-rework.md][gui-tag-folder-rework]]), the GUI opens a panel on
whatever the user typed. Today the only way to find out is to run it.

The obvious fix — have the daemon *refuse* the query shapes it cannot serve from
the bitmap index, behind an "extended" flag — is the wrong one. The set of
shapes the index declines is an implementation detail of the accelerator, and it
is *meant* to move: the =:parent= aspect is about to be added, the adaptive
planner ([[file:spec-indexing.org][spec-indexing]]) will change it again. Freezing it into user-visible
surface turns every improvement of the index into a contract change, and the
list is not even the right predicate: "not served by the index" is not the same
as "slow" — on a small repository the SQL engine answers instantly, while an
index-served query over a large one can still cost.

So the daemon **describes** instead of refusing, and the client decides:

: POST /repos/:repo/query/explain

answers, *without running the query*, which engine would serve it, which leaves
force that choice, what the work decomposes into, and — as an indication, not a
promise — how long it should take. A client then drops its counter, warns, or
refuses to run, on its own terms.

** Non-goals

- *Not a profiler and not a metrics system.* No aggregates, no percentiles.
- *Unrelated to the slow-operation log* ([[file:spec-slow-log.org][spec-slow-log]]). That log is a debugging
  artefact: threshold-based, persistent, and it also records GUI-side time. It
  is not an input to this feature and this feature does not write to it.
- *No promise of a duration.* The estimate is a band derived from declared
  constants (see [[*Calibration]]), and it is explicitly marked as such.
- *Not a planner.* Explain describes the plan the engines will actually use. It
  does not choose one — though its cost model is the piece the adaptive planner
  will need, which is why the two must share it (see [[*Where the model is
  computed]]).

* Where the model is computed

The symbolic cost is built **while the query is compiled**, as a by-product of
the compilation that would run anyway — not by a second traversal written for
explain.

This is a hard constraint, not a preference. Supportedness is currently
discovered *by evaluating*: the =Unsupported= comes out of =index::eval=. An
explain that re-derives it in a parallel classifier is two implementations of one
decision, which is the shape that has already produced real bugs in this project.
So:

- the leaf-supportedness decision is extracted as a **pure function** of
  =(query leaf, index metadata, caller-resolved seeds)=, called by both
  =index::eval= and explain;
- =query_exec='s compiler annotates each node it compiles with its cost term, so
  the SQL side of the model is produced by the code that builds the SQL;
- explain runs compilation and classification, and stops there.

It is *not* computed in the DSL parser. The parser lives in =core= and produces
the IR; it knows nothing about the repository, and every term of the model needs
cardinalities. The cost is a property of (IR × data), one step after the parse.

** Fast by construction

Explain must never do the work it describes. Concretely it may not evaluate a
predicate, may not run the FTS pass (it *reports* that one is needed), and may
not walk the forest — path and node seeds resolve through the resident tree cache
like any query preparation, which is a hash lookup.

Its bound is =O(query nodes) + O(path operands)=, independent of the repository
size. A client may call it before every query.

* Parameters

Every term of the model is a count expressed in these, all of which the index
already knows in O(1) unless stated otherwise.

| Symbol | Meaning                                              | Known                          |
|--------+------------------------------------------------------+--------------------------------|
| =M=    | metarecords in the repository (index universe)       | exact                          |
| =R_f=  | rows carrying field =f= (=present= ∪ =absent=)       | exact                          |
| =V_f=  | distinct values of field =f= (encoding buckets)      | exact                          |
| =K=    | metarecords the query matches                        | *estimated* from selectivities |
| =N=    | rows returned (=limit=, else =K=)                    | exact once =K= is estimated    |
| =T_n=  | size of the subtree at node =n=                      | from the resident forest       |
| =D=    | depth of the forest (bounded at 1000)                | exact                          |
| =C=    | candidate rows an FTS trigram lookup returns         | *estimated*                    |

=K= and =C= are the two the daemon cannot know without doing the work. They are
reported as estimates, and every term that depends on them inherits that flag —
a client that needs a hard answer reads the terms that do not.

* Three providers, two engines

A query is served by three resident systems, not two, and naming them is what
makes the table below readable — each category is one system's work.

| Provider                       | Holds                                    | Executes                                        |
|--------------------------------+------------------------------------------+-------------------------------------------------|
| the forest (=tree_cache=)      | the TreeRef trees: path ↔ node, children | =path.resolve=, =path.assemble=, tree sort keys |
| the bitmaps (=index/=)         | the per-field roaring / BSI encodings    | =bitmap.leaf=, =bitmap.combine=, =count=        |
| SQLite (=field=, =field_text=) | the authoritative rows                   | =sql.scan=, the CTE =sort=, =assemble=          |

Only two of them *evaluate a query*: the bitmaps and SQLite. The forest is a
provider both of them call, which is why =path.resolve= reads "same" on both
sides of the cost table — and why "cache-walked descendants" appears below in a
column headed SQL: the SQL engine walks the forest in memory like everyone else,
and hands SQLite only the resulting uuids, as inline literals.

Two categories are one question answered by two different providers, and they are
the two whose count changes with the engine: =follow.transitive= (a forest walk,
or a bitmap expansion) and =fts.scan= (SQLite =REGEXP= over rows, or an in-memory
scan of distinct values).

* The cost table

One row per category. =count= is the contract: it is derived from the query and
the parameters above and does not depend on the machine. =constant= is
calibration ([[*Calibration]]).

| Category            | Count                              | Index path                  | SQL path                     | Constant  |
|---------------------+------------------------------------+-----------------------------+------------------------------+-----------|
| =path.resolve=      | one per path / exact-node operand  | forest lookup, O(1)         | same                         | =t_path=  |
| =bitmap.leaf=       | =R_f= (equality) / =V_f= (ordered) | bucket union                | —                            | =t_bit=   |
| =bitmap.combine=    | Σ operand cardinalities            | AND/OR/NOT over containers  | —                            | =t_bit=   |
| =follow.transitive= | =D= ops (index) / =T_n= rows (SQL) | iterative bitmap expansion  | materialises the subtree §7  | =t_bit= / =t_row= |
| =fts.scan=          | =C= with a literal, else =R_f=     | value scan or pre-resolved  | same pass                    | =t_regexp= |
| =sql.scan=          | =R_f= per value predicate          | —                           | no index on the value columns | =t_row=  |
| =sort=              | =K= reps + =K log K=               | BSI representatives         | window functions             | =t_sort=  |
| =count=             | 0 (index) / one full filter (SQL)  | O(1) from the bitmap        | re-runs the CTE chain        | —         |
| =assemble=          | =N= × selected fields              | row read + serialisation    | same                         | =t_row=   |

Three of these rows are the ones that surprise people, and they are the reason
the table exists rather than a single number:

- *Bitmap work is not O(M).* A Roaring =AND= costs the cardinality of the
  containers it touches. A selective query is cheap, and a model that prices
  every bitmap pass at =M= would say the opposite.
- *An SQL value predicate is O(R_f), not O(M) and not O(all field rows).* =db.rs=
  indexes =(field_name, …)= and never =value_text= / =value_int= / =value_real=,
  so the scan is confined to the rows of that one field name — and =R_f= is
  exactly what =present_of(f).len() + absent_of(f).len()= gives.
- *The FTS pass is a cliff, not a coefficient.* =fts::required_fts_literal=
  either extracts a mandatory ≥3-character literal — a trigram lookup over =C=
  candidates — or does not, and then every row of the field goes through
  =REGEXP=. Which of the two, and why, is the single most actionable thing this
  endpoint can report: it is the one the user can fix, by rewriting the pattern.

** What each category is

The table above prices the work; this one says what the work *is*: which query
shape raises a category, and what each engine runs for it. It is the answer to
"what is a =path.resolve=", and to "why does this query carry an =fts.scan=".

Two things it is easy to misread. *The tree cache is neither engine*: it is one
in-memory structure both paths use, so "cache-walked" appears in the SQL column
without meaning the index served the query — the SQL engine does that work in
memory too and hands SQLite only its result, as literals. And *one leaf can raise
two categories*: =tag ->* "music/jazz"= is a =path.resolve= (the path operand to
its metarecord) followed by a =follow.transitive= (the expansion from it), where
=tag ->* (rating > 3)= has no =path.resolve= at all — the sub-query replaces it.

| Category            | Raised by                            | On the SQL path                     | On the index path                 |
|---------------------+--------------------------------------+-------------------------------------+-----------------------------------|
| =path.resolve=      | =->= / =->*= path target, exact node | =TreeCache::resolve_path=, no SQL   | the same lookup, in =QueryRoots=  |
| =bitmap.leaf=       | a comparison / presence leaf         | — (it is the =sql.scan= row)        | union of the operand's buckets    |
| =bitmap.combine=    | =and= / =or= / =not=                 | =INTERSECT= / =UNION= / =EXCEPT=    | Roaring =&=, =\|=, universe =-=   |
| =follow.transitive= | =->*=, ~=>*~, 1-term =osm= path      | cache-walked descendants, =VALUES=  | expansion over children bitmaps   |
| =fts.scan=          | =matches=, =osm= =direct=            | =REGEXP= scan, FTS5-narrowed        | the regex over distinct values    |
| =sql.scan=          | presence, comparison, =same=, =->=   | one =field= scan per =field_name=   | — (it is the =bitmap.leaf= row)   |
| =path.assemble=     | the =:path= aspect, multi-term =osm= | per-node paths, matches as =VALUES= | not served (pre-resolved, or SQL) |
| =sort=              | each =sort= key                      | the =_p{i}= / =_s{i}= CTEs          | one rep per id, then the page     |
| =count=             | =count: true=                        | the chain re-run as =COUNT(*)=      | =matched.len()=, O(1)             |
| =assemble=          | always, for the page's uuids         | =versions_for= + =field_rows_for=   | identical (after the choice)      |

The SQL column, verbatim — this is what a term of each category stands for:

#+BEGIN_SRC sql
  -- sql.scan: one leaf. `(field_name, ...)` is indexed and the value columns are
  -- not, so this reads the rows of that one field name, whatever the predicate.
  SELECT DISTINCT metarecord_uuid AS uuid FROM field
   WHERE field_name = ? AND (<value predicate>)

  -- fts.scan: the same scan under REGEXP. The `id IN (...)` line is present only
  -- when `fts::required_fts_literal` found a mandatory literal of 3+ characters;
  -- without it every row of the field is re-checked. That is the cliff.
  SELECT DISTINCT metarecord_uuid AS uuid FROM field
   WHERE field_name = ?
     AND id IN (SELECT rowid FROM field_text WHERE text MATCH ?)
     AND ((value_type = 'string'   AND value_text REGEXP ?) OR
          (value_type = 'tree_ref' AND value_name REGEXP ?))

  -- follow.transitive / path.assemble: hybrid. The forest work happens in the
  -- tree cache and only its result reaches SQL, as inline literals.
  SELECT column1 AS uuid FROM (VALUES (x'<uuid>'), (x'<uuid>'), ...)

  -- sort, per key: the representative row (min asc / max desc) of the *filtered*
  -- universe, plus `_p{i}` reassembling a tree_ref's whole path.
  _s{i} AS (SELECT uuid, present, grp, vnum, vtext, vblob FROM (
              SELECT _res.uuid, ...,
                     ROW_NUMBER() OVER (PARTITION BY _res.uuid
                                        ORDER BY <grp> <dir>, <num> <dir>, ...) AS rn
                FROM _res LEFT JOIN field ON field.metarecord_uuid = _res.uuid
                                         AND field.field_name = ?
                                         AND field.value_type != 'nothing'
                          LEFT JOIN _p{i} ON <terminal>) WHERE rn = 1)
#+END_SRC

The code calls this a *seed* (=expand_subtrees= grows a frontier from it,
=prepare_indexed_query= resolves "the query's index seeds"), and the category was
named after it. It is =path.resolve= here: only =->= / =->*= is seeded from, and
an exact-node =mfr_path = "/a/b"= resolves a path the very same way and then
traverses nothing.

Two rows read differently on the two engines, and that is where an estimate goes
wrong if the distinction is dropped:

- =fts.scan= *is not the same work on both sides.* SQL re-checks *rows* (=R_f=,
  or =C= behind the trigram pre-filter); the index tests *values* (=V_f=), with
  no FTS involved at all. On a field whose values repeat — a tag, an extension, a
  directory name — those are different orders of magnitude, and only the SQL form
  has the literal/no-literal cliff.
- =path.assemble= *is a walk of the forest, not of the match set.* A =:path=
  comparison or a multi-term =osm= path rebuilds the path of every node of the
  field before testing any of them, on either engine. It has no row in the cost
  table yet (see [[*Open questions]]).

** Totals

: relative = Σ count_i × weight_i
: duration = Σ count_i × constant_i

=weight_i= is a fixed, machine-independent number shipped with the daemon, so
=relative= is comparable across machines and across versions of the same
repository. =duration= is =relative= priced with the local constants, and is
reported as a *band*, never a figure: a user reads "1.5 s" as a promise.

* Which engine runs it

=engine= is the first thing the response says, and it does not report a
preference: the daemon *always* tries the bitmap index, and the SQL engine is
its fallback (=routes::run_query_filter=). "Both are possible" is therefore not
a decision point — the index wins whenever it can answer, and what explain has
to describe is the outcome of a three-step rule.

1. *Preparation*, engine-independent (=prepare_indexed_query=): the path seeds
   are resolved through the tree cache, and some text leaves are rewritten to
   the uuid set they match.
2. *The index is tried* on the prepared query. Every IR variant is handled
   there; what is left to SQL is a property of an *operand* — an unresolved
   path, a pattern the index cannot compile, a comparison the encoding cannot
   answer — never of a node type.
3. *A coverage gap falls back*, and only a coverage gap: the query re-runs on
   the SQL engine, from the *original* query (the un-prepared one). A *state*
   gap — an accelerator not in the shape a serving repository guarantees — is a
   =500=, never a silent fallback to an engine that would answer anyway.

The choice is a function of the query shape alone: the =count= flag does not
change the preparation, precisely so that page 1 and page 2 cannot land on
different engines and reject each other's cursor. Explain's answer is stable for
a whole paginated session.

** Why not one compiler over three providers

The natural shape — one compiler routing each *operation* to the provider that
serves it best — is not what runs, and explain describes what runs. The two
engines are whole-query: the index is tried on the entire query, and a single
operand it cannot serve sends the *entire* query to SQL, which re-plans it from
scratch.

Per-operation routing does exist, but only in the preparation and only in one
direction: a path operand is resolved on the forest before either engine starts,
and a text leaf the bitmaps cannot serve is evaluated on SQLite and injected back
as a =uuid_in= set. The currency that makes that possible — a uuid set is both a
bitmap and a =VALUES= list — is already what a real planner would need. What is
missing is a cost model to choose with, which is this document, and the
willingness to compose the two engines *both* ways: a bitmap result has never
been fed into a SQL chain.

So: three providers, two engines, one ad-hoc bridge in between. Generalising the
bridge is the adaptive planner deferred in
[[file:spec-indexing.org][spec-indexing]], and not a change this endpoint may
make on its own ([[*Non-goals]]). What this document can do for it is price by
*provider* rather than by engine — every category names one system's work — so
the model survives a planner that stops choosing an engine per query and starts
choosing a provider per node. Only =engine= and =fallback[]= would then be
replaced, by a per-node attribution.

** What forces the SQL path

Each row is one =Unsupported= a leaf can raise; =fallback[]= reports it verbatim,
with the address of the leaf that raised it.

| Operand / shape                           | Reported as                          | Why the index defers                              |
|-------------------------------------------+--------------------------------------+---------------------------------------------------|
| the =:parent= aspect, anywhere            | ="the ':parent' aspect"=             | the parent uuid lives in the tree cache           |
| the =:path= aspect, anywhere              | ="the ':path' aspect"=               | idem for the assembled path                       |
| a field seen only through =Nothing=       | ="... field with no indexed values"= | no value partition; empty would be a wrong answer |
| a shape SQL answers with a =400= (below)  | the matching message                 | the rejection has one author, and it is SQL       |
| a multi-term =osm= path, not pre-resolved | ="multi-term osm path"=              | ordered matching runs on assembled paths          |
| an unresolved path target / exact node    | ="path-target follows"=              | only when the caller skipped the preparation      |
| a cursor from another (query, sort)       | ="cursor does not match ..."=        | SQL then rejects it on its own encoding           |

The =400= shapes the index hands over rather than answering: an ordered
comparison on a =bool=, on a reference, or on a bare =tree_ref=; =matches= on a
bare =tree_ref=; an =osm= path on a non-=tree_ref= field; an empty =and= / =or=;
a pattern that does not compile. The index could report several of them itself,
and deliberately does not — one query, one author of its error.

The *state* gaps are not in this table on purpose: ="tree_ref sort without a
resident forest"=, or a missing index on a repository that is serving, are daemon
bugs. They are a =500=, and explain reports them as such rather than as a plan.

** What keeps a query on the index

The preparation is what makes a query that *reads* like a fallback shape stay on
the index. It is also why one query can carry both an =fts.scan= and =bitmap.*=
terms: one leaf ran in SQL, the rest of the tree on bitmaps.

| Preparation step                 | Applies to                          | Effect                               |
|----------------------------------+-------------------------------------+--------------------------------------|
| path targets → =QueryRoots.path= | =->= / =->*= with a path target     | a =path.resolve=, not a fallback     |
| exact nodes → =QueryRoots.node=  | =mfr_path = "/a/b"= and its =!==    | idem — "no such node" ≠ "defer"      |
| =resolve_index_leaves=           | =matches=, =osmd=, multi-term =osm= | the leaf becomes an inline =uuid_in= |
| =SortKeys= from the forest       | a =tree_ref= sort key               | the path keys no BSI can hold        |

The third one is conditional, and explain must apply the same condition: the text
leaves are pre-resolved only for a whole-set resolution, or when the query holds
an =osm= path leaf. Elsewhere a =matches= leaf is served by the index's own
in-memory value scan — which is why the two are one category with two counts.

A client reading =engine: "index"= next to a non-empty =fts.scan= term is looking
at exactly this: the query is index-served, and one leaf was paid for in SQL.

* State is reported, never estimated

The shape of a query is predictable. The moment is not, and the moment routinely
dominates:

- =index.refresh= runs on the read path before every query. It is incremental
  (one or two operations) in steady state, but rebuilds fully when HEAD was
  rewritten — which is what =log rollback= / =undo= do — when an operation type
  is not replayable, when the delta exceeds =REBUILD_OVER=, or when tombstones
  have piled up.
- the =wait:conn= / =wait:cache= / =wait:index= waits: the repository connection
  is =locking_mode = EXCLUSIVE=, so a watcher flush in progress is a wait of
  unbounded length.
- the page cache, which no model here can see.

None of these belong in the estimate. They are reported next to it as *observed
state* — how many operations the index is behind HEAD, whether a rebuild is
therefore expected, whether the forest is resident, whether a lock is currently
held — so a client can say "the number below assumes the index does not rebuild
first" instead of being wrong by two orders of magnitude.

* The endpoint

: POST /repos/:repo/query/explain

Body: the same shape as =POST /repos/:repo/query= — =query= (required), plus the
optional =sort=, =limit=, =select=, =count= — so that what is explained is
exactly what would be sent. =verbose= (bool, default =false=) adds the
attribution of each term to the leaves that cause it.

An invalid query is rejected here exactly as it would be by =query= itself:
=validate_query= runs upfront, engine-independently, so explain is also a dry run
of the =400= (a comparison with =nothing=, an ordered comparison on a =bool= or
a reference, =MATCHES= on a =tree_ref= without an aspect, an over-wide
combinator).

#+BEGIN_SRC json
  {
    "engine": "sql",
    "fallback": [
      {"leaf": "mfr_path:parent = \"/music/live\"",
       "at": "and[1]",
       "why": "the ':parent' aspect"}
    ],
    "parameters": {
      "metarecords": 512340,
      "result": {"value": 1830, "estimated": true},
      "page": 100
    },
    "cost": {
      "relative": 61200,
      "duration_ms": {"low": 240, "high": 900, "calibrated": true},
      "terms": [
        {"category": "sql.scan", "count": 512340, "constant_ms": 0.0008,
         "ms": 410, "estimated": false,
         "leaves": ["mfr_path:parent = \"/music/live\""]},
        {"category": "sort", "count": 1830, "constant_ms": 0.002,
         "ms": 4, "estimated": true, "leaves": ["sort mfr_path"]}
      ]
    },
    "state": {
      "index_ops_behind_head": 0,
      "rebuild_expected": false,
      "forest_resident": true
    }
  }
#+END_SRC

=leaves= is present only under =verbose=. =at= is a stable address into the IR
tree (=and[1]=, =or[0].not=), so a GUI can highlight the offending sub-expression
in the query the user typed.

The response is purely additive to the API surface — a new route, no change to
any existing one — so it needs no =core::API_VERSION= bump.

* Calibration

The constants are declared, not discovered, and they live in the daemon
configuration (=~/.config/metafolder/daemon/config.toml=, shipped default in
=crates/daemon/default-config/config.toml=):

#+BEGIN_SRC toml
  [query-cost]
  # milliseconds per unit of the corresponding count
  bit = 0.000002      # per element of a bitmap pass
  row = 0.0008        # per field row scanned or serialised
  regexp = 0.004      # per candidate re-checked
  sort = 0.002        # per sorted element
  path = 0.01         # per path resolved through the forest
#+END_SRC

A missing or malformed value follows the daemon's existing optional-config model
(missing key → default; malformed file → startup error). When the section is
absent the shipped defaults apply and the response reports
=calibrated: false=, so a client knows the duration is generic rather than
measured on this machine.

Refining them from observation is deliberately left out of this increment: it
needs a sampling mechanism this feature would have to own (the slow log is not
it, see [[*Non-goals]]), and the =relative= total — which is machine-independent —
is what a client should gate on anyway.

* Clients

- *GUI*: gates on the answer before running an expensive query, with an explicit
  "run it anyway" control. Any threshold is scaled on the repository's own size
  (=parameters.metarecords=), never on an absolute duration, so a large
  repository does not become unusable by construction.
- *Scripts*: probe once at start-up. A walk that wants a per-question counter
  ([[file:gui-tag-folder-rework.md][gui-tag-folder-rework]]) keeps it when the count is =O(1)= on the index, drops
  it otherwise, and can refuse to run when even the step query is a scan.
- *CLI*: a thin =explain= surface over the same body. Its exact spelling in the
  noun/verb tree is left to the CLI increment.

* Open questions

- *Estimating =K=.* Per-leaf selectivity from the cardinalities is easy and
  crude; nothing in the index records value distributions. The first increment
  should multiply leaf selectivities and mark the result estimated rather than
  pretend to more.
- *=T_n= without walking.* A subtree size is O(subtree) to count unless the tree
  cache keeps sizes at its nodes. Until it does, the =follow.transitive= SQL term
  is an estimate too.
- *Pricing =path.assemble=.* The =:path= aspect and a multi-term =osm= path walk
  the whole forest to rebuild paths before testing them, on either engine. The
  cost table has no row for it, so a query whose only expensive leaf is a path
  comparison is currently under-priced; it needs a count (nodes of the field ×
  average depth) and a constant of its own.
- *Exposing =weight_i=.* Keeping the weights internal makes =relative= a black
  box; publishing them makes them contract. Start internal, publish if a client
  needs to reproduce the arithmetic.
