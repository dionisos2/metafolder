#+TITLE: Metafolder — Query Cost Estimation (=query/explain=)
#+OPTIONS: toc:2 num:t

* Status

*Not implemented.* This is a design document: there is no =query/explain= route
and no cost model in the code. What it describes the daemon *doing* is therefore
a proposal; what it describes the daemon *being* (one engine, three providers,
the preparation) is current, and is specified in
[[file:spec-indexing.org][spec-indexing]] and [[file:spec-query.org][spec-query]].

* Overview

A client cannot tell, before sending a query, whether it will come back in a
millisecond or in a minute. That matters wherever a query sits inside a loop
with a human in it: the tagging scripts ask one question per entry and want a
live counter next to it ([[file:gui-tag-folder-rework.md][gui-tag-folder-rework]]), the GUI opens a panel on
whatever the user typed. Today the only way to find out is to run it.

The obvious fix — have the daemon *refuse* the query shapes it cannot serve from
the bitmap index, behind an "extended" flag — is the wrong one. The set of
shapes the index declines is an implementation detail of the accelerator, and it
is *meant* to move: the =:parent= aspect has just been taken out of it, the
adaptive planner ([[file:spec-indexing.org][spec-indexing]]) will change it
again. Freezing it into user-visible
surface turns every improvement of the index into a contract change, and the
list is not even the right predicate: "not served by the index" is not the same
as "slow" — and since the index is now the only thing that serves a filter
([[file:spec-indexing.org][spec-indexing]] "No operand runs in SQL"), a shape it
declines is a =500=, not a slow answer. What is left to describe is *cost*, and
an index-served query over a large repository can cost a great deal.

So the daemon **describes** instead of refusing, and the client decides:

: POST /repos/:repo/query/explain

answers, *without running the query*, what the work decomposes into — which
provider does which part, and how much of it — and, as an indication rather than
a promise, how long it should take. A client then drops its counter, warns, or
refuses to run, on its own terms.

** Non-goals

- *Not a profiler and not a metrics system.* No aggregates, no percentiles.
- *Unrelated to the slow-operation log* ([[file:spec-slow-log.org][spec-slow-log]]). That log is a debugging
  artefact: threshold-based, persistent, and it also records GUI-side time. It
  is not an input to this feature and this feature does not write to it.
- *No promise of a duration.* The estimate is a band derived from declared
  constants (see [[*Calibration]]), and it is explicitly marked as such.
- *Not a planner.* Explain describes the work the daemon will actually do. It
  chooses nothing — though its cost model is the piece the adaptive planner
  will need, which is why the two must share it (see [[*Where the model is
  computed]]).

* Where the model is computed

The symbolic cost is built **while the query is prepared and classified**, as a
by-product of work that would run anyway — not by a second traversal written for
explain. (Nothing is "compiled" any more: there is no SQL to build, only the
preparation and the index's own walk of the IR.)

This is a hard constraint, not a preference. Supportedness is currently
discovered *by evaluating*: the =Unsupported= comes out of =index::eval=. An
explain that re-derives it in a parallel classifier is two implementations of one
decision, which is the shape that has already produced real bugs in this project.
So:

- the leaf-supportedness decision is extracted as a **pure function** of
  =(query leaf, index metadata, caller-resolved seeds)=, called by both
  =index::eval= and explain — it no longer decides *where* a leaf runs, only
  whether the daemon can serve it at all, but it is still one decision and must
  stay one implementation;
- each node is annotated with its cost term by the code that would do its work,
  not by a parallel classifier written for explain;
- explain runs the preparation and the classification, and stops there.

It is *not* computed in the DSL parser. The parser lives in =core= and produces
the IR; it knows nothing about the repository, and every term of the model needs
cardinalities. The cost is a property of (IR × data), one step after the parse.

** Fast by construction

Explain must never do the work it describes. Concretely it may not evaluate a
predicate, may not run a text scan (it *reports* that one is needed), and may
not walk the forest — path and node seeds resolve through the resident tree cache
like any query preparation, which is a hash lookup. Note that this rules out
pre-resolving a =:path= leaf, which the real preparation *does* do (it walks the
forest): explain reports the walk as a =path.assemble= term instead of
performing it.

Its bound is =O(query nodes) + O(path operands)=, independent of the repository
size. A client may call it before every query.

* Parameters

Every term of the model is a count expressed in these, all of which the index
already knows in O(1) unless stated otherwise.

| Symbol | Meaning                                              | Known                          |
|--------+------------------------------------------------------+--------------------------------|
| =M=    | metarecords in the repository (index universe)       | exact                          |
| =R_f=  | rows carrying field =f= (=present= ∪ =absent=)       | exact                          |
| =V_f=  | distinct values of field =f= (encoding buckets)      | exact                          |
| =K=    | metarecords the query matches                        | *estimated* from selectivities |
| =N=    | rows returned (=limit=, else =K=)                    | exact once =K= is estimated    |
| =T_n=  | size of the subtree at node =n=                      | from the resident forest       |
| =D=    | depth of the forest (bounded at 1000)                | exact                          |

=K= is the one the daemon cannot know without doing the work. It is reported as
an estimate, and every term that depends on it inherits that flag — a client
that needs a hard answer reads the terms that do not.

* Three providers, one engine

A query is served by three resident systems, and naming them is what makes the
table below readable — each category is one system's work.

| Provider                       | Holds                                    | Executes                                        |
|--------------------------------+------------------------------------------+-------------------------------------------------|
| the forest (=tree_cache=)      | the TreeRef trees: path ↔ node, children | =path.resolve=, =path.assemble=, tree sort keys |
| the bitmaps (=index/=)         | the per-field roaring / BSI encodings    | =bitmap.leaf=, =bitmap.combine=, =sort=, =count= |
| SQLite (=field=)               | the authoritative rows                   | =assemble= — and nothing else                   |

Only one of them *evaluates a filter*: the bitmaps. The forest answers the two
leaves no bitmap can hold (the =:path= aspect, an order-sensitive =osm= path) by
rewriting each into the uuid set it matches, before evaluation, and resolves the
path seeds and the =tree_ref= sort keys. SQLite is asked for rows *by uuid*, once
the answer is known: it holds the authoritative data but takes no part in
deciding what matches ([[file:spec-indexing.org][spec-indexing]] "No operand
runs in SQL").

This is why the model prices by *provider*: the cost of a query is which of the
three does how much work, and that is a property of the query's shape rather
than of a routing decision.

* The cost table

One row per category. =count= is the contract: it is derived from the query and
the parameters above and does not depend on the machine. =constant= is
calibration ([[*Calibration]]).

| Category            | Count                              | What runs                         | Constant  |
|---------------------+------------------------------------+-----------------------------------+-----------|
| =path.resolve=      | one per path / exact-node operand  | forest lookup, O(1)               | =t_path=  |
| =bitmap.leaf=       | =R_f= (equality) / =V_f= (ordered) | bucket union                      | =t_bit=   |
| =bitmap.combine=    | Σ operand cardinalities            | AND/OR/NOT over containers        | =t_bit=   |
| =follow.transitive= | =D= expansions over =T_n= bits     | iterative bitmap expansion        | =t_bit=   |
| =text.scan=         | =V_f=                              | the regex over distinct values    | =t_regexp= |
| =path.assemble=     | nodes of the field × average depth | one walk of the resident forest   | =t_path=  |
| =sort=              | =K= reps + =K log K=               | BSI / store representatives       | =t_sort=  |
| =count=             | 0                                  | O(1) from the result bitmap       | —         |
| =assemble=          | =N= × selected fields              | row read + serialisation (SQLite) | =t_row=   |

Three of these rows are the ones that surprise people, and they are the reason
the table exists rather than a single number:

- *Bitmap work is not O(M).* A Roaring =AND= costs the cardinality of the
  containers it touches. A selective query is cheap, and a model that prices
  every bitmap pass at =M= would say the opposite.
- *A text predicate costs values, not rows.* The regex is compiled once and run
  over the field's *distinct* values (=V_f=), not over its rows (=R_f=) — and on
  a field whose values repeat (a tag, an extension, a directory name) those are
  different orders of magnitude. (The oracle, which scans rows, is where the
  =R_f= figure still means something: =tests/index_oracle.rs= only asserts the
  *answer*, never the cost.)
- *=path.assemble= is a walk of the forest, not of the match set.* A =:path=
  comparison or an order-sensitive =osm= path rebuilds the path of every node of
  the field before testing any of them, and it happens in the *preparation*,
  before a single bitmap is touched. It is the one term that can dominate a
  query whose every other leaf is O(1).

** What each category is

The table above prices the work; this one says what the work *is*: which query
shape raises a category, and which provider runs it. It is the answer to "what is
a =path.resolve=", and to "why does this query carry a =text.scan=".

One thing it is easy to misread: *one leaf can raise two categories*.
=tag ->* "music/jazz"= is a =path.resolve= (the path operand to its metarecord)
followed by a =follow.transitive= (the expansion from it), where
=tag ->* (rating > 3)= has no =path.resolve= at all — the sub-query replaces it.

| Category            | Raised by                               | Provider | What runs                                     |
|---------------------+-----------------------------------------+----------+-----------------------------------------------|
| =path.resolve=      | =->= / =->*= path target, exact node    | forest   | =TreeCache::resolve_path=, into =QueryRoots=  |
| =bitmap.leaf=       | a comparison / presence leaf, =:parent= | bitmaps  | union of the operand's buckets                |
| =bitmap.combine=    | =and= / =or= / =not=                    | bitmaps  | Roaring =&=, =\|=, universe =-=               |
| =follow.transitive= | =->*=, ~=>*~, 1-term =osm= path         | bitmaps  | expansion over the children bitmaps           |
| =text.scan=         | =matches=, =osm= =direct=               | bitmaps  | the regex over the field's distinct values    |
| =path.assemble=     | the =:path= aspect, order-sensitive =osm= | forest | one walk, then the leaf becomes a =uuid_in=   |
| =sort=              | each =sort= key                         | bitmaps  | one rep per id, then the page (tree keys: forest) |
| =count=             | =count: true=                           | bitmaps  | =matched.len()=, O(1)                         |
| =assemble=          | always, for the page's uuids            | SQLite   | =versions_for= + =field_rows_for=             |

Only the last row reaches SQLite, and it is addressed by uuid:

#+BEGIN_SRC sql
  -- assemble: the page's rows, for uuids already decided.
  SELECT metarecord_uuid, field_name, value_type, ... FROM field
   WHERE metarecord_uuid IN (…)
#+END_SRC

The relational form of each *filter* category still exists in
=crates/query-oracle=, where it is the equivalence oracle
(=tests/index_oracle.rs=) and not a plan: its =_repo= universe CTE, its per-leaf
=field= scan and its window-function sorts describe what the index is checked
against, never what a request runs. An explain term therefore has no SQL to
quote, which is the point of the model being written per provider.

The code calls a resolved path a *seed* (=expand_subtrees= grows a frontier from
it, =prepare_indexed_query= resolves "the query's index seeds"), and the category
was named after it. It is =path.resolve=: only =->= / =->*= is seeded from, and
an exact-node =mfr_path = "/a/b"= resolves a path the very same way and then
traverses nothing.

** Totals

: relative = Σ count_i × weight_i
: duration = Σ count_i × constant_i

=weight_i= is a fixed, machine-independent number shipped with the daemon, so
=relative= is comparable across machines and across versions of the same
repository. =duration= is =relative= priced with the local constants, and is
reported as a *band*, never a figure: a user reads "1.5 s" as a promise.

* How a query is served

There is one engine, so explain has no routing decision to report — no =engine=
field and no =fallback[]=. (An earlier draft of this document carried both, from
the period when the index had a SQL fallback; they went with it. The terms stay,
and their attribution was always per node.) What explain describes is the
outcome of two steps.

1. *Preparation* (=routes::prepare_indexed_query=): the path seeds are resolved
   through the tree cache, and the leaves the bitmaps cannot hold are rewritten
   into the uuid set the forest says they match.
2. *The index evaluates* the prepared query. Every IR variant is handled there —
   the match in =index::eval= is exhaustive on purpose.

The preparation is a function of the query shape alone: the =count= flag does
not change it, precisely so page 1 and page 2 cannot be evaluating different
queries and reject each other's cursor (which is bound to a hash of the
rewritten query). Explain's answer is stable for a whole paginated session.

** What the preparation carries

| Preparation step                     | Applies to                                | Effect                              |
|--------------------------------------+-------------------------------------------+-------------------------------------|
| path targets → =QueryRoots.path=     | =->= / =->*= with a path target           | a =path.resolve=                    |
| exact nodes → =QueryRoots.node=      | =mfr_path = "/a/b"=, =!==, =:parent==     | idem — "no such node" ≠ "unresolved" |
| =forest_query::resolve_path_leaves=  | the =:path= aspect, order-sensitive =osm= | a =path.assemble=; the leaf becomes a =uuid_in= |
| =SortKeys= from the forest           | a =tree_ref= sort key                     | the path keys no BSI can hold       |

The third is where a query's cost can be decided before any bitmap is touched:
the rewrite is unconditional, and it walks the forest. A =matches= or an =osm=
=direct= leaf needs no rewrite at all — the index runs the regex over the
field's distinct values — which is why those raise a =text.scan= and not a
=path.assemble=.

** What the index can still decline

A shape the index declines is a *daemon bug*, answered =500=
([[file:spec-indexing.org][spec-indexing]] "Three kinds of gap"), so none of these
is a plan explain can describe — it reports them as the error they are. They are
listed because explain must not *invent* a term for them:

| Operand / shape                           | Reported as                          | Why it cannot happen through the API                |
|-------------------------------------------+--------------------------------------+-----------------------------------------------------|
| a =:path= leaf the forest could not answer | ="the ':path' aspect"=              | the forest is resident on any serving repository    |
| an order-sensitive =osm= path, not rewritten | ="multi-term osm path"=            | idem — the preparation rewrites it                  |
| an unresolved path target / exact node    | ="path-target follows"=              | only if a caller skipped the preparation            |
| a =tree_ref= sort with no resident forest | ="tree_ref sort without a resident forest"= | a state gap, same reason                     |

The one gap that is *not* a bug is a cursor from another (query, sort): that is
the client's own input, answered =400=.

The type-dependent and IR-level =400=\s are raised before any of this, by
=query_validate= (spec-query "Comparison validity", "Field aspects"): an ordered
comparison on a =bool=, on a reference, or on a bare =tree_ref=; =matches= on a
bare =tree_ref=; an ordered operator or =matches= under =:parent=, which reads a
uuid; an =osm= path on a non-=tree_ref= field; an empty =and= / =or=; a pattern
that does not compile. Explain runs the same pass, so it is a dry run of those
=400=\s too — one query, one author of its error.

* State is reported, never estimated

The shape of a query is predictable. The moment is not, and the moment routinely
dominates:

- =index.refresh= runs on the read path before every query. It is incremental
  (one or two operations) in steady state, but rebuilds fully when HEAD was
  rewritten — which is what =log rollback= / =undo= do — when an operation type
  is not replayable, when the delta exceeds =REBUILD_OVER=, or when tombstones
  have piled up.
- the =wait:conn= / =wait:cache= / =wait:index= waits: the repository connection
  is =locking_mode = EXCLUSIVE=, so a watcher flush in progress is a wait of
  unbounded length.
- the page cache, which no model here can see.

None of these belong in the estimate. They are reported next to it as *observed
state* — how many operations the index is behind HEAD, whether a rebuild is
therefore expected, whether the forest is resident, whether a lock is currently
held — so a client can say "the number below assumes the index does not rebuild
first" instead of being wrong by two orders of magnitude.

* The endpoint

: POST /repos/:repo/query/explain

Body: the same shape as =POST /repos/:repo/query= — =query= (required), plus the
optional =sort=, =limit=, =select=, =count= — so that what is explained is
exactly what would be sent. =verbose= (bool, default =false=) adds the
attribution of each term to the leaves that cause it.

An invalid query is rejected here exactly as it would be by =query= itself:
=query_validate= runs upfront, before anything evaluates the query, so explain
is also a dry run of the =400= (a comparison with =nothing=, an ordered
comparison on a =bool= or a reference, =MATCHES= on a =tree_ref= without an
aspect, an over-wide combinator).

#+BEGIN_SRC json
  {
    "parameters": {
      "metarecords": 512340,
      "result": {"value": 1830, "estimated": true},
      "page": 100
    },
    "cost": {
      "relative": 61200,
      "duration_ms": {"low": 240, "high": 900, "calibrated": true},
      "terms": [
        {"category": "path.assemble", "count": 512340, "constant_ms": 0.01,
         "ms": 410, "estimated": false,
         "leaves": ["mfr_path:path MATCHES \"live$\""]},
        {"category": "sort", "count": 1830, "constant_ms": 0.002,
         "ms": 4, "estimated": true, "leaves": ["sort mfr_path"]}
      ]
    },
    "state": {
      "index_ops_behind_head": 0,
      "rebuild_expected": false,
      "forest_resident": true
    }
  }
#+END_SRC

=leaves= is present only under =verbose=. =at= is a stable address into the IR
tree (=and[1]=, =or[0].not=), so a GUI can highlight the offending sub-expression
in the query the user typed.

The response is purely additive to the API surface — a new route, no change to
any existing one — so it needs no =core::API_VERSION= bump.

* Calibration

The constants are declared, not discovered, and they live in the daemon
configuration (=~/.config/metafolder/daemon/config.toml=, shipped default in
=crates/daemon/default-config/config.toml=):

#+BEGIN_SRC toml
  [query-cost]
  # milliseconds per unit of the corresponding count
  bit = 0.000002      # per element of a bitmap pass
  row = 0.0008        # per field row read back and serialised
  regexp = 0.004      # per distinct value tested
  sort = 0.002        # per sorted element
  path = 0.01         # per path resolved through the forest
#+END_SRC

A missing or malformed value follows the daemon's existing optional-config model
(missing key → default; malformed file → startup error). When the section is
absent the shipped defaults apply and the response reports
=calibrated: false=, so a client knows the duration is generic rather than
measured on this machine.

Refining them from observation is deliberately left out of this increment: it
needs a sampling mechanism this feature would have to own (the slow log is not
it, see [[*Non-goals]]), and the =relative= total — which is machine-independent —
is what a client should gate on anyway.

* Clients

- *GUI*: gates on the answer before running an expensive query, with an explicit
  "run it anyway" control. Any threshold is scaled on the repository's own size
  (=parameters.metarecords=), never on an absolute duration, so a large
  repository does not become unusable by construction.
- *Scripts*: probe once at start-up. A walk that wants a per-question counter
  ([[file:gui-tag-folder-rework.md][gui-tag-folder-rework]]) keeps it when the count is =O(1)= on the index, drops
  it otherwise, and can refuse to run when even the step query is a scan.
- *CLI*: a thin =explain= surface over the same body. Its exact spelling in the
  noun/verb tree is left to the CLI increment.

* Open questions

- *Estimating =K=.* Per-leaf selectivity from the cardinalities is easy and
  crude; nothing in the index records value distributions. The first increment
  should multiply leaf selectivities and mark the result estimated rather than
  pretend to more.
- *=T_n= without walking.* A subtree size is O(subtree) to count unless the tree
  cache keeps sizes at its nodes. Until it does, the =follow.transitive= term is
  an estimate too.
- *Counting =path.assemble=.* The category has a row and a constant
  (=t_path=), but its count — nodes of the field × average depth — is not
  something the forest reports in O(1) today. Either the tree cache grows the
  two numbers, or the term is marked estimated like =K=.
- *Exposing =weight_i=.* Keeping the weights internal makes =relative= a black
  box; publishing them makes them contract. Start internal, publish if a client
  needs to reproduce the arithmetic.
