#+TITLE: Metafolder — Trash-bin Specification
#+OPTIONS: toc:2 num:t

* Overview

A single trash-bin per repository, shared by *every* metafolder file operation
that would overwrite or delete a file — rollback today (see
[[file:spec-event-log.org][spec-event-log.org]] "Filesystem coordination"), cross-repo sync tomorrow (see
[[file:spec-sync.org][spec-sync.org]], v2). It guarantees no byte is ever lost: the destroyed content is
set aside, and the user decides later whether to bring it back or discard it.

The trash-bin is filesystem state managed *entirely by the clients* — the CLI
and the GUI (the daemon never touches files); it lives under =internal/=,
excluded from tracking like =db.sqlite=. The daemon's only involvement is
exposing the repo's =internal_dir= in =GET /repos/:repo= so a client can locate
it without guessing the =.metafolder= location. The shared filesystem layer
(=TrashDir=: locate, move, list, restore, prune) lives in =crates/core=
(=metafolder_core::trash=); each client adds its own glue (resolving a
metarecord to a path, re-linking after a restore).

Restoration is always an explicit act (=mf trash restore=), never automatic: an
operation only ever *moves victims into* the trash, and the log/navigation are
never coupled to it.

* Layout

: .metafolder/internal/trash/<id>        -- the trashed file's bytes (the blob)
: .metafolder/internal/trash/<id>.json    -- the entry's manifest

=<id>= is a fresh 32-char lowercase hex UUID (collision-free; the blob carries
no extension — the original name is in the manifest). The blob is written
*before* its manifest, so a manifest on disk always implies its blob is present;
=list= enumerates =*.json=. One directory, flat, no per-reason subdirectories.

The manifest (=<id>.json=) records everything =restore= and =prune= need:

#+BEGIN_SRC json
{
  "id":            "<32-hex>",
  "original_path": "/abs/path/the/file/was/at",
  "original_name": "basename.ext",
  "trashed_at":    1733500000000,          // unix-ms — prune -d, and list order
  "size":          12345,                   // bytes — prune -s
  "reason":        "rollback",              // rollback | sync | manual
  "revision":      101,                     // op id that trashed it, or null
  "metarecord":    "<32-hex-uuid>"          // the record it belonged to, or null
}
#+END_SRC

=reason=/=revision=/=metarecord= are provenance: they let the user correlate a
trashed version with the operation that displaced it (e.g. which rollback step),
but restoration itself is driven purely by =original_path=.

* Moving into and out of the trash

Trashing *moves* the path into =internal/trash/= (a rename, falling back to
copy-then-delete when the trash sits on a different filesystem than the file —
possible with an external =.metafolder= location; the fallback carries the
modification time over, which =fs::copy= does not, so a cross-device round-trip
keeps the file's timestamp). A file, a symlink, or a whole *directory* can be
trashed: a directory is moved as one blob (which is itself a directory), with
its subtree intact, and its recorded =size= is the recursive total; a symlink is
trashed as the link itself (the rename moves the link, not its target; its size
is the link's). Restoring moves the blob back to =original_path= (or an explicit
target) and deletes the entry. Trashing a directory naturally cascades: its
tracked children disappear too, and the watcher records that like any other
removal; restoring the directory brings the whole subtree back.

Trashing itself never touches the data model — that stays the watcher's job
(and where watching is off, the frozen metadata is left alone). *Restoring*,
however, re-links the entry's recorded =metarecord= authoritatively: if that
metarecord is *orphaned* (its =mfr_path= is =Nothing= or absent — the state a
deletion leaves), the CLI writes its =mfr_path= to the restored location (a
=force= write, since =mfr_path= is reserved).

Ordering matters, and is the crux of correctness. The restore target is always
*free* (an occupied one is refused), so the re-link is always done *before* the
file is moved into place: the metarecord then already claims the path, so when
the watcher sees the arrival it finds the path tracked (=resolve= → refresh) and
neither fingerprint-searches nor creates a metarecord. This is what makes restore
reliable — a freshly tracked file has *no stored full hash*, so the watcher's
fingerprint search cannot re-home it and would otherwise =create= a *duplicate*.
(If the move then fails, the metarecord points at a not-yet-present file until
the restore is retried — no content is lost, the blob stays in the trash.)

The re-link is a *no-op when the metarecord still carries an =mfr_path=* (a
watch-off repo never cleared it — nothing to fix, and the frozen metadata is
respected), and it is skipped with a note when the restored path lies outside
the repo or its parent directory is untracked. The restore itself is never
blocked by a re-link failure.

Restore never overwrites a file: an occupied target is refused outright (no
=--force=) — *except* a directory blob onto an existing directory, which is
*merged* (contents the target lacks are moved in, shared subdirectories merge
recursively; a leaf that would overwrite an existing file refuses the whole
restore up front). To bring a file back over an occupied path, move the occupant
aside first.

* Rollback auto-restore

A deletion that went through the trash is *fully reversible by rollback*: the
log records a =file_deleted=, but the bytes survive in the trash, so rollback
can put them back. This closes the loop with =mf trash -f= (and, in v2, with
sync overwrites recorded as =file_modified=).

The correlation is by *metarecord version*, not by timestamp — the version is
exactly what a rollback restores, so it pins the historical state
unambiguously even when a record has been trashed several times:

- When =mf trash -f= trashes a path, it records the metarecord's current
  =version= on the entry (the "file present" version, before the watcher
  records the deletion, whose =entity_version_before= equals it).
- During rollback, for a =file_deleted=/=file_modified= inverse step, the CLI
  looks for a trash entry whose =metarecord= and =version= equal the op's
  =entity_uuid= and =entity_version_before= (see
  [[file:spec-event-log.org][spec-event-log.org]] "Filesystem coordination"). On a match it moves the file
  back and lets the daemon apply the real inverse (=step {}=), which restores
  =mfr_path= and the version to match. With no match the step is skipped as
  before, plus a =mf trash restore= hint.

The restored file's arrival is buffered by the rollback lock and, once the
navigation's inverse has re-established =mfr_path=, reconciled as a plain
refresh — no duplicate, and no reliance on a fingerprint (a freshly tracked
file has no stored full hash). A concurrent write to the metarecord between the
trash and the watcher's =file_deleted= would shift =entity_version_before= and
make the match miss — safe: it degrades to the skip + hint, never a wrong
restore.

* Retention

The trash grows without bound until pruned; pruning is the retention mechanism
(=mf trash prune=, see [[*=mf trash=]]), by age (=-d=), by total size
(oldest-first until under budget, =-s=), or wholesale (=--all=). There is no
automatic expiry — a lost byte is worse than a full disk the user can see and
clear.

* =mf trash=

Manages the repository's trash-bin. Purely a CLI filesystem operation — the
trash location comes from =GET /repos/:repo= (=internal_dir=); no daemon
endpoint is involved. This is not v2 (unlike cross-repo sync): rollback already
routes overwrites through the trash.

#+BEGIN_SRC
mf trash [list]
mf trash -f <path>
mf trash restore <id>
mf trash prune (-s <size> | -d <duration> | --all) [--dry-run]
#+END_SRC

=list= (the group default, so =mf trash= ≡ =mf trash list=) prints one row per
entry — id, original path (a trailing =/= marks a directory), size, age (from
=trashed_at=), reason — newest first.

=-f=/=--file <path>= manually trashes a *tracked* file or directory — a safe
delete (=reason=manual=, the entry records the path's metarecord). It errors,
*before moving anything*, if the daemon is unreachable or the path has no
metarecord (the CLI resolves =path -> mfr_path= metarecord through =POST …/query=
with the exact-path idiom =mfr_path -> "/parent" AND mfr_path = "name"=, using
the =root= from =GET /repos/:repo=). A directory is trashed whole, its subtree
included; in a watched repo the ensuing disappearance(s) are recorded as
=file_deleted= like any other, and =mf trash restore= brings the subtree back.
=-f= cannot be combined with a subcommand.

The metadata update is the watcher's job, and =mf trash -f= deliberately does
*not* do it itself: a tracked file is, by construction, watched (=mf_watch= is
inherited down the =mfr_path= tree), so the watcher records the deletion. Where
watching has been turned *off* — which is done precisely to freeze the
metarecords against external file movements — the metadata is intentionally left
untouched (=mfr_path= stays as recorded); a later reconcile or re-enabled watch
picks it up. Either way the file's bytes are safe in the trash.

=restore <id>= moves the blob back to its =original_path= and removes the entry.
An occupied target is refused — never overwritten — except a directory that
*merges* into an existing directory (move a file occupant aside first). Because
the target is therefore free (or a mergeable directory), the associated
metarecords are re-linked *before* the move (see above), making restore
deterministic; in a watched repo the arrival is then reconciled as a plain
refresh, and nothing is written to the event log.

=prune= permanently deletes entries; exactly one selector is required:
- =-s=/=--size <size>= — delete oldest first until the total is at/under the
  budget. =<size>= is a human size: a bare integer (bytes) or a number with a
  =k=/=m=/=g=/=t= suffix (base 1024, case-insensitive; a trailing =b= is
  allowed, e.g. =100mb=, =1g=, =512k=).
- =-d=/=--older-than <duration>= — delete entries older than the duration.
  =<duration>= is =<n><unit>= with unit =y= (365 d), =w=, =d=, =h=, =m= (minute),
  =s= (e.g. =1y=, =30d=, =12h=).
- =--all= — empty the trash (also sweeping any orphan blobs — manifest-less
  files a failed manifest write could leave — which the other selectors, keyed
  on the manifest, never see).
=--dry-run= lists what would be removed and reclaimed without deleting.

* GUI

The GUI exposes the same trash-bin (spec-gui.org), driving the shared
=metafolder_core::trash= layer through Tauri commands (=trash_list=,
=trash_selected_metarecord=, =trash_restore=, =trash_remove=, =trash_empty=);
like the CLI it locates =internal_dir=/=root= through =GET /repos/:repo= and
re-links a restored metarecord through the daemon — there is still *no daemon
trash endpoint*.

- *Send to the trash* — the =metarecord:trash= command (a shell builtin) sends
  the workspace's =selected_metarecord='s file to the trash (=reason=manual=,
  recording the metarecord and its current =version=, exactly like =mf trash
  -f=). It is bound to =Delete= in every panel that carries a selection
  (=metarecord-list=, =metarecord-detail=, =file-manager=, =treeref=,
  =ref-list=) and offered as a *Trash file* context-menu item in the metarecord
  panels. Because =Delete= is a bare key, the action is *confirmed* even though
  it is reversible. The metadata update is still the watcher's job (as for =mf
  trash -f=): the file's bytes are safe regardless.

- *trash panel* (=panel:set-type trash=, default =s b=) — lists the entries
  (name, size, age, reason, path), newest first, and offers *Restore* (=Enter=;
  re-links the metarecord before moving the file back, as the CLI does),
  *Delete* one entry permanently (=Delete=), and *Empty trash* — the two
  destructive actions confirmed. Prune by size/age is CLI-only.
