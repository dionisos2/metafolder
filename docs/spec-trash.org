#+TITLE: Metafolder — Trash-bin Specification
#+OPTIONS: toc:2 num:t

* Overview

A single trash-bin per repository, shared by *every* metafolder file operation
that would overwrite or delete a file — rollback today (see
[[file:spec-event-log.org][spec-event-log.org]] "Filesystem coordination"), cross-repo sync tomorrow (see
[[file:spec-sync.org][spec-sync.org]], v2). It guarantees no byte is ever lost: the destroyed content is
set aside, and the user decides later whether to bring it back or discard it.

*The trash takes the metarecord with the bytes.* Trashing captures the
metarecord — and, for a directory, its whole subtree — into the entry, and then
*deletes it from the repository*. Restoring puts it back at its original UUID.

That is a deliberate reversal of an earlier design in which trashing left the
metarecord behind, orphaned (=mfr_path = Nothing=), for the watcher to record.
Two things were wrong with it. The orphan polluted every query, count and
listing for as long as the entry survived; and =mf orphan detect= /
=orphan:delete= would destroy it — presented to the user as a safe cleanup —
while the bytes were still sitting in the trash, recoverable. The metadata was
the one part of the promise the trash did not keep.

So the invariant is now: **a metarecord dies with its bytes, never before.**
=prune= is the single point of destruction, and "orphan" recovers its strict
meaning — a file that went away without being asked to (see
[[file:spec-file-tracking.org][spec-file-tracking.org]] "Orphan scan").

The trash-bin is filesystem state managed by the clients — the CLI and the GUI;
it lives under =internal/=, excluded from tracking like =db.sqlite=. The daemon
still never touches a file. It now owns exactly one half of the operation, the
half that is its own: deleting the metarecords, through a single endpoint
([[*Deleting the metarecords]]). The shared layer (=TrashDir=: locate, move,
list, restore, prune, capture, recreate) lives in =crates/core=
(=metafolder_core::trash=); each client adds its own glue.

Restoring the *bytes* is always an explicit act — =mf trash restore=, or a
rollback that walks back over the trashing. Nothing restores them on its own.

* Layout

: .metafolder/internal/trash/<id>          -- the trashed file's bytes (the blob)
: .metafolder/internal/trash/index.sqlite  -- the entry index (dedicated database)

=<id>= is a fresh 32-char lowercase hex UUID (collision-free; the blob carries
no extension — the original name lives in the index). One directory, flat, no
per-reason subdirectories. Everything under it except =index.sqlite= (and its
journal) is a blob.

The index is a small **dedicated** SQLite database (not the daemon's
exclusively-locked =db.sqlite=): the trash is pure client state (CLI and GUI),
so this DB is opened directly by them, short-lived, one connection per
operation. SQLite buys locking against concurrent =mf trash=, atomic writes,
indexed lookup, corruption resistance, and queryable prune (by size/age without
reading every entry) — cheap to adopt pre-distribution. Two tables:

#+BEGIN_SRC sql
CREATE TABLE entry (
  id TEXT PRIMARY KEY,            -- <32-hex>; the blob file name
  original_path TEXT,            -- absolute path the file was at (restore target)
  original_name TEXT,            -- basename, for display
  trashed_at INTEGER,            -- unix-ms — prune -d and list order
  size INTEGER,                  -- bytes (recursive total for a directory) — prune -s
  is_dir INTEGER,                -- the blob is a directory (a whole subtree)
  reason TEXT,                   -- rollback | sync | manual
  revision INTEGER,              -- op id that trashed it, or NULL
  metarecord TEXT,               -- the record it belonged to, or NULL
  version INTEGER                -- the record's version when trashed (provenance)
);
CREATE TABLE node (              -- the captured metarecords: one row each
  entry_id TEXT REFERENCES entry(id) ON DELETE CASCADE,
  uuid TEXT, parent TEXT, name TEXT, -- its original mfr_path TreeRef
  fields TEXT,                       -- its fields, as JSON (NULL: pre-capture entry)
  trashed INTEGER                    -- 1: deleted with the entry; 0: an ancestor
);
#+END_SRC

=fields= holds the metarecord's fields exactly as the daemon renders them and
exactly as they will be sent back to =POST …/metarecords/bulk=. It is *JSON*,
which the rest of the system deliberately avoids: =field= and =op_snapshot=
decompose a value into typed columns because the daemon *queries* those columns.
Nothing queries these. They leave the daemon as JSON and return to it as JSON,
so decomposing them would be work in the service of no question.

=trashed= is what keeps a restore from resurrecting more than it should. The
capture reaches past the trashed subtree: it also walks *up*, recording the
ancestors, so that a restore can rebuild the chain if those were orphaned in the
meantime. Those ancestors are not being trashed — the parent directory stays —
so they are captured with =trashed = 0=, are never deleted, and are never
recreated. Only =trashed = 1= nodes are the entry's own.

The index has no schema-version mechanism: =open()= issues =CREATE TABLE IF NOT
EXISTS= and nothing else. Columns added later therefore need an explicit
=PRAGMA table_info= probe followed by =ALTER TABLE=, in the shape the daemon's
own migrations use. A database written before =fields= existed reads it as
=NULL=, which is exactly the "nothing captured" case a restore must already
handle.

The blob is moved *before* the row is written, so a row always implies its blob;
an index failure only ever leaks an unindexed blob, swept by =prune --all=.
=reason=/=revision=/=version= are provenance: they let the user see which
operation displaced a given version, but nothing routes on them. =metarecord= is
different — it is the *key* a rollback uses to find the entry holding a given
metarecord ([[*Finding the entry]]). Where the bytes go back is not their
business either: that is =original_path= alone. The =node= rows are what let a
restore rebuild the *whole* trashed subtree ([[*Restoring]]).

* Moving into and out of the trash

Trashing *moves* the path into =internal/trash/= (a rename, falling back to
copy-then-delete when the trash sits on a different filesystem than the file —
possible with an external =.metafolder= location; the fallback carries the
modification time over, which =fs::copy= does not, so a cross-device round-trip
keeps the file's timestamp). A file, a symlink, or a whole *directory* can be
trashed: a directory is moved as one blob (which is itself a directory), with
its subtree intact, and its recorded =size= is the recursive total; a symlink is
trashed as the link itself (the rename moves the link, not its target; its size
is the link's). Restoring moves the blob back to =original_path= (or an explicit
target) and deletes the entry. Trashing a directory naturally cascades: the
whole subtree goes with it, metarecords included; restoring the directory brings
all of it back.

** What trashing does, in order

Trashing is three steps, and the order is not free:

1. *Capture.* The client reads the target metarecord, walks up to record its
   ancestors, and walks down the =mfr_path= forest to record every descendant —
   each with its fields ([[*Layout]]). All of it through the daemon's ordinary
   read endpoints, before anything is touched.
2. *Delete the metarecords* — the trashed set only, never the ancestors — in one
   revision ([[*Deleting the metarecords]]).
3. *Move the bytes* into =internal/trash/=.

Deleting before moving is what keeps the watcher out of it. When the file
disappears, the watcher looks the path up in the forest, finds nothing there any
more, and has nothing to orphan: the removal is a no-op. The reverse order would
have the watcher orphan the records in the gap between the two steps, writing a
revision that says something that is about to stop being true.

The capture must come first for the obvious reason — once the metarecords are
gone there is nothing left to read.

A trashing is *one revision*, so it is one thing to undo
([[*Undo, rollback and redo]]).

** Deleting the metarecords

: POST /repos/:repo_uuid/metarecords/trash

Body ={"uuids": [...], "force": false}=. Deletes the given metarecords in a
single revision stamped =revision.origin = 'trash'=
([[file:spec-event-log.org][spec-event-log.org]] "Revision origin"). Response:
={"deleted": N}=.

This is the trash-bin's *only* daemon endpoint, and it exists because the
operation has two halves that belong to different owners: the bytes are the
client's business, the data model is the daemon's. Neither reaches into the
other's.

The origin is fixed by *which endpoint was called*, never by a parameter. A
client that could name its own origin could disguise its writes as the daemon's
and make them un-undoable; the stamp has to stay the daemon's word. That is why
this is a separate endpoint rather than a flag on =POST …/query/delete=.

Each deleted metarecord also *leaves its duplicate group*, exactly as orphaning
one does (spec-duplicates "Leaving a group"). Skipping that would leave the
group metarecords counting members that no longer exist.

*** Refusing to break a reference

A metarecord that other metarecords point at cannot be deleted without leaving
those references dangling. The endpoint therefore *refuses* — =409=, nothing
written — when any metarecord in the set is referenced from *outside* the set,
naming the referrers. =force= overrides it.

Only references from outside count. A subtree's own internal references travel
with it and come back together on a restore, so refusing on those would make it
impossible to trash a folder whose files reference each other — which would empty
the guard of its purpose.

The check is served from the index's reverse maps: the repository's =ref= and
=tree_ref= field names come from the field catalogue (a handful), and each one
answers "who points at this set" with one bitmap lookup per target. It is
proportional to the number of reference-typed *fields*, not to the number of
rows — it must never become a scan of the value columns (spec-main, the
=INDEXED BY= invariant).

*Not covered*: =ExternalRef= and =RefBase= values do not populate those reverse
maps, so an inbound reference of either kind is not detected. An =ExternalRef=
comes from another repository, whose sync state lives outside the data model
anyway; the gap is accepted, and named here rather than left to be discovered.

** Restoring

Restoring is the inverse, and it runs in the mirror order: metadata first, bytes
second.

1. *Recreate* every =trashed= node the repository no longer holds, at its
   original UUID and with its captured fields, through
   =POST …/metarecords/bulk= — parent before child, since the forest refuses a
   =TreeRef= whose parent has no row yet (spec-data-model "Bulk creation").
   Recreating carries no version: a version is a hash of the metarecord's
   content, so a metarecord recreated at its UUID with its fields *is* at the
   version it had (spec-data-model "Version").
2. *Re-link* the nodes that still exist. A metarecord that survived the trashing
   — an ancestor, or one the user recreated — keeps its identity; if it is
   orphaned (=mfr_path= absent or =Nothing=), its =mfr_path= is written back to
   the restored location (a =force= write, =mfr_path= being reserved).
3. *Move the blob back* to =original_path=, and consume the entry.

Ordering matters, and is the crux of correctness. The restore target is always
*free* (an occupied one is refused), so the metadata is in place *before* the
file arrives: the path is then tracked, so when the watcher sees the arrival it
finds it (=resolve= → refresh) and neither fingerprint-searches nor creates a
metarecord. This is what makes restore reliable — a freshly tracked file has *no
stored full hash*, so the watcher's fingerprint search could not re-home it and
would =create= a *duplicate* instead. (If the move then fails, the metarecords
point at a not-yet-present file until the restore is retried — no content is
lost, the blob stays in the trash.)

The re-link half is a *no-op when the metarecord still carries an =mfr_path=*,
and it is skipped with a note when the restored path lies outside the repo or its
parent directory is untracked. The restore itself is never blocked by a re-link
failure.

*An entry captured before this design* has no =fields= on its nodes. Nothing can
be recreated from it, so it restores exactly as it used to: re-link what still
exists, and leave the rest to the watcher. No entry is migrated.

That =mfr_path=-still-present state has a second, transient cause in a *watched*
repo: a metarecord the trashing did not delete (an ancestor) whose own removal is
still buffered. The watcher closes the race: a buffered =Remove=/=RenameFrom=
whose path *exists again on disk at flush time* is recognised as an *undone
deletion* (the file was recreated, or a trash→restore round-trip put it back) and
is skipped — the record stays linked and the arrival in the same batch is
reconciled as a plain refresh. This is a general watcher property (any fast
delete→recreate at one path collapses to a refresh, consistent with the
batching-window compaction). See [[file:spec-file-tracking.org][spec-file-tracking.org]] "Event batching".

Restore never overwrites a file: an occupied target is refused outright (no
=--force=) — *except* a directory blob onto an existing directory, which is
*merged* (contents the target lacks are moved in, shared subdirectories merge
recursively; a leaf that would overwrite an existing file refuses the whole
restore up front). To bring a file back over an occupied path, move the occupant
aside first.

* Undo, rollback and redo

A trashing is an ordinary revision the user asked for, so it is *undoable* —
which it was not before. Under the old design the metadata half was the
watcher's =file_deleted=, and undo skips the daemon's own revisions by its first
exclusion rule, so a trashing could not be taken back at all
([[file:spec-event-log.org][spec-event-log.org]] "Undo"). Now the trashing writes
its own revision, and =origin = 'trash'= is deliberately *not* =watcher=: only
=watcher= disqualifies a revision from being undone.

** Two ways back, and what each is for

- =mf trash restore <id>= — the client recreates the metarecords from the
  captured fields and moves the bytes back ([[*Restoring]]).
- *undo / rollback* — the *daemon* recreates the metarecords, by the log's own
  inverse of the =delete_metarecord= operations; the *client* moves the bytes
  back from the trash and consumes the entry.

Each stays in its own domain: the daemon never touches a file, the client never
recreates a metarecord behind the daemon's back. They converge because both end
with the same metarecords at the same UUIDs and the bytes at the original path.

The capture in the entry is *not* redundant with the log, and this is why it has
to exist: **the log is prunable** (=mf log prune=) and the trash promises
durability. Once a trashing has been pruned out of the log there is no inverse
left to apply, and =mf trash restore= is the only way back. It must not depend on
history the user is free to discard.

** Finding the entry

On an inverse step over a =delete_metarecord= written by a trashing, the client
looks for the *live entry that holds that metarecord*. Not by an id recorded on
the operation: after an undo (which consumes the entry) and a redo (which trashes
again, into a fresh entry), a recorded id would name an entry that no longer
exists. There can never be two live entries for one metarecord — after a trashing
the metarecord is gone, so nothing can trash it again until it comes back.

If no entry holds it — the trash was pruned, or the entry was deleted by hand —
the step is skipped: the metadata rewinds and the bytes stay gone, with a note
saying so. A rollback is never blocked by content the user has chosen to discard.

** Redo

The *forward* direction of a trashing is "trash this file again": the bytes move
back into the trash, into a **new** entry, and the metarecords are deleted again.
Re-applying only the metadata half would delete the metarecords and leave the
file in place, where the watcher would immediately track it afresh — a duplicate
of the thing that was just undone.

* Retention

The trash grows without bound until pruned; pruning is the retention mechanism
(=mf trash prune=, see [[*=mf trash=]]), by age (=-d=), by total size
(oldest-first until under budget, =-s=), or wholesale (=--all=). There is no
automatic expiry — a lost byte is worse than a full disk the user can see and
clear.

Pruning now destroys the *metadata* too: the captured metarecords go with the
blob. That is the point of the design — the metarecord dies with its bytes, and
=prune= is where both die. Until then, a metarecord that is not in the
repository is not lost, it is in the trash.

* =mf trash=

Manages the repository's trash-bin. The bytes are the CLI's own business — the
trash location comes from =GET /repos/:repo= (=internal_dir=) — and the metadata
half goes through the one endpoint the daemon owns
([[*Deleting the metarecords]]).

#+BEGIN_SRC
mf trash [list]
mf trash -f <path> [--force]
mf trash restore <id>
mf trash prune (-s <size> | -d <duration> | --all) [--dry-run]
#+END_SRC

=list= (the group default, so =mf trash= ≡ =mf trash list=) prints one row per
entry — id, original path (a trailing =/= marks a directory), size, age (from
=trashed_at=), reason — newest first.

=-f=/=--file <path>= manually trashes a *tracked* file or directory — a safe
delete (=reason=manual=). It errors, *before touching anything*, if the daemon is
unreachable or the path has no metarecord (the CLI resolves =path -> mfr_path=
metarecord through =POST …/query= with the exact-path idiom
=mfr_path -> "/parent" AND mfr_path = "name"=, using the =root= from
=GET /repos/:repo=). A directory is trashed whole, subtree and metarecords
included. =-f= cannot be combined with a subcommand.

It captures the metarecords, deletes them, and moves the bytes, in that order
([[*What trashing does, in order]]). Unlike the design it replaces, this holds
whether or not the subtree is watched: a repository with =mf_watch= off used to
keep a metarecord pointing at a file that was no longer there — a stale claim
only an orphan scan would ever find — and now does not.

=--force= trashes anyway when something outside the trashed set still references
one of its metarecords ([[*Refusing to break a reference]]). Without it the
refusal names the referrers and nothing is touched.

=restore <id>= recreates the metarecords, re-links what survived, and moves the
blob back to its =original_path=, then removes the entry ([[*Restoring]]). An
occupied target is refused — never overwritten — except a directory that
*merges* into an existing directory (move a file occupant aside first).

=prune= permanently deletes entries; exactly one selector is required:
- =-s=/=--size <size>= — delete oldest first until the total is at/under the
  budget. =<size>= is a human size: a bare integer (bytes) or a number with a
  =k=/=m=/=g=/=t= suffix (base 1024, case-insensitive; a trailing =b= is
  allowed, e.g. =100mb=, =1g=, =512k=).
- =-d=/=--older-than <duration>= — delete entries older than the duration.
  =<duration>= is =<n><unit>= with unit =y= (365 d), =w=, =d=, =h=, =m= (minute),
  =s= (e.g. =1y=, =30d=, =12h=).
- =--all= — empty the trash (also sweeping any orphan blobs — manifest-less
  files a failed manifest write could leave — which the other selectors, keyed
  on the manifest, never see).
=--dry-run= lists what would be removed and reclaimed without deleting.

* GUI

The GUI exposes the same trash-bin (spec-gui.org), driving the shared
=metafolder_core::trash= layer through Tauri commands (=trash_list=,
=trash_selected_metarecord=, =trash_path=, =trash_restore=, =trash_remove=,
=trash_empty=); like the CLI it locates =internal_dir=/=root= through
=GET /repos/:repo= and goes through the same single daemon endpoint for the
metadata half.

- *Send to the trash* — the =metarecord:trash= command (a shell builtin) sends
  the workspace's =selected_metarecord='s file to the trash (=reason=manual=,
  capturing and deleting the metarecord, exactly like =mf trash -f=). It is
  bound to =Delete= in the panels that carry a metarecord selection
  (=metarecord-list=, =metarecord-detail=, =treeref=) and offered as a *Trash
  file* context-menu item in the metarecord panels. Because =Delete= is a bare
  key, the action is *confirmed* even though it is reversible.

- *file-manager delete* — the =file-manager= panel deletes the *highlighted
  filesystem entry* (=Delete=, or the context menu) through =trash_path=. When
  the entry is *tracked* it resolves the metarecord and captures and deletes it
  like every other trashing: the GUI is the path most deletions actually take,
  and it must not be the one that still leaves orphans behind. An *untracked*
  entry has nothing to capture and is trashed as bytes alone. With no active
  repository there is nowhere to restore from, so the removal is permanent
  (=metafolder.fs.remove=). All are confirmed.

- *trash panel* (=panel:set type trash=, default =t b=) — lists the entries
  (name, size, age, reason, path), newest first, and offers *Restore* (=Enter=;
  recreates and re-links the metarecords before moving the file back, as the
  CLI does),
  *Delete* one entry permanently (=Delete=), and *Empty trash* — the two
  destructive actions confirmed. =f= jumps to an entry by name, each candidate
  carrying the path it was trashed from (spec-gui "Find an entry"). Prune by
  size/age is CLI-only.
