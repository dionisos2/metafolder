La liste de toutes les pages du wiki (=docs/wiki/=) et d'où vient leur contenu.
On la complète item par item. La conception est dans
[[file:doc-wiki-proposal.md][doc-wiki-proposal.md]] ; l'outil est =scripts/doc=.

* Mode d'emploi

- *Un item = un sujet = un commit.* Un item est =FAIT= quand :
  1. ses notes sont écrites (les cases ci-dessous, cochées au fur et à mesure) ;
     la liste est une proposition, que l'item précise ou corrige ;
  2. chaque affirmation a été *vérifiée dans le code*, pas recopiée de la spec
     (un écart se corrige dans le code ou dans la doc, et se signale) ;
  3. les commandes, panels et scripts qu'il couvre ont leur note (=scripts/doc
     new --from-gen …=), à la place de la liste « Not documented yet » ;
  4. les citations =spec-x "Section"= du code vers les sections couvertes
     deviennent =doc "Titre"= ;
  5. les sections reprises sont supprimées de leur spec (un fichier vide est
     supprimé), la page help d'origine aussi, avec son entrée dans
     =pages/index.json= ; ses alias passent sur la nouvelle note ;
  6. les décisions de conception de la mémoire qui relèvent du sujet deviennent
     des notes =rationale= =audience: dev= (la mémoire ne garde que les pièges
     d'environnement et les méthodes) ;
  7. =scripts/doc check= est vert.
  8. les mentions du sujet déjà écrites ailleurs dans le wiki (en texte, faute
     de note à l'époque) deviennent des liens : =scripts/doc find <nom>=.
- Notation des notes : =Titre= — /kind/ (/dev/ si =audience: dev=, /deferred/ ou
  /proposed/ ou /record/ si ce n'est pas =implemented=).
- Chaque sujet a sa note d'ensemble (/overview/) portant le titre du sujet, qui
  sert de tag à ses notes. Les sujets s'emboîtent par tags (indiqué entre
  parenthèses : « sous … »).
- Pour les catalogues, « GUI : =trash:*= (9) » veut dire : les 9 commandes GUI
  dont le nom commence par =trash:= reçoivent leur note dans cet item.

* Conventions apprises au pilote

- On ne met un lien que vers une note qui existe (le contrôle refuse les
  autres) ; une note pas encore écrite est nommée en texte (=`metarecord-list`=,
  « the event log »), et le point 8 du mode d'emploi la relie plus tard.
- Wikitext : un élément de liste tient sur *une* ligne (pas de continuation
  indentée) ; =--= devient un tiret demi-cadratin hors code, donc une option de
  CLI s'écrit toujours entre accents graves ; les liens CamelCase sont coupés
  (=$:/config/WikiParserRules/Inline/wikilink=).
- =<<key "commande" repli>>= : le repli est la touche par défaut, lue dans la
  note générée de la commande ; =scripts/doc check= refuse une commande inconnue.
- Une section retirée d'une spec qui reste en place (spec-gui…) devient un
  paragraphe-pointeur (« Moved to the wiki: doc "…" ») : d'autres passages de la
  spec y renvoient encore.
- Après une réécriture de citations, relancer les tests « golden » du catalogue
  (=cargo test -p metafolder-cli --bin mf doc_gen=, idem =-p metafolder-gui --lib=) :
  un commentaire =///= de =crates/cli/src/main.rs= est un texte d'aide de clap.
- Une note de commande ne répète pas sa partie générée (usage, options,
  touches) : elle dit ce que la commande fait et renvoie aux notes du sujet.

* Ordre

Le pilote d'abord, puis les petits sujets autonomes, puis les gros sujets
transversaux, la GUI en dernier (elle cite tous les autres) :

1. Corbeille (pilote : on y fige la granularité et les conventions)
2. Doublons, journal des opérations lentes, tâches, authentification, configuration
3. Démon et dépôts, conventions de la CLI, schéma, stockage
4. Modèle de données, requêtes, langage simplifié
5. Suivi des fichiers (6 items), journal des événements (6 items)
6. Synchronisation, tags hiérarchiques, plateforme, sécurité
7. GUI (shell, commandes, panels, scripts)
8. Développement, puis la clôture
