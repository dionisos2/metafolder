#+TITLE: Metafolder — Cross-repo Synchronisation Specification
#+OPTIONS: toc:2 num:t

* Overview                                                               :v2:

The daemon provides low-level primitives for cross-repo sync. Orchestration
(deciding what to link, in which order, and running the file operations)
lives in the CLI (=mf sync=) and user scripts.

Sync state — the links between metarecords of two repositories and the
snapshot of their common state at the last sync — lives *outside the data
model*, in a dedicated per-pair SQLite database (see [[*The sync database]]).
Links and snapshots are not metarecords: they never appear in queries, are
absent from the event log, and are not subject to rollback.

* Concepts

** Design principles

- The daemon never touches files. File operations are always performed by the
  CLI command or script.
- File content is never destroyed. Any file operation that would overwrite or
  delete a file (a =copy= over existing content, a =delete=, a =move= onto an
  occupied path) first moves the existing file into the *trash-bin* under
  =internal/= — so a botched or unwanted sync is always recoverable. Rollback
  obeys the same rule for the =mv= it performs. Both route every
  overwrite/delete through the single shared trash-bin, whose layout,
  restoration and pruning are specified in [[file:spec-trash.org][spec-trash.org]]; restoration is
  always an explicit act (=mf trash restore=), never automatic.
- Sync intentions (which metarecords to link) are expressed as queries in the
  intents file, not stored in the database. Whether a record's content is
  metafolder's to move or an external tool's is the record's inherited
  =mf_sync= field (=internal= / =external=).
- Both repos must be loaded in the same daemon instance for every sync
  primitive (link creation/deletion, status, commit).
- For cross-machine sync, the recommended approach is to mount the remote
  repository root over SSH (e.g. SSHFS) and load it into the local daemon.
  The daemon itself makes no network calls.
- Sync state is bookkeeping, not user data: it lives outside the data model
  and the event log, so the log, rollback, queries and the index are entirely
  unaffected by sync. (A rollback still moves the linked metarecords' own
  =version= counters, which change detection accounts for — see
  [[*Version-based change detection]].)

** The sync database

Each synchronised pair of repositories =(A, B)= shares one *sync database*: a
single SQLite file named

: .metafolder/internal/sync-<uuid_A>-<uuid_B>.sqlite

where =<uuid_A>= and =<uuid_B>= are the 32-char lowercase hex repo UUIDs in
canonical order (see below). The file lives in the =internal/= directory of
*one* of the two repos — the *host* repo, chosen when the pair is first
created (see [[*Location and discovery]]). Living under =internal/=, it is
excluded from tracking like =db.sqlite=.

There is exactly one copy: every sync-state mutation is a single ordinary
SQLite transaction, so link state is always internally consistent — no
replication, no repair protocol. The trade-off is redundancy: if the file is
lost or corrupted, the pair's sync state is gone and the next sync starts
over as a first sync (divergent fields resurface as immediate conflicts;
records at the same TreeRef identity re-link silently).

A repo may participate in any number of pairs, each with its own sync
database. Only the pair being synced is ever opened; sync state adds no
weight to the main database, its index, or its queries.

*** Canonical pair order

The two repo UUIDs are ordered lexicographically (as 32-char lowercase hex):
the smaller UUID is *repo A*, the larger is *repo B*. This order is derivable
from the pair alone and is used consistently for:

- the file name (=sync-<uuid_A>-<uuid_B>.sqlite=),
- the =a=/=b= role names in the schema and the HTTP API,
- the canonical perspective of snapshots (see
  [[*Ref and TreeRef fields in the snapshot]]).

The canonical order does *not* choose where the file lives — that is the
host repo, an independent choice (see [[*Location and discovery]]).

The order of repos in a URL or on the =mf sync= command line is irrelevant;
the daemon and CLI normalise to canonical order internally. Conflict policies
therefore never say "a" or "b" — they name the repo (see [[*Conflict resolution]]).

*** Schema

#+BEGIN_SRC sql
-- Identification and format version. Rows: format_version (currently "1"),
-- repo_a, repo_b, host (32-char hex). On open, repo_a/repo_b must match the
-- file name and the repo pair being synced; a mismatch (e.g. a file copied
-- from another pair) is an error and the file is not used. host records the
-- repo whose internal/ holds the file (updated if the file is moved).
CREATE TABLE meta (
    key    TEXT PRIMARY KEY,
    value  TEXT NOT NULL
);

CREATE TABLE link (
    uuid       BLOB PRIMARY KEY,        -- 16-byte link id
    record_a   BLOB NOT NULL UNIQUE,    -- metarecord UUID in repo A
    record_b   BLOB NOT NULL UNIQUE,    -- metarecord UUID in repo B
    version_a  INTEGER,                 -- E_A.version at last sync-commit (NULL before)
    version_b  INTEGER                  -- E_B.version at last sync-commit (NULL before)
);

-- Snapshot of the common field state at the last sync-commit. Value columns
-- are encoded exactly like the =field= table of the main database (same
-- value_type tags, same column usage), from repo A's perspective; for =ref=
-- and =tree_ref= rows, =value_uuid_b= additionally stores the B-perspective
-- UUID captured at commit time (dual perspective — see
-- [[*Ref and TreeRef fields in the snapshot]]).
CREATE TABLE snapshot_field (
    link_uuid   BLOB NOT NULL REFERENCES link(uuid) ON DELETE CASCADE,
    field_name  TEXT NOT NULL,
    value_type  TEXT NOT NULL,
    value_text  TEXT,
    value_int   INTEGER,
    value_real  REAL,
    value_uuid  BLOB,
    value_uuid_b BLOB,
    value_ref_repo BLOB,
    value_name  TEXT
);
CREATE INDEX idx_snapshot_link ON snapshot_field(link_uuid);
#+END_SRC

The sync database is opened on demand with journal mode =DELETE= and
=synchronous = FULL= — never WAL: the host repo may be the SSHFS-mounted
one, and WAL's shared-memory file cannot work on a network filesystem.

Links are 1:1: a metarecord of A is linked to at most one metarecord of B and
vice versa — enforced by the two =UNIQUE= constraints.

The =version_a= / =version_b= columns are written only by the sync-commit
primitive; =record_a= / =record_b= are immutable after creation. (There is
no stored method: whether a record's content is metafolder's or an external
tool's is the =mf_sync= field on the record itself — see
[[*Metadata versus content: the =mf_sync= field]].)

*** Location and discovery

The sync database lives in the =internal/= directory of one of the two
repos, the *host*. The first mutating primitive on a pair creates the file
(with its =meta= rows); the request designates the host repo, defaulting to
canonical repo A. Choosing the host lets the user keep sync state on the
machine that orchestrates the syncs (e.g. the local repo rather than the
SSHFS-mounted one).

The two repo UUIDs of a pair must differ (=400= otherwise). Every pair
primitive locates the file by checking both loaded repos' =internal/=
directories, then checks its =meta= table matches the file name and the pair
(=409= on mismatch):

- found in exactly one → use it (and update =meta.host= if the file was
  moved by hand — relocation is supported: move the file, nothing else).
- found in neither → the pair has no sync state yet (empty link set;
  mutating primitives create the file, read-only ones return empty).
- found in both → ambiguous (=409=); the user deletes the stale one. The
  daemon never merges two sync databases.

A missing file simply means an empty link set; an unreadable or corrupted
one is an error — deleting it abandons the pair's sync state (the next sync
starts over as a first sync).

*** Consistency and access

The daemon opens the file on demand, for the duration of one primitive call,
and closes it afterwards — no handle is kept in the repo state. Every
sync-state mutation (link creation, deletion, batched sync-commit) is one
ordinary SQLite transaction on the single file, so link state is always
internally consistent, whatever crashes. Cross-database consistency (sync
state vs. the two main databases) is the job of the change-detection
machinery: a crash between a metadata write and its sync-commit simply
leaves the link "changed", re-detected and re-committed on the next run
(see [[*Version-based change detection]]).

Concurrent primitive calls on the same pair are serialised by the daemon
(the two repos' locks are acquired in canonical order, so no deadlock).
Concurrent mutation from *two* daemons is excluded by the main databases'
exclusive locks (both repos must be loaded to touch a pair); on network
filesystems with unreliable locks (SSHFS) that exclusion can weaken, and the
sync database's own SQLite locking is then the last line of defence —
syncing the same pair from two daemons concurrently is unsupported.

** Version-based change detection

After a successful sync of metarecords =E_A= (repo A) and =E_B= (repo B), the
sync-commit primitive writes the current versions of both metarecords into the
link:

- =version_a= ← =E_A.version= at time of sync
- =version_b= ← =E_B.version= at time of sync

On the next sync, for each linked pair:

| =E_A.version= vs =version_a= | =E_B.version= vs =version_b= | Meaning          | Action          |
|------------------------------+------------------------------+------------------+-----------------|
| equal                        | equal                        | No changes       | Nothing to do   |
| different                    | equal                        | Only A changed   | Propagate A → B |
| equal                        | different                    | Only B changed   | Propagate B → A |
| different                    | different                    | Both changed     | Conflict        |

"Different" rather than "greater": a rollback can restore a *smaller*
=E_X.version=; any difference from the recorded value means the metarecord
changed relative to the last sync point. Equality, conversely, proves the
state is unchanged — a version number is never reused for a different state
(the per-metarecord =next_version= allocator, which navigation never
restores; see [[file:spec-data-model.org][spec-data-model.org]]). A rollback can also make a linked
metarecord *disappear* (undo its creation); that is indistinguishable from a
deliberate deletion, which is why deletion propagation is never silent (see
[[*Metarecord deletion propagation]]).

The version test is a cheap pre-filter, not the definition of change:

- A *conflict* is a field changed on both sides *to different values* (after
  ref translation). Both sides changed to the *same* value → the field is
  simply in sync; nothing to propagate.
- A changed version whose *effective diff* is empty (only excluded =mfr_*=
  fields moved — see [[*Field coverage and diff semantics]] — or a stat-only
  attribute change) means the link is in sync: the run simply records the
  fresh versions instead of reporting a change or a conflict. This also
  makes crash recovery benign: a crash between metadata propagation and
  sync-commit re-detects the link as "changed on both sides", but the values
  are equal, so the next run just records the versions.

The *snapshot* — the =snapshot_field= rows of the link — records the common
field state at the last sync-commit and is what resolves the "both changed"
case into three:

- changed only in A = =diff(E_A, snapshot)= → propagate A → B;
- changed only in B = =diff(E_B, snapshot)= → propagate B → A;
- changed in both = a conflict → resolved by policy (see [[*Conflict resolution]]).

The snapshot is replaced at every sync-commit alongside =version_a= /
=version_b=. Before the first sync there is none (state =never_synced=) and
union semantics apply (see [[*The metadata diff]]).

*** Ref and TreeRef fields in the snapshot

For non-Ref fields, E_A and E_B hold identical values after sync, so the
snapshot is unambiguous. For =Ref= and =TreeRef= fields, the same logical
reference has different local UUIDs in each repo.

The snapshot stores these values in *dual perspective*, both captured at
commit time:

- =Ref=: =value_uuid= holds repo A's local UUID, =value_uuid_b= holds repo
  B's (translated through the link table as it stood at commit).
- =TreeRef=: same for the parent UUID; the =name= component is portable
  (identical across repos) and stored once.
- A perspective whose translation was unknown at commit time stores =NULL=
  on that side.

Because the snapshot lives in its own table (not in the =field= table of
either main database), these UUIDs are inert bytes: they trigger no tree
validation, no uniqueness constraint, and no dangling-ref concern.

Consequences for the diff — no translation is ever needed at diff time,
which also makes the diff immune to links deleted or re-created between two
commits:
- =diff(E_A, snapshot)=: compare against =value_uuid= directly.
- =diff(E_B, snapshot)=: compare against =value_uuid_b= directly.
- A =NULL= perspective (untranslatable at commit time) → conservative
  treatment: flag as potential conflict and warn.

Translation through the *current* link table still happens when propagating
a Ref/TreeRef value to the other repo (see [[*Ref translation during sync]]).
=ExternalRef= values are self-contained (repo + metarecord) and are copied
verbatim, never translated.

** Field coverage and diff semantics

*** Metadata versus content: the =mf_sync= field

Every field of a record is *metadata* and is always synced (subject to the
diff below). Only the record's *content* — the file's bytes and its position
(=mfr_path=) — may be handled by metafolder or by an external tool, and that
choice is the =mf_sync= field:

- =internal= (the default) — metafolder owns the content: it copies/moves
  files and creates/renames directories as needed to make the two sides
  agree.
- =external= — something outside metafolder owns the content (a git repo, a
  manually-run =rsync=, …): metafolder performs *no* file or directory
  operation. A content or path divergence between the two sides then means
  the external sync is incomplete and is reported as an error (aggregated by
  subtree in the =run= summary, not one line per file).

=mf_sync= is a reserved config field (=mf_= prefix, needs =force=), set on a
directory and *inherited* down the =mfr_path= tree exactly like =mf_watch= /
=mf_ignore= (nearest ancestor wins; absent everywhere ⇒ =internal=). So a git
repository is marked once — =mf_sync = external= on its root — and its whole
subtree inherits it; a =.gitignore='d subdirectory metafolder should still
manage gets =mf_sync = internal= closer to the leaf. It governs *files and
directories* alike; on a directory it doubles as the inheritance anchor. It
is itself an ordinary synced field, so the two sides agree on it before any
content decision (metadata precedes content — below), and a contradiction is
a normal metadata conflict resolved at plan time.

*** The metadata diff

=mfr_*= fields are *excluded* from the snapshot, the diff, and propagation,
with two carve-outs: =mfr_path= (the file's position, synced) and
=mfr_permissions= (the file's mode). The rest are stat- and content-derived:
each repo describes its own file (=mfr_size=, =mfr_mtime=, hashes), so
propagating them would ping-pong forever, and any version bump they cause (a
stat-only change) is absorbed by the empty-effective-diff rule above.
=mfr_permissions= *is* synced (constraint: an =internal= file must end up with
the same mode on both sides): it participates in the diff and is applied to
the target file by =chmod= — so a mode change propagates even without a
content change. Ownership (=mfr_uid=/=mfr_gid=) is *not* synced: =chown= needs
privilege and uid/gid rarely mean the same thing across machines, so owner and
group stay local. All non-=mfr_= fields — user data, and reserved =mf_*=
(including =mf_sync=) written with =force= — are propagated as ordinary field
writes.

Fields form a multi-map: the diff compares, per field *name*, the full
*multiset* of values (after ref translation on the B side). Propagation
replaces the target's whole row set for that name (set semantics, not
append). A field name absent on one side and present in the snapshot is a
*removal*, propagated as an unset — "absent" (unknown) and =Nothing= (does
not apply) are distinct states and both are preserved by snapshot and
propagation. Conflict prompts operate per field name and display the full
multisets.

At the *first sync* the snapshot is empty, so union semantics apply: a name
present on one side only is propagated to the other; present on both with
equal multisets is in sync; present on both with different multisets is an
immediate conflict, resolved by policy before the first sync-commit.

*** Content operations (=internal= records only)

- *File content*: the stored content signatures (=mfr_full_hash=, falling
  back to =mfr_partial_hash= + =mfr_size=) of the two endpoints are compared;
  if they differ, a transfer is planned from the changed side (for a content
  conflict — both sides changed — the conflict policy chooses the direction,
  like any conflicting field). A record present on one side only is created
  on the other (bare metarecord + transfer/mkdir). A transfer that would
  overwrite existing bytes trashes them first (see [[*Design principles]]).
- =mfr_path=: a placement (onto a sync-created record) or a move/rename of a
  linked file or directory. Path operations are applied top-down (parents
  before children); a translated TreeRef whose parent is missing or orphaned
  is rejected by forest validation (=400=), skipped and reported.

For an =external= record none of the above runs: no transfer, no
create/mkdir, no move. Instead, a content or path *difference* between the
two sides is recorded as an error in the report (the external tool should
have reconciled it). Metadata still syncs normally.

*Metadata gates the disk.* An =internal= record's file/directory operation is
performed only *after* its metadata propagation — every field write,
=mf_sync= and the translated =mfr_path= included — has fully succeeded on the
target. If any metadata write is rejected (=409= precondition, =400=
forest/schema violation, an unresolved conflict), the operation is skipped
and the link is not committed: metadata and content never diverge from a
partial sync. This ordering also gives three guarantees for free: the two
sides agree on =mf_sync= before the content decision reads it; =mfr_path= is
written before the file is placed, so a sync-created record already exists at
its path when the file arrives and the watcher's create/arrival event
resolves to it rather than duplicating it (spec-file-tracking: =Create= /
=Rename(To)= resolve by path first); and a crash between the metadata write
and the disk operation leaves only a stale path, which the next run
(uncommitted link, re-detected) or =reconcile= repairs.

** Metarecord deletion propagation

- =mfr_path= set to =Nothing= (file deleted, metarecord preserved) → link is kept;
  the metarecord still exists and its metadata remains meaningful.
- Metarecord fully deleted → the sync command propagates the deletion to the
  corresponding metarecord in the other repo, then deletes the link (and with
  it the snapshot, which has no existence of its own).

For =external= records this stays metadata-only: metafolder removes the peer
metarecord and the link but never deletes the file (the external tool owns
the content). For =internal= records the peer file is moved to the trash as
part of the propagation (never destroyed — see [[*Design principles]]).

Deletion propagation is destructive on the surviving side and a rollback can
make a record vanish without any user intent, so it is never silent: =mf sync
plan= lists planned deletions nominatively and confirms them interactively
before writing them into the plan (a non-interactive =plan= omits unconfirmed
deletions). The deletions that survive into the plan are then plainly
visible in the file for review before =run=.

Normative order (used by =DELETE …?with_endpoint= and the CLI alike): delete
the endpoint metarecord *first* (a logged, rollbackable write), then delete
the link. A crash in between leaves state =missing_x=, which the next run
re-detects and completes — never a deleted link with a live record that a
later run would resurrect as "new".

** Two-phase sync process

Sync is split into two commands over a *plan* that is itself stored as
metarecords (see [[*The plan repo]]):

1. *Planning* (=mf sync plan=): query both repos, resolve conflicts and
   ambiguous matches interactively, and write the plan — one metarecord per
   operation (linking phase: matches, creations, drops; sync phase:
   transfers/moves with direction, field propagations, deletions), each
   carrying, *for the metarecords it touches, the =version= they were read
   at* — the plan's baseline. The plan can be browsed and edited with the
   ordinary =mf= / GUI tooling before running (=mf sync show=).

2. *Execution* (=mf sync run=): execute each operation whose metarecords are
   still at their baseline =version=, *skip* the rest, and delete every
   operation that succeeded — so the plan repo is left holding exactly what
   did *not* happen. =run= does *not* re-plan: the reviewed (and possibly
   edited) plan is exactly what executes, minus what has since changed.

The per-operation baseline check is the freshness guard. Because a version
number is never reused for a different state (the =next_version= allocator,
see [[*Version-based change detection]]), a record still at its baseline is in
the exact state the plan was computed from, so that operation's decisions —
including a resolved conflict — are still valid, and =run= re-reads current
field values instead of embedding them in the plan (equal version ⇒
identical fields). A record that changed fails the check: every operation
touching it is skipped, for a later plan to pick up. The check runs on the
daemon as the =expected_version= precondition of each write, so a concurrent
writer that slips between check and write is caught too.

This covers *file* changes too: modifying a file bumps its record's =mfr_*=
version through the watcher, so the baseline no longer matches and the file
operation is skipped. This is why =run= does *not* suspend the executors —
they are what keeps versions current (see [[*Why the executor keeps running]]).

After execution, =run= prints a summary, leaves the un-executed operations in
the plan repo for inspection, and recommends =reconcile= to catch any residual
filesystem drift (e.g. a change inside the executor's sub-second quiet-period
window).

** The plan repo

The plan is stored as metarecords in a *dedicated metafolder repo*, so it is
browsed, filtered and edited with the ordinary =mf= / GUI tooling — the query
engine, the cache and the panels come for free, which is exactly what a
reviewable/editable plan needs. (This does not contradict keeping *links*
out of the data model: links are internal bookkeeping shared by the two main
repos, whereas the plan is isolated in its own repo and being browsable is
its whole point.)

*** The repo

A data-only metafolder repo — =mf_watch = false=, no files, only abstract
metadata metarecords — stored under =internal/= (=plan-<uuid_a>-<uuid_b>/=),
recreated from scratch by each =mf sync plan= (only the latest plan exists).
It is *loaded into the daemon* alongside the two synced repos (both are
necessarily loaded during planning), and marked a *system repo* (a flag in
its =config.json=) so it is hidden from =mf repo list= unless =--all= is
passed. Its in-memory cache/index may be dropped right after creation if
memory is tight; nothing depends on it staying warm.

*** Operations as metarecords

One metarecord per operation, with no =mfr_path= (an abstract entity, as the
data model already allows for tags/collections/links):

- =plan_kind= (String): =create-link= | =drop-link= | =sync= | =copy= |
  =move= | =delete=.
- =plan_a=, =plan_b= (ExternalRef): the touched records in repo A / repo B.
- =plan_version_a=, =plan_version_b= (Int): the baselines that gate the op.
- =plan_from= (String, =a= | =b=): the winning/source side for a =sync= /
  =copy= / =move=; =plan_side= for a =delete=.

A conflict is one =plan_kind = conflict= metarecord *per (link, field)*:
=plan_field=, the two candidate values, and =plan_resolve= (=a= | =b= |
=skip=) — the one editable field. Reviewing conflicts is a query
(=plan_kind = "conflict"=); resolving one is =mf … field set plan_resolve=…=,
itself logged (and undoable) in the plan repo.

*** Live overlay (=mf sync show=)

Browsing the plan repo directly shows the operations but with *stored*
references. The sync-specific =mf sync show= adds the live context the
generic query cannot: it follows each =plan_a= / =plan_b= ExternalRef into
the (loaded) synced repos to display current paths and values, and compares
=plan_version_*= to the records' current versions to flag operations that
will be *skipped* (their baseline no longer matches) — the red/green view.
Following an ExternalRef across repos is not a generic query feature, so this
overlay is the one piece the plan repo does not get for free.

** Sync intentions

Sync intentions declare the sync *scope* — which records to link and keep in
sync between the pair. (They no longer carry a transfer method: whether a
record's content is metafolder's or an external tool's is the inherited
=mf_sync= field, see [[*Metadata versus content: the =mf_sync= field]].) They are
a list of entries, each naming a *source repo* and a query (see
[[*The intents file]]). Intents are *directional*: the query runs on the source
repo only, and its result is the set of source records that must be linked to
the other repo. Example (source repo before the arrow):

#+BEGIN_SRC
laptop:  tag = "sync_pc_b"
laptop:  mfr_path ->* "/projects"
nas:     tag = "image" AND tag = "family"
#+END_SRC

The union of the entries is the scope. It maintains the link set:

- an in-scope source record with no link → link it (see
  [[*The linking phase: match or create]]);
- a link neither of whose endpoints is in any intent scope → drop the link
  (never the records);
- every remaining link is then synchronised — the sync phase, i.e. the
  change-detection/propagation machinery above driven by the =mf sync= flow
  (see [[*CLI]]).

*** The linking phase: match or create

A metarecord's cross-repo identity is its *TreeRef fields*: the =tree_ref=
-valued fields it carries, each occupying a unique position in its forest
(the =(field_name, parent, name)= UNIQUE index, spec-schema). A file has one
such field, =mfr_path=; a tag/collection node has its forest field
(e.g. =tag=); an abstract record may have none. **Content hashes are not used
for matching** — a moved file is recognised by its path, not its bytes. This
is deliberately uniform (no file/non-file special case); the cost is that a
file moved on *one* side before it was ever linked is matched by its new
path, not recognised as the same bytes, so it may be duplicated at first sync
(a real duplicate the user fixes in one repo, propagated next sync).

Matching keys on the *reconstructed path* of each identity field — portable
across repos (the =name= components are identical; only the local parent UUID
differs), and 1:1 by construction (one metarecord per forest position), so
path matching is never ambiguous. For each in-scope source record without a
link, by the number of identity TreeRef fields:

- **None** — no positional identity (e.g. a deleted-file tombstone,
  =mfr_path = Nothing=, on both sides). Matching falls back to a heuristic:
  a target record whose *sync-relevant* fields (all fields except the
  excluded =mfr_*=, see [[*The metadata diff]]) form the same multiset is
  linked — but only when unambiguous (exactly one such record on each side).
  Ambiguous or absent → no link (create / leave for =mf sync link=). This
  heuristic is intentionally minimal and may be refined later.

- **One** field =F= at path =P= (the common case). The record links to the
  target-side record at position =P= in forest =F=. If none exists there, a
  record is created at =P=: its parent is resolved by path, or created
  recursively top-down, so the ancestor chain exists first. Parents are *not*
  themselves linked (they may be out of scope) — a created ancestor is a bare
  node carrying only its TreeRef.

- **Several** fields ={(Fi, Pi)}=. Compute, for each, the target-side record
  occupying position =Pi= in forest =Fi= (∅ when free). Let =E= be the
  distinct non-empty occupants.
  - =|E| ≥ 2= — the identities map to *different* target records → *type-2
    incoherence*: =mf sync plan= aborts and lists the offending records and
    positions.
  - =|E| = 1=, occupant =T= — for each field whose =Pi= is free, =T= must not
    already occupy a *different* position in =Fi=; if it does, that is a
    *type-1 incoherence* (abort). Otherwise link to =T=, and any missing
    =Fi = Pi= is added to =T= by ordinary field propagation in the sync phase.
  - =|E| = 0= — no position occupied → one record is created, placed at all
    =Pi=.
  Occupancies are computed first and =|E| ≥ 2= is tested *before* the
  per-field type-1 check. An abort leaves no partial plan; the report names
  each problematic pair for manual resolution.

A record with no match *and* =internal= yields a *bare* metarecord (no fields)
on the target, whose UUID creates the link; if =external=, it cannot be
created (metafolder owns no content there) and the failure is reported.

Sync-created records are bare: *everything* — the file itself (content
transfer), =mfr_path= (file placement, directories top-down), every field,
references included — arrives through the sync phase that follows (the new
link's first sync, union semantics). The linking phase also **closes the scope
over references**: every =Ref=/=TreeRef= target reachable from an in-scope
record is materialised on the target side (see [[*Ref translation during
sync]]). By then the link table and placements are complete, so translation
has every mapping it will ever have — reference-carrying propagation is
well-defined, never guessing a target-side UUID.

Links are 1:1. Once linked, a record keeps its link by UUID whatever moves or
renames happen — path divergence is then an ordinary =mfr_path= change or
conflict.

** Ref translation during sync

=Ref= and =TreeRef= fields store local UUIDs; a TreeRef =value_name= is
portable and written as-is, and =Nothing= needs no translation. Translation
maps a referenced record to its target-repo counterpart:

- =Ref= → the *linked* target-repo record.
- =TreeRef= *parent* → **link-first, path-fallback**: use the parent's link
  when it is linked (this follows the parent through any rename); otherwise the
  target-forest record at the parent's reconstructed *path*. The two agree when
  the parent is linked and unmoved. This is what lets =tag = "musique/jazz"=
  translate even when its =musique= parent is out of scope and unlinked.

A referenced record out of sync scope has no counterpart at first. Rather than
drop the field, the linking phase **materialises** the referenced record on the
target side — the *referential closure* of the scope — so every reachable
reference is translatable. Materialisation is *by identity* (see
[[*The linking phase: match or create]]) and links only when there is nothing
to re-match on:

- referenced record **with a TreeRef identity** → =find-or-create= at its
  reconstructed path (ancestor chain top-down), **not linked**: it re-links by
  path if it later enters scope, so a link would be redundant;
- referenced record **with no identity** (abstract) → a **bare** record is
  created and **linked** to the original — the link is the only memory of the
  correspondence. It is not field-synced (out of scope); should it later enter
  scope, the existing link means it is synced, never duplicated.

This runs in the linking phase, before any translation, so the link table and
all placements are complete when the sync phase translates. It is bounded: a
bare record is empty, so it has no further references to close over; an
identity record pulls only its ancestor chain; cycles terminate because
materialisation reuses an existing link/placement before creating. Forest
positions being unique, find-or-create never duplicates, and a position found
occupied by a different record at run time is a forest violation (=400=),
skipped and reported.

=Ref= values have no foreign-key constraint on =value_uuid= (see schema). The
system tolerates dangling refs: =Follows= on a dangling =Ref= simply returns no
results. Circular references (A → B → A) are likewise permitted; =Follows= is
non-recursive so cycles are not a concern.

** Schemas must be identical

Syncing two repositories with different user schemas makes little sense —
the same metadata would be legal on one side and illegal on the other. =mf
sync plan= and =mf sync run= therefore start by fetching both repos' schemas
(=GET /repos/:repo/schema=) and abort with an error if they differ.
"Identical" is structural equality of the parsed schema documents (JSON
value equality — formatting and key order do not matter); two repos with no
schema at all are identical. The schema file itself is never propagated by
sync (see [[file:spec-schema.org][spec-schema.org]]): resolving a mismatch is a manual step.

Field propagation still goes through the ordinary field endpoints of the
target repo, so the target's schema validates it like any user write — even
with identical schemas a propagated field can violate a constraint in
combination with the target record's other fields. Such a violation rejects
that write; the CLI reports the field as skipped with the violation message
and continues. Sync never bypasses the schema.

* Daemon

** Why the executor keeps running

Sync never suspends the watcher or its executor. The running executor is
what keeps metarecord versions current with the filesystem, and current
versions are exactly what the per-operation baseline check relies on: a file
modified during a run bumps its record's =mfr_*= version, so the stale
operation is skipped rather than run against changed content. Freezing the
executor would freeze versions and defeat that guard. Nothing needs
mutual-exclusion machinery (owner tokens, unload locks, rollback-lock
interplay): concurrency is handled uniformly by the =expected_version=
precondition on every write, and a rollback in progress simply makes those
writes fail (=423=), skipping their operations.

*** Suppressing sync's own echoes

Sync's own file operations make the watcher enqueue events that, once
applied, would refresh =mfr_*= and bump the very versions the sync-commit
just recorded — so the next plan would see every synced link as changed.
Two mechanisms make these echoes no-ops:

1. As part of each file operation, sync sets the target record's
   stat-derived fields (=mfr_size=, =mfr_mtime=, cleared hashes) to match
   the file it just wrote — the same fields the watcher would refresh,
   folded into the write the sync-commit records. The database is thus
   already consistent with the file.
2. The executor's data refresh is *idempotent*: it produces no operation and
   no =version= bump when the record's stored stat already matches the file
   on disk (see [[file:spec-file-tracking.org][spec-file-tracking.org]]). So the buffered echo of a sync
   operation finds nothing to do.

A *genuine* concurrent user change has a different size/mtime, so it is not
idempotent-skipped: it is applied normally and bumps the version — which is
exactly what makes the baseline check catch it. Any sync write that raced it
was already fenced by the =expected_version= precondition.

** HTTP API

All UUIDs are 32-char lowercase hex. Pair endpoints take the two repo UUIDs
in either order in the URL; responses always use canonical =a=/=b= roles
(=repo_a= < =repo_b= lexicographically) and include both repo UUIDs so
clients need not re-derive them. Every pair endpoint requires both repos to
be loaded (=404= otherwise).

*** Per-repo primitives

- Single-record write endpoints (field =POST=/=PUT=/=DELETE=, whole-record
  =PUT=, and metarecord =DELETE=) accept an optional =expected_version=
  query parameter: the write is rejected with =409= if the metarecord's
  current =version= differs (see [[file:spec-data-model.org][spec-data-model.org]] "Conditional writes").
  Sync propagation and deletion propagation always set it to the plan's
  baseline, so a metarecord that changed since the plan makes its operation
  skip (and be reported) instead of being run against stale state.

*** Pair primitives

- =GET /sync/:repo/:repo/links= — list links:
  #+BEGIN_SRC json
  { "repo_a": "…", "repo_b": "…", "host": "…",
    "links": [ { "uuid": "…", "record_a": "…", "record_b": "…",
                 "version_a": 5, "version_b": 9 } ] }
  #+END_SRC
  =host= is the repo whose =internal/= holds the sync database (=null= when
  no sync database exists yet — the link list is then empty).
  =version_a= / =version_b= are =null= before the first sync-commit.

- =GET /sync/:repo/:repo/links/:uuid= — one link, plus its decoded snapshot
  and both endpoint metarecords inline (avoids extra round-trips while
  diffing):
  #+BEGIN_SRC json
  { "link": { …as above… },
    "snapshot": [ { "name": "rating", "value": { "type": "int", "value": 5 } } ],
    "record_a": { …full metarecord JSON… } | null,
    "record_b": { …full metarecord JSON… } | null }
  #+END_SRC

- =POST /sync/:repo/:repo/links= — create a link.
  Body: ={ "record_a": "<uuid>", "record_b": "<uuid>", "host"?: "<repo uuid>" }=
  (canonical roles). Both metarecords must exist (=404=) and be unlinked in
  this pair (=409=). =host= designates the repo that will hold the sync
  database; it is honoured only when the database does not exist yet
  (default: canonical repo A) and ignored otherwise. The link is created
  with no versions and no snapshot (state =never_synced=). Returns the link
  JSON.

- =DELETE /sync/:repo/:repo/links/:uuid[?with_endpoint=a|b]= — delete a link
  and its snapshot (one transaction). With =with_endpoint=, the endpoint
  metarecord on that side is deleted in the same call, *before* the link
  (deletion propagation helper — see [[*Metarecord deletion propagation]] for
  the normative order). Returns ={ "deleted": true }=.

- =POST /sync/:repo/:repo/candidates= — the linking phase's *heuristic*
  matcher, for source records with **no TreeRef identity** only (e.g.
  deleted-file tombstones; see [[*The linking phase: match or create]]).
  TreeRef-identity records are matched by the CLI by reconstructed path
  (=…/metarecords/:uuid/fields/:name/resolve-tree= + an exact-path query) —
  1:1 and exact, needing no heuristic. Read-only, stored values only. Body:
  #+BEGIN_SRC json
  { "source": "<repo uuid>", "records": [ "<uuid>", … ] | null }
  #+END_SRC
  =records= =null= means every unlinked no-TreeRef metarecord of the source.
  For each, an unlinked target-side record whose *sync-relevant* fields (all
  except the excluded =mfr_*=, see [[*The metadata diff]]) form the same
  multiset is returned — only when unambiguous (exactly one on each side).
  #+BEGIN_SRC json
  { "candidates": [ { "source": "…", "target": "…" } ] }
  #+END_SRC

- =GET /sync/:repo/:repo/status= — the per-link change/conflict state:
  #+BEGIN_SRC json
  { "repo_a": "…", "repo_b": "…",
    "links": [ { "uuid": "…",
                 "state": "never_synced" | "in_sync" | "ahead_a" | "ahead_b"
                        | "conflict" | "missing_a" | "missing_b"
                        | "missing_both",
                 "e_a_version": 7, "e_b_version": 3,
                 "version_a": 5, "version_b": 3 } ] }
  #+END_SRC
  States, in decreasing precedence:
  - =missing_a= / =missing_b= / =missing_both= — an endpoint metarecord no
    longer exists (deletion to propagate; =missing_both= → just delete the
    link).
  - =never_synced= (no sync-commit yet), then the change-detection truth
    table: =in_sync=, =ahead_a=, =ahead_b=, =conflict=.

- =POST /sync/:repo/:repo/links/commit= — sync-commit, batched. Body:
  #+BEGIN_SRC json
  { "commits": [ { "link": "<uuid>",
                   "version_a": 8, "version_b": 4,
                   "snapshot": [ { "name": "rating",
                                   "value": { "type": "int", "value": 5 },
                                   "value_b": null }, … ] } ] }
  #+END_SRC
  Snapshot values are given in wire JSON, A-perspective; for Ref/TreeRef
  entries =value_b= carries the B-perspective UUID captured by the client at
  commit time (dual perspective). Normative client rule: =version_a= /
  =version_b= are the versions whose field state the client actually read
  and propagated — *never* re-read at commit time. (No server check can
  enforce this — re-read versions are indistinguishable from honest ones —
  and none is needed: committing an honest-but-stale version is safe, the
  link simply shows =ahead= on the next run and the concurrent write gets
  propagated then.) The batch is applied in a single transaction: for each
  commit, the link columns are updated and the =snapshot_field= rows
  replaced. Returns ={ "committed": N }=.

** Performance concerns                                                   :v2:

=internal= transfers/moves are native (=fs::copy= / =fs::rename=), one call
per record, no process spawn — so a large batch of small files costs syscalls,
not =fork+exec=. The concerns below are about the daemon round-trips, not the
file operations.

1. *Batching*: when the sync database is hosted on the SSHFS-mounted repo,
   each transaction is slow. Batch transactions (the =commits= array) reduce
   this cost at the price of more re-work after a crash (at most one batch
   to redo). The optimal batch size is to be determined by benchmark; it is
   configurable in the intents file (=[settings]=). For file metarecords,
   batches should be smaller than for pure metadata metarecords, since each
   batch corresponds to file transfers (idempotent, but slow to re-transfer
   if the batch is large).

2. *Tree-cache rebuilds during =mfr_path= propagation*: every manual TreeRef
   write currently triggers a full tree-cache rebuild in the target repo —
   propagating paths for N records is O(N) rebuilds. Batching the rebuild
   (one per metadata batch) is an optimisation to evaluate with the
   benchmark.

* CLI

The orchestration described in [[*Two-phase sync process]] and
[[*Sync intentions]] lives in the CLI; the daemon only provides the primitives
listed in [[*HTTP API]].

** =mf sync=                                                              :v2:

#+BEGIN_SRC
mf sync plan <repo_a> <repo_b> --intents <file> [--host <repo>] [--on-conflict <policy>]
mf sync show <repo_a> <repo_b> [--conflicts | --files | --summary]
mf sync run  <repo_a> <repo_b> [--yes]
#+END_SRC

=<repo_a>= / =<repo_b>= are repo names or UUIDs; their order on the command
line does not matter (roles are canonical — see [[*Canonical pair order]]).
Both repositories must be loaded in the same daemon instance (for a remote
repo: mount it, e.g. over SSHFS, and =mf repo load= it first). The plan lives
in a per-pair plan repo (see [[*The plan repo]]), not a file — nothing to clean
up, and only the latest plan exists.

*** =mf sync plan=

Read-only w.r.t. the synced repos. Produces the plan repo =show= / =run=
operate on. Steps:

1. Check that both repos' schemas are identical (abort otherwise — see
   [[*Schemas must be identical]]).
2. Evaluate each intent query on its source repo, fetch =GET …/status= and
   =GET …/links=, and match unlinked in-scope records by TreeRef identity
   (reconstructed path; the no-identity heuristic via =POST …/candidates=).
   A multi-TreeRef *incoherence* (see [[*The linking phase: match or create]])
   aborts the plan with a report of the offending records. Then compute the
   diffs.
3. Resolve interactively: =ask= conflicts (per conflicting field name, show
   the record's path/uuid and the A / B values; choices: keep A, keep B,
   skip field, skip link) and the deletion confirmation. When every conflict
   is covered by a non-interactive =[[conflict]]= rule (=skip=/=prefer=) or
   =--on-conflict= is given, nothing prompts and unconfirmed deletions are
   omitted.
4. (Re)create the plan repo and write one operation metarecord per action —
   linking phase (create/drop links, bare-record creations), sync phase
   (field propagations, transfers/moves with direction, deletions, and the
   resolved conflicts) — each tagged with its baseline versions (see
   [[*The plan repo]]).

The plan can then be reviewed and edited with ordinary tooling: =mf sync show=,
a raw query on the plan repo, the GUI, or =mf … field set plan_resolve=…= to
change a resolution.

*** =mf sync show=

Renders the current plan with live context: current paths/values of the
touched records (following the ExternalRefs into the synced repos) and a
red/green flag on each operation (green = baseline still matches → will run;
red = a record changed → will be skipped). =--conflicts= / =--files= /
=--summary= filter the view; the default is a summary plus the reds.

*** =mf sync run=

Executes the plan, deleting each operation that succeeds. Steps:

1. Re-check that both repos' schemas are identical (abort otherwise).
2. Confirm (showing the summary + reds) unless =--yes=.
3. Execute the *linking phase*: drop out-of-scope links, create the planned
   links (onto matched records or freshly-created bare records).
4. Execute the *sync phase*, interleaved by batches (=[settings]=). For each
   link: propagate all metadata first (field writes with ref translation and
   =expected_version= set to the plan's baselines, =mf_sync=, the translated
   =mfr_path=, deletion propagation). Then, only for =internal= records and
   only if the metadata fully succeeded, perform the file/directory operation
   (transfer, move, create — routing any overwrite/delete through the trash)
   and set the target's stat fields to match (see
   [[*Field coverage and diff semantics]] "Metadata gates the disk"). Then
   =POST …/links/commit=.
5. A rejected write (=409= stale baseline, =400= forest violation) or a failed
   transfer leaves the file untouched and skips that operation. *Every
   operation that succeeds is deleted from the plan repo*; the rest remain.
6. Print a summary (counts of what was done; =external= content/path
   divergences aggregated by subtree; a pointer to =mf sync show= for the
   operations left un-executed) and recommend =mf reconcile= on both repos.

Crash mid-run: file transfers are idempotent, committed links are consistent,
un-deleted plan operations simply re-run next time (the value-equal rule
prevents phantom conflicts). Metadata is always written before its file
operation, so a sync-created record exists at its path before the file does
and the watcher can never duplicate it; a crash between the two leaves a
stale path that the next run or =reconcile= repairs.

*** Utility subcommands

#+BEGIN_SRC
mf sync status <repo_a> <repo_b>                 # print per-link states
mf sync link   <repo_a> <repo_b> <uuid_a> <uuid_b> [--host <repo>]
mf sync unlink <repo_a> <repo_b> <link_uuid> [--with-endpoint a|b]

** The intents file

TOML. It declares only the sync *scope* (which records to link) and a few
policies — no transfer methods (whether a record's content is metafolder's
or an external tool's is the inherited =mf_sync= field on the record, see
[[*Metadata versus content: the =mf_sync= field]]).

#+BEGIN_SRC toml
  # Directional: each query runs on its source `repo` only; its result is the
  # set of records that must be linked to the other repo of the pair. The
  # union of the entries is the scope.
  [[intents]]
  repo   = "laptop"            # source repo (name or UUID; one of the pair)
  query  = 'tag = "sync_pc_b"'

  [[intents]]
  repo       = "laptop"
  query      = 'mfr_path ->* "/projects"'
  simplified = false           # if true, expand with the simplified grammar first

  [[intents]]
  repo   = "nas"
  query  = 'tag = "image" AND tag = "family"'

  # Conflict rules, ordered; first match wins. A rule matches a conflicting
  # (record, field) when its `field` (if given) and its `query` (if given,
  # tested against either endpoint) both match. A rule with neither is the
  # default. Replaces the old global policy + per-field tables with one list.
  [[conflict]]
  field  = "rating"                    # field-scoped
  policy = "prefer:laptop"

  [[conflict]]
  query  = 'mfr_path ->* "/photos"'    # record-scoped (a subtree, a tag, …)
  policy = "prefer:nas"

  [[conflict]]
  policy = "ask"                       # default: "ask" | "skip" | "prefer:<repo>"

  [settings]                   # optional
  commit-batch-size    = 50    # links per sync-commit call
  transfer-batch-size  = 20    # file transfers between metadata batches
#+END_SRC

Matching is exact (TreeRef identity by path, 1:1); there is no similarity
threshold. The no-identity heuristic (see [[*The linking phase: match or
create]]) may grow tuning knobs here later.

** Conflict resolution

A conflict is a field changed on both sides since the last sync (or differing
at first sync). The policy applied to a given =(record, field)= is the *first
matching* =[[conflict]]= rule in the intents file (see [[*The intents file]]) —
a rule matches when its optional =field= equals the field name and its
optional =query= matches either endpoint; a rule with neither is the default.
The =--on-conflict <policy>= flag on =plan= overrides all rules. Each policy:

- =ask= (default) — interactive prompt at =plan= time (see the =plan= flow).
- =skip= — leave both sides untouched; the field stays unsynced and will
  conflict again next time.
- =prefer:<repo>= — take the value from the named repo (name or UUID; never
  "a"/"b", which are canonical-order artefacts users should not need).

A non-interactive =plan= (every conflict covered by a =skip=/=prefer= rule,
or =--on-conflict= given) never prompts. Whatever the source, the outcome is
the =plan_resolve= field on the conflict metarecord (see [[*The plan repo]]) and
can still be changed before =run= (=mf … field set plan_resolve=…=, or in the
GUI).
