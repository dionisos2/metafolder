#+TITLE: Metafolder — Cross-repo Synchronisation Specification
#+OPTIONS: toc:2 num:t

* Overview                                                               :v2:

The daemon provides low-level primitives for cross-repo sync. Orchestration
(deciding what to link, in which order, with which method) lives in the CLI
(=mf sync=) and user scripts.

Sync state — the links between metarecords of two repositories and the
snapshot of their common state at the last sync — lives *outside the data
model*, in a dedicated per-pair SQLite database (see [[*The sync database]]).
Links and snapshots are not metarecords: they never appear in queries, are
absent from the event log, and are not subject to rollback.

* Concepts

** Design principles

- The daemon never touches files. File transfers are always performed by the
  CLI command or script.
- Sync intentions (which metarecords to link, with what method) are expressed as
  queries in the intents file, not stored in the database.
- Both repos must be loaded in the same daemon instance for every sync
  primitive (link creation/deletion, status, commit).
- For cross-machine sync, the recommended approach is to mount the remote
  repository root over SSH (e.g. SSHFS) and load it into the local daemon.
  The daemon itself makes no network calls.
- Sync state is bookkeeping, not user data: it lives outside the data model
  and the event log, so the log, rollback, queries and the index are entirely
  unaffected by sync (see [[*Interaction with rollback]]).

** The sync database

Each synchronised pair of repositories =(A, B)= shares one *sync database*: a
single SQLite file named

: .metafolder/internal/sync-<uuid_A>-<uuid_B>.sqlite

where =<uuid_A>= and =<uuid_B>= are the 32-char lowercase hex repo UUIDs in
canonical order (see below). The file lives in the =internal/= directory of
*one* of the two repos — the *host* repo, chosen when the pair is first
created (see [[*Location and discovery]]). Living under =internal/=, it is
excluded from tracking like =db.sqlite=.

There is exactly one copy: every sync-state mutation is a single ordinary
SQLite transaction, so link state is always internally consistent — no
replication, no repair protocol. The trade-off is redundancy: if the file is
lost or corrupted, the pair's sync state is gone and the next sync starts
over as a first sync (divergent fields resurface as immediate conflicts;
identical fields re-link silently via candidates).

A repo may participate in any number of pairs, each with its own sync
database. Only the pair being synced is ever opened; sync state adds no
weight to the main database, its index, or its queries.

*** Canonical pair order

The two repo UUIDs are ordered lexicographically (as 32-char lowercase hex):
the smaller UUID is *repo A*, the larger is *repo B*. This order is derivable
from the pair alone and is used consistently for:

- the file name (=sync-<uuid_A>-<uuid_B>.sqlite=),
- the =a=/=b= role names in the schema and the HTTP API,
- the canonical perspective of snapshots (see
  [[*Ref and TreeRef fields in the snapshot]]).

The canonical order does *not* choose where the file lives — that is the
host repo, an independent choice (see [[*Location and discovery]]).

The order of repos in a URL or on the =mf sync= command line is irrelevant;
the daemon and CLI normalise to canonical order internally. Conflict policies
therefore never say "a" or "b" — they name the repo (see [[*Conflict resolution]]).

*** Schema

#+BEGIN_SRC sql
-- Identification and format version. Rows: format_version (currently "1"),
-- repo_a, repo_b, host (32-char hex). On open, repo_a/repo_b must match the
-- file name and the repo pair being synced; a mismatch (e.g. a file copied
-- from another pair) is an error and the file is not used. host records the
-- repo whose internal/ holds the file (updated if the file is moved).
CREATE TABLE meta (
    key    TEXT PRIMARY KEY,
    value  TEXT NOT NULL
);

CREATE TABLE link (
    uuid       BLOB PRIMARY KEY,        -- 16-byte link id
    record_a   BLOB NOT NULL UNIQUE,    -- metarecord UUID in repo A
    record_b   BLOB NOT NULL UNIQUE,    -- metarecord UUID in repo B
    version_a  INTEGER,                 -- E_A.version at last sync-commit (NULL before)
    version_b  INTEGER,                 -- E_B.version at last sync-commit (NULL before)
    last_sync_method  TEXT              -- method used during the last sync (informational)
);

-- Snapshot of the common field state at the last sync-commit. Value columns
-- are encoded exactly like the =field= table of the main database (same
-- value_type tags, same column usage), from repo A's perspective; for =ref=
-- and =tree_ref= rows, =value_uuid_b= additionally stores the B-perspective
-- UUID captured at commit time (dual perspective — see
-- [[*Ref and TreeRef fields in the snapshot]]).
CREATE TABLE snapshot_field (
    link_uuid   BLOB NOT NULL REFERENCES link(uuid) ON DELETE CASCADE,
    field_name  TEXT NOT NULL,
    value_type  TEXT NOT NULL,
    value_text  TEXT,
    value_int   INTEGER,
    value_real  REAL,
    value_uuid  BLOB,
    value_uuid_b BLOB,
    value_ref_repo BLOB,
    value_name  TEXT
);
CREATE INDEX idx_snapshot_link ON snapshot_field(link_uuid);
#+END_SRC

The sync database is opened on demand with journal mode =DELETE= and
=synchronous = FULL= — never WAL: the host repo may be the SSHFS-mounted
one, and WAL's shared-memory file cannot work on a network filesystem.

Links are 1:1: a metarecord of A is linked to at most one metarecord of B and
vice versa — enforced by the two =UNIQUE= constraints.

The =version_a= / =version_b= / =last_sync_method= columns are written only by
the sync-commit primitive; =record_a= / =record_b= are immutable after
creation.

*** Location and discovery

The sync database lives in the =internal/= directory of one of the two
repos, the *host*. The first mutating primitive on a pair creates the file
(with its =meta= rows); the request designates the host repo, defaulting to
canonical repo A. Choosing the host lets the user keep sync state on the
machine that orchestrates the syncs (e.g. the local repo rather than the
SSHFS-mounted one).

Every pair primitive locates the file by checking both loaded repos'
=internal/= directories:

- found in exactly one → use it (and update =meta.host= if the file was
  moved by hand — relocation is supported: move the file, nothing else).
- found in neither → the pair has no sync state yet (empty link set;
  mutating primitives create the file, read-only ones return empty).
- found in both → ambiguous (=409=); the user deletes the stale one. The
  daemon never merges two sync databases.

*** Consistency

Every sync-state mutation (link creation, deletion, batched sync-commit) is
one ordinary SQLite transaction on the single file — link state is always
internally consistent, whatever crashes. Cross-database consistency (sync
state vs. the two main databases) is the job of the change-detection
machinery: a crash between a metadata write and its sync-commit simply
leaves the link "changed", re-detected and re-committed on the next run
(see [[*Version-based change detection]]).

Concurrent mutation of the same pair from two daemons is excluded by the
main databases' exclusive locks (both repos must be loaded to touch a
pair). On network filesystems with unreliable locks (SSHFS) that exclusion
can weaken; the sync database's own SQLite locking is then the last line of
defence. Syncing the same pair from two daemons concurrently is unsupported.

*** Interaction with rollback

The sync database is not part of the data model: link state is never recorded
in the event log and cannot be rolled back.

Rolling back a repo's event log *does* restore the =version= counters of the
linked metarecords themselves. A restored =E_X.version= that no longer
matches the recorded =version_x= — even if numerically smaller — simply means
"changed since the last sync" and is reported as such by the status primitive
(see [[*Version-based change detection]]).

Version *equality* is trustworthy even across rollbacks: versions are
assigned from the per-metarecord =next_version= allocator, which navigation
never restores, so a version number is never reused for a different state
(see [[file:spec-data-model.org][spec-data-model.org]]). =E_X.version == version_x= therefore guarantees
the metarecord is in the exact state it had at the last sync-commit.

A navigation can also make a linked metarecord *disappear* (rollback before
its creation). This is indistinguishable from a deliberate deletion at the
data level, which is why deletion propagation is never applied silently (see
[[*Metarecord deletion propagation]]).

** Version-based change detection

After a successful sync of metarecords =E_A= (repo A) and =E_B= (repo B), the
sync-commit primitive writes the current versions of both metarecords into the
link:

- =version_a= ← =E_A.version= at time of sync
- =version_b= ← =E_B.version= at time of sync

On the next sync, for each linked pair:

| =E_A.version= vs =version_a= | =E_B.version= vs =version_b= | Meaning          | Action          |
|------------------------------+------------------------------+------------------+-----------------|
| equal                        | equal                        | No changes       | Nothing to do   |
| different                    | equal                        | Only A changed   | Propagate A → B |
| equal                        | different                    | Only B changed   | Propagate B → A |
| different                    | different                    | Both changed     | Conflict        |

"Different" rather than "greater": a rollback can restore a *smaller*
=E_X.version=; any difference from the recorded value means the metarecord
changed relative to the last sync point. Equality, conversely, proves the
state is unchanged: version numbers are never reused for different states
(the =next_version= allocator — see [[*Interaction with rollback]]).

The version test is a cheap pre-filter, not the definition of change:

- A *conflict* is a field changed on both sides *to different values* (after
  ref translation). Both sides changed to the *same* value → the field is
  simply in sync; nothing to propagate.
- A changed version whose *effective diff* is empty (e.g. only excluded
  =mfr_*= fields moved — see [[*Field coverage and diff semantics]]) means the
  link is in sync: the run re-commits the fresh versions silently instead of
  reporting a change or a conflict. This also makes crash recovery benign: a
  crash between metadata propagation and sync-commit re-detects the link as
  "changed on both sides", but the values are equal, so the next run just
  re-commits.

Conflict resolution is left to the sync command (user prompt or declared
policy in the intents file).

When a link is created for the first time, =version_a= / =version_b= are
=NULL= and no snapshot exists (state =never_synced=). If =E_A= and =E_B=
already have divergent fields, this is treated as an immediate conflict to
resolve before the first sync-commit can record versions and snapshot.

The snapshot (the =snapshot_field= rows of the link) captures the common
field state after each successful sync. It is replaced at every sync-commit
alongside =version_a= and =version_b=. During conflict resolution (both sides
changed), the sync command computes:

- Fields changed only in A = diff(E_A, snapshot)
- Fields changed only in B = diff(E_B, snapshot)
- Fields changed in both   = conflict → manual resolution

Fields changed on only one side are propagated automatically.

*** Ref and TreeRef fields in the snapshot

For non-Ref fields, E_A and E_B hold identical values after sync, so the
snapshot is unambiguous. For =Ref= and =TreeRef= fields, the same logical
reference has different local UUIDs in each repo.

The snapshot stores these values in *dual perspective*, both captured at
commit time:

- =Ref=: =value_uuid= holds repo A's local UUID, =value_uuid_b= holds repo
  B's (translated through the link table as it stood at commit).
- =TreeRef=: same for the parent UUID; the =name= component is portable
  (identical across repos) and stored once.
- A perspective whose translation was unknown at commit time stores =NULL=
  on that side.

Because the snapshot lives in its own table (not in the =field= table of
either main database), these UUIDs are inert bytes: they trigger no tree
validation, no uniqueness constraint, and no dangling-ref concern.

Consequences for the diff — no translation is ever needed at diff time,
which also makes the diff immune to links deleted or re-created between two
commits:
- =diff(E_A, snapshot)=: compare against =value_uuid= directly.
- =diff(E_B, snapshot)=: compare against =value_uuid_b= directly.
- A =NULL= perspective (untranslatable at commit time) → conservative
  treatment: flag as potential conflict and warn.

Translation through the *current* link table still happens when propagating
a Ref/TreeRef value to the other repo (see [[*Ref translation during sync]]).
=ExternalRef= values are self-contained (repo + metarecord) and are copied
verbatim, never translated.

** Field coverage and diff semantics

*** Which fields sync covers

=mfr_*= fields (except =mfr_path=) are *excluded* from the snapshot, the
diff, and metadata propagation. They are stat- and content-derived: each
repo's watcher/reconcile owns them, and after a file transfer the target's
executor refreshes =mfr_size= / =mfr_mtime= and clears the stored hashes —
propagating them would ping-pong forever. Their version bumps are absorbed
by the empty-effective-diff rule above.

- *File content* is synced as a *file transfer*, not a field write: for a
  changed/conflicting file link, the stored content signatures
  (=mfr_full_hash=, falling back to =mfr_partial_hash= + =mfr_size=) of the
  two endpoint records are compared; if they differ, a transfer is planned
  from the changed side (for a content conflict — both sides changed — the
  conflict policy chooses the direction, like any conflicting field).
- =mfr_path= is synced as a *file operation*: propagating a path change
  means the CLI physically renames/moves the file in the target repo, then
  force-writes the translated =mfr_path= so the queued watcher event becomes
  redundant. Moves and creations are applied top-down (parents before
  children, across batches if necessary): a translated TreeRef write is
  rejected by the daemon's forest validation if the parent is missing or
  orphaned, so directory links must be resolved first. Such a =400= is
  treated like a schema violation: skip and report.
- All other fields (user data, including reserved =mf_*= written with
  =force=) are propagated as ordinary field writes.

*** Diff semantics

Fields form a multi-map: the diff compares, per field *name*, the full
*multiset* of values (after ref translation on the B side). Propagation
replaces the target's whole row set for that name (set semantics, not
append). A field name absent on one side and present in the snapshot is a
*removal*, propagated as an unset — "absent" (unknown) and =Nothing= (does
not apply) are distinct states and both are preserved by snapshot and
propagation. Conflict prompts operate per field name and display the full
multisets.

*** First sync

When a link is created, the snapshot is empty; the first sync uses union
semantics:

- a field name present on one side only → propagated to the other side;
- present on both sides with equal multisets (after translation) → in sync;
- present on both sides with different multisets → an immediate conflict,
  resolved by the normal policy before the first sync-commit records
  versions and snapshot.

** Metarecord deletion propagation

- =mfr_path= set to =Nothing= (file deleted, metarecord preserved) → link is kept;
  the metarecord still exists and its metadata remains meaningful.
- Metarecord fully deleted → the sync command propagates the deletion to the
  corresponding metarecord in the other repo, then deletes the link (and with
  it the snapshot, which has no existence of its own).

Deletion propagation is destructive on the surviving side and a rollback can
make a record vanish without any user intent (see
[[*Interaction with rollback]]), so it is never silent: planned deletions are
listed nominatively, and =mf sync run= requires an explicit interactive
confirmation for them — or the =--allow-deletions= flag in non-interactive
runs; =--yes= alone never covers deletions.

Normative order (used by =DELETE …?with_endpoint= and the CLI alike): delete
the endpoint metarecord *first* (a logged, rollbackable write), then delete
the link. A crash in between leaves state =missing_x=, which the next run
re-detects and completes — never a deleted link with a live record that a
later run would resurrect as "new".

** Two-phase sync process

Sync is split into two distinct phases:

1. *Planning* (watcher running): query both repos, compute all operations to
   perform (file transfers, metadata propagations, conflicts). The plan
   records, for each repo, a *change token* (see below) at planning time.
   The user can inspect the plan before proceeding.

2. *Execution* (executor suspended): validate that each repo's change token
   still equals the recorded value. If any repo has changed — even by a
   single write — the plan is invalidated and the user must re-plan. This is
   intentional: detecting *what* changed is complex, and even a single change
   could mean the plan would overwrite recent modifications. If valid,
   suspend the pending operation executor on both repos (see
   [[*Executor suspension during sync]]), then execute operations in order:
   file transfers first (all idempotent), then metadata commits in batches.

After execution: resume the executor, let it flush, then re-commit the
links whose versions moved during the flush (see the =mf sync run= flow and
[[*Executor suspension during sync]]). Running =reconcile= is recommended to
catch any remaining filesystem drift.

*** Change token

The freshness guard is derived from the event log:

: { "head": <log_head.op_id or null>, "last_op_id": <MAX(operation.id) or 0> }

Two tokens match only if *both* fields are strictly equal. Every logged write
creates operation rows (=last_op_id= grows); a pure rollback/redo navigation
creates no operations but moves =head=. Both kinds of change are therefore
detected.

The token's soundness depends on =operation.id= being =AUTOINCREMENT= (ids
are never reused, even after a log prune) — a requirement on the event-log
schema. A prune between plan and run can *shrink* =last_op_id=, causing a
spurious (but safe) "repository changed" abort. (=PRAGMA data_version=
cannot serve here: it only reacts to *other* connections, and the daemon
holds a single EXCLUSIVE connection per repo.)

** Sync intentions

Sync intentions are declared in the intents file as an *ordered* list of
entries, each naming a *source repo*, a sync method, and a query (see
[[*The intents file]] for the concrete format). Intents are *directional*:
the query runs on the source repo only, and its result is the set of source
metarecords that must be linked to the other repo. Example (source repo
before the arrow):

#+BEGIN_SRC
laptop:  rsync  ←  tag = "sync_pc_b"
laptop:  git    ←  files "/projects"
nas:     rsync  ←  tag = "image" AND tag = "family"
#+END_SRC

For a metarecord matched by several intents, the first matching entry (file
order) wins; the same rule picks the method of a link whose two endpoints
are covered by intents from both sides. The intent scopes maintain the link
set:

- an in-scope source record with no link → link it (see
  [[*The linking phase: match or create]]);
- a link neither of whose endpoints is in any intent scope → drop the link
  (never the records);
- every remaining link is then synchronised with its method — the sync
  phase, i.e. the change-detection/propagation machinery above driven by the
  =mf sync= flow (see [[*CLI]]).

*** The linking phase: match or create

For each in-scope source record without a link, the CLI looks for a match
on the target side (=POST …/candidates=):

- an *exact* match — same content (=mfr_full_hash=) for a file, same
  reconstructed path for a directory — is linked automatically;
- failing that, a *similar* record — the four-signal similarity score of
  spec-file-tracking "File Similarity" (already used by reconcile), computed
  across the two repos, at or above =similarity-threshold= — is proposed:
  linked after interactive confirmation, skipped in a non-interactive run;
- no match → the record is *created* on the target side and linked: for a
  file, transfer + track (directories created top-down first); for a
  metadata-only record, a bare metarecord.

Records created by sync start *minimal*: all their fields — references
included — arrive through the sync phase that follows (the new link's first
sync, union semantics). By then the linking phase has completed the link
table, so Ref/TreeRef translation has every mapping it will ever have: a
reference that still has no translation points at a record genuinely out of
sync scope and is skipped with a warning ([[*Ref translation during sync]]).
This ordering is what makes reference-carrying creations well-defined —
there is never a moment where a new record must guess a target-side UUID.

Links are 1:1, so matching is too: when several source records match the
same target record (duplicate content), the group is ambiguous and never
auto-linked — it is prompted for, or resolved manually with =mf sync link=.
Once linked, a record keeps its link by UUID whatever moves or renames
happen — path divergence is an ordinary =mfr_path= change or conflict.

** Ref translation during sync

=Ref= and =TreeRef= fields store local UUIDs. When propagating such a value,
the CLI translates it through the link table: for =Ref=, the target-repo
UUID of the linked metarecord; for =TreeRef=, the parent UUID is translated
and =value_name= is written as-is (portable); =Nothing= needs no
translation. The linking phase runs first and sync-created records start
minimal ([[*The linking phase: match or create]]), so the link table is
complete at translation time: a missing translation means the referenced
metarecord is genuinely out of sync scope — the field is skipped with a
warning.

=Ref= values have no foreign-key constraint on =value_uuid= (see schema). The
system tolerates dangling refs: =Follows= on a dangling =Ref= simply returns no
results. Circular references (A → B → A) are likewise permitted; =Follows= is
non-recursive so cycles are not a concern.

** Schemas must be identical

Syncing two repositories with different user schemas makes little sense —
the same metadata would be legal on one side and illegal on the other. =mf
sync plan= and =mf sync run= therefore start by fetching both repos' schemas
(=GET /repos/:repo/schema=) and abort with an error if they differ.
"Identical" is structural equality of the parsed schema documents (JSON
value equality — formatting and key order do not matter); two repos with no
schema at all are identical. The schema file itself is never propagated by
sync (see [[file:spec-schema.org][spec-schema.org]]): resolving a mismatch is a manual step.

Field propagation still goes through the ordinary field endpoints of the
target repo, so the target's schema validates it like any user write — even
with identical schemas a propagated field can violate a constraint in
combination with the target record's other fields. Such a violation rejects
that write; the CLI reports the field as skipped with the violation message
and continues. Sync never bypasses the schema.

* Daemon

** Sync database lifecycle

The daemon opens the pair's sync database on demand, for the duration of one
primitive call, and closes it afterwards; no handle is kept in the repo
state. The file is located by the discovery rule (both loaded repos'
=internal/= directories — see [[*Location and discovery]]); on every open, the
=meta= table is checked against the file name and the repo pair (=409= on
mismatch, and =409= when the file is found on both sides). The two UUIDs of
a pair must differ (=400= otherwise).

The file is created (with its =meta= rows) by the first mutating primitive
on the pair, in the host repo designated by the request (default: canonical
repo A). A missing file simply means an empty link set; an unreadable or
corrupted one is an error — deleting it abandons the pair's sync state (the
next sync starts over as a first sync).

Concurrent primitive calls on the same pair are serialised by the daemon (the
two repos' locks are always acquired in canonical order, preventing
deadlock).

** Executor suspension during sync

The file watcher *always keeps running* during sync execution — it continues
reading OS events and writing them to the =pending_operation= table (see
[[file:spec-event-log.org][spec-event-log.org]]). What is suspended is the *executor*: the component that
reads from =pending_operation= and commits operations to the data tables.

Without executor suspension, watcher events (e.g. a file rename during a file
transfer) could increment =version= on a metarecord mid-sync, corrupting
change detection and invalidating the change-token guard.

Suspension is per-repo and *exclusive*: suspending an already-suspended
executor is rejected with =409=. This makes two concurrent sync runs sharing
a repo mutually exclusive — otherwise the first run to finish would resume
the shared repo's executor in the middle of the other run. It is likewise
mutually exclusive with the rollback lock, enforced in both directions
(=executor/suspend= is rejected while a rollback lock is held, and
=rollback/start= is rejected while suspended, both =409=). Unloading a
suspended repo is rejected with =409= too: reloading would replay the
pending buffer unconditionally, defeating the suspension.

Suspension is not persisted: a daemon restart clears it and replays the
pending buffer as usual. If a sync client dies without resuming (SIGKILL —
the CLI resumes on every error path it can see, but cannot survive a kill),
the suspension leaks until resolved manually: it is visible as
=executor_suspended= in =GET /repos/:repo=, and =POST /repos/:repo/executor/resume=
(or a daemon restart) clears it. =mf sync run= aborts with a hint to that
effect when suspension returns =409=.

Normal API writes remain allowed while suspended — the executor gate only
stops *watcher-originated* commits. They are guarded per-link by the
expected-version preconditions (see [[*HTTP API]]).

On resume, pending events accumulated in =pending_operation= are processed
normally:

- Events for the files sync itself touched are *not* strict no-ops: the
  executor refreshes stat-derived =mfr_*= fields (and clears stored hashes),
  bumping versions after the sync-commit recorded them. This is why =mf sync
  run= performs a re-commit pass after resuming, and why =mfr_*= fields are
  excluded from the diff (see [[*Field coverage and diff semantics]]).
- Events for paths that diverge from the database (user-driven changes
  during the suspended window) → processed normally (path update, =version=
  bump, etc.).

Crash safety: because =pending_operation= is a persistent table, events are
never lost on crash or SIGKILL. The executor replays them automatically on
daemon restart before accepting new requests.

** HTTP API

All UUIDs are 32-char lowercase hex. Pair endpoints take the two repo UUIDs
in either order in the URL; responses always use canonical =a=/=b= roles
(=repo_a= < =repo_b= lexicographically) and include both repo UUIDs so
clients need not re-derive them. Every pair endpoint requires both repos to
be loaded (=404= otherwise).

*** Per-repo primitives

- =GET /repos/:repo/sync/change-token= →
  #+BEGIN_SRC json
  { "head": 41, "last_op_id": 44 }
  #+END_SRC
  =head= is =null= for an empty history.

- =POST /repos/:repo/executor/suspend= → ={ "suspended": true }=
  (*not* idempotent: =409= if already suspended, while a rollback lock is
  held, or vice versa — see [[*Executor suspension during sync]]).
- =POST /repos/:repo/executor/resume= → ={ "suspended": false, "flushed_events": N }=
  (idempotent; flushes the pending buffer synchronously before returning).
- =GET /repos/:repo= gains an =executor_suspended= boolean.

- Field-write endpoints (single-record =PUT=/=POST=/=DELETE= on fields, and
  the whole-record =PUT=) accept an optional =expected_version= query
  parameter: the write is rejected with =409= if the metarecord's current
  =version= differs (see [[file:spec-data-model.org][spec-data-model.org]] "Conditional writes"). Sync
  propagation always uses it, so a user write racing the execution phase
  makes the affected link skip this run instead of being silently
  overwritten.

*** Pair primitives

- =GET /sync/:repo/:repo/links= — list links:
  #+BEGIN_SRC json
  { "repo_a": "…", "repo_b": "…", "host": "…",
    "links": [ { "uuid": "…", "record_a": "…", "record_b": "…",
                 "version_a": 5, "version_b": 9,
                 "last_sync_method": "rsync" } ] }
  #+END_SRC
  =host= is the repo whose =internal/= holds the sync database (=null= when
  no sync database exists yet — the link list is then empty).
  =version_a= / =version_b= / =last_sync_method= are =null= before the first
  sync-commit.

- =GET /sync/:repo/:repo/links/:uuid= — one link, plus its decoded snapshot
  and both endpoint metarecords inline (avoids extra round-trips while
  diffing):
  #+BEGIN_SRC json
  { "link": { …as above… },
    "snapshot": [ { "name": "rating", "value": { "type": "int", "value": 5 } } ],
    "record_a": { …full metarecord JSON… } | null,
    "record_b": { …full metarecord JSON… } | null }
  #+END_SRC

- =POST /sync/:repo/:repo/links= — create a link.
  Body: ={ "record_a": "<uuid>", "record_b": "<uuid>", "host"?: "<repo uuid>" }=
  (canonical roles). Both metarecords must exist (=404=) and be unlinked in
  this pair (=409=). =host= designates the repo that will hold the sync
  database; it is honoured only when the database does not exist yet
  (default: canonical repo A) and ignored otherwise. The link is created
  with no versions and no snapshot (state =never_synced=). Returns the link
  JSON.

- =DELETE /sync/:repo/:repo/links/:uuid[?with_endpoint=a|b]= — delete a link
  and its snapshot (one transaction). With =with_endpoint=, the endpoint
  metarecord on that side is deleted in the same call, *before* the link
  (deletion propagation helper — see [[*Metarecord deletion propagation]] for
  the normative order). Returns ={ "deleted": true }=.

- =POST /sync/:repo/:repo/candidates= — find link targets for unlinked
  source records (the linking phase's matcher). Read-only. Body:
  #+BEGIN_SRC json
  { "source": "<repo uuid>",
    "records": [ "<uuid>", … ] | null,
    "threshold": 0.7 | null }
  #+END_SRC
  =records= =null= means every unlinked metarecord of the source repo. For
  each source record, at most the best unlinked target-side match is
  returned: exact content (stored =mfr_full_hash=; confidence ="full"=),
  exact reconstructed path (confidence ="path"=), or — only when
  =threshold= is given — the best similarity-scored candidate at or above
  it (the four-signal score + MinHash banding of spec-file-tracking "File
  Similarity"; confidence ="similar"=). No hashing is performed; stored
  values only, and paths come from the database, which may be stale
  relative to the filesystem (reconcile deliberately leaves stale TreeRefs
  in place).
  #+BEGIN_SRC json
  { "candidates": [ { "source": "…", "target": "…",
                      "confidence": "full" | "path" | "similar",
                      "score": 0.87,
                      "path_source": "/x/y", "path_target": "/x/y" } ] }
  #+END_SRC

- =GET /sync/:repo/:repo/status= — the per-link change/conflict state plus
  both change tokens (one round-trip for planning):
  #+BEGIN_SRC json
  { "repo_a": "…", "repo_b": "…",
    "links": [ { "uuid": "…",
                 "state": "never_synced" | "in_sync" | "ahead_a" | "ahead_b"
                        | "conflict" | "missing_a" | "missing_b"
                        | "missing_both",
                 "e_a_version": 7, "e_b_version": 3,
                 "version_a": 5, "version_b": 3 } ],
    "change_token_a": { "head": 41, "last_op_id": 44 },
    "change_token_b": { "head": 12, "last_op_id": 12 } }
  #+END_SRC
  States, in decreasing precedence:
  - =missing_a= / =missing_b= / =missing_both= — an endpoint metarecord no
    longer exists (deletion to propagate; =missing_both= → just delete the
    link).
  - =never_synced= (no sync-commit yet), then the change-detection truth
    table: =in_sync=, =ahead_a=, =ahead_b=, =conflict=.

- =POST /sync/:repo/:repo/links/commit= — sync-commit, batched. Body:
  #+BEGIN_SRC json
  { "commits": [ { "link": "<uuid>",
                   "version_a": 8, "version_b": 4,
                   "last_sync_method": "rsync",
                   "snapshot": [ { "name": "rating",
                                   "value": { "type": "int", "value": 5 },
                                   "value_b": null }, … ] } ] }
  #+END_SRC
  Snapshot values are given in wire JSON, A-perspective; for Ref/TreeRef
  entries =value_b= carries the B-perspective UUID captured by the client at
  commit time (dual perspective). Normative client rule: =version_a= /
  =version_b= are the versions whose field state the client actually read
  and propagated — *never* re-read at commit time. (No server check can
  enforce this — re-read versions are indistinguishable from honest ones —
  and none is needed: committing an honest-but-stale version is safe, the
  link simply shows =ahead= on the next run and the concurrent write gets
  propagated then.) The batch is applied in a single transaction: for each
  commit, the link columns are updated and the =snapshot_field= rows
  replaced. Returns ={ "committed": N }=.

** Performance concerns                                                   :v2:

1. *Batching*: when the sync database is hosted on the SSHFS-mounted repo,
   each transaction is slow. Batch transactions (the =commits= array) reduce
   this cost at the price of more re-work after a crash (at most one batch
   to redo). The optimal batch size is to be determined by benchmark; it is
   configurable in the intents file (=[settings]=). For file metarecords,
   batches should be smaller than for pure metadata metarecords, since each
   batch corresponds to file transfers (idempotent, but slow to re-transfer
   if the batch is large).

2. *Executor suspension duration*: the executor is suspended only during the
   execution phase. Watcher events accumulate in =pending_operation= (crash-safe)
   and are replayed on resume. =reconcile= remains the fallback for any
   filesystem drift that the watcher missed (e.g. if the daemon was down).

3. *Tree-cache rebuilds during =mfr_path= propagation*: every manual TreeRef
   write currently triggers a full tree-cache rebuild in the target repo —
   propagating paths for N records is O(N) rebuilds. Batching the rebuild
   (one per metadata batch) is an optimisation to evaluate with the
   benchmark.

* CLI

The orchestration described in [[*Two-phase sync process]] and
[[*Sync intentions]] lives in the CLI; the daemon only provides the primitives
listed in [[*HTTP API]].

** =mf sync=                                                              :v2:

#+BEGIN_SRC
mf sync plan <repo_a> <repo_b> --intents <file> [--json]
mf sync run  <repo_a> <repo_b> --intents <file> [--yes] [--on-conflict <policy>]
#+END_SRC

=<repo_a>= / =<repo_b>= are repo names or UUIDs; their order on the command
line does not matter (roles are canonical — see [[*Canonical pair order]]).
Both repositories must be loaded in the same daemon instance (for a remote
repo: mount it, e.g. over SSHFS, and =mf repo load= it first).

*** =mf sync plan=

Read-only. Checks that both repos' schemas are identical (abort otherwise —
see [[*Schemas must be identical]]), evaluates each intent query on its
source repo, fetches =GET …/status= and =GET …/links=, matches unlinked
in-scope records (=POST …/candidates=), computes the three-way diffs, and
prints the plan in two parts.

The linking phase ([[*The linking phase: match or create]]):

- links to create onto matched records (exact matches automatic; =similar=
  matches and ambiguous groups pending confirmation);
- records to create on the target side (transfer + track + link, minimal);
- links to drop (no endpoint in any intent scope).

The sync phase:

- deletions to propagate (states =missing_a= / =missing_b=), listed
  nominatively (see [[*Metarecord deletion propagation]]);
- file transfers with direction and method (content-signature rule — see
  [[*Field coverage and diff semantics]]);
- field propagations (states =ahead_a= / =ahead_b=);
- conflicts (state =conflict= and first-sync divergences) with the resolution
  each policy would choose;
- warnings (untranslatable refs, similar/ambiguous candidates);
- both change tokens.

=--json= prints the plan as JSON for scripting.

*** =mf sync run=

1. Re-plan (as above), recording fresh change tokens.
2. Resolve interactively *now*, before anything is suspended: =ask=
   conflicts (per conflicting field name: show the record's path/uuid and
   the snapshot / A / B multisets; choices: keep A, keep B, skip field, skip
   link, abort), similar/ambiguous candidates, and the deletion confirmation
   (see [[*Metarecord deletion propagation]]; =--allow-deletions= replaces it in
   non-interactive runs). =--yes= only skips the final "execute this plan?"
   confirmation — never conflict prompts, never the deletion confirmation.
3. Suspend the executor on both repos; a =409= aborts with a hint (another
   sync is running, a rollback is in progress, or a stale suspension needs
   =…/executor/resume=).
4. Re-fetch both change tokens; on any mismatch with step 1, resume and abort
   ("repository changed during planning; re-run").
5. Execute the *linking phase*: drop out-of-scope links, create the planned
   links — onto matched records, and onto records created for the purpose
   (file transfer + track, directories top-down, minimal records). A failed
   transfer skips that record for this run and is reported.
6. Execute the *sync phase*, interleaved by batches (=[settings]= in the
   intents file): each batch of file transfers and file operations (moves
   for =mfr_path=, top-down), then its metadata work (field propagation with
   ref translation and =expected_version= preconditions, deletion
   propagation), then =POST …/links/commit= for the fully-synced links of
   the batch. A failed transfer or a =409= precondition skips that link for
   this run and is reported; execution continues.
7. Resume both executors (also on every error path). The resume flushes the
   pending buffer synchronously; the run then performs the *re-commit pass*:
   links whose endpoint versions moved during the flush (transfer events
   refreshing =mfr_*=) but whose effective diff is empty are re-committed
   with the fresh versions, so the next plan starts clean.
8. Print a summary and recommend =mf reconcile= on both repos.

=--host <repo>= (name or UUID) designates the sync database's host repo when
the run creates it (first sync of the pair); ignored otherwise.

Crash mid-run: file transfers are idempotent, committed links are consistent,
uncommitted links re-detect as changed on the next run and re-commit or
re-propagate (the value-equal rule prevents phantom conflicts) — at most one
batch of re-work. If the CLI is killed outright, the executor suspension
leaks and must be cleared manually (see [[*Executor suspension during sync]]).
A transferred file whose metadata write was skipped is left to the watcher's
ordinary arrival semantics (it may be adopted by fingerprint into an orphan
record); =mf reconcile= sorts out the rest.

*** Utility subcommands

#+BEGIN_SRC
mf sync status <repo_a> <repo_b>                 # print per-link states + tokens
mf sync link   <repo_a> <repo_b> <uuid_a> <uuid_b> [--host <repo>]

=link=/=unlink= are the manual escape hatch for similar or ambiguous
candidates; =resume= recovers from a killed run.

** The intents file

TOML. Example:

#+BEGIN_SRC toml
# Transfer methods as command templates. The built-in method "copy" (native
# file copy, no external tool) is always available unless overridden.
[methods]
rsync = "rsync -a {src} {dst}"
scp   = "scp {src} {dst}"

# Ordered list; directional: the query runs on the source `repo` only, its
# result is the set of records that must be linked to the other repo. For a
# record (or a link's method) matched by several intents, the first match
# wins (later matches produce a warning).
[[intents]]
repo   = "laptop"            # source repo (name or UUID; one of the pair)
method = "rsync"
query  = 'tag = "sync_pc_b"'

[[intents]]
repo       = "laptop"
method     = "copy"
query      = 'files "/projects"'
simplified = true            # expand with the simplified-query grammar first

[[intents]]
repo   = "nas"
method = "rsync"
query  = 'tag = "image" AND tag = "family"'

[conflicts]
policy = "ask"               # "ask" | "skip" | "prefer:<repo name or uuid>"

[conflicts.fields]           # optional per-field overrides
rating   = "prefer:laptop"
mfr_path = "skip"

[settings]                   # optional
commit-batch-size    = 50    # links per sync-commit call
transfer-batch-size  = 20    # file transfers between metadata batches
similarity-threshold = 0.7   # enable similar-record matching in the linking
                             # phase (absent: exact matches only)
#+END_SRC

Template placeholders (substituted after shell-word splitting, one token at a
time — file names are never shell-interpreted):

| Placeholder  | Value                                        |
|--------------+----------------------------------------------|
| ={src}=      | absolute path of the source file             |
| ={dst}=      | absolute path of the destination file        |
| ={src_root}= | source repository root                       |
| ={dst_root}= | destination repository root                  |
| ={rel_path}= | repo-relative path (leading =/=), same on both sides for new files |

The CLI creates missing destination parent directories before invoking the
method. An intent naming an unknown method, or a template with an unknown
placeholder, is a usage error (exit 2).

** Conflict resolution

A conflict is a field changed on both sides since the last sync (or differing
at first sync). Resolution policies:

- =ask= (default) — interactive prompt (see the =run= flow).
- =skip= — leave both sides untouched; the field stays unsynced and will
  conflict again next time.
- =prefer:<repo>= — take the value from the named repo (name or UUID; never
  "a"/"b", which are canonical-order artefacts users should not need).

Precedence: =--on-conflict= flag > =[conflicts.fields]= entry > =[conflicts]
policy=. A non-interactive run (=--on-conflict skip= or a file policy other
than =ask=) never prompts.
